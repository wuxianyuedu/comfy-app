# 从工作树到 `master`：`pnpm ship`

**逻辑只有一份，在 `scripts/ship*.mjs` 这一族里。** 本 Skill 不重抄流程，只说什么时候用它、
它的边界在哪、以及哪几格仍然要人判断。要看全部旗标与阶段名就读 `scripts/ship.mjs` 的文件头
（那里列了这一族各自的职责：`-core` 判断、`-args` 旗标层、`-build` build 取数、`-exec` 效应适配、`-platform` 平台侧三段 + 分支清理、
`-poll` 轮询那一格、`-pull-body` PR 正文那一格、`-local` 本地两段、`-close` 关单、`-claim` 领取 / 结束 / 列表 / 建单分派、`-issue-new` 一步建单、
`-diagnose` 只读诊断、`-stage-log` 只读取某一格的日志正文、`-preflight` 阶段 0、`-preflight-d0` D0 预跑机制层，
`-codes` 退码表（唯一出处）、`-stage` 「走到哪了」阶段进度行（唯一出处），入口只做装配与收口）。

## 什么时候用

**动手之前**：这次要改的是一个缺陷（碎片的段落会写成 `## Fixed`）⇒ **先立案再改**。
那张单就是问题报告的本体（症状 / 当场读数 / 根因），不是改动写完之后再凑的编号 ——
`pnpm ship` 阶段 0 会把「这次挂在 `#N` 上」念出来，`## Fixed` 而号是 `0` 的那几份额外点一句
「先立案」（规范 §13.10.9）。

改动写完、`changelog.d/` 碎片也补了，准备交出去时：

```bash
pnpm ship --dry-run          # 先看它打算跑哪些命令（一条都不执行，但阻塞照报）
pnpm ship --no-preflight-d0  # 关掉阶段 0 的 D0 预跑（默认开：提交前把钩子 D0 只读判据预跑一遍、红一次报齐；双付明说，提交时钩子照判）
pnpm ship --branch feat/x    # 还没有分支时，让它先把分支建出来再往下走（名字必须人给）
pnpm ship --add src/a.ts --allow-staged   # --add 的暂存面默认封闭：index 里另有未点名
                                          # 文件 ⇒ 退 2；只有确认它们该一起走才给这枚
pnpm ship                    # 到「CI 出终态 + 打印下一动作」为止
pnpm ship --merge            # CI 绿了才合并（squash）
pnpm ship --merge --close-issue --clean-branch   # 合上之后关单、并把**这一次那条**分支收掉
pnpm ship --mode auto                            # 全托管：= 上面那三枚旗标的**显式别名**（一次点名授权整组）
pnpm ship --mode confirm                         # 同一组动作，但合并 / 关单 / 删分支每步先问 [y/N]
                                                 #  （回答不是 y ⇒ 未授权：跳过该动作、念出手动出口，
                                                 #   收尾结论行前汇总；EOF / 非交互 fail-closed）
pnpm ship --merge --close-issue 2179             # 本轮号（标题末尾的 (#N)）+ 人点名的号，并集去重
pnpm ship --close-issue 2179                     # 只补关：本轮不合，凭平台侧「已合并 PR」的落地证明关它
pnpm ship --claim 2187                           # 领取：打 `处理人:` + `参与人:` 标签，评论「已接单」（写后回读）
pnpm ship --release 2187                         # 结束：评论「开发结束」+ 撤 `处理人:`（`参与人:` 保留）
pnpm ship --claims                               # 列出自己领取中（state=open）的单子
pnpm ship --branches                             # 只读：逐条本地分支给「落地了没有」（判据只有 PR 的 `is_merged`）—— 一次也不删，与任何显式动作同行退 2
pnpm ship --rerun-ci                         # CI 红/未判定要重跑：在**当前 PR 分支**推一笔空提交重新派生流水线（平台侧没有 PR 重跑入口）；动手前有一层只读前置读数（ISSUE #3341）：在跑的提醒先等终态、红的念红在哪些格与「重跑不会改变 infra 故障」、被取消的念「重跑正是对的」—— 读数不是闸，空提交照推
pnpm ship --diagnose cnb-xxx-yyy                  # CI 红了：只读取回失败格 + 失败行（带行号）+ 日志链接（不给 sn 按 HEAD 的 sha 归属）
pnpm ship --stage-log [cnb-xxx-yyy] <格名|格 id>   # 只读：念出某一格的日志正文（绿跑也能用）——按格名反查 stageId，认不出/命中多格退 2，不替你挑一格
pnpm ship --new-issue "fix(x): …" --issue-body-file .git/issue.md --priority P1   # 一步建单：建 → 补提单人标签 → 独立回读（标题/正文人给）
pnpm ship --comment 2719 --body-file .git/comment.md   # 往已有单子补一条读数：写 → 独立逐字回读（正文只从文件来）
pnpm ship --whoami                               # 只读自查：这份检出的留痕短名 + 署名格式 + 手工补 PR 标签的粘贴命令
pnpm ship --reap                 # 这一轮结束时收掉本检出**端口上那批**残留进程（默认只念读数）
```

## 几条必须先知道的边界

0. **工作模式是打包旗标的显式别名，不是新判定（ISSUE #3512）。** `--mode auto` 在语义上
   等于人亲手给了 `--merge --close-issue --clean-branch`（展开发生在解析层，阶段表不认识
   「模式」这个词），所以四条红线全部照旧：终态仍只认 build 的 `data.status` 与 PR 的
   `is_merged`，结论一次也不来自模式本身。`--mode confirm` 是同一组动作 + 每步一句
   `[y/N]`（CI 已经红的那一跳不问合并，照旧走「给了 --merge 而 CI 红 ⇒ 退 1」）；回答不是
   `y` / `yes`（含 EOF / 非交互）按**未授权**处理：跳过该动作、当场念出手动出口，收尾
   结论行**之前**汇总跳过清单 —— 跳过不是失败（与默认不给 `--merge` 的那一跳同状态），
   但**跳过必须被读出来**，不许在屏幕上长得像执行过。词表只有 `auto` / `confirm`，
   词表外 / 重复 / 缺值 ⇒ 退 2 不静默收下；与 `--claims` / `--diagnose` / `--reap` 等
   单件动作的互斥走既有清单（展开后守卫点名的是展开面）。

1. **退码分型表（0–7）：看到退码就知道是哪件事，`2` 及以上都不等于通过**（ISSUE #3083）。
   唯一出处 `scripts/ship-codes.mjs`，`--merge` 与 `--diagnose` 同一套码：
   `0` 走到终态且事实为绿；`1` 有事实是红的；`2` 没跑起来（**泛化兜底**：`cnb` 不在、
   cancelled、按 sha 归属不到 build、用法错）；`3` PR 与 base **冲突**，平台不派生 CI
   （先 `git fetch <远端> && git merge <基线>` 解掉再重跑，脚本只检测、**不自动解冲突**）；
   `4` CI 无终态（排队 / 在跑超预算 / 轮询断流，PR 可合并）；`5` 关键读数缺失
   （`mergeable_state` / `is_merged` / `state` 缺键、回读没跑起来、基线取不到）；`6` 守卫拦住这一跳
   （已随 PR 落地 #2250 / 跑期内分支被切换 #2812）；`7` 本地前置不成立
   （非 git 检出 / 在 master 上 / 缺碎片 / 依赖没装）。`0` / `1` / `2` 的旧语义不变，
   「没跑起来家族（≥2）压 1、1 压 0」的合码口径不变，CI 与自动化照旧按「非零即不过」消费。
   把非零读成「跑过了没问题」仍是这一族最贵的误读 —— 它和「测了，结果是绿的」
   在多数终端里长得一样。反过来把「没拿到结论」念成 `1`（有事实是红的）同样有害：
   它会让人去修一条并不存在的红。
   **「走到哪了」另有一套输出**（同一张单）：预检通过 / 分支推送 / 新建或复用 PR
   （PR 号 + **平台回读**的标题）/ 等 CI（构建号）/ 冲突（PR 号 + 冲突面文件）/
   合并（squash + 合并提交 sha + 目标分支）/ 关单（回读 state/state_reason）/ 清分支，
   每格一句 `[ship] ▶ <阶段> | key=value`（唯一出处 `scripts/ship-stage.mjs`）——
   进度说走到哪，退码说结果分类，两套信息互不替代，都不用翻日志。
   **同一把尺在手工那一跳更松：`cnb` 认不出的子命令打印 usage 却退 `0`**（ISSUE #2436）。
   例：把评论敲成 `cnb issues create-comment` —— 仓里既有的正确形状是
   **`post-issue-comment`**（`ship-claim.mjs` 用的就是它），而那一次 `EXIT=0`、
   平台**一条也没写**，只有独立回读 `list-issue-comments --sort -created` 才看得出入没进去。
   脚本侧早有防线：`ship-exec.mjs` 的 `cnbJson` 以「输出必须是可解析 JSON」为在场条件，
   拿不到 JSON 就落「没结论」。所以手工口径就一句 —— **`cnb … -v` 的结论只认 JSON 里的
   `data.*`；退出码 `0` 既不许读成「写成功」，也不许读成「取到了空结果」**，
   要下结论必须独立回读对象本身一次。
2. **它不代写提交信息，也不替你 `git add -A`。** 提交信息是判断（症状 / 读数 / 因果），
   暂存面是「这次包含什么」的声明。树脏而没给 `--message` ⇒ 它会停在阶段 1 并说明原因。
   要它代为暂存就逐个点名：`--add src/a.ts --add changelog.d/0-x.md`。
   **`--add` 在场时暂存面是封闭的（ISSUE #3597）**：`git commit` 吃的是整个 index，
   所以点名之外、**在调用 ship 之前就已暂存**的文件（`git apply --3way` 解的基线冲突、
   手工 `git add`、并行检出的在途工作）默认让这一笔**退 2**，并逐个念出路径与三条出口
   （补点名 / `git restore --staged` 撤出去 / 确认要一起走就 `--allow-staged`）。
   点名目录 ⇒ 该目录下已暂存的文件都算声明过。没给 `--add` 的那条路不看暂存面
   （暂存面本来就由你负责），行为一字不变。
   **点名的改动已全部在 HEAD ⇒ 跳过提交段**（#3602）：并行检出树上挂着**别的会话**的
   常驻脏文件时，已提交（含 amend 过）的那一轮不再被推进 `git commit`——旧判据「树上有
   任何改动就提交」会让钩子在空暂存面上判红（doc-mirror-pairing 退 2），push / PR 全堵死。
   判据是逐条**按路径限定**问 `git status`（空输出 = 与 HEAD 一致），不解析 porcelain 的
   路径名单（`core.quotePath` 会转义中文路径，名单匹配会把脏的中文名路径误判成已提交）；
   跳过时会念出 HEAD 的 sha 与「树上另有 N 项未提交改动」——那句是读数，不是「全部已处理」。
   **多行提交信息一律用 `--message-file`**：`pnpm run`（`pnpm ship` 就是它）会把 argv 里的
   真换行改写成字面量 `\n`，于是整条信息变成**一行 subject** 直接进历史（那样一笔当时就是 PR 标题、被平台拒过一次）。它现在会在提交前认出这个形状并停下，给出两条出口
   （`--message-file`，或 `pnpm exec node scripts/ship.mjs --message "…"`）。
   **PR 标题与 squash 那一行的权威顺序是：`--title` > 平台上这条 PR 的现标题 > branch-first 推导
   > 顶端那一笔（兜底）**。branch-first 取「这条分支相对 **PR 的目标分支**（`base.ref`）的第一笔
   非常规提交」，不是顶端那一笔 —— 先合 master 再 `--merge`、或最后补一笔碎片，都会让顶端那笔
   不再是这次变更本身（主干上留着两句这样的坏标题）。区间也不跟本地 upstream 走：栈式 PR 的
   upstream 是父分支的远端副本，本地引用一旦过期就会把别人的提交算进来（ISSUE #3021）。这条 PR
   其实是一件事、而分支开口那笔写小了，就显式 `--title "…"`。
   复用一条**已在平台上改过标题**的 PR 时，squash 那一行取平台现标题（ISSUE #2806：
   评审在平台上读到的标题与 `git log` 里那一行本该是同一句）；那一眼回读没跑起来会明念
   「读数缺失」再退回 branch-first —— 与「这条 PR 本来没改标题」在屏幕上长得不一样。
   **PR 正文照录 `changelog.d/` 碎片原文**（ISSUE #3360：标题只说「改了哪类」，碎片里写的才是
   「具体改了什么」——概览页直接看得到根因、改动、代价与用例）。整份按字节预算贴，装不下的整份省略
   并念出份数；**diffstat 是摘要**（逐行明细只留样本、总计数行永远在、省了多少条写在正文里），
   因为平台对正文有硬上限而 `--stat` 的行数与改动面成正比；顶穿上限时它**不建 PR** 并说明出口
   （拆小 / 手工建），被平台拒绝时那一行 `errcode · errmsg` 会单独念出来（ISSUE #2248）。
   **PR 正文有显式注入口：`--pr-body-file <文件>`。** 给了就把这份人写的正文注入到自动事实段
   **之前**（碎片清单 + 碎片原文 + diffstat 在后，用 `---` 与一句说明隔开）；复用/更新已有 PR 时同一枚旗标
   做的是**整篇覆盖**（给了就更新整篇、不给就一个字节都不动 —— 「只更新自动段」会让同一份正文
   一半来自这一跑、一半来自上一跑，读的人分不出哪句是现在的）。正文只从文件读（与
   `--message-file` 同一条理由）；空文件 / 读不到按用法错停 `2`。写后独立回读逐字比对：缺
   `body` 键退 `2`（没有落地证明）、回读与写入不一致退 `1`（有写入但没落地）。它**不自动加
   `Closes`**：原文里本来写了就念一行提示（关单是统一动作，见下面第 4 条），但脚本不改写人的判断。
3. **合并是显式动作。** 不给 `--merge` 就停在判决处。给了 `--merge` 而 CI 是红的，
   它退 `1` 拒绝合并；PR 冲突 / CI 还在跑 / 读数缺键分别退 `3` / `4` / `5`，
   平台明确说没合上也是 `1`（`head.sha` 对不上是守卫，退 `6`）—— 这个拒绝是功能，不是故障。
   **`is_merged` / `state` 缺键 ≠ `false`**（ISSUE #3059）：平台应答间歇缺这两键，
   所有消费点走三态分型（确认真值 / 确认假值 / 缺键，`ship-core.mjs` 的 `classifyIsMerged`），
   缺键一律 unknown 退 `5` —— 合并后回读缺 `is_merged` 不按「没合上」落红、
   关单回读缺 `state` 不按「没关成」落红、落地守卫里 sha 相同而 `is_merged` 缺键不建幽灵 PR。
4. **关单也是显式的（`--close-issue`），而且「凭什么关」只有一条线：没有落地证明就不关。**
   号有两种来源，前提**刻意不同**：
   - **不点名** ⇒ 关**落地那一行的标题本体**里点名的 `(#N)`，前提是本轮合并已验真；
   - **点名**（`2179` / `#2179` / 一次多张 / `--close-issue=2179,2186`）⇒ 本轮也合并时并集去重；
     **只点名、不 `--merge`** 时走**只补关**那一路（不跑 preflight / commit / push），前提换成
     「平台查得到它随某条**已合并**的 PR 落地」。
   反查 `pulls list-pulls --state closed` 之后**逐条认 `is_merged`** —— 列表的 `--state` 没有
   `merged` 这一档，`closed` 里混着「合了」与「关了没合」；标题先剥掉平台追加的 `(#<PR号>)`
   再提号，本仓 PR 号与 issue 号共用一套编号，喂整行会去关一张别人正在用的单子。
   ⚠️ **推定只认「认领形态」`(#N)`，正文里裸写的 `#730` 不算**（ISSUE #2646）：那类写法是
   引用（「这一格是 #730 那次的防线」），不是「我做完了 #730」的声明。实测一次把两种写法
   喂给同一条正则的代价 —— PR #2642 的标题 `test(gates): #730 … (#2603)` 让 `#730` 也被关掉
   （那张早已 closed 才只是 no-op）。现在裸写的号会被**念成一次可读的拒绝**
   （「标题引用了 #730，它不在认领形态里 ⇒ 没关；要关请 `--close-issue 730`」），
   而**人点名仍照关** —— 收窄针对推定，不针对显式动作。
   没有验真的合并、又查不到落地证明 ⇒ 那一格落 `2` 并说明，**不静默跳过**，也一次都不碰 `cnb`。
   关完走一次独立的 `get-issue`，把 `state` / `state_reason` / `closed_at` 三件原值打出来
   （回执不算结论）。**它不写 issue 的内容**：那条「已落地 + 读数 + 因果」的记录是判断，
   与提交信息同一档。
   **一张单列几条，关的是整张**（ISSUE #2251）：关完之后紧着一行正文的条目**形态**读数
   （`###` 小节 / 未勾 / 已勾 / 序号 各几条）—— 是读数、不改退码，也不判「哪一条做完了」，
   那是人写在评论与 PR 里的判断。未处置的条目**另立一单**，别让它随整张关掉的单子一起
   失去可见性（`--close-issue` 不核剩余条目）。
   **落地证明有第二条入口，但它不是绕过口**（ISSUE #2491）：
   `pnpm ship --close-issue <单号> --as-merged <PR号>`。存在的原因是「按 PR 标题反查」那一路
   对**每日档自动立案**的单子结构上永远查不到 —— 它的标题是「构建 sn · 事件 · 时刻 · 红在哪一格」，
   没有任何 `(#号)`，而修法常来自另一张人立的单。人这里只点名**一条凭据**；合没合并仍由
   `pulls get-pull` 回读 `data.is_merged` 原值：`true` ⇒ 关，`false` ⇒ **退 1**（前提被平台推翻，
   那是事实、不是没跑起来），取不到 ⇒ **退 2**。没带 `--close-issue` 时它没有执行者 ⇒ 退 2。
   ⚠️ 别为凑证明往 PR 标题里塞别人的号 —— 那是一张别人在用的单子（#2199 记过同形事故）。
5. **长链分跳跑，别塞进一条后台命令**：`pnpm ship --no-wait`（提交 / 推送 / 建 PR）→
   `pnpm ship`（轮询出终态）→ `pnpm ship --merge`。每跳都幂等，PR 已存在就复用；
   但「已存在」只认**开放** PR —— 合并成功会把 PR 转 `closed`，所以**内容已落地的分支上再跑
   会撞落地判定那一格**（ISSUE #2250）：它按 `head.sha` 认平台的 `is_merged`，命中就停下念
   「已随 PR #N 落地 ⇒ 要接着改请开新分支」并退 `6`，没有绕过口。
   一条整链在 push 那跳被宿主断掉时，屏幕上不会留下任何线索（实测只剩一个 `127`）。
   单跑 `--only=commit|push|pull-request` 已不可能：那会一段结论都不落，如今退 `2`。
   `--only=close-issue|clean-branch` 同理被拒（`--only` 只认那三段）—— 要单跑关单就用
   `--close-issue <号>` 那一路，不带号时它仍要合并那一段的验真结果。
6. **分支的两头：建可以代做，名字不行；删必须点名。** `--branch <名字>` 只补「动 ref」那半件事（在 `master` / 游离 HEAD 上才建，已在同名分支上
   是幂等，名字撞了已存在的 ref 就退 `2` 而不是覆盖，当前在**另一条**分支上也停 —— 它不在
   分支之间搬工作树）。**它不从 issue 号或提交信息里造名字**：名字是判断。
   `--clean-branch` 只删**这一次跑的那一条**分支，且只跟在验真的合并之后；本地那笔用的是
   `git branch -D`（squash 之后 `-d` 的祖先判据恒假，实测六条已合并分支全部被拒），
   所以删之前会把那笔 sha 打出来当恢复线。本地删除被 git 拒掉时会把**拒因与出口**念出来
   （ISSUE #3617）：当前检出占着 ⇒ `git checkout --detach <恢复线 sha>` 再删；别的
   worktree 占着 ⇒ 指到那个路径，去那边切走或收掉后再删；退码仍是红（诚实红是对的）。
   「把所有已合并分支一次清掉」不在它的动作面里 ——
   那需要另一套判据（"什么算已合并"在 squash 形态下只能问平台，不能问 `merge-base`）。
7. **那一行「单子」是读数，不是闸。** 阶段 0 打印 `单子：#N · 无号碎片 N 份`，
   其中段落是 `## Fixed` 而号是 `0` 的会点一句「先立案」—— 它**一次也不参与退码**
   （用例把这条钉着）。做成硬闸的直接后果不是「大家都立案」，而是「为了让屏幕上念出个号，
   随手挂一张最近开着的别人的单子」，那正是 §13.10.8 记的那次事故（号挂错比不写更贵，
   而号只是个字符串，没有任何判据会红）。`ship` **不替你写**单子：标题与正文是判断；
   写好之后可以用 `--new-issue` 一步建单（建单 → 补 `提单人:` → 独立回读，见第 12 条与 §13.10.12）。
   **方向是「发现即立案」**（AGENTS 硬规则 29 / §13.10.9）：读到的缺陷 / 坑 / 不规范 /
   可优化点 / 漏洞当场建单，**不必马上处理**；动手前若这次改动没有对应的单，先建单再改。
   **单子的另两格（提单人 / 优先级）同样是读数。** 阶段 0 紧接着一行
   `单子身份：提单人=<短名>（标签 提单人:<短名>） · 优先级走平台原生 --priority（P0|P1|P2|P3，本脚本不代填）`。
   留痕的来源是一条**取值链**（`scripts/dev-handle.mjs`）：`.env` 的 `COMFYAPP_DEV_HANDLE`
   （进程环境同名优先）→ `CNB_NPC_NAME` / `CNB_TOKEN_USER_NAME` → `git config user.name`
   → 兜底 `cnb`。**没配也有名字**（ISSUE #2355）：「取的」会在身份那一行之后另念一句
   （换台机器会变），`pnpm ship --whoami` 也念；`pnpm env:init` 会把取到的值写进 `.env`
   而不是补一个空值。因为**平台给不了这一格**：issue 是被 token 的账号本体创建的，
   这台机器上多份并行检出回读的 `author.username` 与那串 noreply 子地址**逐字相同**（实测五张单、
   跨并行会话），而提交那一侧可分的通道（git author 子地址，见 `docs/guides/git-identity.md` §4）
   在单子上不存在。那一行 `.env` 整行缺失时，下一动作是 `pnpm env:init` —— 它只把
   `.env.example` 里有、而这份 `.env` 里没有的键补上（已有值一律不覆盖，#2186），
   而 ship 念的那句会带上**这一份检出的路径**（四份并行检出时「去 `.env` 加一行」指不出是哪份）。
   缺单或没配留痕时才念出口，且是**两条命令**：
   ① `cnb issues create-issue --repo <组织>/<仓库> --title "…" --body-file <正文文件> --priority <P0|P1|P2|P3>`；
   ② 建完再 `cnb issues post-issue-labels --repo <组织>/<仓库> --number <号> --labels 提单人:<短名>`
   —— 实测 ① 里的 `--labels` **不落地**（回读 `labels: []`），标签只能建完之后按。
   三枚前缀说的是**角色**，不是仓库：提单人 `提单人:<短名>`、当前处理人 `处理人:<短名>`、
   经手过的人 `参与人:<短名>`（仓库由 `--repo` 区分）。名称一律取 `COMFYAPP_DEV_HANDLE`
   的原值，不补 `dev:` 之类的壳。
   **同一套 `.env` 缺键的读数也进了阶段 0**：`dev` / `start` / `ship` 共用
   `env-preflight.mjs` 的 `envInitHint()`（#2205），缺什么键就念什么、并给出 `pnpm env:init`；
   它是读数，不参与退码，`.env` 齐的时候一个字也不出现。
   优先级那张表（P0 挡在所有人的主干前面 / P1 本迭代内要有人动 / P2 平台默认值，**没被判断过的
   单子才会落在这里** / P3 记录性、可以不做）写在规范 §13.10.10；`--priority` 的值是判断，
   `ship` 不代填，也**不许**做成「不填就红」的闸 —— 那只会收获一串随手填的 P0。
   别拿标签冒充优先级：平台有原生字段，而标签没有仓库级词表、没有任何判据会红。
8. **进程那一格：读数每轮都念，动手要点名，而 session 那一档不归它收。** 阶段 0 另有一行
   `本检出应用实例：无 / N 个（via session|port · pids …）`，取自硬规则 9 那条归属判据
   （`launcher-core/port-reap.mjs` 的 `runningAppInstances()`）—— **是读数，不参与退码**：
   有人在用 dev server 是正常状态，把「有进程在跑」判成红就是误报。`--reap` 才动手，
   而且**只收 `via:"port"` 那批**（有人绕过编排器自己起的那种，才是任务结束后还在跑的残留）；
   `via:"session"` 意味着**编排器还活着** —— 那不是残留，停它要走编排器自己的收尾
   （`tools/start/*` 或 `dev-launcher.mjs` 的退出回收），这一格落 `2` 并说清「不是没东西可收」。
   收完必须**独立回读**同一条判据：`reap-process.mjs` 全部退 0 也不算结论（回读还在 ⇒ 红，
   回读拿不到 ⇒ 2）。不泛匹配 `node.exe`、不按端口反查；不给旗标一次都不伸手；`--dry-run` 只进计划。
9. **轮询只掐「重复」，不掐「慢」。** 签名 = `(build sn, data.status, pipeline 完成数-总数, stage 完成数-总数)`，
   连着 10 眼一模一样**且此刻没有一格在飞** ⇒ 不再轮询（`POLL_STALL_MAX`）。任何一件变了就归零，
   有格在飞也归零，所以推进很慢的流水线不会被掐。**stage 级那一件不是可选的**：本仓的 PR 是
   「一条 pipeline、三十几个 stage」，只看 pipeline 级计数时整跑都停在 `0-1`，推进到 28/33 也会被
   念成「没在动」而掐掉（2026-10-22 实测 `cnb-7d9-1k5h9edct`）；而运行中那一格的 `duration` 是占位
   `0`，当不了进度，平台上「正在跑」的词汇是 `start`（数完成时要把它排除掉）。
   **「在飞」那一判也不是可选的**（同日 ISSUE #2184）：计数是**离散**的，一格跑久了签名自己不动 ——
   `…/pending/0-1+11/33` 连满 10 眼被断流，而几分钟后同一条构建是 28/33（组 C 单跑实测过 1411s）。
   所以停滞 = 签名不变 **且** `inFlightStages()` 为 0；只认逐格那份词汇（在飞：`start`/`running`/
   `processing`；`pending` 是「还没轮到」，**不算**在飞 —— 队列里没起来正是要断掉的那一形）。
   靠调大上限治不了这个：那只是把误掐概率换小，两件事仍然分不开。
   断流那一格落 **`4`（CI 无终态）**，不是红 —— `4` 在这里的读法是「PR 可合并、CI 还没出终态」，
   下一动作是人去看那一格的日志，或过一会儿再 `pnpm ship`（PR 复用不重建）。
   轮询中途读到 PR 冲突则当场落 **`3`**（冲突的 PR 平台不派生 CI，干等没有结论，#3083）。
   45 分钟墙钟预算保留，兜「动得很慢」那条路，两条判点各打各的话。
10. **平台留痕：写文字开头带统一署名，PR 建完补 `处理人:` 标签并回读（ISSUE #2204 / #2213）。**
    凡向平台写文字（提单 / PR 正文、领取 / 结束评论），**最前面**一行粗体署名，**同一格式、
    不分角色**：`**[评论人：<短名>]**`（空一行再接正文）；未配就如实写「未配」，不编、
    也不拿 git `user.name` 顶替（那是提交身份，不是提单 / 处理身份）。**有且只有一行** ——
    正文文件里自己已经写了署名的，`ship` 不再前插第二遍，也不改写那一行里的人名
    （ISSUE #2268：无条件前插过一次，平台正文就出现两遍同名）。角色分工由标签承担
    （提单人 / 处理人 / 参与人），正文不再重复写 `提单人:` / `处理人:`。
    **这一格有只读审计**（ISSUE #2269）：`pnpm check:comment-headers` 扫 open 单子与 open PR
    的正文首行，三态 0 在场 / 1 有缺或重复或不在首行 / 2 没读到读数 —— 它一次也不写。
    **存量不批量回填**（ISSUE #2276）：审计的红不是待办队列，改哪张单就顺手补哪张的署名行；
    唯一的批量动作留给「形状修正」那一类（如去重 #2258，改前逐字节核对、改后独立回读）。改了上面那四条写文字的出口之后就跑一次。`ship` 建的 PR
    （含复用已有 PR）会自己 `post-pull-labels` → **独立回读** `list-pull-labels`，回读里
    看得见 `处理人:<短名>` 才念「已打上」；`post-pull` 与 `create-issue` 同形，没有 `--labels`。
    手工 `cnb pulls post-pull` / `cnb issues post-issue-comment` 不经过 `ship`，那两条路
    要自己带：`pnpm ship --whoami` 打出这份检出的短名、署名格式与可粘贴命令 —— 它一次
    也不碰平台、不改任何状态。未配 handle **不阻断**（留痕是读数，不是判据）；Windows
    检出会给**这一份** `.env` 的绝对路径与 `pnpm env:init`。
11. **领单 / 结束 / 我的单子：一次只做一件，且不与主流程同跑。**
    `--claim <号>` 打两枚标签、再评论「开发者 <短名> 已接单，正在开发中。」：`处理人:<短名>`
    是**当前谁在做**（结束即撤），`参与人:<短名>` 是**谁做过**（只增不删）。两枚用途不同、
    不能合并 —— 拿 `处理人:` 兼任历史会让这张单永远「有人在做」。旧单已有 `处理人:` 但缺
    `参与人:` 时只补后者，不重复打已有的那枚。
    `--release <号>` 先评论「开发者 <短名> 开发结束。」、再撤 `处理人:` 标签，`参与人:` **保留**
    （评论没落地就**保留** `处理人:`）。两处都**写后独立回读**，回执不算结论。
    与 `--merge` / `--close-issue` / `--message` / `--add` / `--only` 等任一旗标同跑 ⇒ `2`
    且一个 `cnb` 调用都不发；未配 handle ⇒ `2`。
    **标签不是锁**：平台没有 compare-and-set，别人名下的单不领取；两个「处理人」同时挂上
    ⇒ 当场落 `1` 让人裁定，不替你撤别人的标签（评论不受限，谁都能在单子上说话）。
    同一张单可以「领取 → 结束 → 再领取」：幂等判断取 **`-created` 新到旧的第一条自己的
    状态评论**，不看「历史上出现过」。`--claims` 列 `state=open` 且在 `处理人:` 名下（只认
    当前状态）的单，分页到顶会明说「只看了前 N 张」，读不到列表落 `2`（那是「没拿到」、
    不是「没有」）。
    关单验真之后若处理人是你，同一套收尾会补「开发结束」评论、撤 `处理人:`，并保留
    `参与人:`；处理人是别人则**不代发**。
12. **建单走 `--new-issue`；CI 红了先 `--diagnose`，别手抄 `get-build-stage`。**
    `pnpm ship --new-issue "<标题>" --issue-body-file <正文> [--priority <P0..P3>]`：建单 →
    补 `提单人:<短名>` → **独立 `get-issue` 回读**（标题 / 优先级 / 标签）之后才念结论。
    标题与正文是判断，必须人给（§13.10.9：修缺陷先立案）；正文开头那行 `**[评论人：<短名>]**`
    由脚本保证**有且只有一行**（自己写了的不再重复补，见第 10 条）。
    `--priority` 只认平台词表，不给就走默认 `P2`，词表外 ⇒ `2`（§13.10.12）。
    `pnpm ship --diagnose [sn]` 只读取回整跑判决 + 每一格红格 + **失败行（带完整日志行号）** +
    末尾若干行 + 完整日志链接；不给 `sn` 时按 HEAD 的 sha 在 `pull_request` 构建里逐字归属
    （找不到 ⇒ `2`，不拿「最新那条」顶上）。退出码走退码表（`ship-codes.mjs`）：绿 `0` /
    真红 `1` / 被取消等泛化没跑起来 `2` / 归不到 build 时当前分支的开放 PR 冲突 `3` /
    还在跑 `4` / 取不到或 PR 可合并但无 build `5`。它**不写平台**（只发三条读命令）、也**不归因**
    （那是 `base-check.mjs`）；与主流程和单子动作互斥，排在 preflight 之前 —— 在 `master` 上、
    工作树脏时照样能跑（§13.10.13）。两个形状坑（`pipelinesStatus` 是按 id 索引的对象、
    格日志 `content` 是带 ANSI 的行数组）只有一份实现，别再按数组 / 字符串读。
    「还在跑」那一支现在带格子进度（签名与轮询那行同一份计算，`progressReadout` 一次算好，
    ISSUE #2304）；「没推进」要连续两眼才念得出 —— 基数落在 `.git/comfy-diagnose-last/<sn>.json`，
    签名不变 + 间隔 ≥ 10 分钟 + 没有一格在飞，三件同时成立才念「疑似派发未出勤」并把出口点成
    `pnpm ship --rerun-ci`；缺一件就仍念「还在跑」。它仍是 `2`，不改判据。
    **「有格在飞」不一定是长跑**（ISSUE #2901）：一格的 `status` 是 `start` 而 `endTime`
    不大于 `startTime`（`duration` 却不为 0）时，那一格**不会回来了** —— 平台唯一的兜底是
    8640s（2h24m）客户端超时。轮询与 `--diagnose` 都会在越线（10 分钟）时明写「疑似 runner
    失联」并给出口（`--rerun-ci` / 先 `--diagnose` 复核）。那几行是**读数**，不改退码、也
    不新增一种结论 —— 断流那一判依旧要求「没有一格在飞」，所以在这一形上它照样掐不掉。
    **绿跑里某一格念了什么**走同一读者的第二个入口：`pnpm ship --stage-log [<sn>] <格名|格 id>`
    （#2455）。它按**格名逐字**反查 `stageId` —— 认不出或多格同名时退 `2` 并列出候选，
    **不替你挑一格**（挑错的那一格也有日志、也带行号，看起来就像证据）。`0` 念的是
    「正文取到了」，不等于「这一格绿了」；取数、归一与「按 sha 归属哪一跑」都和
    `--diagnose` 共用同一份（§13.10.13）。
13. **往已有单子补读数走 `--comment`，正文只从文件来。**
   `pnpm ship --comment <号> --body-file <文件>`：评论（开头那行署名由脚本保证有且只有一行）→
   **独立 `list-issue-comments --sort -created` 逐字回读**之后才念结论。正文只收文件 ——
   命令行里的多行与反引号会被 shell / `pnpm run` 吃掉；`--body-file` 与建单那格的
   `--issue-body-file` 是两个对象。**末尾换行先归一再比对**（平台会吞掉文件末尾那一个，
   实测 1818 ⇄ 1817），**带图正文先归一图片资产链接再比对**（ISSUE #3655：平台存评论时把
   上传图片的相对链接 `/-/imgs/issues/…` 改写成绝对地址，四张图各差 39 字那一次恒判红），
   其余任何差异 ⇒ `1`；写没跑起来 / 回读没跑起来 ⇒ `2`，且回读没跑起来时
   **别急着重跑**（可能已经写进去了，先去单子上看一眼）。一次只做一件：与领取 / 结束 / 主流程
   任一旗标同跑 ⇒ `2`，`--body-file` 不跟 `--comment` 一起出现也 ⇒ `2`（§13.10.17）。

## 等 CI 那一格别空等：做一次回顾（规范 §13.10.14）

`pnpm ship` 轮询那几分钟到十几分钟，是**最后一个上下文还完整的窗口** —— 分支一合、工作树
一清，「我当时为什么这么绕」就没人知道了。同族的第二处、第二次敲的同一串命令、被抄成第二份
的东西，都只有在这时候看得见（#2445 那一轮之后开出的 #2453 / #2454 / #2455 三张单子，
就是在这个窗口里回头看出来的）。

清单的**唯一出处在规范 §13.10.14**，本 Skill 不抄第二份（抄一份，下一次清单扩充时就脱钩了）。
那一格是**读数与出口，不是闸**：不参与退码、不阻断合并 —— 做成闸只会收获一串随手勾完的勾。

**但「发现即立案」是动作，不是出口（ISSUE #3560，规范 §13.10.9 交付收尾段）。** 全托管跑完给
任务派发者的交付 / 流程总结里，回顾窗口读到的**问题 / 建议 / 坑 / 不规范 / 可优化点**，代理
**当场** `pnpm ship --new-issue "<标题>" --issue-body-file <正文> --priority <P0..P3>` 立案，
**不许**只在总结里写「要不要提单」「是否提单」「建议提单」等人点头 —— 立案不是决策、排期才是
（§13.10.9「在不在账上不由人决定」），问一次就多一次「随会话消失」。**后续是否处理**在对应
单子里讨论，不在本次交付里替人决定。总结里只放**已立案的号 + 一句话**（或「本轮没有发现」的
显式说明），不堆没有号的建议 / 待办清单。一条诉求一张单（ISSUE #2251）。

**不写自动扫描建单的工具，也不让 ship 代写标题正文**：判「什么算发现、正文怎么写」是判断
（§13.10.12 / §12.20），编排层一次也不写内容。`pnpm report:session` 生成的汇报骨架第五节是
这一格的形状：从「人填待办」改成「已立案清单 + 不许只询问」，由 `tests/session-report.test.ts`
逐字钉住。边界 0 那句「模式是显式别名、红线照旧」不因此开口子 —— 提单动作由代理在收尾执行，
不进 ship 的阶段表。

## 它不重复判的东西

| 要做的事                   | 谁在做                                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 提交门槛                   | `.githooks/pre-commit`（由 `git commit` 触发；阶段 0 只预跑它的 D0 只读子集）                                             |
| 这次提交的形态红（预报）   | 阶段 0 的 D0 预跑（ISSUE #3200）：清单从 `.githooks/pre-commit` 的 D0 组解析（单一出处，不抄第二份），每步按原样命令起、红不短路 ⇒ 所有红一次报齐落 `1` 停手（与提交钩子同权）；清单取不到 ⇒ 跳过不冒充结论；跳过条件各念一行（`--add` / dry-run / 依赖没就绪 / 旗标关），暂存面为空静默；双付明说（`--no-preflight-d0` 关） |
| 这一笔会带进哪些文件（#3597） | 提交段自己读一次 `git diff --cached --name-only -z` 并比对 `--add` 点名集合（`ship-local.mjs` 的 `classifyStagedSurface`）：点名之外还有已暂存文件 ⇒ 退 `2` 并逐个点名；`--allow-staged` 才放行。没给 `--add` 时不判（暂存面本来就由调用方负责） |

| 「这条红是我的还是主干的」 | `scripts/base-check.mjs`（CI 红时它会点名这个入口，不自己归因）                                                         |
| 流水线终态                 | 平台 build 的 `data.status`                                                                                             |
| CI 红在哪一格、失败行是什么 | `pnpm ship --diagnose [sn]`（只读取回；取数/归一只有 `ci-build-readout.mjs` 一份实现，归因仍归 `base-check.mjs`）        |
| 绿跑里某一格念了什么 | `pnpm ship --stage-log [<sn>] <格名\|格 id>`（只读；按格名逐字反查，认不出/命中多格退 2 且列出候选，不替你挑一格；与 `--diagnose` 共用同一份取数与「按 sha 归属」）  |
| 合没合上                   | PR 的 `is_merged` **且**回读解析出的主干基线顶端有没有那份碎片                                                          |
| 这次变更挂在哪张单子上     | 阶段 0 的 `ticketReading()`：碎片文件名的号 + 首行段落（**读数，不改退码**）                                            |
| 单子关没关上               | 本轮号跟验真的合并；人点名的号在本轮没合并时反查 `pulls list-pulls`（`closed` 里**逐条认 `is_merged`**，标题先剥 PR 尾数）。关完一次**独立的** `get-issue`：`state` / `state_reason` / `closed_at`（`update-issue` 的回执不算结论） |
| 分支**删之前**：它落地了没有 | `pnpm ship --branches`（只读）。判据只有 PR 的 `is_merged` 原值 —— `git diff origin/master…<分支>`（三点，起点是 merge-base）与 `git branch -d` 的祖先判据在 squash 拓扑下**恒假/恒非空**，都不是判据（实测九条已合并分支被三点 diff 判成「都没合」）。窗口取没取满会自证；取不到的那条给「没结论」，不是「没合并」（§13.6.5） |
| 分支收干净没有             | `--clean-branch` 之后各问一次事实：`git ls-remote --heads` 与 `git show-ref --verify`（push / branch 的退码都不算结论） |
| 进程收干净没有             | 阶段 0 念 `runningAppInstances()` 的归属读数；`--reap` 只发 `reap-process.mjs`，**收完再读一次同一份判据**才算数        |
| 这条流水线还在不在动       | 轮询的签名 `(sn, data.status, pipeline 完成数, stage 完成数)` **加上「此刻有没有一格在飞」**（`inFlightStages`）—— 两件同时成立才断流，不做无新读数的等待 |

⚠️ **`ship` 提交段「全过」不等于 tsc / eslint / 用例过了**。`pre-commit` 默认只跑形态档，
重档由 `COMFY_HEAVY_GATES=1` 那一档与平台兜底（规范 §13.5.25）—— 钩子自己会打印
「本地**没跑**：组 A B C D」，那句话不是客套，别把它读成「已通过」。
本地要全套：`COMFY_HEAVY_GATES=1 pnpm ship …`，或合并前 `pnpm check:premerge --full`。

**它自己一次也不判「绿不绿」。** 所以：不要为了「跑得快」去绕过它直接调 `cnb`，
也不要把它打印的结论再加工一遍 —— 它转述的就是执行者的原值。

## 平台侧不可用时

这台机器上没有可用的 `cnb` 时，本地两段（提交、push）照跑，平台那几段会显式记成
「没有执行者」并退 `2`，同时打印一句让你自己去开 PR。
**那不是失败，也不是完成** —— 那一格没有结论。别把它写成「已合并」。

## 与硬规则 6 的关系

本仓不许直连 `master`（`check-branch-guard.cjs` 在组 0 判）。`ship` 在阶段 0 也会先看
HEAD 在哪条分支上并拒绝在 `master` 上继续，但**那只是提前给个可读的提示**，
真正的防线仍是钩子与平台分支保护 —— 别把它当成守卫本身。
