# 从工作树到 `master`：`pnpm ship`

**逻辑只有一份，在 `scripts/ship.mjs`。** 本 Skill 不重抄流程，只说什么时候用它、
它的边界在哪、以及哪几格仍然要人判断。要看全部旗标与阶段名就读那份脚本的文件头。

## 什么时候用

改动写完、`changelog.d/` 碎片也补了，准备交出去时：

```bash
pnpm ship --dry-run          # 先看它打算跑哪些命令（一条都不执行，但阻塞照报）
pnpm ship                    # 到「CI 出终态 + 打印下一动作」为止
pnpm ship --merge            # CI 绿了才合并（squash）
```

## 三条必须先知道的边界

1. **退出码三态，`2` 不等于通过。** `0` 走到终态且事实为绿；`1` 有事实是红的；
   **`2` 有一步没跑起来**（`cnb` 不在、按 sha 取不到 build、非 git 检出）。
   把 `2` 读成「跑过了没问题」是这一族最贵的误读 —— 它和「测了，结果是绿的」
   在多数终端里长得一样。
2. **它不代写提交信息，也不替你 `git add -A`。** 提交信息是判断（症状 / 读数 / 因果），
   暂存面是「这次包含什么」的声明。树脏而没给 `--message` ⇒ 它会停在阶段 1 并说明原因。
   要它代为暂存就逐个点名：`--add src/a.ts --add changelog.d/0-x.md`。
3. **合并是显式动作。** 不给 `--merge` 就停在判决处。给了 `--merge` 而 CI 不是绿的，
   它会拒绝合并并退 `1` —— 这个拒绝是功能，不是故障。

## 它不重复判的东西

| 要做的事                   | 谁在做                                                          |
| -------------------------- | --------------------------------------------------------------- |
| 提交门槛（五组五十步）     | `.githooks/pre-commit`（由 `git commit` 触发）                  |
| 合并前固定动作三段         | `.githooks/pre-push` → `premerge-proof.mjs`，落一份机器本地证明 |
| 「这条红是我的还是主干的」 | `scripts/base-check.mjs`（CI 红时它会点名这个入口，不自己归因） |
| 流水线终态                 | 平台 build 的 `data.status`                                     |
| 合没合上                   | PR 的 `is_merged` **且**回读 `origin/master` 顶端有没有那份碎片 |

**它自己一次也不判「绿不绿」。** 所以：不要为了「跑得快」去绕过它直接调 `cnb`，
也不要把它打印的结论再加工一遍 —— 它转述的就是执行者的原值。

## 平台侧不可用时

这台机器上没有可用的 `cnb` 时，本地两段（提交、push）照跑，平台那几段会显式记成
「没有执行者」并退 `2`，同时打印一句让你自己去开 PR。
**那不是失败，也不是完成** —— 那一格没有结论。别把它写成「已合并」。

## 与硬规则 6 的关系

本仓不许直连 `master`（`check-branch-guard.cjs` 在组 0 判）。`ship` 在阶段 0 也会先看
HEAD 在哪条分支上并拒绝在 `master` 上继续，但**那只是提前给个可读的提示**，
真正的防线仍是钩子与平台分支保护 —— 别把它当成守卫本身。
