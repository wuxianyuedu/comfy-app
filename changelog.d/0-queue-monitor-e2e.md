## Added

- **队列与运行屏补上浏览器判据（`e2e/queue-monitor.spec.ts`，4 条 @critical）。** 这一屏此前只有 jsdom 那几份用例，三件「只在真渲染里才成立」的事没人判：
  - 「排队中（N）」标题里的数与下面真的铺出来的行数一致（含 0 的空态 —— 空态铺的是说明文字，不许留下半个 `<li>`）。对不上的现场是「写着 3 条在排、下面只有两行」，用户正是据此决定要不要再提交一条。
  - 三段按「跑动中 → 排队中 → 最近结果」的顺序铺，且每段都有自己的 `aria-labelledby` 名字（顺序与名字是这一屏的主干，写歪一处读屏就跳错段）。
  - 跑动中最多一张卡：同一时刻只该有一处在跑的那张被表达，多个 `RUNNING` 不许叠成两屏。
  - **每 2 秒的重读真的在发请求**：`refetchInterval` 是运行时行为，jsdom 里定时器不跑网络 —— 这条只有浏览器能判。屏面停在某一帧上时，用户看不出来。

## Notes

- **这一屏的浏览器判据刻意不桩数据，因为桩不通（实测，不是猜）。** `route.fulfill` 打给 `/api/trpc/task.list?batch=1` 的响应到不了客户端：
  - 四种信封形状各测一次 —— 数组一行、数组 + 换行、索引对象、索引对象 + 换行，都按真服务端录下来的 superjson 结构逐字段对齐（`[{"result":{"data":{"json":…,"meta":{"values":{"tasks.N.createdAt":["Date"]},"v":1}}}}]`；`meta.values` 缺了会让 `createdAt` 停在字符串上）；
  - **负控制**：返回一段坏 JSON，与上面四种行为完全一致 —— 屏面照旧、控制台零报错、`loggerLink` 照样打 `<< query`；
  - 桩的处理函数确认命中（同一 URL 打了 3 次 `HIT-STUB`），无 service worker 插手。
  - 结论：问题不在形状，是这条链路上 fulfill 根本不被消费。因此这 4 条判据只判**与机器上有什么数据无关**的不变量，拿真库真服务跑。
- 顺带一条事实（同一批实测带出的）：`e2e/critical-flows.spec.ts` 里那份 `stubBackend` **喂不进数据** —— 它只让界面不卡住，不改变任何一行内容。该文件现有断言确实没有依赖数据，所以这个问题一直没暴露；任何后来想靠它断数据的人会把力气花在猜信封上（本次四种猜法都试过）。已另开 #1442 记这条（含四种信封、负控制与相关实现的分析）。
- 位次方向（后端按 `createdAt` 倒序返回、执行器 FIFO，所以视图必须反一次让最早提交的是「第 1 位」）这条最像「只有看屏幕才发现」的判据，本次**没有**进浏览器用例 —— 它依赖能喂进去的数据。它现在由 `queue-monitor-config.test.ts` 与 `QueueMonitor.test.tsx` 在 jsdom 里判着；等桩这条路修通后再补浏览器那份。
