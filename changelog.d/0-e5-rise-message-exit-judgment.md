## Added

- **E5 那条横切判据补上第六维：拒涨的那句话本身要给得出可执行的下一步**（`tests/ratchet-update-guards.test.ts`）。前五步判的是**行为**（建基线、基线=现状必须绿、加违规必须红、`--update` 必须非零且基线逐字节不变、0 基线上也不许放宽），这一维判的是**话术的方向**：第 ④ 步已经证明「在这个状态下跑 `--update` 会被拒绝」，那么同一段红话就不许再把 `--update` 当作出路递给人 —— 三种自洽写法才放行：**先改再 `--update`**（把顺序写明，如 `check-circular-deps` 的「先按 §12.7 拆环…再 --update」）、**明说不要用 `--update`**（如 `check-code-duplication` / `check-theme-colors` 的「不要用 --update 掩盖」）、**改成人的动作**（手工登记 / 逐条写理由）。
  立案实例是上一批顺手修掉的 `check-tsc-diagnostic-executors.cjs`：它的「声明新增（上涨）」写着「再跑 `--update`（= 把基线收紧到 N）」，而同一个 `--update` 对上涨是 `exit 2` —— 照红话跑只会再吃一次红，而它要人回答的那个真问题（「这条声明由谁执行、谁来敲」）一次都没被回答。这类红话比没有红话更糟：它**教人绕开判据**（§11.18.4）。
  先量了存量再定判据（口径同 E5：判据必须先看得见全部存量）：按「同一段上涨语义的红话里提到 `--update`」粗筛命中 15 家 / 16 处，逐处读过之后确认**它们全都已经是自洽写法**（「先…再」「不要用…掩盖」「只用于收口后降数字」）—— 也就是说这一格今天没有欠账，加下来是 0 误报的预防闸：新加一家棘轮、或有人把现成的修法那句改掉，会在**那一次**红。实测：13 家 × 该维全绿；变异一刀（把 `check-theme-colors` 的「新增写死色值必须先 token 化，不要用 --update 掩盖」换成一句「请处理上述新增项」）→ 只有那一家的第 ①-④ 格红，报「--update 拒涨了，但红话没给出可执行的下一步」。
- 规范 §11.25 那张五步表补成**六步**（新增 ⑥ 一行，含三种自洽写法与「为什么『再跑 --update』不算」）。
