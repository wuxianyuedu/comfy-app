## Fixed

- **启动日志里看不到服务在干什么**：`dev server` 的 stdout/stderr 被 `spawnInGroup` **直接重定向成文件描述符**（给的是 fd，没有 pipe、没有 tee），因此 `▲ Next.js` 横幅、编译与路由日志、首次编译的报错既不进编排器 stdout、也不在 `shell-launch.log` 的 `[orchestrator] …` 那一路里——启动页「查看日志」只拼编排器的四段，于是面板上只有 `[launcher]` / `[orchestrator]` 两段。`get_launch_log` 增加两段服务自己的输出（`log/current/nextjs/` 下前缀匹配 + **mtime 最新**的 `nextjs-stdout-*` / `nextjs-stderr-*`，限长限行）；取「最新」按 mtime 而不是文件名序，是 ISSUE #576 那个坑的回归点（戳的历史形态与现行形态字典序与时间序相反）。路径收在 Rust 侧 `shell_launch::nextjs_log_dir()` / `latest_prefixed_log()`，不在别处拼 `log/nextjs` 字面量。证据：`src-tauri/src/lib.rs`、`src-tauri/src/shell_launch.rs`。

- **状态栏闪一下「应用服务已断开」而服务一直在应答**（消息中心因此多出「已断开 + 已恢复」两条）：探活打的是应用服务自己的 HTTP（`/api/dev/server-id`），**冷编译 / 按需编译某条路由 / Turbopack 抢锁**时那一拍会超过探活超时，而判据是「单拍失败即断开」。改为**连续失败 2 拍（≈4 秒）**才算断开，门槛常量 `OFFLINE_CONFIRM_FAILURES` 收在取事实那一层（`use-dev-server-liveness`）；判据层（`deriveDevServerStatus`）改收抗抖动后的 `reachable`，不再收单拍的 `lastProbeOk`。恢复侧不加门槛：抖动期间离线边沿根本没成立，消息中心自然什么都不记。证据：`src/components/studio/hooks/use-dev-server-liveness.ts`、`src/lib/shell/dev-server-status.ts`。

- **「应用服务已断开」的原因查不到，且给了一个与事实相反的归因**：① 写侧只挂在**就绪等待期**那条路径上（`concludeDownstreamExit` 的唯一入口在就绪等待循环里），于是「服务起来之后自己没了」——用户在界面上真正会看到的「应用服务已断开」——一条记录都不写，恢复后读回 `null`。新增**运行期**写点 `runtimeExitRecord`（纯函数，可逐分支断言）：只有 **dev 先退出**才写，壳先走（用户关窗 / 壳被收走）与编排器收到 SIGINT/SIGTERM 都不写——那两种是服务被带走或有序收尾，补一条只会把设计内行为说成故障。② 文案把「读不到记录」一律归因为「纯手工 `pnpm dev` 起的服务」，而读不到有三条互斥成因（从未写过 / 写侧只覆盖启动期 / 记录与当前 runId 相同被判掉），从这一个事实里分辨不出是哪一条；手验现场恰恰是走启动编排的双击 exe，且那次服务根本没退出过。改为只说**这一次是什么形态**（冷启动 = 本次运行还没有服务结束过；恢复 = 断开期间没有旁证人写下结束事实）并指明服务自己的输出在 `log/current/nextjs/`——归因猜错比不归因更坏，它会把排查引向另一条路。证据：`scripts/dev-launcher.mjs`、`src/lib/shell/app-service-message.ts`、`tests/app-service-exit-runtime.test.ts`。
