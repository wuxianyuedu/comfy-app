## Fixed

- **CI 的「文件结构硬规则」对 `master` 恒红：R5 棘轮把一个字都没改的文件判成「继续变大」**。`src/components/studio/logs/LogPanel.tsx` 的基线 `988` 记于修订号 `116666f` —— 那是个分支提交，合入后不再有 ref 指向，`git gc` 一跑就成不可达对象。`git show 116666f:…` 从此一律失败，**按 `baselineRev` 同口径重数**（ISSUE #637）静默退化成「拿记录值直接比」，而记录值记在另一个格式时代的源码上：该文件今天按同一套计数口径是 993 行。结果是 `R5 超限文件继续变大(… → 988 → 993 行)`，报错与真实原因（基线修订号不可达）毫无关系，且任何 PR 都过不了这一步。
- 判据拆成两支：**基线修订号可达** → 照旧同口径重数；**不可达** → 直接报 `R5 基线修订号 … 在本检出里取不到`，可行动作是补历史（`git fetch --unshallow`）后执行 `--update` 重记基线，**不再把它说成「这个文件变大了」**（那是另一支判据）。
- 修法同时把这点记进规范 §12.13.3：同口径重数有个前提 —— **基线里那个提交还在检出里**。`--update` 时也顺带确认一次，浅克隆上会提示先取全历史。
- `R5_RULE_VERSION` 3 → 4：旧的记录值（记于其格式时代）对当前内容不再成立，须一次性重记；基线的 `baselineRev` 也因此指向当前提交，这个陷阱在存量数字上一并清掉。
- 回归测试（`tests/check-file-structure.test.ts`）新增三条：修订号不可达 → 报「取不到」并指向重记基线、**不**含「继续变大」；不可达且内容真变大 → 同样只指向重记基线；可达 → 走同口径重数那一支。
