## Added

- **提交前增量测试层：改到哪、测到哪**（`scripts/affected-tests.mjs` +
  `tests/affected-tests.test.ts`，规范 §13.5.8）：`.githooks/pre-commit` 的 C 组从
  「写死几个结构守护用例」升级成 **固定清单 + 本次暂存改动牵扯到的用例**，仍然只起
  一次 vite。固定清单的唯一出处搬进脚本（`FIXED_STRUCTURAL_TESTS`）—— 钩子再抄一份
  就会在用例改名后变成「一条都不跑、钩子却全绿」。
  命中判据五条（方向一律「宁可多跑，不许漏跑」）：① 改动的测试自身；② 同名兄弟与
  快照宿主；③ 直接 import（静态 / 副作用 / 动态 / `require` / `vi.mock`，含 `~/` `@/`
  别名，相对说明符按引用方位置解析）；④ barrel 同目录（转出口会把改动透出去）；
  ⑤ 改动路径以字面量出现在测试里（门禁 `execFileSync` 起被测脚本、主题用例按路径读
  CSS），外加 `scripts/<name>` ⇄ `tests/<name>.test.ts` 的同名配对。
  **已知边界写进文档而不是藏起来**：这一层不保证传递依赖；公共地基
  （`vitest.config.ts` / `tests/setup.ts` / `package.json` 与 lockfile / `tsconfig.json` /
  `.githooks/**`）被改时明确**放弃收窄**并把理由打到 stderr —— 兜底刻意不是「跑全量」，
  因为全量当前带着别线的基线红（§11.13），那等于把提交闸变成不可用。等基线红清零后
  把 `mode === "all"` 那条分支改成跑全量。
  代价实测：解析一次（读全部 437 个测试文件）约 1.7s；一次 3 文件的真实改动解析出
  11 个用例。同时把散在文档里的「第 N 步」引用改成按组指向（那些序号在钩子并行重排
  之后就已经对不上了）。
