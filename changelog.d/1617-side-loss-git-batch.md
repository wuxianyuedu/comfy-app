## Fixed

- **「合并有没有把一侧整份覆盖掉」这条判据不再随 diff 规模线性变慢**（ISSUE #1617 / #1618 的续账）。
  两档执行者原先各自在循环里取证：逐文件 `git log --no-merges <ref> -- <file>`，再对该文件的
  每条历史候选逐条 `git rev-parse <sha>:<file>` —— spawn 次数 =「变更文件数 ×（1 + 该文件历史条目数）」。
  本机实测（空载）0 文件 0.7s / 1 文件 3s / 3 文件 6.2s / 35 文件 84.6s / **48 文件 133–218s**，
  约 2–3s/文件。两个后果都是撞上的事实：
  - `tests/premerge-check.test.ts` 中断言 `mergeLoss` 那一段的两条用例**在任何 ≳10 文件的分支上恒超时红**
    （报 `Test timed out in 30000ms`，而 vitest 记的单条耗时 132s / 133s ⇒ 子进程真跑完了、预算先到）。
    锚点是 `merge-base(上游, HEAD)`，所以红在分支、绿在主干，与改动内容无关。
    **没有抬全局 `testTimeout`**（它的注释明写是「给真进程留的余量，不是给慢用例兜底」），
    **也没有登记 `KNOWN_FAILED_FILES`**（那张表粒度是整份文件，登记会连带摘掉同文件另外 15 条已绿断言）；
  - 挂在 `.githooks/prepare-commit-msg` 的提交前档，一次大合并会让 `git commit` 静默挂几分钟。
- 取证收成家族里的**第三份模块** `scripts/merged-side-loss-git.mjs`（分工单向：
  `merged-side-loss-core.mjs` 纯判定、不含传输层；新模块纯取证、不认识业务名词；两个执行者只管语义），
  两次批量做完：一次 `git log --format=@%H --name-only --no-merges <ref>` 遍历反向建「文件 → 候选历史」，
  再把全部 `<rev>:<path>` 一次性喂 `git cat-file --batch-check`。同一批真实范围实测 6–10s 且与文件数基本无关
  （立案现场 `bfeb33f0..ad81a912`，128 文件、86 处命中：**8.3s**）。
- **读数等价性是对跑出来的**：`--batch-check` 与逐条 `rev-parse` 在 144 条真实请求上逐字相同
  （含路径在那个版本不存在的 `missing`）；8 个真实范围（三次立案事故 + 最近 6 条主干）两侧最终清单逐字一致。
  候选清单继续**排除基线自己那一版**（提交前档同理会排除 `HEAD` 那一版），与旧口径逐字同。
- ⚠️ **顺带补掉一个结构性盲区**：单路径遍历会在合并处按 TREESAME 剪枝（只跟第一父本，被并进来的那条线
  整条不访问），于是「某文件只在侧线上被改成过某一版、那次合并 `-s ours` 取了自己、之后又被写回那一版」
  这种**真退回**，旧读法取不到候选、看不见。新读法取得到；`tests/merged-side-loss-gate.test.ts` 第 ⑨ 格
  先自证「逐文件那条读法里没有那次提交」，再断言判据仍然报出它。
- **读不懂就整单判「没跑起来」**：批量解析输出行数对不上或某行不合形状时取证层返回 `null`，
  事后复算档转退出码 2、提交前档保守放行并说明原因 —— 不许把「没取证」说成「没命中」。
- 回潮有执行者：新增 `tests/merged-side-loss-git.test.ts` 用注入的假 `run` 数进程（每个函数各 1 次、
  空清单 0 次），并核对两个执行者的源码不再自己拼 `rev-parse \`${...}:<path>\``、也不出现 `cat-file`。
  两份门禁自测把传输模块列进夹具 `copy` 清单（漏了的表现是子进程 `MODULE_NOT_FOUND`，看着像判据坏了）。
- 机制与实测表落档 §11.23.6.2（`docs/standards/11-测试与可观测性.md`，`docs/generated/**` 同批重渲染）。
