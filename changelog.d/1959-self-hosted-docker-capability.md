## Changed

- **规范补一节：自托管 Runner「默认不开启 Docker 能力」不等于「开不了」，但那一格对本仓
  仍是硬约束，而且那扇门不在仓库手里**（ISSUE #1959）。§13.5.3.4 那张对照表的第一条是这
  条件路径成立的**全部前提**，而官方原文里的**「默认」**二字很容易被读成「让管理员开一下
  就好了」—— 于是「自托管没有 docker」看起来像本仓配置写错、或平台缺了一块能力。
  新增 §13.5.3.4.1 把这条判断落成一句可引用的结论：**没有任何文档能回答「怎么开」**
  （自托管 Runner 只有「构建节点」一篇，通篇是接入 / `namespace` / `tags` / 调度，不含
  开关式配置项；`services: docker` 属于 `pipeline` 级、注入的是平台池那套容器化构建环境
  的组成，而 `pipeline.docker.image` 已写明「不会生效」），所以真正的分岔不是「默认 vs
  非默认」，而是**「谁控制这台机器」**。

  同时点名一条最容易被混掉的分界，它决定了「这一步到底有没有路可走」：**失效的是声明
  构建环境与挂载**（`pipeline.docker.image` / `pipeline.docker.volumes`），而**任务在独立
  容器里执行仍然成立**（脚本任务带 `image`、插件任务必带 `image`，与平台池同形）。于是
  「要装好工具的现成环境」走插件任务或任务级 `image`、「要构建镜像」走插件市场的
  Kaniko（原文「无需 Docker daemon」，本仓当前没有镜像可构建、故不入流水线）、
  「要跨节点共享缓存」走 `docker:cache` 内置任务 —— 三条都不需要 dind、也不需要宿主机
  有 docker。

  **为什么不给这一节加机器判据**：可执行的那一半已经在配置里（`.cnb.yml` 不声明任何
  `docker` / `image` / `volumes`，「工具链自证」把「这台机器该有什么」变成会红的断言），
  而「本仓还需要不需要 docker」是**人**的问题 —— 与 §13.5.3.8 那条「不要靠调
  `runner.cpus` 调优」同族，说的是「别去动那个不生效的旋钮」。
