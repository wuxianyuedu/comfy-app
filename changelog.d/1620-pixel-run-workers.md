## Added

- **像素档多了一条「降并发跑」的出路：`node scripts/pixel-run.mjs --workers=N`（ISSUE #1620）**。
  像素档的默认并发是 `playwright.config.ts` 的 `fullyParallel: true`，而开发机（尤其 win32）
  的 dev server 在视觉套件持续负载下会失稳 —— 实测形态是**整批红、单个 spec 或 1-worker 跑就绿**。
  按规范 §11.13 那句硬动作，这属于**负载假红**：隔离（降并发）绿才是对它该有的定性，杠杆是
  **并发**而不是抬 `threshold`（后者会把「真挂死」一起放过）。新开关把 N 透传给 Playwright；
  默认口径仍是唯一的那个 —— 不写 `--workers` 时它不出现在命令里。非法值（`0` / 负数 / 非数字 /
  空）**当场拦**（退出码 4），不静默当成「没给」。

## Fixed

- **像素基线的新鲜度账此前只有「整批全绿」一条写入路径，于是默认并发下失稳的机器写不出
  自己那一档的账、pre-commit 因此红（ISSUE #1620）**。修法有两半：
  ① `pixel-run.mjs` 支持 `--workers=N`，降并发跑绿**照常记账** —— 这条账要证的是「这一档的
  基线在本机可复现」，负载假红证的正是它；
  ② `writeFreshness` 的 `how` 现在可被覆盖，降并发那次如实记成
  `pnpm check:visual --workers=N`（缺省仍取名义跑法）。没有这一半，「本机默认跑得动」与
  「本机得降并发才跑得动」在账面上会长得一模一样，下一个人按名义命令复跑必红、却指不出
  差别在哪。规范 §11.8 的「按需跑」那一节同步写清这条出路与「不是新默认」。
