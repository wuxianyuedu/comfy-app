## Fixed

- **`bundle-budget` 判红时那句「无法判断源码动过几次」现在数得出来了，锚点也不再记那枚会消失的提交**
  （ISSUE #2082；规范 §13.5.4 第四档那一段同步改写）：
  - **症状是同一条输出里的两句互相拆台**：`gzip 总量上升：2276.7 KB → 2277.2 KB（+543 B）`
    与 `基线修订号 0a618c1c 在本检出里不可达（基线过期 / 浅克隆）—— 无法判断这批读数与基线之间源码动过几次`，
    而它给的下一步（「先分清这点体积该不该认账」）需要的正是它自己说拿不到的那份归因。
  - **第二归因通道**（`commitsSinceDateTouchingSource()`）：`stale` 那一档改按基线里另一个实测值
    `generatedAt` 数主干上其后动过 `src/` 的提交，并把最近几笔标题一起打出。现场读数：
    `改按基线日期 2026-10-17 归因：src/ 侧其后有 11 次主干提交`，最前几笔是
    `44e45fdc 懒加载分块空闲预热` / `55aa5aac 新增全局队列事件通道` / `1fca2df4 分块失败不再整屏崩`
    —— 都是往客户端加代码的合并。三条边界写死：数出来是 **0 也要报 0**（0 是结论不是量不到）、
    日期本身不可信时**明说判断不了**（不许编一个数顶上去）、**补的是归因不是判决**（红照旧红，
    `别直接 --update 重记` 那句一字不松）。
  - **病根是锚点记错了方向**（这是 #1988 的另一半）：#1988 挡住的是 `baselineRev: null`，而这一份
    **形状完全合法、却在任何一次主干检出上都查不到** —— 本仓 PR 走 squash 合并，记录那一刻的 HEAD 是
    分支提交，合入后没有 ref 指向它，`git gc` 之后一律消失。于是那条归因在**每一次判红上**都失效，
    而账面全绿、没人报错，比 `null` 那一半更安静。现在 `--update` 落
    `merge-base HEAD origin/master`（主干上的提交，squash 之后仍在场），问不到主干才退回 HEAD，
    并把用的是哪一枚连同为什么打在输出里（两种锚点的失效方向不同，不写出来就只能事后猜）。
  - **这笔 +543 B 按 §13.5.4 例外流程认了账**（`--update --allow-increase`）：before/after 两档
    `gzip 2276.7 → 2277.2 KB`、`文件数 221 ⇄ 221`（一条没多）、无新依赖、净差是总量的 0.02%，
    归因就是那 11 笔主干合并。基线锚点因此落在 `d752ed11`（主干可达）。
  - 用例五条（`tests/check-bundle-budget.test.ts`）：有数 / 数是 0 / 日期不可信不许冒充 /
    锚点落主干那枚而非 HEAD / 问不到主干时退回并打在脸上。四条判据各带反向复算。
