## Fixed

- **设置页 ComfyUI 状态不再在「启动中 / 未运行 / 运行中」之间来回跳（ISSUE #442）**。点「启动 ComfyUI」后状态行先显示「正在启动…」，日志里已经打出「ComfyUI 已就绪」，上面那格却**闪回「未运行」**，几秒后才变回「运行中」。根因是拉起动作与「确认到运行中」之间那段空窗（拉起 → 端口绑定 → `/system_stats` 就绪）里的判定没人兜住：`comfyStatus` 每 5s 轮询一次，空窗里问出的「进程表还没命中 + HTTP 也没通」被当成事实渲染出去。现在判定层补两条判据：**「启动中」有计时窗口**（唤起动作发出后的一段窗口内不落「未运行」，`starting` 单飞锁只覆盖「本进程发出的那次拉起」，覆盖不到保存配置、探测确认这些空窗）；**「探明没在跑」的结论有黏滞期**（一次成功的进程表查询没命中才叫探明，相邻一轮的探针抖动——查询超时、环境反查没认出 uv 起的实例——证据更弱，不许改口，黏滞 10s）。两条都收在新增的纯函数 `deriveComfyUiStatus` 里，判定规则可逐条断言；启动 / 关闭动作显式失效时两把标记同清，不会把状态行按在错的答案上。
- **运行态快照多一个「这次到底查过进程表没有」的字段（ISSUE #442）**。此前的快照分不清「查了但没命中」（可信的「不在跑」）与「一条候选都没有、根本没查」（什么都不代表），两者都是 `running=false` + `unverified=false` —— 上层据此把空快照读成「未运行」的证据。新增 `didQueryProcTable` 明确区分，判据：命中任一候选（含 bound 子进程）或确实发过候选查询即为真；0 条候选为假，此时状态行显示「检测中…」而不是「未运行」。
