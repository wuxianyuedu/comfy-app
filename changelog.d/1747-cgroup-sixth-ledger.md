## Changed

- **C 组「第六笔账」：两个「看起来能省」的方向都被实测否决**（ISSUE #1747 续，
  规范 §13.5.8.2 末尾）。上一轮结尾把这两条留作「按规矩该您拍板」的候选，本轮
  把它们量到了底，**两条都不落地**：
  - **tw4 报告的拒涨两格不能降频，只能降成本（而降不动）**。两格成本差 30 倍且
    原因已定位：`tw4-canonical-report.mjs` 四次 spawn 实测
    `1928 + 1865 + 1940 + 1817 = 7553ms`（第二格同量级），而
    `tw4-spacing-canonical.mjs` 两格只要 `56 + 52 + 50 + 45 = 206ms` —— 后者沙箱里
    没有任何 px 任意值候选，`TOKEN`/`PX_VALUE` 正则当场早退，**一行都没问过引擎**。
    canonical 那 1.6–1.8s 是**首次 `canonicalizeCandidates` 建全量类名表**的成本
    （`import` 只 8ms、`loadDesignSystem()` 只 15–26ms、之后同实例 0ms），且
    **与问了多少条、有没有违规都无关**（干净沙箱单次 `--check` 仍 1.9s）。每格的
    每运行都起新进程、搭新沙箱 ⇒ 引擎状态跨不了进程 ⇒ **「共用一次启动」在一格内部
    无对象可共**。降频（搬出固定清单 / 只跑一次）等于废掉 §11.25 六步行为证明里
    「下一次有人改这个脚本时才拦得住」的那四步，**维持现状**。
  - **55 份 <300ms 的小用例合并省不出墙钟**（先纠正读数：不是 48 份，清单会长，
    以判据现算为准）。受控探针里合并确实快 3 倍（40 份 → 8 份：`1.6s → 0.52s`，
    vitest 自己也报 `~90ms startup each (spawn + environment, per file)`），
    **但真 C 组有长尾，合并一分不省**：40 份独立 + 一个 16s 长尾 = **16.5s**，
    8 份合并 + 同一长尾 = **16.5s**。真仓库同向复核（77 份 / `--maxWorkers=4`）：
    全量 **22.0 / 22.1s**，只留 22 份大用例 **20.3 / 20.7s** —— 那 55 份合计
    只值 **≈1.5s（≈7%）**，且它们本来就被长尾（`ratchet-update-guards` 单份 16.8s）
    留下的空闲 worker 吃掉。⇒ **合并 = 3 个新文件换 ≈0 收益 = 纯复杂度**。
    `isolate: false` 探针里同样零收益（16.4s = 16.4s），且它会让**文件之间的模块
    状态与副作用互相可见**（失效形态是静默的），**不在这里开口子**。
- 规范 §13.5.8.1 末尾补一段指路，把「这两个方向已量过、结论是不做」写清，
  免得下一个人再走一遍。
