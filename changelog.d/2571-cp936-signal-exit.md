## Fixed

- **CI 外壳不再把「被终止的一跑」念成通过**（ISSUE #2571）。`scripts/ci-cp936-exit.mjs`
  的 `close` 回调只接了第一个形参，于是 `settle(code ?? 0)` 把 `code === null`
  （子进程不是自己退出的）直接落成「退出 0」。当场复现（本机 Node 26.12.1，真起
  `setInterval` 长跑子进程、400ms 后 `SIGTERM`）：`close` **照来**，带的是
  `code=null signal=SIGTERM`，旧写法在那里转出去的是 **0**。
  现在折算收成一处纯函数 `exitCodeFromTermination(code, signal)`：有码照原样，
  无码有号按 POSIX 折 `128 + 号`，**号查不到与 `code`/`signal` 双 null 都落
  `UNKNOWN_TERMINATION_EXIT = 128`** —— 三个分支没有一个能回到 0。
- **同批把那句错的因果从三处复述点撤掉**：文件头那条「输出攒到 `close` 才发」写的
  理由是「被 kill 的进程上 `close` 永远不会来」，实测否掉 —— 不来的那一档是**外壳自己
  被平台按 stage 墙钟掐掉**（那时本文件一句都不会执行，读到的结论是平台自己的
  `timeout … exceeded`，它没读外壳的码）。同一句因果还留在 `close` 那段行内注与规范
  §13.5.3.5 第十二处（含那张两行表）里，三处一起订正，并把「`?? 0` 为什么看起来安全」
  这件事写成第十七处：**错前提的第二重代价是它替一处可疑代码作了解释**。
- **被终止那一格现在念一行出声**：「子进程被 `<signal>` 终止（没有跑到结论）⇒ 外壳退出
  `<n>`；这不是那条命令自己退的码」，因为那个码是外壳折算的、不是子进程给的 ——
  不写明，读日志的人会拿 143 去查「哪条命令退 143」，而那条命令一次都没退出过。
  它走 `write`（CP936 那一跳）而非 UTF-8 直写的 `emit`（与收尾那条总数同一条通道，
  ISSUE #1977）；`code` 有值时不发（与 ISSUE #2326「只在该出声时才出声」同一口径）。
- 判据 `tests/ci-cp936-exit.test.ts` 39 → 45：信号终止 ⇒ 非零且那行带着信号名与折算码、
  双 null ⇒ `UNKNOWN_TERMINATION_EXIT`、干净退出的 `0` 照旧且**不多说话**、那一行走
  `write` 不走 `emit`、折算表本体逐档（`3`/`127`/`0` 原样、`SIGKILL`→137、`SIGTERM`→143、
  未知号非零），以及**真起一条长跑子进程再从外面 `SIGTERM`** 那一条（`spawnProc` 交回
  真 `spawn` 的进程，收尾走生产那条 `close` —— 「`close` 到底带什么」只有真进程能回答）。
  注入面 `fakeChild` 补第二形参：只喂 `code` 的话「被信号终止」那一档在测试层根本不存在。
  反向复算三次：退回 `code ?? 0` ⇒ 4 红；压掉那句出声 ⇒ 3 红；废掉「有码照原样」⇒ 3 红。
- 一处陈名顺手改掉：`runWithCp936Exit` 的文档注写着「`main()` 调它」「退出码走
  `resolve` / `reject` 的第二个值」，而本文件没有 `main()`、那条 Promise 也没有
  `reject` —— 现在按实际形态写（文件尾的直接执行入口 / 退出码是这条 Promise 的唯一值）。
