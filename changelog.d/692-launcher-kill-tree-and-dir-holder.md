## Fixed

- **启动器起不来 + 打包启动器报「无法清理 start-tauri」，真因是同一处路径没跟着目录迁移改**：进程树回收模块从 `src/lib/` 迁到 `src/lib/process/` 时，`scripts/dev-launcher.mjs` 与 `scripts/reap-process.mjs` 里**拼字符串拼出来**的动态 import 说明符没跟着改（`tsc` / `eslint` 不解析运行时字符串，复核时也搜不到），只在执行到那一行才炸 `ERR_MODULE_NOT_FOUND` —— 而这条路正是「回收上一次启动留下的进程」。于是编排器一起步就崩（用户看到的是「启动 start-tauri.exe 失败」），它拉起的 dev server 再没人回收。现在两处说明符都写成字面量，并由 `tests/cross-platform-launcher.test.ts` 守住「`scripts/**` 里指向 `src/lib` 的动态说明符必须真实存在」（一条都扫不到即失败，避免判据静默失效）。
- **另一种「无法清理 start-tauri」：回收入口打印了命令，却什么都没杀（Windows）**：进程树回收模块在 Windows 上是**异步派发** taskkill（不等它结束），而命令行入口 `scripts/reap-process.mjs` 派发完就 `process.exit()` —— 那条命令会随父进程一起消失，现象是 stdout 正常、退出码 0、目标进程还在（实测：不等时目标存活，等 3 秒后消失）。这条兜底正是「启动器异常退出后回收孤儿 dev server」的唯一手段，它静默失效时产物目录就一直被锁着。现在该入口显式等命令结束（模块新增 `wait` 选项，`via` 里带退出码），命令起不来时返回 `ok:false` 而不抛错；`src/lib/process/kill-process-tree.windows.test.ts` 加了 `wait` 语义与「起不来不抛错」的断言，`tests/cross-platform-launcher.test.ts` 加了 Windows 上的端到端用例（真起进程 → 真跑入口 → 核实目标真的没了）。
- **打包启动器报「无法清理 start-tauri」时不再猜占用者（ISSUE #621 补第二条判据）**：占住产物目录的不止启动器 exe —— 启动器拉起的 dev server（`node` → `pnpm` → `next`）会把 `start-tauri\_internal\*.dll` 映射进自己的进程（实测 pnpm 侧的 `VCRUNTIME140.dll` 就取自产物目录），启动器异常退出后它们残留成孤儿，目录照样删不掉，而按 exe 名 / 路径判断的判据一个都查不到：现场拿到的结论是「没发现启动器在跑」，紧接着 `Remove-Item` 失败，提示继续猜「是不是启动器没关」。新增 `Get-ProductDirHolder`（判据：**被映射文件的路径**落在产物目录内）与统一出口 `Write-ProductDirLockHint`：前置检查把启动器与孤儿两类命中写在同一条消息里（省掉「杀掉启动器 → 重跑 → 又被告知目录还被占着」），清理失败时先给**真实异常文案**与占用者清单（PID / 进程名 / 被映射的文件）+ 逐条 `taskkill /PID <pid> /T /F`，只有查不到人时才给「杀毒 / 索引服务正在扫描，或权限不足」那条分流。
