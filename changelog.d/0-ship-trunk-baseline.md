## Fixed

- **`pnpm ship` 在推送之后重跑必被拒**（实测：`pnpm ship --no-wait` 在
  `refactor/ship-module-split` 上报 `碎片 0 份 ⇒ 单 PR 单变更那条不成立`、退 1）。
  根因是 `resolveUpstream` 把**「谁在跟踪」当成了「主干在哪」**：`git push -u origin feat/x`
  会把这条分支的上游设成**它在远端的副本** `origin/feat/x`，于是基线比对变成
  `origin/feat/x...HEAD` —— 自己与自己比，结果恒空，而空串在这一格读起来与
  「这条分支什么都没带」一模一样。撞上它的正是**推送之后的那一次跑**，
  也就是 `pnpm ship --merge` 那一跳：第一次跑（还没上游）走的是「唯一远端」那一档，
  所以推上去之后才坏 —— 也正因为它坏在第二跳，`--dry-run` 与首轮真跑都测不到。
- 基线改成按**事实强弱**取，且「取不到」与「是空的」继续分两格：
  ① `@{u}` 仅当它的分支段**不是本地分支自己**（往 `release/*` 线开 PR 就是这一形，
  人显式设的比较目标不许被默认分支顶掉）；② `refs/remotes/<远端>/HEAD` ——
  远端默认分支，git 本地就有这条符号引用，零网络；③ `<远端>/master`，
  只在两处都取不到时用，且**打印里标明来源是推的**；④ 都没有 ⇒ `null`，调用方退
  `NOT_RUN`。原来那条「基线引用必须真的存在」的正面校验不动 —— 猜错的主干照样被它抓住。
- 顺带收掉 dry-run 计划里的一条**已经没人执行的命令**：`planCommands` 还在打印
  `git ls-files changelog.d`，而执行面早在 #2034 换成了「分支相对主干已提交的 ∪ 还没提交的」
  两条查询。`ls-files` 数出整个目录 118 份、于是那条守卫恒真，正是 #2034 修掉的起因 ——
  计划里留着它等于把错的取数面教给读者。判据补一条「计划里的碎片那一查与执行面同形」
  （含带斜杠的主干名不能被拼成 `cnb/release`）。
- 撤掉三处注释里一条并不存在的规范引用：它们写着「本仓按规范只有一个叫 `cnb` 的远端
  （硬规则 6 / §13.6：远端名 `cnb`，无 `origin`）」，而 `docs/standards/13-提交与-code-review.md`
  里没有任何一节给远端命名，硬规则 6 判的是「不在 `master` 上直提」。当场事实：
  本检出 `git remote -v` **只有 `origin`**，审计 `docs/audits/2026-10-12-architecture-risk-review.md`
  R12-01 记的是「并行检出里见过 `cnb`」⇒ 那句话把「某台克隆机器上的事实」写成了
  「仓库的规范」，还被当成设计理由引用。改成陈述真的那件事：远端名与默认分支**都是
  每台克隆自己的事实**，所以判据必须现算。
- 探针先红再修：新增三条（`resolveUpstream` 的自跟踪一档 + `main()` 里「上游是分支自己
  的远端副本」与「远端没有 `HEAD` 符号引用」两条现场形状）打在未修代码上是
  **3 failed / 39 passed**，其中 e2e 那两条复现的就是屏幕上那句「碎片 0 份」。
  夹具同时把「按写死的基线名命中」改成**照 git 的语义答**（拿自己当基线就是空），
  否则夹具替被测代码担保了它选的那条引用是对的。修完 43/43 绿。
