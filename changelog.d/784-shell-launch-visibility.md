## Fixed

- **双击 `app.exe` 时，启动页与日志面板不再「什么都读不到」**（ISSUE #784 手验反馈）：
  壳自己承担编排之后，可见性那一层还留在旧链路里 —— `run/launch-status.json` 由
  `dev-launcher.mjs` 在壳起编排器**之后**才创建，而 release 壳（Windows 无控制台）的
  stdout/stderr 没有任何去处。于是「壳已接手、编排器还没写字」这段**唯一的启动路径**
  在磁盘上是一片空白：启动页显示「暂时读不到日志」，并让用户去翻那两份此刻恰好为空的
  文件。修法分三处：

  ① **壳侧编排链路日志**（新增 `log/launcher/shell-launch.log`）：壳把「拉起编排器的
  完整命令与 cwd」「编排器的 `[orchestrator] …` 输出」「启动报告」都落这一份。它是启动
  期**最先有内容**的日志，不依赖编排器起来；`get_launch_log` 也把它读进面板。

  ② **常驻进度快照**：壳在接手时写 `run/launch-status.json`（`fallback: true`，进度 0），
  编排器一写自己的状态就把它顶掉。启动页据此显示「壳在做什么 / 在等谁」，但**不拿它当
  就绪判据** —— 就绪仍只有 `status.ready === true`（或壳快照期间退回 `/api/health` 自主探测）。

  ③ **失败与空面板都指向真实存在的路径**：`mark_launch_failed` 与「一条日志都没有」的
  兜底都带上 `diagnostics`（壳侧链路日志 / 壳日志 / 状态文件 / 项目根），或按**文件存在性**
  逐项列出候选。原先写死的 `run/launch-status.json` 在项目根推不出来时指向一个不存在的
  位置，用户照着找只会更困惑。

- **`get_launch_status` 区分「编排器还没写」与「项目根推不出来」**：读不到文件时不再只回
  一句无信息量的 `Err`，而是回结构化兜底（`phase: "no-status-file"` + 原因 + 诊断路径）。
  真故障（权限 / IO 错误）仍然回 `Err` —— 兜底不吞真问题。

## Added

- `src/lib/shell/launch-diagnostics.ts`：壳侧启动链路的路径与形态（纯函数 + 薄 fs 适配），
  与 Rust 侧 `shell_launch.rs` 逐项同形；13 条单测锁住路径、快照语义（进度必须 < 1，
  否则启动页会把它画成「✓」）与「哪些状态不算权威进度」。

## Changed

- 启动页文案不再断言文件位置：空面板的清单与「等待超过 90 秒」的提示都改成走壳给出的
  路径，避免「提示指向空文件」重复发生。
