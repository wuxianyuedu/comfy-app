## Fixed

- **CI 上 R5 文件行数棘轮把「全库 prettier 格式化」误判成「本次改动让文件变大」**。`src/components/studio/logs/LogPanel.tsx` 的基线 `1102` 记于全库格式治理**之前**，治理后同一文件（一个字没改）已是 1236 行；此后任何人一行都不碰它，CI 也会报 `R5 超限文件继续变大(… → 1102 → 1236 行)`，而作者无从下手 —— 要他为了过门禁把已 prettier 化的文件再压缩回 1102 行，等于让门禁否掉 §13 的格式口径（ISSUE #637）。
- 修法：基线自带**记它那一刻的修订号** `baselineRev`，比对前先用 `git show <rev>:<file>` 取基线版本的内容、按**今天同一套计数口径**重数出 `baseLines`，再与当前行数比较 —— 判据从「两个不同格式时代的绝对行数相减」改成「同口径下这个文件比基线那一刻多没多」。基线版本里没有该文件（本次新增）/ 基线缺 `baselineRev`（旧基线）/ git 不可用时退回基线上的记录值，与历史行为一致、也不静默漏放。判据版本 `R5_RULE_VERSION` 2 → 3（旧数字与新口径不是同一个量，须一次性重记基线）。
- **不要改成「全仓整体行数比」换算**（试过，实测不行）：prettier 逐文件重排，各文件展开倍率差异极大（同一批 9 个超限文件里既有 0.958 也有 1.130），全仓比例约等于 1.0，换算后对 `LogPanel.tsx` 仍判「变大 136 行」。这条已写进规范 §12.13.3，免得后人再试一遍。
- 回归测试（`tests/check-file-structure.test.ts` 新增「R5 行数口径随 baselineRev 重数」一组，真 git 仓库造「基线版本 / 当前」两态）：基线数字记少 → 同口径重数后放行；内容未变 → 放行、再真加 20 行 → 阻断；基线版本无此文件 / 旧基线无 `baselineRev` → 退回记录值。规范 §12.8、§12.13 的表述同步更新。
