## Fixed

- **平台侧构建日志里的中文乱码：根因定死，并把纠正动作与读数接进流水线**
  （ISSUE #1959）。

  ## 一、乱码是什么（逐字节复算出来的，不是推断）

  用户截的那一行是 `工具链自证通过 ✓` 变成了 `宸ュ叿閾捐嚜璇侀€氳繃 鉁?`。把前半段按
  UTF-8 取字节、再按 GBK 解，正好回到 `工具链自证通过`；末尾那个 `?` 是 `✓`
  （U+2713，UTF-8 三字节 `E2 9C 93`）被 CP936 解出 `鉁` 之后剩下的**孤字节**。
  也就是说：**Node 写出去的 UTF-8 被按 CP936 解码了**。

  同一份 runner 日志里 `Set-Variable : 缺少参数"Exclude"…`（PowerShell 自己打的，
  连 `行:1 字符: 5` 都在）却是完好中文 —— 两个方向互为对照，所以「谁按什么编码
  解码」这一格是可判的：**抓取端按宿主的 ANSI 代码页解码**（中文 Windows 上是
  CP936），PowerShell 顺着它写字节所以是好的，Node / pnpm / drizzle-kit 无条件写
  UTF-8 所以全花。全部 49 行带非 ASCII 的输出里，只有 PowerShell 打的那几行与
  抓取端自己回显的脚本行是干净的。

  ## 二、纠正动作：把控制台输出编码钉成 UTF-8

  新增 `scripts/ci-console-encoding.mjs`（纯 `node:*`，装依赖之前就能跑）：
  - `readConsoleEncoding()` 只读那个代码页（`[Console]::OutputEncoding.CodePage` +
    `chcp` 原文），**量不到回 `null`**——「没量到」不是「量到的是错的」；
  - `applyConsoleEncoding()` 把 `chcp` 与 `[Console]::OutputEncoding` 都钉成 UTF-8，
    并**按复核后的读数**判成败（命令退 0 不等于结果落地，与 Python / 浏览器那两条
    装通道同口径）；
  - 两者都**不抛、不阻断**：编码不对只让日志难读，不会让哪一步算错，把它判红等于
    拦住与之无关的变更。

  `.cnb.yml` 第一步（`工具链自证`）现在**先纠编码再打印任何中文**（`--apply` 那一行
  排在脚本调用之前，位置由用例按源码顺序钉住）。`chcp` / `[Console]::OutputEncoding`
  改的是**控制台对象**上的设置、同一控制台里的进程共享它，所以第一步设、后面的
  stage 都受益。

  顺带：`环境前提` 那一步现在把宿主代码页当**读数**打出来（非 UTF-8 时话术里直接给
  下一动作），于是「这一跑的日志能不能读」不再靠人猜 —— 与那条诉求
  「别等到执行几十分钟后才发现」同一个取向。

  ## 三、能判什么、不能判什么（如实记）

  **不能**判「日志里到底有没有乱码」：抓取端的解码发生在本进程之外，本进程看不到
  自己的字节被怎么解。能被机器判的只有**宿主当前的代码页读数**，以及纠正动作有没有
  真的把读数改到 UTF-8 —— 用例判的就是这两件（`tests/ci-console-encoding.test.ts`
  10 条 + `tests/ci-env-probe.test.ts` 里那 3 条读数档）。

  若已钉上而读数仍不是 UTF-8，说明这台节点的控制台设置没传递到后续 stage ——
  那是**宿主侧动作**（把系统区域设成「Beta: 使用 Unicode UTF-8 提供全球语言支持」，
  或让 Runner 服务以 UTF-8 控制台启动），话术里也这么写。
