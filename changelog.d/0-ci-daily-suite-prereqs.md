## Changed

- **CI 的 `单元测试`（全量 vitest + 覆盖率）回来了，但落在每天 04:00 那一跑，不在每条 PR 上**
  （ISSUE #2018 的口径，`tests/no-platform-ci-config.test.ts` + §13.5.23）。用户那句是
  「可能会负载假红的，都看看能不能挪 CI 去执行」—— 答「能，但不是挪到 PR 那一条」，两条
  理由都是这台机器的事实：① 自托管节点与本地钩子**共用同一台 16 核机**，挪过去不减总负载，
  改变的只是谁被假红卡住与重试的代价；② `scripts/ci-load.mjs` 自己写死了「不同 PR 之间
  仍然会叠加」（`lock` 按 PR 分锁只掐同一 key），而历史上三条全量流水线挤同一台机时
  `单元测试` 跑到 **8640s 被墙钟掐断**，只留下一句 `timeout of 8640000ms exceeded`。
  04:00 那一跑没有并发 PR、机器是空的 —— 这是「负载读数不可信」这一族唯一的解法（抬预算与
  降门槛都被 §11.13 / §13.6.4 明令禁止）。**代价写在明处**：最晚 24 小时才发现，与本节上面
  `生产构建` 那条是同一个取舍，而「每日档有主」那套新鲜度账接得住它。

  同时**撤掉「平台侧有全量单测执行者」这句话的空头支票**：§13.5.4 那张表这一行此前写着
  「有」，而那一格其实被临时停用着 —— 说的有、实际没有。现在是真的有了，并写明它在定时那一跑。

- **当场修掉一个只会在 04:00 现形的黑洞**：定时那一跑此前**只有构建那一格**，而
  `artifact-run.mjs` 跑的是 `pnpm run build`；每次构建都是全新 job 目录、`node_modules`
  恒不在场（`工作区复用读数` 两跑实测，形态①）—— **那一格会在明天 04:00 以「找不到 next」
  的形态红**，而它一天只触发一次，最快也要第二天才看得见。同批补三格前提并排在校前面：
  `每日安装依赖` / `每日 Python 可用性` / `每日同步数据库表结构`（缺解释器时相关用例只走
  `env` 档跳过 = 静默少判；没建库时读库用例报的是「连不上」，看着像业务故障）。
  这正是上一格那份读数在这儿的直接收益：没有它，这条昨天刚合入的流水线要等到第一次触发才暴露。

- **`每日单元测试` 也打「分文件耗时榜」**（前 10 + 合计 + 中位，junit 落 `os.tmpdir()`，
  与钩子那侧**共用 `parseJunitXml`**）：本地账本看得见「哪几份在吃时间」，节点上此前看不见，
  而砍线要的是节点那份。`full-suite-run.mjs` 的读数参数走 `planRun` 第三个入参、**不进
  `extra`** —— 进了 `extra` 会被 `isWholeTrackRun` 判成「不是整档」，于是每一次 CI 全量跑都
  绿着不记账（比不加读数坏得多）。junit 没落盘时打「**没有**」而不是「0 份」。

- **两跑之间同几格不共用 stage 名字，改由判据钉「命令行逐字相同」**：名字带「每日」前缀是为了
  让按名字取块的解析器不撞车；镜像判据只比**真正会执行的行**（丢空行与 `#` 注释），因为两格
  该解释的事情本来不同 —— 要求散文也逐字相同只会逼人删解释，而漂移藏在命令行里。
  `每日单元测试` 另有三条判据：必须点名跑法脚本、不许带任何收窄参数、`timeout` 必须大于
  `FULL_SUITE_TIMEOUT_MS`（否则先被掐的是 stage，那一刀不带「被预算砍 vs 判据红」的分流话术）。
