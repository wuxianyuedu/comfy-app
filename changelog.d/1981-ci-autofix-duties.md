## Changed

- **平台侧的「自动修档」：`生成态文档与源同步` 红了就地重渲染再判一次，且它现在按扫描面增量**
  （ISSUE #1981 / 规范 §13.5.19）：用户的诉求是「`pnpm doc:render` 尽量不要本地跑，
  CI 检测到文档改动就自己跑一遍再判」。这句话里其实是三件事，各落在不同地方 ——

  · **「先检测有没有改动」** → stage 级 `ifModify`：`docs/**` / `src/**` /
    `package.json` / `pnpm-workspace.yaml` / `next.config.js` 一个都没命中就跳过这一步
    （`docs/generated/**` 只由这几处决定）。改一行 README 不再为它付费。
  · **「红了就自己补上再判」** → `--check --autofix`：先判一次，绿了一次都不多写；
    红了就地重渲染、**再判一次**，结论永远来自第二次判定。只跑写入模式就退 0 等于把
    未经复核的写入报成通过。
  · **「跑完一并提交、再重新 CI」** → **刻意不做**：这条流水线在 PR 与 push 上都跑，
    而「CI 回写分支」绑在目标分支策略上（`master` 走分支保护、PR 源分支可能来自 fork），
    那是一条单独的决策。本档交付「修好的工作区 + 一句照抄就能用的命令」，提交与重跑
    仍由人 / 代理那一侧做。

  **为什么不给每条判据都加自动修**：前提是两条 —— 产物是纯确定的重新生成、且红了没有
  第二种成因。绝大多数判据不满足第二条，对它们自动「修」等于把一次真回归悄悄改写成一次
  通过。所以登记表里**只有一行**：`scripts/ci-autofix-duties.mjs` 的 `AUTOFIX_DUTIES`。

  **「哪几档会自己改工作区」也只有一处出处**：`tests/ci-autofix-duties.test.ts`
  （**进固定清单**，每次提交都跑）双向核对 —— 登记表里每条 ⇒ 配置里同名 stage 的
  `script` 真的点名它的入口、且 `--check` 与 `--autofix` 逐字都在；配置里带 `--autofix`
  的 ⇒ 必须在登记表里。少了任一半，「某天某个 stage 忽然改写了工作区」就没有任何信号。

  **修不好时必须红**：自动修只写「源 → 产物」这一条路 —— 孤儿产物它不删、缺失的源它不替。
  所以重渲染之后仍不一致时，这一档把 `落后 / 缺失 / 多余` 点名打出来并退非零，
  而不是「跑过写入模式就当我赢了」。
