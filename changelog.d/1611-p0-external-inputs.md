## Changed

- **阶段三那四条卡在外部资源上的 P0，从「未接通 / 零上报 / 无关联 / 无签名」改写成「等外部输入（等什么）」（ISSUE #1611）。** 原写法读起来像「我们这边还没开工」，而实际形态是**代码那一侧已就位或半就位、缺的东西在仓库之外** —— 这四条不是同一件事的四种难度，是**四种不同的外部凭据**，所以每条都写明三样：现状到哪一步、等什么、给到之后我做什么。
  - **P0-2 自动更新**：`app-update-client` / 设置页「应用更新」区 / `updater:default` + `process:default` 权限都在位，`endpoints: []` / `pubkey: ""` / 未开 `createUpdaterArtifacts` 是**三个空格子**。等的是 **minisign 密钥对**（私钥由人持有，我不该也不能替）与**一个能托管 `latest.json` 的 HTTPS 地址**。接入三步在 `launch-and-build` §7.1「应用自更新」那节**已经写好**、不再抄第二份；本笔只补它没覆盖的两件（发布流程落成入口 + 一条钉「端点与公钥要么都空、要么都非空」的用例 —— 今天「端点填了、公钥还空」在运行期静默变成**未验签更新**）。
  - **P0-3 崩溃上报**：服务端 / Edge 两份配置与 `SENTRY_DSN` 的 env 收口都是现成的，缺客户端那一份和一个**项目 DSN**。
  - **P0-4 release / source map**：与 P0-3 是同一个账号的两半。**如实写明这条有一半不卡外部** —— release 恒取 git sha、`.map` 不随包出厂，这两件现在就能做，拿到 token 那天是「接上传」而不是从零开始；release **刻意不取 `package.json` 的 version**（D7：版本号三处手工重复、无同步守卫，拿它当 release 会在第一次忘记升版本时把两次发布并成一条）。
  - **P0-6 代码签名 / 公证**：`bundle` 段的 `windows` 与 `macOS` **两个键根本不存在**（不是存在但为空），因为**没有任何凭据可填**。等的是 Windows 证书（`.pfx` / Azure Trusted Signing）与 macOS 的 Developer ID 证书 + 公证凭据两套。顺带记一条**后果要几年后才显现**的判据：配了签名就不许缺时间戳服务（无时间戳的签名在证书过期后连已发出的安装包一起失效）。
- **纠正一处台账漂移：阶段计划（#1611）那张表把 P0 段记成了「更新 / 崩溃 / sourcemap / migrate / 签名 / 自动备份」，与本文档实际条目对不上。** 实际是 **CI / 更新 / 崩溃 / sourcemap / migrate / 签名** —— 「自动备份」在本文档里是 **P1 段的 D6**，CI 那条反被表漏掉。本笔按实际条目归位，并在 P0 段首写明分档：**四条真「等外部输入」**（P0-2/3/4/6）、**P0-1 是额度与策略**（不是缺输入）、**P0-5 已收**。
- **D6（自动备份 / 恢复）改写成「等一个决策，不是等外部输入」，并写清三种待拍的口径**（备份时机 / 保留几份放哪 / 恢复入口给谁）。它**不卡任何账号或凭据**、代码全部可写；把它排进「等外部输入」是错档 —— 而错档的代价是它会被永久搁置。选错默认的形态是「备份看着有了，真要恢复时那份已经不在或是坏的」，比今天「知道自己没备份」更危险，所以必须由人拍而不是我默认一个。
