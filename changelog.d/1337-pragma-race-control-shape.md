## Fixed

- `tests/sqlite-pragma-sites.test.ts` 的「量具没坏」对照**在 master 上约 1/3 的运行会自己红**（ISSUE #1337），
  而红的时候并没有指出任何回归 —— 因为「N 个独立进程同时抢那份新库的 WAL 独占转换窗口」
  本身是**亚毫秒窗口上的概率事件**。同形状连跑 5 轮实测每轮抛 `0 / 1 / 2 / 3 / 4` 次，
  真用例跑 3 次是 2 绿 1 红；而 #1282 当年记的「3/8 抛」是**单轮读数**，不是一条稳定规律。
  不可归因的判据久了就没人看（ISSUE #1179 写的就是这个下场），所以把两半拆开各归其位：

  - **因果交给新的单元层**：注入 `SQLITE_BUSY` 的假连接，确定性地量五件事 —— 裸循环第一次就抛、
    出口重试到成功（同一条 PRAGMA 试 3 次）、非锁族错误一次都不重试、穷尽后照样抛且正好试
    `SQLITE_PRAGMA_BOOT.maxAttempts` 次、只给 message 不给 code 的驱动仍按锁族重试
    （最后那条是写夹具时被 `isSqliteBusyError` 的 message 兜底分支咬出来的，顺手钉住）。
    变异验证：把 `applySqlitePragmas` 的重试摘掉 → 恰好 3 条红、两条「必须立刻抛」的仍绿。
  - **现场保真留在进程层**：仍然真起 N 个独立进程互撞，但改成**多轮、见一次抛就停**
    （常态仍是 1 轮 ≈ 3–6s），并把**到位数**变成判据的一部分。

## Added

- 同一份量具补上两条一直存在的静默通道（都在 #1337 的归因里量到）：
  `waitForArrivals` 上一版是「上限 10s，超时也继续」且不回报 —— 没齐就发令时，那批进程
  错开起跑的形状恰好就是「一次都不抛」，等于把假红伪装成结论；现在到位数进 `RaceRound`，
  「全绿」那条也要求这一轮确实齐步过，红话分别指向「错开起跑（查 tsx 冷启 / 负载）」与
  「每轮都齐了却没人撞锁（转换形状真的变了）」两种完全不同的下一步。上限按本机
  tsx **冷启实测 7.4s** 放到 25s，两条竞态用例的预算显式给（否则会以「超时红」失败，
  而那条红又像极了「前提不成立」）。
- 用例名与量具对齐：原来写「8 进程」，而 `RACE_PROCS` 是 7（照 #1282 那轮
  `Collecting page data using 7 workers` 取的）。同时在常数注释里记下今天读到的
  **`using 15 workers`** —— 这个数随 CPU 与版本变，别当常量信仰；按 7 跑是偏保守的一侧
  （进程更少 ⇒ 更容易错开 ⇒ 更容易「一次都不抛」）。

## Changed

- 一条**实测否掉**的替代方案，写进量具的注释免得下次再想：想用「另一个进程持住
  `BEGIN EXCLUSIVE`」造出确定性的撞锁不成立 —— 持锁方在场时，攻方执行
  `PRAGMA journal_mode = WAL` 直接返回 `wal`，既不抛也不静默 no-op。这条通道上挡得住 WAL
  转换的只有「另一个进程正在同一瞬间转换」，而那本质是概率的 —— 所以因果必须在单元层。
- 判据**没有被放宽**：单元层那五条是新增的确定性判决，进程层那一轮仍然要求「至少抛过一次」，
  只是不再赌单轮运气；`KNOWN_FAILED_FILES` 里也没有它。
