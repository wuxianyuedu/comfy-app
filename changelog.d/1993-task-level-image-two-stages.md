## Changed

- **「宿主机直跑」的那条主线上，多出两格进容器**（ISSUE #1993 续）。用户要的是
  「保持宿主机直跑，能用 docker 提速的部分，用任务级 `image:` / 插件任务」——
  前一句本来就是这个仓的形态（`.cnb.yml` 不声明 `pipeline.docker.*`），所以这次改的是
  后一句，而且**只改两格**：`浏览器安装` 与 `E2E 关键流程` 加上
  `image: mcr.microsoft.com/playwright:v1.63.0-noble`。

  选它们的理由只有一条：**这两格在等网络，不在算 CPU**。它们的形状一直是
  「取回 ~120 MiB 的浏览器二进制」——正是这条链路七跑以来的全部卡点
  （规范 §13.5.3.5 那串读数）。官方 Playwright 镜像里已经装好 headless shell，
  于是「取不回来」在容器那一层不存在，本步只剩「在不在」那一次复验。
  主干（工具链自证 / 安装 / 全部静态判据 / `生产构建`）**一格没动**：
  它们共用同一个检出与同一份 `node_modules`，逐个塞进容器等于每格一份新环境。

- **`PLAYWRIGHT_BROWSERS_PATH: /ms-playwright` 与镜像同批给**。镜像把浏览器装在
  `/ms-playwright`，而落点判据（`playwrightBrowsersRoot()`）优先读这个变量、
  否则按账号 profile 推 —— 在 Windows 宿主上推到的是宿主那个空目录，于是
  「镜像里明明有」与「一件都没有」在日志里逐字同形。两格共用这一行（写在 stage 层，
  不写第二份：两份会漂）。

## Added

- **`镜像身份` 那条读数多打一行：本仓的容器格是哪几格**。此前「到底哪几格在容器里」
  只能翻 900 行 YAML —— 而这句话太容易被读反（「没有 docker」被当成「没有容器」）。
  现在由 `platformImageStages()` 从 `.cnb.yml` 读出来，跟着每次构建落进日志：
  `容器格（任务级 image:）：浏览器安装 → …；E2E 关键流程 → …`。

- **判据：进容器的 stage 名单逐格点名**（`tests/ci-image-identity.test.ts` 的「容器格」
  一组，4 条）。这条守的是「多一格少一格都不报错」那个形态：有人顺手给 `类型检查`
  也加个 `image:`，配置照跑、日志照绿，而那一格要拉镜像、要重装依赖。四条分别判
  名单一致、两格镜像相同且标签钉版本、`PLAYWRIGHT_BROWSERS_PATH` 与镜像同源、
  解析器不把 `env:` 里的同名键算进来。

## Docs

- **规范 §13.5.3.4.1.3（新增）**：「没有 docker」≠「没有容器」—— 把「默认档 = 宿主机
  直跑 / 例外档 = 任务级 `image:`」写成一张表，并记下那三条边界（落点变量必须与镜像
  同源、标签钉 `-noble` 因为宿主的 Node 版本门槛、两格必须同一张镜像）。

## Notes

- 这条改动**依赖一次真跑验证**：镜像标签 `v1.63.0-noble` 钉的是 Playwright 版本，
  与仓库依赖里的 Playwright 必须是同一个大版本（跨版本时它要的 browser revision
  不同，等价于「装了一份错版本的浏览器」）。升级 Playwright 要同批改这一行 ——
  判据只钉形态（`playwright:vX.Y.Z-noble`），版本号本身由人跟着 `pnpm-lock.yaml` 走。
