## Fixed

- **五个棘轮判据的「只许降不许升」从来没有真正生效过**，而失效方式有三种：
  · **拒涨那一支是死代码**：`check-theme-colors.cjs` 里的 `prev` 在 `--update` 这条路上**恒为 null**（那个三元式带着 `!UPDATE`），而它偏偏用 `if (prev && …)` 判「基线在不在」—— 于是这一支永远不会拒。
  · **基线清到 0 之后短路**：`check-theme-colors.cjs` 与 `check-overlay-z.cjs` 写的是 `if (before && after > before)`，`before` 是基线总数 —— 而**真仓库今天的基线正是 0 处**（治理做完的那个状态），条件整个短路、拒涨检查根本不执行。于是「新写一条色值 / 一条内联 `zIndex`，再跑一次 `--update`」就把它收进基线：**棘轮在最不该松的时候松着**。同一形状在 `check-ui-logic-separation.cjs` 里已经修过一轮（它的 `diffAgainstBaseline` 注释就是这条口径的出处），这次是第三、第四次重现。
  · **`UPDATE` 分支无条件落盘**：`check-dead-exports.cjs`、`check-circular-deps.cjs`、`check-comment-language.cjs` 三家连比较都没写，只在「不带 `--update` 的下一次跑」里报新增；三份基线的 `note` 字段里则逐字写着「只许降不许升」。
  修法统一成两条：**判「基线在不在」而不是「基线里的数是不是非零」**（首次建立基线仍放行，否则新检出无法起步）+ **落盘之前先拒**（点名旧值/新值与改法，`exit 1`）。

- **为什么以前没人发现**：用 grep 数「脚本里有没有那句拒涨的话」会给出**相反的结论** —— 「只许降不许升」那几个字就写在 `note` 字符串里，五家全部命中。文本盘点在这件事上是无效方法，只有把脚本跑起来才看得见（同 §11.2.1「源码长这样不是执行记录」）。

## Added
