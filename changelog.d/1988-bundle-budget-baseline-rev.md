## Fixed

- **体积基线的 `baselineRev` 不再是一条「取不到」的死账**（ISSUE #1988）：PR #1988 的「生产构建」红在
  bundle 体积预算，输出是「gzip 总量上升：2275.4 KB → 2276.4 KB（+1.0 KB）／基线修订号：取不到」——
  两句话叠在一起读，谁都会以为这是抖动。坏账在基线本身：master 上那份（生成于 2026-10-15）记着
  `b6c3c353`，而那个提交在本检出里根本不存在（分支合入 + `git gc` 的常见形态），于是「基线是否过期」
  此后只能猜。三处同批改：① **读**那一侧把「压根没记（`null` / 旧格式）」与「记了但本检出里不可达」
  拆成两档 —— 后一档明说这是**基线过期**，并点明「别直接 `--update` 重记，先分清这点体积该不该认账」，
  因为两档的下一步一个是重记、一个要先判断，混成一句就把人推向跳过判断；② **写**那一侧只认 40 位
  十六进制：`--update` 取不到当前修订号就不写盘、退 1，既不许落 `baselineRev: null`，也不许落短哈希 /
  ref 形态（读那侧同样查不到，只是把失效挪到下一步）；③ 判据 `tests/check-bundle-budget.test.ts`
  补三条互为反面的用例 —— 非 git 检出拒绝且**一个字都没落盘**、不可达那一档说「基线过期」且不出现
  「取不到」、没记那一档说「取不到」且不出现「不可达」。口径见规范 §13.5.4「`baselineRev` 的四个档」
  那一段（同批它与 §12.13.3 引它的那句一起订正）。
