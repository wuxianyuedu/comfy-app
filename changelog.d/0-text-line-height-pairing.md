## Fixed

- **文档里 `text-sm` 的配对行高写错了（16px，实际 20px），而它已经被当成推理前提写进两次提交**：
  真 Chromium 读数（Storybook 沙箱加载的就是这份编译产物）—— `text-xs` 12/16、`text-sm` 14/**20**、
  `text-lg` 18/28；16px 是 `text-xs` 的值。依赖里的出处是 `--text-sm--line-height: calc(1.25 / 0.875)`。
  连带订正三处因果句：
  · 13px 那批并入 `text-sm` 的真实行盒变化是 **19.5 → 20（+0.5px）**，不是 19.5 → 16（−3.5px）；
  · 14px 那批并入 `text-sm` 是 **21 → 20（−1px）**，不是 21 → 16（−5px）—— 第 3 刀的「按结构判」
    结论不变（实际变化比当时写的更小），但依据里的数字是错的；
  · `log-virtual.ts` 的 `28` / 每行 `19` 走的是**显式 `leading-snug`**（14px 下 19.25，该文件自己
    注明），与配对值无关 —— 从前那句把它归因给了「档位自带 16px」。
- **给配对行高补一条值判据**（§11.3 那一层，不新建任何像素工具）：`tests/helpers/text-tiers.ts`
  现在也解 `--text-*-line-height`（`calc(a / b)` 与裸数值两种形状，**认不出形状就抛错**，
  解出少于四颗也抛错 —— 静默漏一条会让「按行高推理」的判据拿到缺东西的表）；
  新判据钉住 `xs` 16 / `sm` 20 / `lg` 28，并钉住 `2xs` / `3xs` **没有配对**（那 52 处并入的行盒
  只可能由继承来，哪天被配上配对值，像素账要重算）。文档侧同钉一条：DESIGN.md 不许再出现
  「`text-sm` 出 16px」。
- **订正两处「像素档撤除」的口径**（03 §3.6.2 与 §3.10.1）：撤掉的是**页面级**像素基线，
  组件那一侧仍然有两层有人管 —— Storybook 工作台（§16）与 `getComputedStyle` 值断言（§11.3）。
  从前那两句写成「没有任何自动回归能证明改对了」，读起来像组件形态也没人管，于是本轮
  第 3、4 刀只交了结构判。改后的口径：**改字号档要拿这两层量一次真读数**，
  「整页有没有变形」才是真的没有判据。
