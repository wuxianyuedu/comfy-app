## Fixed

- **日志面板的来源计数与「全部来源」对不上：同一条日志被六路轮询重复计了一遍**（ISSUE #1240 / #1282）。e2e 那条守恒判据在整批跑时必红（实测 `Expected: 5000, Received: 3335`），而它红得有理：
  - 面板的六个来源各读**自己那一份文件**，其中若干份装的是同一段内容的副本（`dev-launcher.log` 转写 dev 的输出、`shell-launch.log` 与 launcher 的两份互相重叠）。同一条启动行因此每个来源各算一份，逐来源相加必然大于「全部来源」——那个等式在真实数据上从来不成立，只在「互不重复」的夹具下成立；
  - 撞上时间线上限（`LOG_STORE_MAX = 5000`）时，「全部来源」被截到上限、各分类之和还在算被挤掉的那些，连「撞上限之前」都对不上；
  - 面板在 `all` 与逐来源两个口径上都拿同一批行累加，于是**界面上没有任何地方能看出这两个数字量的不是同一件事**。
- 修法是让两个口径各自成立、各自可断言：
  - `logEntryKey`（= `time + level + message`，**刻意不含 `origin`**）成为行身份的唯一事实；`mergeTimeline` 按它去重，并把同一毫秒写下的同一段正文（`arrivalKey`）并进已落板那一行的 `origin`——原先各来源的副本会各自落板，切到某个来源时看到的行与它自己那份文件无关；
  - 「全部来源」按**身份**计一次（新出口 `dedupeByIdentity`），等于时间线条数、也等于页脚「面板共保留 N 条」；
  - 逐来源各按**自己那份文件**的条数计，与 `computeFiltered` 的筛选结果逐条对齐（「按钮上写 2、切过去只剩 1」这条守的是它）。
- 界面按新口径写清楚：`ORIGIN_TEXT.all` 改为「全部来源（按条去重）」。少了这个限定语，候选列表里那六个分项读起来就是「加起来应该等于上面那个数」，而它们的语义是「切过去会看到几行」。
- e2e 那条守恒判据改成钉**两条各自成立的等式**（逐来源内部守恒 + 「全部来源」= 页脚条数），不再钉跨来源相加；样本值用 `getByRole("option")` + 文本锚定取（原先按 accessible name 的 `RegExp` 匹配，零条目的项渲染成「— 无」时会静默失配、等到 60s 超时）。
