## Added

- **WS 那条通道到底承载什么，现在数得出来了**（ISSUE #1315 的取证结论，P3 §5 ADR §28）。这条账是 #1278 那次自我订正（PR #1316）顺带问出来的：`executor-ws` 那套按节点分支在「comfy-cli 是唯一提交实现」之后还有没有活路？

  - 取证分两步。第 1 步数 trace 的 kind 分布，host 与 inline 两种形态各一轮，都是 `cli`=80 / `history`=1 / **`ws`=0**；但这只能证明「带 `prompt_id` 的执行帧没来」——当时四个 `trace("ws", …)` 出口里只有「非合法 JSON」在 `if (!promptId) return;` **之前**，其余三个都在之后，于是「帧来了但不带 `prompt_id`」与「一条帧都没来」在诊断文件里长得一模一样。第 2 步就是把那一跳变成可观测的，再数一次：**35 条，全是 `status`×4 / `kaytool.resources`×16 / `dasiwa.system_monitor`×15，一条执行帧都没有**。
  - ⇒ 连接是活的、帧确实在来，但 ComfyUI 只把执行事件发给**排队那个 client**（ comfy-cli 自己那条连接）。`executor-ws` 的 `node-started` / `node-finished` / `progress` 三段与 `protocol-adapter` 的对应分类**今天是零消费的**。
  - **不删**：那是给「直连 `/prompt`」形态留的正确实现，帧哪天回来就得是对的；删掉等于把「回到那形态时静默丢现场」埋回去。改为把口径钉进两个模块的头——**面板里的按节点现场只可能来自 `executor-cli-stream.ts`**，在这条通道上补可见性类功能会测不出效果（#1278 在 WS 侧没有可修对象正是这条的直接推论）。
  - 那一跳的留证**按类型只落第一帧**并设类型数上限（32）：逐帧落盘的话一轮里三分之二是同一类型的重复行、遥测约 1s 一条，长会话一小时就是几千行诊断噪声，而这个问题只需要「这类帧来过」这一个事实。
- 判据：`src/lib/comfyui/executor-ws.test.ts` 新增 2 条（含 4 个断言：留证存在 / 同类型不重复 / 新类型仍要落——预算不许退化成「只记第一条」/ 不碰执行侧 / 集合有界）。变异验证：拿掉两条预算 → 2 条红（`got 2` 与 `got 40`），还原全绿。没有给「按节点行只来自 cli」写机器判据——它断言的是外部服务的运行期行为，不是仓库里的源码形状，写出来必然误报；改为「文档 + 可观测点」，将来执行帧真开始到达时帧型分布会自己暴露它。
- 顺带一条复演手法（ADR §28）：测 inline 形态不必碰用户的实时链路——副本库用 `vacuum into`、`DATABASE_URL` 与 `COMFY_EXECUTOR` 都走子进程 env（优先于 `.env` 回读，所以 `.env` 里那句 `host` 不影响取证，也不往用户的库与任务历史写东西）、`next dev` 经 `process.execPath` + `resolve("next/dist/bin/next")` 起在**另一个端口**（避开 #1182 的共写），跑完整树回收。
