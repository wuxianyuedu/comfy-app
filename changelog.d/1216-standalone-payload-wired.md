## Fixed

- **桌包 standalone 形态（壳自己起内嵌 server、不经编排器）此前从未真通过；本刀把断掉的八层逐一接通**（P3 §5 · Phase 3-E2a，ISSUE #1216。立项前提「产物已能跑、只差拉起者」被实测否掉，更正见规范 §7.6 与 ADR §16）。八条的表现都是同一类：双击后窗口停在启动页，或页面 200 而接口全 500，而构建期一片绿（桌包链路既不在 pre-commit 也不在 CI）。
  - **没有装配者**：`tauri.conf.json` 的 `bundle` 段只有 `externalBin`、没有 `resources`——实测 `pnpm tauri build` 生成的 `installer.nsi` 里 `; Copy resources` 段是**空的**，Install 段只有主 exe 与 `File /a "/oname=node.exe"`，所以 `src-tauri/static` 组装得再完整也没人把它放进 `resource_dir()`。补 `bundle.resources: ["static/"]`（实测落点 `resource_dir()/static/**`，目录前缀保留；安装包 27 MB → 57 MB）。
  - **sidecar 与载荷根两处路径拼错**：壳找 `resource_dir()/binaries/node.exe`，打包器落 `resource_dir()/node.exe`（剥三元组后缀、不留 `binaries/` 子目录）；`server.js` 同理被拼在资源根而不是 `static/` 下。各收一处，`spawn_sidecar` 的源码形态由 `standalone_payload_tests` 反向钉住。
  - **交给 node 的参数不能是绝对路径**（真跑壳才暴露）：Windows 上 `std::env::current_exe()` 返回 `\\?\` verbatim 路径、`resource_dir()` 由它派生，Rust 侧 `exists()` 判得对，但那份字符串当参数交给 node 会在 `\\?\F:` 处断开并报 `EISDIR: illegal operation on a directory, lstat 'F:'`。运行目标因此改成**相对载荷根**的两个常量（`SIDE_REL_RUNTIME_ENTRY` / `SIDE_REL_SERVER`），`exists()` 判据与传参同源；这条历史上从没人踩到，因为开发检出永远走 prebuilt 分支。
  - **载荷不是自包含的**（真跑最先炸的一条）：`.next/standalone/node_modules` 的顶层条目是**指向仓库 store 的绝对软链**，`cpSync({dereference:true})` 摊平后 `next` 成了真实目录、赖以解析的兄弟包还留在 `.pnpm/<key>/node_modules/` 那一层 → `Cannot find module '@swc/helpers/_/_interop_require_default'`（require stack 指向 `next/dist/server/config.js`，看着像产物缺件，实际是**布局语义**没搬过来）。`build-desktop.mjs` 新增 §载荷实体化：把 store 里的包上提到顶层再删 `.pnpm`（实测上提 36 个包、载荷 404 MB → 254 MB），随后**真解析** `next/dist/server/next.js` / `@swc/helpers/_/_interop_require_default` / `@libsql/client`——解析不到就构建失败，而不是让用户双击时才发现。同名多版本取第一个发现者这条取舍之所以可接受，正是后面那三条解析断言在兜。
  - **首启建不了表**：载荷只带生产依赖，`drizzle-kit` 不在其中，桌面用户既没有 pnpm 也没有检出——现场 `/workspace` 200、`/api/health` 503 + `db:"empty"`，而 hint 写着「执行 pnpm db:push」。§首启建表 用 `drizzle-kit export --sql` 每轮现生成 `schema.sql` 随包（不另存手工 SQL 副本），两条构建期断言：必须有 `CREATE TABLE`、**不许出现 `INSERT INTO`**（后者是「不带出厂数据」的机器判据，不是注释承诺）。
  - **第 6 层：写模式的调用点够不到真安装形态**（把前五层修好后重跑壳才暴露）：`COMFYAPP_LAUNCH_MODE` 原先只在 `start_self_orchestration` 里写，而 `self_launch` 的判据含「项目根推得出来」——安装目录里既没有 `package.json` 也没有 `scripts\dev-launcher.mjs`，于是那条链整段不跑，`setup_standalone_runtime` 读到空串走 else 分支「跳过 standalone sidecar，使用 dev URL」（壳日志 `launch mode=""`）。**桌包因此永远起不了内嵌 server，与载荷对不对无关**。修法：在 `run()` 里幂等写一次模式，位置见下面第 8 层——顺序契约由 Rust 用例 `launch_mode_is_decided_before_the_splash_ever_asks` 钉住（「写在读之前」这类顺序契约在本仓库已经栽过几次，靠阅读顺序维持不住）。
  - **第 7 层：启动页在第一轮就把应用地址锁死了**。载荷与 sidecar 都真起来了（日志 `boot pid=… port=1239`、浏览器打开那个端口 `/api/health` 200），窗口仍停在启动页 0%：`splash.html` 的 `if (!appUrl) appUrl = await resolveAppUrl()` 第一轮拿到的是壳的**初始**地址（按检出路径推导的默认端口），而 standalone 的端口是 `pick_free_port()` 现挑的、在那之后才写回状态，于是页面每轮探测一个没人听的端口。改成每轮向壳重取 `get_app_url`（取不到才走兜底链）。
  - **第 8 层：模式定得太晚，于是启动页在健康启动上说假话**。第 6 层的修法原本落在 setup 末尾，而建启动页在它之前——standalone 实测中间隔着 8 秒，那 8 秒里页面每 250ms 问一次状态，壳只能按「项目根推不出来」回答：画面上是三段指错方向的提示（回检出启动 / 去跑构建脚本），日志里 66 条同一条 WARN（放跑一次 33 分钟就是 2 MB）。现在模式提到 `run()` 建窗之前定，结果记进应用状态，`get_launch_status` 在空根时先判形态：standalone 回「独立版由壳自己拉起内嵌服务，没有编排器状态文件」，不再报故障。
  - **两条只在链走通之后才看得见的**：① `watch_main_first_paint` 里「URL 还不是应用地址」那一支 `continue` 跳过了循环底部的 `sleep`，480 次探测在微秒内烧完，日志启动 2 秒就打 `timed out (120s)`——看护在它最该在场的时刻已经下班；② §载荷实体化 带出的是 store 里的**整包**，自带 `docs/*.md`（实测 472 个），产物护栏因此判红。修法**不是**给护栏加 `node_modules` 豁免（加了将来漏剥就再没人知道），而是让两侧同判据：护栏照旧判「要不得」，剔除侧在组装步删掉它（实测在实体化之后再剥一次命中 0 个，2.2 的位置已经够）。
  - 新增 §5 排障九行（停在启动页 / 接口全 500 且 `db:"empty"` / `Cannot find module '@swc/helpers…'` / `lstat 'F:'` / `MissingEnvFileError` / `launch mode=""` / 探测端口与 boot 端口不一致 / 健康启动却显示「项目根未推导出来」 / `timed out (120s)` 出现在启动后 2 秒），每行都给「看哪一处文件存在性或哪两行日志对不对得上」的判据；规范新增 §7.6 记录八层断点、实测证据与为什么选「壳起入口」。
  - **边界**：`tauri bundle` 只重打包、不重装配——实测用它会把上一次运行期写出的 `static/db.sqlite` 一起打进安装包（产物层检查报得出来，见同批 `## Security`）。文档口径因此仍以 `pnpm tauri build`（先跑 `beforeBuildCommand` 重装配）为分发路径；`tools/build/build-standalone.ps1` 那条「产出 `target\release\`（含 `server.js`）」的说法要不要按实测安装包改写，留给桌包线（不在本刀凭推断改）。
