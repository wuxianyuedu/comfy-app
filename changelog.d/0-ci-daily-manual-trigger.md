## Added

- **每日档现在也能手动触发**（业主追加：「每日档除了指定时间触发，还需要可手动触发」）。
  全部理由是**延迟**：撤掉 PR 那一条之后，「master 的 HEAD 今天行不行」最晚要等到第二天
  04:00 才有答案，而「刚合完一笔碰构建链的改动，想现在就验一次」这个动作此前只能等。
  新增官方形态：`.cnb/web_trigger.yml` 里定义按钮（`branch: [{reg: ^master$, buttons:
[{name, description, event: web_trigger_daily}]}]`），`.cnb.yml` 里多一条
  `master.web_trigger_daily` 流水线（官方 `zh/build/web-trigger.html`）。

- **两个触发口共用同一份清单**：那七格从 crontab 流水线里搬出来，做成顶层锚点
  `.daily-gates: &daily_gates`，定时与手点两条都写 `stages: *daily_gates`。
  写成两份的那一刻就是它俩开始各漂的那一刻（哪天给每日档加一格、忘了加到手点那条，
  「手点一遍每日档」得到的就不是每天 04:00 那一跑）—— §12.12 的孪生形态，只是它长在配置里。
  搬动还顺带改掉一个旧盲区：那些格子以前缩进在流水线内部（8 空格），`parseStageIfModify()`
  只认两空格缩进的 stage 项，于是它们**根本不在容器/`ifModify` 那两条判据的扫描面里**；
  现在它们在顶层锚点上、被同一套解析器看得见。

## Fixed

- **`pipelineStageNames()` 现在认得 `stages: *锚点`**（此前只会读内联清单，遇到引用形态回
  `[]`）。这个洞一直在，只是没人把 `stages` 写成引用：读回空清单的判据会安静地拿到一个
  「这条流水线一格都没有」的假结论，而「两个触发口是不是同一份」这件事根本没有执行者。
  解析与夹具用例同批补上（内联与引用两种形态都要读得出，读不出必须是 `[]` 而不是猜）。

- **四条新判据，各做过反向 mutation**（`tests/no-platform-ci-config.test.ts`）：
  ① 定时与手点两条各自解析出的 stage 名单必须等于 `COMFYAPP_CI_DAILY_GATES`
  （把 `stages: *daily_gates` 改成引用 PR 那份清单 ⇒ 红）；② `.cnb/web_trigger.yml` 里的
  `event:` 与 `.cnb.yml` 里的 `web_trigger_*:` 键**双向**核对（按钮名改错一个字母 ⇒ 红，
  那两种失效各自的表现是「按下去什么都不跑」与「这条流水线永远没人点」，都不会让对面变红）；
  ③ 按钮的 `reg` 必须是锚定的 `^master$`（`reg` 是正则，写 `master` 会前缀匹配到
  `master-x` 那种分支，按下去跑的是那条分支的 HEAD —— 每日档要证的从来是 master）；
  ④ `<<: *common` 的引用数 = 流水线数（三 → **四**）：少引用一条 = 那一条没有
  `runner.namespace: group` + `tags`，会**静默回落到计费的平台池**，而定时与手点这两条
  恰是「不会有人盯着」的那一类。

  两处仍然不同，别把「手点」读成「重跑夜里那一跑」：
  **执行身份**：定时那条是配置持有者（官方负责人机制），手点这条是按按钮的人 —— 红了先说清
  是谁发起的。**取的是哪份代码**：两条都取当时 master 的 HEAD，所以夜里那次红修好后手点，
  验的是「修完的 master 行不行」，要**复现**夜里那一跑得先确认中间没人往 master 推过东西。
  `lock` 与定时那条同一个 key，04:00 那一跑还在跑时手点会把它掐掉（`cancel-in-progress`），
  不会出现两条重档同时压同一台机。规范落点：§13.5.23 新增那张四行表与配置里那段说明。
