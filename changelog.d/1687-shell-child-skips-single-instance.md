## Fixed

- **双击链路里「端口族刚查完，紧接着又查一遍」**（ISSUE #1687）：壳自编排是 `{{shell.app.exe}} → 编排器 → {{shell.app.exe}}` 两段（规范 §1.5），第一段（壳自己的单实例判定：命名互斥量 + 端口族是否空闲）与第二段（编排器靠 `spawnShell` 起壳前先判一遍）问的是**同一个问题**——同一个检出、同一次启动、相邻的两次。重复那一次不该有结论上的价值。
  - 壳侧短路由**注入的标记**判，不看形态：`shell_launch::is_shell_child()`（读 `COMFYAPP_SHELL_SELF_LAUNCH`，与壳起编排器时用的**同一个键**）。标记只在「编排器亲自起的那个壳」身上出现，首壳（双击链路里的编排者）与用户直接双击的壳都照常走 `single_instance::another_instance_running()`。
  - 编排器侧同一键：`spawnShell` 起第二段壳时注入它；`spawnDevServer` 也带上，于是编排器自己也能对壳已经在**同一个进程**里跑完的那次端口族判定放行。
  - **短路换来的失败面是净的**：互斥量名由 `identity_root()`（cwd / 环境块）推导，编排器若在**另一个 cwd** 起壳，名字会与用户第二次双击（cwd = `System32`）推出的不是同一个——短路反而堵掉了「进程名相同、标题相同」的第二个壳进入同一检出的那条缝。
  - 回收语义不变：残留是上一次运行留下的，要么在进程启动那一刻就在（那时短路还没生效，首壳与编排器各自照常判一遍），要么本次运行期间才出现（由常驻循环与退出回收负责，规范 §3.3）。
