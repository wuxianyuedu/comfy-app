## Fixed

- **应用日志面板：启动与启动器两个来源终于有日志内容了（ISSUE #262 六审）**。四审修的是**裁剪**（行被会话起点当成历史丢掉），这一轮是紧挨着的下一段：行抓到了、也没被裁掉，但**没被认成日志行**。根因是解析层的行正则要求级别标记恰好长成 `[INFO]`，而 `dev-launcher.ps1` 的真实行**没有一种长这样**——PowerShell 的 `$lvl.PadRight(5)` 会让 INFO / STEP / OK 变成 `[INFO ]` / `[OK   ]`，引导文案与错误详情是**缩进两格**的续行（`  [10:22:27] [ERROR] …`），颜色码残缺时还会在 `[` 后多留一段假转义（`[[90m[OK`）。三种形态一个都匹配不到，整行于是掉进裸文本兜底，面板上显示的是**带前缀的原文**（`[10:22:24] [INFO ] 预检通过`）——用户读到的就是「启动和启动器 2 项还是没有日志内容」。现在级别标记容错（`[` + 可选残码 + 可选空白 + 级别 + 可选空白 + 可选残码 + `]`）、行首允许缩进，并按 SGR 形状剥掉残缺颜色码。

- **容错只放宽「级别周围」，不放过普通前缀词**：级别名仍限定 `STEP` / `OK` / `INFO` / `WARN` / `ERROR` / `DEBUG` 六个，因此 `[rpc] abc 155ms`、`[system] 找到了` 这类行**不会**被当成级别吞掉（它们是正文的一部分）；时刻仍限 `HH:mm:ss`，带日期的行继续由 `APP_RUNTIME_LOG_RE` / `LAUNCHER_LOG_RE` 接管。另外**不做**「行内任意 `[...]` 都删」的宽松化——那会把正文里正常出现的方括号（如 `[workflow] 已保存`）一起吃掉。

- **判据钉在两层**：`log-store.test.ts` 逐条断言五种真实行形态的级别归一化与「消息里不残留 `[HH:mm:ss] [LEVEL]` 前缀」，并守住「`[rpc]` 行原样保留」；`e2e/critical-flows.spec.ts` 在真实 Chromium 里喂两个来源的行，断言四条正文可见且**每一条都不匹配** `[HH:mm:ss] [LEVEL]`（修复前收到的字符串正是 `"[10:22:24] [INFO ] 预检通过"`）。规范 07 新增 §7.25、launch-and-build §4.1 补了「行形态也是契约」的形态表：**先证「行是行」，再谈「行排在哪儿」**。
