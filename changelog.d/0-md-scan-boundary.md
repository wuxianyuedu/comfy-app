## Changed

- **契约 §Colors 里那条「文档别写全 arbitrary 候选名」的扫描边界，改成实测划出来的**。原来的说法只有结论（`.md` 也会被扫），没有边界，
  于是两个方向都会做错：有人会把「产物里多出死类」甩锅给草稿目录或构建缓存，也有人会为了清掉那几条规则去**改写已合并的碎片**。

  补上的一次性实验（放标记文件、各写一个独此一家的圆角候选名、编译一次看哪个进产物）：

  | 位置 | 是否 gitignored | 结果 |
  | --- | --- | --- |
  | `src/**`、`docs/**`、`changelog.d/**` | 跟踪中 | **被扫** ⇒ 碎片正文里写全一个候选名，每次构建都多一条死规则 |
  | `.workbuddy/`（草稿、探针） | 是 | **不扫** |
  | `.next/`（构建产物） | 是 | **不扫** |

  顺带否证了一件我自己写错过的事：#1536 那轮我曾判断「连 gitignored 目录也一起读」—— 标记实验直接推翻它，
  真实来源是我自己那份碎片的正文（它是跟踪文件，被扫是正确行为）。**同一轮里我一边写下「别把类名写全」的规则，一边在碎片里把它们写全了。**

## 决定：那几条死规则**不消除**

- 产物里现在有几条谁都不用的圆角规则，来源是两枚已合并碎片为了描述「当时收掉了哪些字面量」而写全的类名。
- 不改写的理由就是这条规则自己的依据：碎片是账本（硬规则 14 / §13.10.5 —— 追溯改写等于伪造证据）。
  几条 20 字节的死规则，换不了账本的可信度。
- 因此口径固化成一句可执行的话：**核对调用点存量一律按 `src` 数，不按产物数**（本库相关判据本来就是这么实现的，
  这条只是把「为什么必须这样」补全）。
