## Changed

- **D6（自动备份 / 恢复）的三种待拍口径各给一条建议默认，并把它的实现机制从「运行时不存在的那个」改对（ISSUE #1611）。** 上一笔把它从「外部阻塞」正名为「等一个决策」，但三种口径仍是三个问号；「等一个决策」如果一直等不到人答，形态上和「永久搁置」没有区别。本笔把每条都落到机器事实上，拍板只需答「按建议」或给替换值：
  - **① 备份时机 —— 建议：只在「会动结构的同步之前」自动做一档，另留手动档。** 这是唯一一次失误不可逆的时刻：`ensureSchemaCurrent` 的 `--force` 路（用户在确认弹窗知情后执行）跑的是**删列 / 重建表**（`db-schema-state.mjs` 的 `riskyStatements` 白名单），而它今天**零备份**。不选「应用退出时」的依据是壳对进程树执行**整树强杀** —— 被强杀的进程没有清理机会，备份在「崩溃 / 强杀 / 任务管理器结束进程」这条路上**永远不执行**，而那正是最需要它的那条路。不选「常驻定时」的依据是本项目**同一份 WAL 有两个进程在写**（内嵌 Next server + 执行宿主），多一个常驻写手会把 `SQLITE_BUSY` 的竞争面再放宽一档（#1250 踩过）。
  - **② 保留份数与落位 —— 建议：最近 3 份，落 `<应用根>/data/backups/`。** `data/` 已经就是本机私有状态的既定落点（`app-settings.json` / `llm-secret.key` / `runtime-secret.json` 都在这层、`.gitignore` 收 `/data/`、`standalone-private-inputs.mjs` 还会把它从分发产物里剥掉）。**不放「项目根旁边」**：生产里 `process.cwd()` 就是**安装目录**（NSIS per-user 装到 `%LOCALAPPDATA%\<产品名>`），而下次安装 / 更新会覆盖安装清单里的文件 —— 备份放那儿会被一次升级带走。
  - **③ 恢复入口 —— 建议：设置页一个入口（选份 + 确认），但真正换文件落在「应用没在跑」的那一刻。** 运行期会有多个进程同时持有这个库（内嵌 Next server、执行宿主，以及用户可能开着的 Drizzle Studio），直接覆盖 `db.sqlite` 等于在别人握着句柄时换掉文件。建议形态与既有先例**同形**：`POST /api/schema/push` 那套三层守卫 + `canPush` 决定按钮显不显示；点按钮只写**待恢复标记**，换文件交给启动链（`ensureSchemaCurrent` 同一个落点）—— 那个时刻天然满足「应用没在跑」，不用另造一把锁。只给命令不选，是因为 `guide-database-backup.md` §6 已经是那条命令了，「回滚时应用正持有 DB」这件事并不会因为入口是命令就消失，只是没人处理。
- **纠正 D6 原文里一处运行时不存在的方法。** 原文写「复用 better-sqlite3 现成的在线 `backup()`」，但 **`better-sqlite3` 是 `devDependencies`**（测试基建），生产运行时走的是 **`@libsql/client`**（`dependencies`，`src/server/db.ts`），而它**没有 `backup()`**（`Client` 只有 `execute` / `transaction` / `sync` / `close`）。热备份机制按本容器实测改为 **`VACUUM INTO`**：真驱动、WAL 模式下产出单文件、`pragma integrity_check` 回 `ok`、表数据可读。留着不改的后果是动手那天才发现要换机制，而这一条**动的是用户数据**。
