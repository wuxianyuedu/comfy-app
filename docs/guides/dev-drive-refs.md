# 开发盘（ReFS / Dev Drive）红利指南

> 这份指南回答一个问题：**仓库搬到 Windows 开发盘之后，怎么把这块盘的红利吃满。**
> 结论不写死在文档里 —— 每一条都由 `pnpm dev:drive` 实测当前这台机器后给出
> （入口 `scripts/dev-drive-tune.mjs`，探测层 `scripts/dev-drive-probe.mjs`，
> Windows 双击入口 `tools/start/tune-dev-drive.ps1`）。

---

## 先说三件容易搞混的事

1. **「卷是 ReFS」与「卷是 Dev Drive」不是一回事。** Dev Drive 是**在格式化那一刻**
   被指定（`/DevDrv`）的 ReFS 卷，它额外带来 Defender 性能模式、筛选器策略等。
   既有卷无法就地转换 —— 所以先确认自己的卷是不是 Dev Drive，再谈红利。
2. **块克隆不是「ReFS 就有」，而是「复制操作走的那条路有没有接上」。**
   ReFS 自 Windows Server 2016 起具备块克隆能力；**客户端 Windows 从 24H2 起，
   受支持的复制操作（`CopyFile` / `CopyFileEx` / `robocopy` 等）会原生克隆**。
   于是「在开发盘上复制一个文件」这件事本身就是元数据操作，不搬字节。
3. **别拿 Node 的 `COPYFILE_FICLONE_FORCE` 当卷的体检报告。** 它在 Windows 上
   一律返回 `ENOSYS` —— 那测的是 **libuv 有没有实现强制克隆标志**，不是卷支不支持克隆。
   本仓的探针踩过这个坑，判据因此改成：**复制一份，再比对源与目标的物理簇**。

## 本机实测读数（脚本每次运行都会重测一遍）

| 项 | 读数 | 含义 |
| --- | --- | --- |
| 检出所在卷 | `G:\`，ReFS，卷标「开发」 | 已经是 ReFS |
| 硬链接 | 可用 | pnpm 依赖物化走零拷贝 |
| **块克隆** | **可用**（复制后源与目标物理簇相同） | 复制是元数据级操作，不搬字节 |
| 稀疏文件 | 未启用 | 收益面是 VHDX 形态的开发驱动器与大体积可变文件，本仓两者都不占 |
| SQLite / WAL | 正常（可开 WAL 模式、可建表、读写与检查点均正常） | 应用数据库放在开发盘上**没有已知问题** |
| 开发驱动器 | **受信任**（管理员查 `fsutil devdrv query G:` 实测） | Defender 走**性能模式**（异步扫描），不需要再加排除项 |
| 卷上的筛选器 | `lnvscenter`（联想 / 火绒引擎）、`WdFilter`（Defender） | 第三方防护**不吃**性能模式 —— 但「挂着」≠「在扫」，实测见下一节 |
| pnpm store | 与检出同卷 | 装依赖不再复制字节 |

> 这些是**某一台机器某一时刻**的读数。换机器、换卷、换系统版本都会变 ——
> 所以别把它们抄进别处当结论，跑一次 `pnpm dev:drive` 拿当下的。
> 其中「开发驱动器指定 / 信任状态 / 筛选器清单」**只有管理员查得到**
> （`fsutil devdrv query G:`），非管理员下脚本记「不判」，不猜。

## 第三方过滤驱动到底有没有拖慢开发盘（实测）

**先认人，再看开销。** 卷上挂着 `lnvscenter` 不等于它在扫：

| 事实 | 依据 |
| --- | --- |
| `lnvscenter.sys` 是**火绒引擎的文件系统过滤驱动**（签名主体：北京火绒网络科技） | 读驱动文件的版本信息 |
| 它此刻**在跑**，且挂在 G: 的筛选器栈上 | 驱动服务状态为「已启动 / 系统启动」，管理员查开发卷指定时能看到清单 |
| 但用户态引擎（`wsctrl11`）**自开机累计只用过 0.36 秒 CPU** | 性能计数器读数 |
| 真正在扫的是 **Defender**：一次 1 GB + 5000 文件的负载窗口内，它吃掉约 **19 CPU 秒**；同期火绒引擎 CPU 增量为 **0.000 秒** | 同一次负载窗口内各进程的 CPU 增量 |

**结论：这块开发盘上，第三方过滤驱动当前不构成 I/O 瓶颈**（它只是「能看见」这块卷上的文件，属安全面，不是性能面）。
**没有实测到开销，就不要为了提速去改安全策略** —— 那类改动不可逆。

> 上面那条结论的依据是**同机、同一次负载窗口内各进程的 CPU 增量**——
> 这一条**不掺硬件差**（同一个进程、同一段负载、同一块盘上的读数）。
> 下面那张吞吐表则**掺了硬件差**，两件事别混着用。

同一段负载、同一份数据、同一个进程，测两块卷（`pnpm dev:drive --bench`）：

| 指标 | 开发盘 | 参考卷（系统盘） | 差 |
| --- | --- | --- | --- |
| 顺序写 | 3707 MB/s | 3095 MB/s | 1.20 倍 |
| 顺序读 | 7503 MB/s | 5168 MB/s | 1.45 倍 |
| 小文件创建 | 1832 个/秒 | 1175 个/秒 | 1.56 倍 |
| 小文件读 | 5927 个/秒 | 2972 个/秒 | 1.99 倍 |

> ⚠️ **这两块卷不在同一块物理盘上**，所以这组倍率里**掺着硬件差**：
> 开发盘 = Disk 1（SL7000 40Pro，PCIe 4.0，2TB），参考卷 = Disk 0（WDC SN730，1TB）。
> 它能说明的是「**开发盘这套组合（更快的盘 + ReFS + 筛选器栈）整体不慢**」，
> **不能**当成「ReFS vs NTFS」的差，更**不能**当成「筛选器栈的差」——
> 要归因到文件系统，得拿**同一块物理盘**上的两种文件系统对照。
> 读数还随冷暖态与后台负载变化（本次是暖态、机器有其他任务在跑），**别抄数字当结论**。
>
> 同盘对照另有一份账：今天的耗时基线复测
> （[`2026-10-21-timing-baseline-refs-volume.md`](../audits/2026-10-21-timing-baseline-refs-volume.md)）
> 量的是**同一块物理盘**上的 ReFS 与 NTFS，结论是「元数据密集那一族快 2–4×、
> 文件系统不是慢因」——那份才是能引用到「ReFS 值不值」上的读数。

### 想自己复验

```bash
# 跑一次 I/O 实测：同一段负载测开发盘与系统盘，并归因「谁在吃 CPU」
pnpm dev:drive --bench
```

它会真的写数据（每块卷几百 MB，跑完即删），并在报告末尾列出负载窗口内 CPU 消耗前几名的进程。
**这一步的产出是「实测」，不是「结论」**：结论由工具自己下，三档分开说 ——
第三方引擎**确实在扫**（那才值得动安全策略）、**没在扫**（不动）、**认不出对应进程**（不判，不猜）。

## 怎么跑

```bash
# 只探测 + 报告（不改任何状态）
pnpm dev:drive

# 顺手落仓库级（可逆）调优：git 索引格式与提交图
pnpm dev:drive --apply

# 机器可读输出（JSON），供其他工具消费
pnpm dev:drive --json

# 跑一次 I/O 实测：同一段负载测两块卷，并归因「谁在吃 CPU」
# （会真的写数据：每块卷几百 MB，跑完即删）
pnpm dev:drive --bench
```

Windows 侧双击 `tools/start/tune-dev-drive.ps1`（带 `-Apply` / `-Json` 开关同形）。

脚本只落**仓库级、可逆**的配置（写 `.git/config`）；需要管理员权限、或需要重格式化卷
的动作**只会被打印成命令**，脚本不代跑 —— 那两类要么动全局安全策略，要么动数据。

## 动作矩阵

| 杠杆 | 状态口径 | 落点 |
| --- | --- | --- |
| pnpm store 与检出同卷 | 硬链接零拷贝 | `G:\.pnpm-store`（同卷即达标） |
| 构建与依赖目录的真实落点 | 解开软链接后判卷 | `node_modules` / `.git` / `.next` / `src-tauri/target` 都应在开发盘上 |
| 块克隆 | 复制后比对物理簇 | 已生效：构建产物拷贝、依赖物化都省掉整份字节 |
| git 索引格式与提交图 | 仓库级、可逆 | `--apply` 会替你落 |
| 构建期临时目录 | 用户级环境变量 | `TEMP` / `TMP` 指向开发盘 |
| Rust 依赖缓存 | 用户级环境变量 | `CARGO_HOME` 指向开发盘 |
| Playwright 浏览器 | 用户级环境变量 | `PLAYWRIGHT_BROWSERS_PATH` 指向开发盘 |
| npm 缓存 | 用户级环境变量 | `npm_config_cache` 指向开发盘 |
| 开发驱动器信任状态 | 需要管理员查询 | 受信任 → Defender 性能模式已生效 |
| 开发卷上的筛选器 | 需要管理员查询 + I/O 实测 | 挂着 ≠ 在扫；实测到它没在扫就不动 |
| I/O 实测（两块卷 + CPU 归因） | `--bench` | 谁在吃 CPU、哪块卷更快 |
| Windows Search 索引 | 用户级 | 标成「不索引内容」；工具会抽读覆盖率，标记到位即判「就位」 |

> 为什么临时目录与各缓存也要搬：它们是**跨卷读写**最容易发生的地方 ——
> 构建产物先落临时目录再搬进检出，中间每一步都在跨卷。落在同一块盘上就没有这一步。

## 把缓存目录搬到开发盘之后（实测的连带动作）

搬目录不是搬完就完了。下面三条都是本机实测踩出来的：漏第一条会留下一个**直接坏掉**的
命令；漏后两条只会让旧目录**被重新长出来**。

| 连带动作 | 不做的后果 | 依据 |
| --- | --- | --- |
| 改 `CARGO_HOME` 之后，`PATH` 里那条指向旧 `\.cargo\bin` 的条目要同步改到新位置 | `cargo` / `rustc` / `rustup` 全部变成「不是内部或外部命令」—— 源目录被搬走的同时，那条 `PATH` 条目就指到了空处 | 实测：搬完后查这条命令直接报未找到；把条目改到新位置后 `cargo 1.98.0` 正常 |
| 搬完把源目录本身删掉 | `robocopy /MOVE` 对「目标已存在且内容相同」的文件会判成同一份而**跳过复制、也就不删源** —— 源目录会留下搬不走的残片 | 实测：缓存目录的源侧反复剩下同一批文件 |
| 让新进程读到新的环境变量 | **已经在运行的进程仍用旧值** —— 它们会继续往旧路径写，把刚搬走的源目录重新建出来 | 实测：旧临时目录仍有新写入；新启动的进程已在写开发盘 |

第三条有个容易搞混的细节：**改注册表里的用户环境变量，不等于所有新程序都读到了新值** ——
从桌面启动的程序会继承「资源管理器」那个还没刷新的环境块。
广播一次 `WM_SETTINGCHANGE` 能让资源管理器刷新，但**注销重登最稳**。

### 一个容易搞混的点：`npm_config_cache` 不管 pnpm

本仓的包管理是 **pnpm**，而 pnpm **不读** `npm_config_cache` —— 那一条只对 **npm** 生效。
pnpm 自己有两个落点：

| pnpm 的东西 | 本机落点 |
| --- | --- |
| 包仓库（store） | `G:\.pnpm-store\v11`（`pnpm store path` 的读数，已在开发盘） |
| `pnpm dlx` 与元数据缓存 | `%LOCALAPPDATA%\pnpm-cache`（本机 2.3 GB，**仍在 C 盘**） |

要把后者也搬走，改的是 pnpm 自己的 `cache-dir`，不是 `npm_config_cache`：

```bash
pnpm config set cache-dir "G:\.pnpm-cache"
```

> 这条只在你确实用 `pnpm dlx` 拉临时包时才有意义（本仓用 `pnpm exec` / `pnpm install`，
> 走的是 store，不走 dlx 缓存）。动手前先看一眼 `pnpm store path` 的读数 ——
> store 已经在开发盘上，就别为了搬缓存去动 store。

## CI 侧：流水线也吃开发盘红利

自托管节点就在这台机上（`G:\runner`），而 CI 以 **systemprofile 服务账号**跑 ——
于是「用户级环境变量」那一整套（`TEMP` / `CARGO_HOME` / `PLAYWRIGHT_BROWSERS_PATH` /
`npm_config_cache`）**对 CI 一条都不生效**：服务账号读的是机器级 env 与
`.cnb.yml` 里的 env，不读用户 HKCU。

节点从 `F:` 搬到 `G:` 之后，CI 这边的落点是这样（读数来自节点自己的 stream-log，
`G:\runner\data\orange-ci\stream-log\cnb-<sn>-001.log`）：

| 环节 | 落点 | 在开发盘 |
| --- | --- | --- |
| 检出工作区 | `G:\runner\data\orange-ci\runner\<repoId>\<job>~<rand>\workspace` | ✅ |
| pnpm store | `G:\.pnpm-store\v11`（跟着检出所在卷走） | ✅ |
| 缓存槽 | `G:\ci-cache\comfy-app-t3\<键>` | ✅ |
| 临时目录（`TEMP` / `TMP`） | `C:\Windows\System32\config\systemprofile\AppData\Local\` | ❌ |
| 浏览器落点 | `C:\Windows\System32\config\systemprofile\AppData\Local\ms-playwright` | ❌ |

⇒ 仓库侧的处置是 `.cnb.yml` 的**流水线级** env 里加三行，都指到开发盘：

```yaml
    TEMP: "G:\\Temp"
    TMP: "G:\\Temp"
    PLAYWRIGHT_BROWSERS_PATH: "G:\\.cache\\ms-playwright"
```

三条要点，缺一条就有一类红：

1. **必须写在流水线级，不能写在某一格的 `env:` 里** —— 浏览器装在 `每日浏览器安装`
   那一格、跑在 `每日全量E2E` 那一格，两格必须看**同一个**落点；写在某一格里 ⇒
   那一格看得到、另一格看不到 ⇒ **装好了，探不到**（而「明明装过」与「一件都没有」
   在日志里原本逐字同形）。
2. **临时根要事先存在** —— 临时根不存在时 Node 仍把它当临时目录返回，第一笔写就
   ENOENT，而日志里读不出「目录没了」。`环境前提` 那一格会把它**补出来**（幂等，
   缺了才建）并打印读数；换台节点时记得先把目录建好。
3. **容器那个路径仍然不能写** —— `/ms-playwright` 只在 Playwright 镜像里成立，
   在 Windows 宿主上不存在，写着它等于让落点判据去一个空目录找东西。

判据在两处，各守一半：`tests/ci-image-identity.test.ts` 判「不许指向容器那个路径」，
`tests/ci-dev-drive-root.test.ts` 判「三行在流水线级、成对、同卷、推导只有一处」。
口径与实测读数见规范 §13.5.3.4.4。

> ⚠️ **换节点要跟着换**：这三行是给这台自托管节点写的（它检出在 `G:`）。
> 节点搬到别处时，改这三行 + 改节点上那两个目录，与改别处的配置是同一件事。

## 需要你拍板的两类动作

### 一、需要管理员权限（只读查询 / 改安全策略）

**这块卷是受信任的开发驱动器 → Defender 性能模式已经生效**，所以
**不需要**再加 Defender 排除项（那是对普通 ReFS 卷的兜底做法）。

用管理员查一眼，确认信任状态与卷上挂了哪些筛选器：

```powershell
# 以管理员身份运行（只读）
fsutil devdrv query G:
```

输出里除了信任状态，还有一行「挂了哪些筛选器」：

```
Filters currently attached to this developer volume:
    lnvscenter, WdFilter
```

`WdFilter` 是 Defender；`lnvscenter` 是**联想 / 火绒引擎**的过滤驱动。
微软文档讲明：Defender 的**性能模式只对 Defender 生效**，第三方端点防护不吃这一套。

**但这不等于「它在拖慢开发盘」** —— 挂着 ≠ 在扫。实测（见上一节）：
本机那个第三方引擎在负载窗口内 CPU 增量为 0，**没有构成瓶颈**。
所以正确的顺序是：

1. 先跑一次 `pnpm dev:drive --bench`，看它在负载下到底吃不吃 CPU；
2. **实测到它在扫**，再谈下面两条路（都是安全策略变更，判定权在人）：

```text
更精准：在那个第三方客户端里把开发卷加进它的排除 / 信任列表
        （联想电脑管家 → 设置 → 排除 G:\ ，影响面只有这一块盘）

更彻底：收窄整台机器的开发卷筛选器策略，只留 Defender
        fsutil devdrv setfiltersallowed WdFilter
        （影响这台机器的**所有**开发卷，且第三方防护从此看不见它们）
```

3. **实测到它没在扫，就别动** —— 为了提速去改安全策略是不可逆的取舍，
   而实测已经说明这里没有可换来的性能。

> 「受信任」意味着**这块卷上的内容不再走 Defender 的常规实时保护扫描**；
> 加上第三方防护也可能被摘掉，安全边界由你负责 —— 开发卷里放的是源码与依赖，
> 这个取舍通常合理，但它确实是安全策略变更。

若这块卷**不是**开发驱动器（`fsutil devdrv query` 明确说不是），普通 ReFS 卷唯一
能拿到「接近性能模式」的办法是加排除项：

```powershell
# 以管理员身份运行
Add-MpPreference -ExclusionPath "G:\"
```

Windows 搜索索引同理，标成「不索引内容」即可（用户级，代价是一次全量属性改写）：

```powershell
# 整盘一条命令：自己枚举、跳过符号链接与联接点
$o = [System.IO.EnumerationOptions]::new()
$o.RecurseSubdirectories = $true
$o.AttributesToSkip = [System.IO.FileAttributes]::ReparsePoint   # 不跟 pnpm 那些符号链接
$o.IgnoreInaccessible = $true
foreach ($f in [System.IO.Directory]::EnumerateFiles('G:\', '*', $o)) {
  $a = [System.IO.File]::GetAttributes($f)
  if (-not ($a -band [System.IO.FileAttributes]::NotContentIndexed)) {
    [System.IO.File]::SetAttributes($f, $a -bor [System.IO.FileAttributes]::NotContentIndexed)
  }
}
```

> **为什么不给 `attrib`**（两个坑都实测过，别照抄旧命令）：
> ① `attrib +I /S /D "G:\"` 直接吐 `File not found - G:\` —— 结尾的反斜杠被当字面量，
> 整条命令一次都没生效；
> ② 加上通配符（`attrib +I /S /D "G:\*"`）后，它会跟着 `node_modules` 里 pnpm 的
> **符号链接**递归 —— 实测对着仓库跑 15 分钟、CPU 208 秒，仓库内标记覆盖仍是 **0%**
> （`.pnpm-store` 那种没有符号链接的树倒是标上了）。
> 上面这条自己枚举、显式跳过 reparse point，实测整盘几分钟跑完、覆盖率 100%。
>
> 另两条注意：这条标记只作用于**当前已有**的文件，新落盘的文件不继承它；
> 想要一劳永逸，Windows 搜索的「索引选项 → 排除项」才是按目录长期生效的那一处。
> 跑完要**抽查**（命令不报错 ≠ 标记到位）——或者直接跑一次 `pnpm dev:drive`：
> 它会抽读检出内的标记覆盖率，覆盖到位时那条杠杆从「待办」翻成「就位」。

### 二、需要重格式化（动数据）

**只有当这块卷不是开发驱动器、而你又想要块克隆时**，才需要走这条路：

```powershell
# 以管理员身份运行 —— 会清空该卷，先备份
Format-Volume -DriveLetter G -DevDrive
```

**这条是破坏性的**：它会清空整块盘。另一条不动现有数据的路是另建一个 VHD 形态的
开发驱动器，把检出搬过去（VHD 的额外开销是「少一点性能」，换来「可随时丢」）。

---

## 已知边界（这几条是文档里的硬限制，不是本仓的选择）

- **WSL `metadata` 挂载选项不支持 ReFS**：它靠扩展属性保存 Linux 权限与属主。
  如果你的工作流依赖「Windows 文件上保留 Linux 权限」，那些文件要放 NTFS 卷或 WSL 虚拟磁盘。
- **块克隆自身的限制**（微软文档列的硬条件）：源与目标必须在同一个 ReFS 卷；
  克隆区间要按簇对齐且小于 4 GB；目标区不能越过文件末尾（要先扩文件）；
  源是稀疏文件时目标也得是稀疏文件；源与目标的完整性流设置要一致。
  —— 这些是「为什么某些复制没克隆」的解释，不是本仓的取舍。
- **开发驱动器上不建议装开发工具与 SDK**：它们通常在管理员位置或用户位置，
  装在开发驱动器上会改变 Defender 的行为面。
- **ReFS 比 NTFS 更吃内存**：官方建议至少 8 GB、理想 16 GB。
- **开发驱动器不支持热插拔 / 可移动介质上的卷**，也不支持动态磁盘。
- **卷空间要留够**：块克隆让「多份相同数据」变便宜，但构建产物与依赖缓存本身仍然占地方。
