## 7. 日志系统

> 本项目含客户端日志面板（`LogProvider`）+ Tauri 后端日志事件 + 文件归档。本章给出日志系统的设计、降级与规范。

> **占位符约定**：本文中 `{{...}}` 形式的占位符代表文档引用的真实值（如启动页文件名），
> 真实值由 `pnpm doc:check` 运行时从源码/配置动态提取并核对。占位符语义见
> [`docs/reference-facts.md`](../reference-facts.md)。改动上游源码后可运行
> `pnpm doc:check` 检查本文是否有值未同步。

### 7.1 分层存储

```
内存 (最近 2000 条) ←→ 文件 (完整历史)
     ↑                        ↑
  实时展示/搜索            按需加载/全局搜索
```

### 7.2 搜索范围选择

| 范围           | 速度 | 完整性   | 适用场景     |
| -------------- | ---- | -------- | ------------ |
| 内存           | 快   | 可能不全 | 日常调试     |
| 全部（含文件） | 慢   | 完整     | 排查历史问题 |

### 7.3 日志面板开关快捷键

```tsx
// ✅ 统一快捷键规范
// Ctrl+Shift+L → 日志面板
// Ctrl+F       → 搜索框聚焦（JsonViewer/日志面板内）
```

### 7.4 日志状态用 Zustand，不用 Context

日志每秒可能数十条更新，Context 会导致所有消费组件 re-render。

```tsx
// ✅ Zustand：组件只订阅自己需要的字段
const errorCount = useLogStore((state) =>
  state.logs.reduce((n, l) => (l.level === "error" ? n + 1 : n), 0),
);
```

### 7.5 内存上限 + 环形缓冲

```tsx
// ✅ 默认保留最近 2000 条
const MAX = 2000;
setLogs((prev) => {
  const next = [...prev, ...entries];
  return next.length > MAX ? next.slice(-MAX) : next;
});
```

详见 [2.1 列表/日志必须有上限](02-性能规范.md#21-列表日志必须有上限) 与 [2.1.1 无限历史与虚拟滚动](02-性能规范.md#211-无限历史与虚拟滚动无上限场景兜底)。

### 7.6 console 拦截规范

`LogProvider` 拦截 `console.log/info/warn/error/debug` 把日志同时写入面板：

```tsx
// ✅ 拦截 + cleanup（StrictMode 下不永久污染）
useEffect(() => {
  const originals = { log: console.log, error: console.error, ... };
  console.log = makeLogger("info");
  console.error = makeLogger("error");
  return () => {
    console.log = originals.log;
    console.error = originals.error;
    // ...
  };
}, [addEntry]);
```

**规则**：

- 拦截只在 `LogProvider` 挂载期间生效，卸载后恢复原始方法（防 StrictMode 双调用问题）。
- 调用原始方法保留浏览器控制台输出（`originals.log(...args)`）。
- 序列化参数时处理 `Error` 对象（`stack`）、循环引用（`JSON.stringify` 加 try/catch）。

### 7.7 Tauri 后端日志事件

```tsx
// ✅ 动态 import + try/catch，浏览器环境静默跳过
try {
  const { listen } = await import("@tauri-apps/api/event");
  unlisten = await listen<{ level: string; message: string }>(
    "log:emit",
    (e) => {
      addEntry({
        level: mapLevel(e.payload.level),
        message: e.payload.message,
        source: "tauri",
      });
    },
  );
} catch {
  // 非 Tauri 环境（浏览器开发），忽略
}
```

### 7.8 历史日志加载

- 启动时加载最近 N 个归档文件（`/api/logs/list` + `/api/logs/history`），带大小上限（如 5MB）防止一次加载过多。
- 轮询当前日志文件（`/api/logs/current?offset=...`）增量追加；文件被重置（新运行）时 offset 回零、完整重读。
- 加载失败不应阻塞实时日志轮询（try/catch + 静默忽略）。

### 7.9 导出与复制

```tsx
// ✅ 复制：Clipboard API + execCommand 兜底
async function copyAll() {
  try {
    await navigator.clipboard.writeText(formatForClipboard(logs));
  } catch {
    const ta = document.createElement("textarea");
    ta.value = formatForClipboard(logs);
    document.body.appendChild(ta);
    ta.select();
    document.execCommand("copy");
    document.body.removeChild(ta);
  }
}

// ✅ 下载：Blob + 临时 <a download>
function download() {
  const blob = new Blob([formatForClipboard(logs)], {
    type: "text/plain;charset=utf-8",
  });
  const url = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = url;
  a.download = `logs-${new Date().toISOString().slice(0, 19).replace(/:/g, "-")}.txt`;
  document.body.appendChild(a);
  a.click();
  document.body.removeChild(a);
  URL.revokeObjectURL(url); // 及时释放
}
```

### 7.10 日志序列化健壮性

```tsx
// ✅ 处理各类输入，避免序列化抛错
function serializeOne(a: unknown): string {
  if (typeof a === "string") return a;
  if (a instanceof Error) return `${a.name}: ${a.message}\n${a.stack ?? ""}`;
  try {
    return JSON.stringify(a, null, 2);
  } catch {
    return String(a);
  } // 循环引用/BigInt 等兜底
}
```

### 7.11 应用运行操作日志（app-runtime）

`log/launcher` 与 `log/nextjs` 里的启动/编排日志只能看到**应用启动**过程；用户在应用内
做的**业务操作**（tRPC 调用、生成、任务、工作流增删改）此前几乎不可见——它们要么在
服务端 pino 输出里（落在 `nextjs-*.log`，面板不读），要么根本没打日志。为解决这个
「中间操作看不到」问题，引入**应用运行操作日志通道**：

- 写入端：`src/lib/app-runtime-log.ts` 的 `createAppRuntimeLogger(ns)`，以
  `[YYYY-MM-DD HH:mm:ss.mmm] [LEVEL] [ns] msg` 行格式**追加写**到
  `log/services/app-runtime.log`（与 comfyui/drizzle/ollama runtime 同一套
  「追加写 + 面板轮询」模式）。写入失败绝不阻塞业务主流程。
- 覆盖来源：
  - **tRPC 中间件**（`src/server/api/trpc.ts` 的 `timingMiddleware`）：**只在出问题
    时**才写面板可见日志——调用抛错记一条 error、耗时超过阈值（`SLOW_QUERY_THRESHOLD_MS`）
    记一条 warn；正常成功的调用只走 pino `logger.debug`（落在 nextjs 文件日志），
    不进面板，避免每条 query/mutation 都在面板累积成几千条噪音。
  - **业务里程碑**：生成任务入队（`generate.generate`）、任务完成/失败
    （`comfyui/executor-finalize`）等关键节点补记结构化字段。
- 读取端：`LogProvider` 轮询 `GET /api/logs/current?source=app-runtime`（字节偏移
  增量），面板 `parseFileLogs` 已能识别该行格式并保留级别/命名空间。
- 规范：面板是**本机运行情况视图**，app-runtime 行用**本地时区**时间戳（UTC 会差
  8 小时，用户看不懂）；字段只记事件/耗时/类型，不把 prompt/PII 落盘（对齐 §11.5
  埋点纪律与 pino redact 契约）。

```ts
// 写入端（服务端，src/lib/app-runtime-log.ts 提供）
import { createAppRuntimeLogger } from "@/lib/app-runtime-log";
const log = createAppRuntimeLogger("task");
log.info(`任务完成 ${taskId}`, { outputs: saved.length });
// 行：[2026-09-15 10:20:30.123] [INFO] [task] 任务完成 abc {"outputs":2}
```

### 7.11.1 ComfyUI 原始回执通道（trace）——「结论有出口」不等于「现场可查」（#216）

用户报「生成失败只说未找到生成结果，没有任何 ComfyUI 返回的内容可看」。这是
§7.12「失败但面板空白」的**同族问题换了一层**：面板里其实**有**一行结论
（这是 §7.12 修好的部分），但失败现场（ComfyUI 到底回了什么）没有任何落盘出口。

**为什么不再往面板里塞**：面板是给人读的时间线，规范 §7.13/§7.14 已经定死了
「高频/大块输出先聚合再上屏」。comfy-cli 的 stdout 原始 chunk、`/history` 的完整
JSON、每一个 WS 帧如果逐条进面板，就会把真正有用的行挤出视野——这正是 §7.14.1
修的毛病。所以这里的取舍是**两条通道分工**：

| 通道                                                                  | 内容                                                                                                                               | 读者   |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 面板（`runner-state` 的 `log()`）                                     | 解析后的**事件摘要**：history 的就绪结论、`status/completed/输出节点数`、输出节点明细、执行错误一句话                              | 用户   |
| trace（`src/lib/comfyui/trace.ts` → `log/comfyui/comfyui-trace.log`） | **完整原文**：命令行与参数、每个 stdout chunk 与解析后事件、stderr chunk、全部 WS 帧、`/history` 与 `/queue` JSON、收口时的 errBuf | 排查者 |

契约（与 `comfyui-runtime.log` 等 runtime 家族同一套「追加写 + 行首本地时间戳」）：

- 行格式 `[YYYY-MM-DD HH:mm:ss.mmm] [INFO] [trace] <channel> [<taskId>] <内容>`，
  channel ∈ `cli` / `ws` / `http` / `history` / `session`（同文件内按通道区分来源）；
- **写入失败静默跳过**：trace 是诊断通道，磁盘/权限问题不得把生成带崩；
- **单行上限 8000 字符**（超出标注 `…(truncated)`）：一个巨大 payload 不能把文件
  写成 MB 级；路径取自 `log-paths.ts`（禁止手拼 `log/`）；
- **不参与面板轮询**：不进 `GET /api/logs/current` 的来源列表，检查现场直接看文件
  （定位路径见 [launch-and-build §4.2](launch-and-build.md#42-comfyui-原始回执通道trace与未找到生成结果的定位路径)）；
- **失败收口的结论必须带成因**：`finalizeFailure` 的原因从「未找到生成结果」细化为
  「未找到生成结果：promptId=… ，但 ComfyUI /history 中无该条目的有效结果」/
  「ComfyUI 全程未回传 prompt_id（…）」，并在日志里直接指出 trace 文件位置。

> 判据：**「结论 + 原文」两样缺一不可**。只有结论 = 用户知道失败了但无从排查；
> 只有原文 = 用户拿到几十 KB 也不知道在看什么。新增任何「会失败但没人看得见
> 原始回执」的路径时，必须在 trace 里补一行、在面板里补一句摘要。

### 7.12 「失败但面板空白」的三条补录规则（#273）

用户反馈「遇到问题，日志里什么也没有」时，按下面三类逐一排查——它们的共同点是
**失败不经过任何既有采集通道**：

| 场景                                        | 为什么面板收不到                                                                            | 处理                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| React Query `isError`（如设置页 tRPC 失败） | 失败只体现在组件降级 UI；查询错误不抛到 console，也没有 unhandled rejection                 | 逻辑层在 `hasError` 分支**主动补记** app-runtime 错误日志（同一错误只记一次，用 ref 去重） |
| 同一降级 UI 有多个入口                      | 各写各的兜底，有的只显示一行截断文案                                                        | 复用同一个错误降级组件（如 `SettingsLoadError`），保证「可展开/复制 + 面板指引」一致       |
| 文件转录行沾染错误级别标记                  | `[Fast Refresh] rebuilding [ERROR] …`（热更新行携带上一次编译错误的标记）被整行解析成 error | `parseFileLogs` 对已知框架行做级别矫正（info），与 `isNextDevNoise`（console 侧）互补      |

> **客户端补记 app-runtime 必须走服务端写入通道**（ISSUE #282）：`app-runtime-log.ts`
> 是 Node-only 模块（顶层 `import node:fs`），**禁止**被客户端组件/逻辑层直接 import——
> Turbopack 会把 `node:fs` 静态打进浏览器 chunk，编译报
> `does not support external modules (request: node:fs)`，整页 500。客户端要补记
> `app-runtime` 日志，一律经 `POST /api/logs/app-runtime`（`src/lib/log-file-client.ts`
> 的 `postAppRuntimeLog()`）转交服务端写入；`/*turbopackIgnore*/` 只能豁免动态访问点，
> 挡不住顶层 `import` 的静态打包。

> **同一坑的第二次踩中（ISSUE #317，2026-09-10）**：`src/lib/log-session-scope.ts`
> 顶层 `import fs from "node:fs"`，而客户端组件 `LogProvider.tsx` 只需要它的纯函数
> `clampLogTime` → 浏览器 chunk 被塞进 `node:fs`，`/login` 与 `/workspace` 整页 500、
> `pnpm build` 失败。这次修法做**分层**：纯函数留在 `log-session-scope.ts`（客户端与
> 服务端共用），IO（`fileMtimeMs`）移入 `.server.ts` 后缀的 Node-only 模块，只有服务端
> 路由引用它。
>
> **排查与防线的固定动作**：`rg '^import .*from "node:(fs|path|child_process)"' src/lib`
> 找出所有 Node-only 模块，再反查谁在 `"use client"` 图里 import 它们。
> 静态门禁见 `tests/client-bundle-node-builtins.test.ts`（命中即失败并打印引用链）；
> 该测试把「客户端 bundle 不得含 Node 内建」从约定升级为 CI 硬门禁。

#### 7.12.1 补记的三条硬约束（#304 复盘）

补记本身不够，记错/记漏等于没记。以下三条由 ISSUE #304（「打开设置失败，但日志里
什么也没有」）复盘固化：

1. **「任一查询失败」≠「两份数据都没拿到」**：降级视图的判据是「失败 **且** 需要
   降级」，不是「失败」。多查询页面里只让「两份都空」触发降级，会漏掉「一份成功、
   一份失败」的边界——失败为真、草稿却仍为空，既不满足降级也不满足加载中，一路
   落到兜底文案（如「配置数据未就绪」）：没有原因、没有重试、没有日志指引。
   > 判据写法：`queryFailed = 任一查询 isError`；`hasError = queryFailed && !drafts`。
   > 兜底分支（未加载、未失败、草稿仍空）也必须给**可操作出口**，禁止只渲染一句
   > 没有下文的说明文案。
2. **日志字段要记「实际失败的那个查询」**：多查询页面的补记若把查询名写死成某一个
   （`setting.get`），另一个查询失败时字段就是错的，面板里对不上号。按 `isError`
   逐个收集并拼全（如 `"setting.get,llm.configGet"`）。
3. **可读文案与原始报错两条都要落盘**：`errorMessage` 产出**给人看**的人话（会把
   `Unexpected token '<'` 换掉），`rawErrorDetail` 产出**给排查用**的原文（tRPC
   `code` / 服务端 `message` / `cause` / 堆栈首行）。只记前者，服务端真实报错
   （如 `no such table: xxx`）在面板里彻底丢失，用户拿着翻译后的话无从排查。
   > 取值顺序同理：tRPC 批量流式链路的顶层 `message` 可能只是传输层包装
   > （`signal is aborted without reason`），**真正的原因在 `shape.message`**；
   > 包装文案不得盖掉服务端原文。

原则：**新增「静默失败」路径时必须同步给出面板可见出口**（补记 app-runtime 或
console.error），否则用户遇到问题时面板一片空白、无从排查。

### 7.13 常规调用计时不进面板、面板分页与启动页提醒常驻（#294）

- **常规 tRPC 调用计时行不进面板**：形如 `[rpc] <path> 155ms {"type":"query"}`
  的正常调用计时高频产生会刷屏。面板双通道过滤（`log-store.ts` 的
  `isRoutineRpcTimingLog` / `isRoutineRpcTimingLine`）：
  - 文件侧：`parseFileLogs` 丢弃 INFO 独行计时（ns 前缀 `[rpc]`/`[trpc]` 或无前缀均可识别）；
  - console 侧：`LogProvider` 拦截同形态输出。
  - **WARN/ERROR 级别的调用日志永不过滤**——失败（`x 失败 Nms`）与慢查询
    （超过 `SLOW_QUERY_THRESHOLD_MS`）必须保留，这是「有问题的 query」唯一的面板出口。
    但「保留」不等于「每次都原样重写一行」：同一路径持续慢时按时间桶聚合并
    写累计次数，见 §7.14.1。
- **面板分页**：日志按时间**倒序分页**渲染（`page` 从 1 起，第 1 页最新，
  默认每页 2000 条，store 的 `pageSize`）。页脚提供上一页/下一页/回到最新；
  总页数随过滤结果变化，页码超界自动钳到最后一页。翻到历史页时不自动滚动
  （阅读位置不被新日志冲走），回到第 1 页恢复自动滚动。
- **启动页过期提醒常驻**：`stale_shell` 横幅（旧版桌面壳 / pnpm 版本不匹配）
  一旦出现就锁存显示（splash 的 `window.staleShown`），不随后续 250ms 轮询
  反复显隐——状态文件字段瞬时缺失也不闪没。改 splash 提醒逻辑须同步三份副本：
  `src-tauri/splash-assets/{{shell.splash}}`、`src-tauri/splash-assets/index.html`、
  `public/{{shell.splash}}`（编译期内嵌，改完壳必须重编，见硬规则 5）。
- **启动期警告补录 app-runtime**：dev-launcher 预检（壳过期 / pnpm 不匹配）
  发生在 dev server 就绪前，无法走 `POST /api/logs/app-runtime`；由
  `scripts/dev-launcher.ps1` 的 `Write-ShellStaleRuntimeLog` 直接按
  `[YYYY-MM-DD HH:mm:ss.mmm] [LEVEL] [launcher] msg` 行格式追加写
  `log/services/app-runtime.log`，面板照常轮询解析。

### 7.14 面板「慢 + 刷屏 + 看不出新增」的修法（#346）

用户反馈「设置页状态这么慢、日志还一直刷屏，警告条数在涨却看不到新内容」。
三个现象分别对应一条独立缺陷，都要修——只修其中一条，另外两条会继续制造
「日志不可信」的观感。

#### 7.14.1 慢查询 warn 按「路径 + 时间桶」聚合，不重复写行

慢查询 warn 是必要的出口（§7.13），**不能删**。问题是同一路径在每轮轮询里都慢时，
每轮都写一条**内容完全相同**的行：面板只剩满屏 `setting.comfyStatus 10457ms`，
不仅刷屏，还把真正新增的业务日志挤出视野——用户读到的信息量是零。

`src/server/api/trpc.ts` 的 `recordSlowQuery`：同 `(type, path)` 在同一
`SLOW_LOG_COALESCE_MS`（60s）窗口内只写**首条**，其余累计条数；窗口过期后写一条
带累计次数的汇总行：

```
[2026-09-10 10:36:01.513] [WARN] [trpc] setting.comfyStatus 10457ms {"type":"query"}
[2026-09-10 10:37:01.900] [WARN] [trpc] setting.comfyStatus 12396ms（近 60s 内共 9 次）{"type":"query"}
```

- 失败（`x 失败 Nms`，error 级）**永不聚合**：每次失败都是独立事件，要留全。
- 计数桶挂在 `globalThis`（HMR 单例），键含 `type`，query/mutation 互不干扰。
- 同一时间桶内的汇总计数**有意不写盘**：为了它每次都写一行就回到了刷屏的老路。
  这里牺牲「面板里能看到精确次数」，换「面板里能看到别的东西」。

#### 7.14.2 状态查询结论带 TTL 缓存，慢探测不再被每轮轮询重付

`setting.comfyStatus` 每次都要重付一遍「PowerShell 进程表查询（10s 上限）+
HTTP 探测（1.5s）」，本机实测单次 10~12s——既让状态行刷新慢到看不出变化，
又给上面的慢查询 warn 源源不断地供货。

`src/lib/comfyui/lifecycle.ts` 的 `getComfyUiStatus()` 对**合并后的结论**做
`COMFY_STATUS_TTL_MS`（10s）缓存 + 在途去重（并发查询共享同一次判定）。
两条硬约束：

- **`starting` / `stopping` 不跟着结论缓存**，每次返回都换成此刻的值。
  它们是进程内计时器（启动单飞锁 / 关闭窗口）驱动的**瞬时**态，与探测结果
  无关；把「启动中」缓存十几秒，设置页会在 ComfyUI 已经起来之后仍显示
  「启动中…」（ISSUE #344 的现象）。
- **事实变化时必须显式失效**：`ensureComfyUiReady({ manual: true })`（用户点
  「启动」）与 `stopComfyUiProcess()`（关闭）都先 `resetComfyUiStatus()`，
  下一问必须重新探，不得读到旧结论。

#### 7.14.3 面板按「入库顺序」排列，并显式提示「历史页有新增」

转录行带的是**文件写入时刻**，而三路轮询（launcher / dev / app-runtime）是并发
到达的——`app-runtime` 那一路要多等两个 IO 响应，于是它的**旧时刻行会晚于** dev
的**新时刻行**入库。面板此前按到达顺序 `[...logs, ...fresh]` 堆叠，数组顺序与
时间戳顺序就可能不一致：新增的行被插进中间（滚动位置之外），用户看到的是
「日志停在原地、只有警告计数在涨」——这正是 #346 的现象。

- `LogEntry.seq` 是**入库顺序**（模块级单调计数器），`time` 仍是**展示**时刻。
  `appendSorted` 按 `seq` 合并批次（快路径：批次本就单调时直接 push，不排序）。
- 面板的自动滚动与「有无新内容」判定一律看 `seq`，不看 `filteredLogs.length`
  （长度变了不等于末条变了，反之亦然）。
- **停在历史页（非第 1 页）时新增日志不自动滚动**（避免打断阅读位置），但页脚
  显示「有新的日志 · 回到最新」——否则用户完全看不到「刚才其实有新增」。
- `clear()` 不清零 `seq` 计数器：清空后新日志必须仍然排在历史行之后。

#### 7.14.4 服务会话横幅不再重复写时刻

`comfyui-runtime.log` 的会话横幅此前在标题里再写一遍时刻
（`▶ ComfyUI 启动会话  2026-09-10 19:21:01`），与紧随其后的行首时刻**只差 1 秒**；
用户把两条相似时刻读成一个，于是「ComfyUI 明明起来了、也写了新行，看着却像没新增」。
现在时刻只保留在**每条行首**（`appendRuntimeLog` 的统一口径），横幅只负责划边界。

> 新增「周期性写日志」的通道时，先问一句：**这条内容会不会每轮都一样？**
> 会，就先聚合再写（或在状态变化时才写）——面板的价值是「信息量」，不是「行数」。

### 7.15 面板只显示「本次运行」（#308）

四个轮询来源里，`dev`（`log/launcher/dev-launcher.log`）每次启动都被覆盖重建，
天然只有本次内容；`app-runtime` 与常驻服务 runtime（comfyui / drizzle-studio /
ollama）都是**追加不轮转**的，历史运行的行会一直累积。此前面板把整文件当成本次
运行来读，用户打开面板看到的一屏里混着上一次、上上次启动的日志，分不清哪条是
刚刚发生的。

会话边界（判据、起点下发与行级截断的完整分工见
[launch-and-build §4.1](launch-and-build.md#41-面板只显示本次运行的会话边界)）：
`dev-launcher.log` 的 mtime = 本次启动时刻；`GET /api/logs/current` 的追加写
分支在响应里带 `sessionStart`，面板按行时刻丢弃早于它的条目
（`src/lib/log-session-scope.ts` + `log-store.ts` 的 `dropStaleEntries`）。

规则：

- **不做字节级跳过**：时间戳只能回答「文件有没有在本次运行期间被写过」，
  回答不了「本次内容从第几个字节开始」。线的格式自带毫秒时间戳，按行比较即可
  精确切分，不需要在字节维度猜边界。
- **读不到起点就不截断**：非双击链路启动（`dev-launcher.log` 不存在）时
  `sessionStart` 为 null，面板退化为不做行级过滤——多显示几条历史行，好过因为
  锚点缺失把本次日志也丢掉。新增轮询来源时同样不得「拿不到起点就整段丢弃」。
- **`setSessionStart` 幂等**：起点来自服务端且写入后不回退，页面重载 / 面板重复
  打开不会把起点往后推；`dropStaleEntries` 对同一批条目重复执行结果不变。
- **每行标注来源**：`LogEntry.origin`（`dev` / `launcher` / `app` / `app-runtime`）
  写在行右侧，便于用户对照 `log/` 下的具体文件。
- **裁剪逐来源判定，不是整条时间线一刀切**（#262 四审，见 §7.23）：只有**跨运行
  累积**的来源参与行时刻比较，每次运行覆盖重建的来源不参与。`origin` 因此**参与**
  会话边界判定（此前它「只用于展示」的说法已被推翻）。
- **服务页的启动日志不在覆盖范围**：comfyui / drizzle-studio / ollama 的启动日志
  面板是「单个服务的会话视图」，靠会话横幅区分边界、由用户主动刷新，不套用本机制。

### 7.16 底部状态栏的「就绪」语义与指标降级（#121 / #324）

状态栏右下角最初是一个写死的「就绪 + 绿点」——从不变化、也没有任何判据，
用户反馈「不知道是什么意思」（ISSUE #121）。现由**单一事实**定义，见
`src/lib/comfy-readiness.ts` 的 `deriveComfyReadiness`：

| 状态   | 判据                                        | 文案   |
| ------ | ------------------------------------------- | ------ |
| 已就绪 | ComfyUI 已连接 **且** 能读到显存/内存指标   | 已就绪 |
| 连接中 | 已连接，但首个采样还没回来（首帧/轮询空窗） | 连接中 |
| 未连接 | 连不上 ComfyUI（未运行 / 轮询失败）         | 未连接 |

**队列空闲不参与判据**（决策，勿改回去）：就绪回答的是「这个创作后端现在能不能
收任务」，空队列是「现在没事干」而不是「可用」。若把队列空闲并入判据，正在跑图时
指示会退回「未就绪」——那恰好是用户最需要确认后端可用的时刻。队列状态由任务列表 /
执行日志表达。该边界写进了 `ready` 态的 `title` 文案，有命名用例固定。

**指标降级不得静默**（对齐 §7.12 的「失败路径必须有可见出口」）：

- ComfyUI 未运行时显存/内存占用条隐藏，但状态栏**显示一行可见说明**
  （「ComfyUI 未运行，显存/内存暂不可用」）——用户能看到「为什么没有数字」，
  而不是两项无声消失。
- 非 NVIDIA 卡 / `nvidia-smi` 不可用 → 只显示 ComfyUI 的 CUDA 口径，
  不渲染「显存 —/—」空项（占位空项比不显示更让人困惑）。
- 总量为 0（纯 CPU 后端）→ 该项按「无数据」处理（隐藏），不显示 `0%`。

分层（规范 17 §17.2）：判据是第①层纯函数（`src/lib/comfy-readiness.ts`），
折叠成视图字段是第②层（`src/components/studio/hooks/use-comfy-readiness.ts`），
状态栏只渲染结果。行为测试：
`src/lib/comfy-readiness.test.ts`（语义契约）、
`src/components/studio/hooks/use-comfy-readiness.test.ts`（显隐/降级/三态）、
`src/components/studio/BrowserStatusBar.test.tsx`（可见行为 + FPS 归属）。

**FPS 归属**：画布内的 `FpsMeter` 悬浮层已移除，全应用仅状态栏一处显示实时帧率
（由 `useFps` 提供，`≥50` 流畅 / `30~49` 轻微掉帧 / `<30` 明显卡顿）。

### 7.17 面板时间线重构：按时刻合并、跨来源去重、显示与内存解耦（#262）

用户连续三轮反馈同一件事：「日志看不到中间操作」（#265）→「query 刷满了」
（#280）→ **「连最基本的按时间顺序显示都做不到，锁死 2000 条、不能翻页、
query 刷满了其他内容基本看不到」**（#262）。前两轮都在改**采集**（加一条通道、
过滤一类噪音），#262 暴露的是**面板本身的数据结构与读取口径**不对——所以这一节
不是再加过滤规则，而是把时间线的定义固定下来。

#### 7.17.1 时间线的定义：按时刻合并，跨来源去重

面板的日志来自五路（console 拦截、Tauri 事件、全局错误、文件轮询 ×3），旧
实现按**到达顺序** `[...logs, ...fresh]` 堆叠。三路文件轮询并发到达，而每行带的
是**文件写入时刻**：后到的批次里可能有更早时刻的行。结果是面板里日期会往回跳、
新增的行被插进列表中间（滚动位置之外），用户读到的就是「时间顺序都做不到」
「日志不再刷新了」。

契约（`log-store.ts` 的 `mergeTimeline`）：

- **排序键是 `(time, seq)`**：`time` 是行内时刻（毫秒）；`seq` 是入库序号，
  只在**同一毫秒内**决定先后，保证同一批并发到达的行顺序稳定。
- **跨来源去重**：键为 `time + level + message`。launcher 转写会包含 dev 输出、
  文件被整段重读也会重复送达同一批行——没有这一步，面板条数与真实事件数对不上，
  翻页会翻出重复内容。
- **裸文本行**（读不到时刻，如子进程的普通 stdout）在解析时钳到**当时本地时刻**，
  不会因为缺时间戳被排到时间线开头（用 `00:00:00` 会）。
- **写入侧不变**：五路来源各自保持原有过滤规则（框架噪音、常规 rpc 计时、会话
  边界），排序与去重只发生在合并这一步，不改变「谁该进面板」的判据。

#### 7.17.2 读取口径：尾部窗口按行对齐且够大

`GET /api/logs/current` 在文件超过首屏窗口时只回**尾部一段**。旧实现是
128KB，而 app-runtime 的单行（时间戳 + 级别 + 命名空间 + 消息 + 字段）约
85~150 字节——128KB 只装得下约 **900~1500 行**，用户在一次会话里很容易超过它，
于是**越读越旧**、时间线从中间开始。现在：

- 窗口 `TAIL_BYTES` 提升到 1MB（约 7000~12000 行），且只读请求区间，不把整文件
  读进内存；
- 窗口起点**按行对齐**（跳过被截断的头半行），不会解析出乱码；
- 游标（客户端回传的 `size`）无效时（首帧 / 文件被新运行覆盖重建）回退到尾部窗口，
  `size` 始终是文件总长，客户端据此继续增量。

> `src/app/api/logs/current/route.test.ts` 把这三条钉成断言：改窄窗口、去掉
> 行对齐、或让游标失效时不回退，都会红。

#### 7.17.3 显示与内存解耦：分页不再只有一个「2000 条封顶页」

旧实现把 `pageSize` 直接设成内存上限（2000），于是「翻页」实际上只有一页——
用户看到的就是「锁死 2000 条、不能翻页」。

| 概念                       | 取值    | 谁在管                           |
| -------------------------- | ------- | -------------------------------- |
| 内存上限 `MAX_LOG_ENTRIES` | 2000 条 | 长跑不吃满内存（规范 07 §7.5）   |
| 每页 `LOG_PAGE_SIZE`       | 200 条  | 阅读体验（规范 07 §7.13 的分页） |

- 超上限时裁掉**最旧**的条目（不是最早到达的），保证最近的内容总在；
- 分页在**过滤后的时间线**上做，第 1 页永远是最新一段，往前翻看更早的；
- 页脚给出「第 N / M 页 · 200 条/页 · 匹配 X 条 · 面板保留最近 Y 条」——
  用户能分清「面板保了多少」和「这页在哪儿」；
- 来源筛选（应用运行 / 启动 / 启动器）+ 级别 + 搜索三者叠加，切条件时回到第 1 页。

#### 7.17.4 显示层的两道降噪

采集侧已经过滤了框架噪音与常规 rpc 计时（§7.13 / §7.14），显示层再兜两道：

- **连续重复行折叠**（`dedupeRepeats`）：同一页里连续 N 条**级别 + 内容**相同的
  行，保留前 5 条 + 一条「…（以上内容连续重复 N 次）」。只折叠**连续**重复——
  跨距离的相同行之间隔着别的事件，合并会让人把它读成「同一个事件发生了 N 次」。
  折叠只影响显示，时间线本身不动（折叠后仍需能翻页/导出全文）。
- **搜索命中高亮**：命中片段用 `mark` 标出，配合筛选让「找问题」这一步可以肉眼完成。

#### 7.17.5 「有没有新日志」的判据

历史页的内容不会因新日志而改变，用户此前只能看到「警告计数在涨、面板不动」。

判据换过三代，最终定在**窗口几何量**（#262 复审，见 §7.22）：

| 代                    | 口径                          | 为什么被换掉                                                |
| --------------------- | ----------------------------- | ----------------------------------------------------------- |
| #346                  | 末条 `seq` 变没变             | 按时刻排序后，迟到的旧时刻行会插进中间、末条不动 → 漏报     |
| #262 一轮             | `revision` + 过滤后**长度差** | 时间线**封顶**（环形缓冲 2000 条）时长度差恒为 0 → 永远报 0 |
| **#262 复审（现行）** | **窗口之后还有多少条**        | 几何量，与「谁什么时候读了什么」无关                        |

现行契约：

- 第 1 页的窗口**锚定**在「用户看过的那一段」上（`anchorId`，见 §7.22.2）：
  窗口之后的条数就是「还没看的那批」；
- 历史页则由页码算：第 `page` 页之后（更新的）整段；
- 计数要减去「翻页那一刻窗口之后本来就有多少条」（`viewBaselineAfter`）——
  否则停在第 2 页会一开口就报「有 200 条新的日志」，而那 200 条是用户自己
  翻过去的（现场实测过这个错法）；
- 页脚据此显示「有 N 条新的日志 · 回到最新」；面板不在第 1 页、或用户手动上滚
  离开底部时都显示（`selectShouldPinToLatest`），点击后回到第 1 页并贴底；
- 第 1 页且贴底时不显示（内容就在眼前，多一个按钮只是噪音）。

> `revision` 仍在（时间线真的变过没有的记录），但**环形缓冲截断不推进它**：
> 截断只是把最旧的一批挤出去，没有任何新行真正落板 (§7.22.3)。

### 7.18 「应用服务没启动 + 面板空白」的根治（#360）

用户反馈三个连在一起的现象：**应用服务没起来**、**启动很久还没起来**、**日志面板
是空的**。这不是一个 bug，而是「失败在观测通道之外」的一族问题。逐个成因与修法：

#### 7.18.1 面板为什么可以先什么都不说清

面板只轮询**三路**文件：`launcher` / `dev` / `app-runtime`。而下面这些都是**不在
这三路里**的：

| 现场                                                                 | 落在哪                                    | 此前面板能看到吗 |
| -------------------------------------------------------------------- | ----------------------------------------- | ---------------- |
| Next dev server 首屏编译错误、`FATAL: An unexpected Turbopack error` | `log/nextjs/nextjs-stderr-<ts>.log`       | ❌               |
| 未捕获的服务端异常、pino 的 ERROR 行                                 | stdout / `nextjs-stdout-*` + `log/nextjs` | ❌               |
| 面板的数据源本身不可达（应用服务挂了 / 还在编译）                    | 只体现为 fetch 失败                       | ❌（静默 catch） |
| 应用服务换了一个进程（重启 / 另一实例接管端口）                      | 无从判断                                  | ❌               |

于是「应用服务没起来」时用户打开面板看到的是**空白**——比没有面板更难排查，
因为空白同时兼容「真的没问题」与「观测链路断了」两种解释。

#### 7.18.2 修法：把应用服务自己的输出接进面板（新增第 4 路 `app`）

- **转录**：`src/lib/capture-streams.server.ts`（Node-only）在服务端进程启动时
  （`src/instrumentation.ts` 的 nodejs 分支，动态 import）把 `process.stdout` /
  `process.stderr` 的每一 chunk **额外**转录到
  `log/nextjs/nextjs-panel-<bootId>.log`。转录不是接管：`process.stdout.write`
  直接写 fd 1、不经过 console，因此终端输出、dev-launcher 的 redirect 文件、
  既有 `console.*` 拦截全部行为不变（有回归用例锁住）。
- **轮询**：`GET /api/logs/current?source=app` 读这份转录（按次命名取最新一份，
  保留最近 5 份，与 dev-launcher 清理 `nextjs-stdout-*` 的口径一致）；面板把它作为
  第 4 路来源，筛选项里叫**「应用服务」**（与「应用运行」= app-runtime 区分开）。
- **pino ERROR 镜像**：`src/server/lib/logger.ts` 的 `hooks.logMethod` 在
  `levelNum >= 50` 时把同一条 ERROR 镜像进 app-runtime（面板可见）。只镜像 ERROR：
  INFO/DEBUG 高频，进面板会把真正的问题挤出视野。敏感字段在 pino 的 `redact`
  层已经擦掉，镜像只取 `msg` / `err.message` 文本，不整包透传。

> **四种调用形态都要取得到正文**（ISSUE #440）：pino 的签名有
> `log.error(obj, msg)` / `log.error(msg)` / `log.error(obj)` / `log.error(msg, ...args)`
> 四种。镜像曾只认第一种——**第一个参数不是对象时整条正文被丢弃**，面板里只剩
> 一句无信息的「服务端错误」（`[app] 服务端错误 {"ns":"server"}`）。而仓库里
> 多条真实调用正是字符串形态（`logger.error("[upload] 503 …")`、
> `logger.error(\`❌ tRPC failed on …\`)`），这些失败的具体原因在面板里全部丢失。
现在字符串参数本身就是文案，对象参数才走字段提取；命名空间依次尝试对象里的
`ns`/`event`与字符串形态的第二参数，再回落`server`。**新增日志时不必迁就
镜像去写「对象 + msg」**——两种形态等价，别为了绕开旧限制把可读文案拆散。
回归用例见 `src/server/lib/logger.test.ts` 的「字符串形态的 ERROR 也要带正文」。

> 判据：**新增一个「会导致操作失败但没人看得见」的系统时，必须同步回答
> 「它的输出落在面板的哪一路」**；答不上来就先别加。

#### 7.18.3 空白必须自我说明：不可达与无内容要分开

面板此前的 `catch` 是静默的（「开发服务器尚未就绪时静默忽略」）。这条注释在
**启动阶段**成立，在**运行阶段**就是「把观测链路断了这件事藏起来」。现在的契约：

| 情形                                | 面板里的表现                                                                                                |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 本次运行确实还没有输出              | 空列表（正常，空态文案已说明）                                                                              |
| 拉不到日志（接口 5xx / 网络层失败） | 一条 **warn**：「日志面板暂时读不到日志：应用服务（Next dev server）当前不可达」+ 常见原因 + 去哪看启动日志 |
| 恢复后又断了                        | 只在**状态翻转**时写一条（不刷屏）；恢复时补一条 info                                                       |

#### 7.18.4 服务重启必须可见：`bootId` 贯穿三处

「应用服务没启动」的另一半是「它到底起没起、起了几次」。三个进程（浏览器 / Next
dev server / 桌面壳）各自持有不同的会话概念，此前没有任何一个标识能回答
「当前回答我的是哪个应用服务进程」。现在：

- **来源**：复用 `src/lib/dev-server-id.ts` 的 `getServerBootId()`（进程冷启动即
  重新生成，模块级缓存）。
- **下发**：`GET /api/logs/current` 的**每个**响应都带 `bootId`；客户端带上上一轮
  的 `bootId`，若与当前不一致则响应 `mismatch: true` 并**从头上读**（旧进程的字节
  游标不能用来切新进程的文件）。
- **消费**：`LogProvider` 在 `bootId` 变化或 `mismatch` 时 `setBootId()` 清空时间线、
  重置全部来源的游标（`src/components/studio/logs/log-store.ts`）——否则重启前后的
  行会混成一条线，看起来就是「重启后什么都没有」。
- **展示**：面板页脚常驻「服务 <短标识>」徽标。用户报障时可以准确说出自己连的
  是哪个进程，也让「重启后时间线被重置」这件事自解释。

#### 7.18.5 设置页：一次读失败 ≠ 界面不可用

设置页原来的状态机只有三态：加载中 / 失败（整页错误视图）/ 就绪。而它的两份读
（`setting.get` 走 SQLite、`llm.configGet` 还要先跑 remote storage 迁移）恰好是
服务端最脆弱的两跳——应用服务刚重启、编译中、或数据库迁移的那几秒里失败是**常态**。

改动（`src/app/(main)/settings/hooks/use-settings-page.ts`）：

- 新增 `lastGood`（渲染期 derived state，首值取 sessionStorage 快照）：每次成功
  读到配置就记下；**查询失败且草稿为空**时用它兜底播种，界面照常渲染；
- 新增 `serveState`：`queryFailed && drafts` 时非空，视图在顶部渲染一条**非阻塞**
  提示条（「本次未能读取最新配置，界面显示的是上一次成功读取的内容」+ 原始原因 +
  「重新读取」）；
- `hasError` 收窄为「失败 **且** 连兜底草稿都没有」——只在真的无从渲染时才整页降级；
- API Key 输入态**不进**缓存（它始终从空开始）。

分工一句话：`hasError` = 打不开（全页错误视图）；`serveState` = 打开了但可能不是
最新的（提示条）。新增查询时按同一口径决定它属于哪一类。

#### 7.18.6 启动页：空白也要给出下一步

`src-tauri/splash-assets/`（三份副本同步：`index.html` / `{{shell.splash}}` 与
`public/{{shell.splash}}`，改完必须重编壳，见硬规则 5）：

- 面板**打开即预热一次**（点击时立刻有内容，而不是先空白几十毫秒）；
- 连续取不到日志时区分两种成因并给出可执行指引（日志还没产生 → 稍等并看
  `run/launch-status.json` 与 `log/launcher/`；命令不可用 → 壳版本过旧，重编命令）；
- 等待超过 90 秒时，消息里直接写「可点查看日志 / 看 `run/launch-status.json`」——
  启动页是用户此刻唯一能看到的界面，只显示一个转圈的秒数等于让人干等。

#### 7.18.7 启动页的宽度就是日志的宽度（#397），但窗口不该比内容大（#412）

> 两节同一条契约的两个方向：**日志宽度要够**（#397）与**窗口不要比内容大**
> （#412）。#397 把窗口从 1280 放宽到 1680，解决了「日志挤在中间被切成两截」；
> 但 1680×1000 的窗口配上 720 宽的卡片，在 2K/4K 屏上就变成「一大半是空白」——
> 用户看到的是「外部一大块没用空白区域」。现在的解是**两档尺寸 + 无边框**：
> 开窗就是紧凑档（内容多大窗口多大），展开日志时窗口跟着内容一起长大。

「日志看不到」有两种：**读不到**（上一节）与**看不清**。这一节是后者：面板一直
能拿到日志，但面板整个塞在一张 520px 宽的卡片里，而窗口开着 1280px——**窗口
三成半的宽度空着，日志却挤在中间**。壳日志一行常在 130~160 字符，11px 等宽字
在 520px 卡片里一行只放得下约 65 字符，于是每一行都被切成两截。

宽度在这里不是审美，是**契约**：日志面板是「一行一条、不折行」的布局
（`white-space: pre` + 横向滚动），一行能读多少字符**只由卡片宽度决定**。
因此三处一起定：

| 参数                         | 值                     | 作用                                               |
| ---------------------------- | ---------------------- | -------------------------------------------------- |
| splash 窗口 · 紧凑档（开窗） | 744×216（min 620×180） | **窗口即内容**：收起日志时刚好装下进度与状态       |
| splash 窗口 · 展开档         | 1424×788               | 展开日志时窗口跟着长大，日志一行能读全（#397）     |
| 面板铺满窗口                 | 100vw × 100vh − 内边距 | 不再有固定宽卡片，窗口边缘就是内容边缘             |
| 日志面板高度                 | 不写死，`flex: 1`      | 展开后由窗口高度决定显示多少行，不在面板下方留空白 |
| 窗口装饰                     | `decorations: false`   | 无原生标题栏；最小化/关闭由启动页右上角按钮提供    |

两档尺寸**只在壳里各写一份**（`src-tauri/src/lib.rs` 的 `SPLASH_WINDOW_SIZE` /
`SPLASH_WINDOW_SIZE_EXPANDED`）：页面只把「展开 / 收起」告诉壳（应用命令
`set_splash_compact`），不自己拼尺寸——两处各写一份常量，改一处就会露出空白或
裁掉内容。新增应用命令同样要三处同步（`build.rs` 的 AppManifest、
`capabilities/splash.json`），否则运行期报 `not allowed by ACL`。

两条容易踩的：

- **窗口尺寸必须按显示器收敛**（壳侧 `clamp_to_monitor`）：两档都是静态常量，
  1366×768 笔记本或 1080p 开了高缩放时固定值会把窗口推出屏幕外——「日志看不全」
  换成「按钮点不到」并没有更好。
- **别只改 `{{shell.splash}}`**：三份副本必须逐字一致（`build.rs` 会用
  `public/{{shell.splash}}` 覆写 `splash-assets/` 下两份，不一致就是构建期漂移）。
  「日志不折行」与「横向滚动」这两条曾在一次「同步三份副本」的改动里被一并删掉
  （等于怎么加宽都白搭）——判据因此写进了 `tests/check-file-structure.test.ts`：
  紧凑档够小、展开档够宽、两档都过显示器收敛、面板不写死高度且吃掉剩余空间、
  三份副本必须一致、不折行与横向滚动必须保留、无边框窗口必须自带最小化/关闭。
- **`decorations: false` 是有代价的**：没有系统标题栏，就没有系统的最小化/关闭
  键，也没有拖拽区——启动页必须在右上角自绘最小化/关闭（`-webkit-app-region:
drag` 铺满标题行、按钮用 `no-drag` 排除），否则用户只能靠任务栏或强杀进程。
  这是「去掉原生标题栏」那一行的必配项，不是可选装饰。

> 排查入口不变（`launch-and-build.md` §4）：先看启动页面板，再看
> `log/launcher/` 三份，最后看 `log/nextjs/nextjs-panel-<boot>.log`（应用服务自己的
> 输出，也是面板「应用服务」那一路的数据源）。

### 7.19 面板计数必须分来源，并且一眼看得出警告与错误（#360）

接着 §7.18：面板终于能拿到应用服务的输出了，但用户随即发现**读数本身没法信**：

- 「启动器和启动页签的日志内容是空的」——切到「启动器」来源，里面确实没有警告；
- 「现在这里显示的是所有日志的总数，每一个分类有多少不直观，筛选不同类型时，
  看着警告有很多，切换过去结果显示是空的，这一类型就没有警告」；
- 期望：「一眼就能看出来某个类别有多少警告，多少错误」。

根因不是数据错，而是**计数只有一个维度**：`counts` 是全部来源的合计，来源下拉里
只有名字没有数。于是「全部来源 · 警告 974」与「启动器 · 0 条」在界面上无法区分——
用户切过去看到空列表，第一反应是「日志丢了」，而不是「那 974 条在别的来源里」。

#### 7.19.1 二维计数：来源 × 级别

`log-store.ts` 新增 `computeOriginCounts(logs)`，产出
`LogOriginCounts = Record<LogOriginFilter, LogLevelCounts>`：

| 约定                 | 说明                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| key 就是筛选值       | `all` + 四个来源、每项含 `all` + 四个级别；视图直接 `countsByOrigin[origin][level]` 取，不在视图里换算                                 |
| 逐来源独立           | `launcher.warn` 只数 `origin === "launcher"` 的行；`all` 才是全量                                                                      |
| 无来源的行只进 `all` | console 拦截 / Tauri 事件 / 全局错误本来就不属于任何文件来源                                                                           |
| 与搜索同口径         | 计数和 `computeFiltered` 共用一个 `matchesSearch`：搜索命中的行才计数。两处各写一套规则就会出现「按钮写着 2、切过去只剩 1」（§7.20.3） |

派生字段随每次时间线变化（`derive()`）统一重算，与 `counts` 同源同时机，
两条口径不会漂移；`clear()` / `bootId` 重置后同样归零。

#### 7.19.2 显示：三处都带数，且与内容对得上

`LogPanel.tsx`（排布细节与「为什么是这副样子」见 §7.20）：

- **级别按钮**：数字取**当前来源**（`countsByOrigin[origin]`），与右边来源列表
  同口径——切来源时按钮上的数跟着变。warn / error 非零染级别色，零条目保持灰色
  `0`（**显示而不是隐藏**：`0` 与「列表为空」互相印证，正是用户要的答案）。
- **来源列表**：每个候选一行，行内是「条数 / 信息 / 警告 / 错误」四列定宽数字
  （零条目写「—」），切换之前扫一眼就是一张表。
- **标题旁常驻徽标**：`<当前来源> · <总数> · 警告 <n> · 错误 <n>`。此前这里只显示
  错误数，警告再多也看不见。

> 判据：**筛选器上的数字必须与切过去之后的内容一致**。只给「全部」一个总数，等于
> 让用户自己去做减法——而用户看到的信息是「警告很多但这一栏是空的」，只会得出
> 「日志不可信」的结论。

#### 7.19.3 分层与测试

计数是第①层纯函数（`computeOriginCounts`），视图只做映射（规范 17 §17.2）。

- `log-store.test.ts`：逐来源独立计数、无来源行只进 `all`、「某来源没警告是真 0」
  （不继承全局数）、空表结构完整、store 在时间线变化后重算；
- `LogPanel.test.tsx`：来源列表每项自带四个计数、级别按钮随来源切换同步变化
  （切到零警告来源时按钮是 `0` 且列表确实为空）、标题徽标常驻汇总、
  计数随搜索收窄、页脚的回滚入口（见 §7.20.4）。

### 7.20 面板排布返工：四列对齐、标签在上数字在下、收起态不重复报数（#360 复审）

§7.19 把「数」补齐之后，用户对**摆法**又提了四条，全部是「信息都在，但挤在一起
读不出来」。这一节记录最终排布与背后的取舍——再动 `LogPanel` 的头部/页脚时按它来。

#### 7.20.1 来源列表是自绘的四列表格，不是原生 `<select>`

原生 `<option>` 只能给一行**纯文本**，字体与列宽由操作系统决定：`应用服务 ·
1769 条 · 信息 1769` 与 `启动 · 46 条 · 信息 46` 里的冒号、数字必然参差，读起来
就是「对不齐」。

因此来源筛选改用 `~/components/ui/select`（base-ui）。**收起态（扳机）只写当前
来源的名字**——多少条、多少警告在左边级别按钮和标题徽标上已经有了，这里再报一遍
既重复又把本就紧张的行头再挤掉一块。**展开后的候选列表**才是「切换之前先看行情」
的地方，每行四列：

```
        来源        条数   信息   警告   错误
      全部来源      1822   1821     1     —
      应用运行         1      —     1     —
      应用服务      1769   1769     —     —
```

- 四列**定宽（`w-14`）+ 右对齐 + `tabular-nums`**：宽度随内容变的数字排在一起
  必然参差，定宽是「像表格」的全部要点；
- 列标题写一次在表头，行内不再逐格重复「信息 / 警告」两个字；
- 零条目写 `—`（不是 `0`）：`0` 与「这一格没有东西」长得一样，而这里要表达的正是
  「这个来源没有警告」这个**结论**；
- 每行额外带一份 `sr-only` 纯文本摘要（`3 条 · 信息无 · 警告 2 · 错误 1`）：
  屏幕阅读器与测试都读它，自绘列只是视觉产物。

#### 7.20.2 级别按钮：标签一排、数字一排（**已被后续两轮取代**）

`全部 / 调试 / 信息 / 警告 / 错误` 五个按钮当时改成定宽（`w-8`）的**纵向两行**：
标签在上、数字在下。

> **这一条不再是现状**：`w-8` 随后被 §7.23.2 推翻（按钮整组 `flex-1`、等分富余
> 宽度才是用户要的「可以占用大些空间」），纵向两行又被推翻为**同行**（标签在左、
> 计数在右）。`警…` 这个省略号正是 `w-8` 时代的遗留——§7.24.3 用 `min-w-fit`
> 与 `w-[4ch]` 把「文字 + 四位数字」定为不可压缩的预算。读这一节只当历史。

#### 7.20.3 计数与过滤同口径

计数回答的是「**现在**能选到什么」。`computeCounts` / `computeOriginCounts` 与
`computeFiltered` 共用同一个 `matchesSearch`：搜索时只数命中的行。两处各写一套
匹配规则，就会出现「左边写着警告 2、切过去只剩 1」——那比不显示数字更让人怀疑面板。
页脚因此也跟着改口径：有搜索词时写「筛选命中 N 条」，无搜索词时才是「匹配 N 条」。

#### 7.20.4 页脚写出「正在看哪一段」，并且能一键去掉

页脚原来在分页按钮中间显示来源名，级别与搜索词则完全不可见。现在它是一行**当前
视图的回滚入口**：`全部来源 · 全部 · 搜索「x」`，每一项点一下就去掉那一层筛选
（已生效的项可点，未生效的项禁用且不带 hover）。

它同时解决了行头变窄的代价：筛选器不再需要在收起态报告自己过滤了多少条——「我在看
什么」在页脚，「有哪些可选」在展开的列表里。

#### 7.20.5 一层状态切片：`header`

面板此前在视图里用 `useShallow` 现拼自己要的状态。这有两个问题：视图层出现状态
拼装（规范 17 的分层里不该有），以及**多一处会漂移的中间量**——有一条写入路径漏带
视图状态，面板就继续渲染旧快照（「切了来源却像没切」）。

现在 store 维护一个 `header: LogPanelSlice` 切片（`filteredLogs` / `filter` /
`origin` / `search` / `isOpen` / 两个计数表 / `page` / `pageSize` / `bootId`），
与派生字段在 `applyView()` 里**一次写入**，面板只订阅这一个字段（`state => state.header`）。
新增改视图状态的写入路径时，一律经 `applyView`，切片就不会漏项。

> 注意：`header` 与顶层那几个字段（`filter` / `page` / `isOpen` …）是同一份数据的
> 两个视图，**测试夹具必须同时复位**；只重置顶层字段，面板会继续渲染旧切片。

  候选列表四列各自的数。**真正展开下拉的用例刻意只有一条且排在最后**：base-ui 的

  弹层宿主（只影响测试环境，浏览器里过渡正常结束）。
- `log-store.test.ts`：计数与 `filteredLogs` 同一口径（搜索命中时才计数）。

### 7.21 面板内下拉的层级契约：弹层必须盖过面板遮罩（#262 再审）

§7.20 把来源筛选做成自绘下拉之后，用户仍报三个现象，而且都指向同一处：

- 「点击下拉看不到下拉菜单」——看着像没弹出来；
- 「没办法切换日志类型」——点不到任何候选；
- 「日志没法翻页了」——翻页按钮像失灵。

**这不是三个 bug，是一个**：面板自己是一层**模态遮罩**（`z-99`），而面板里的下拉走
base-ui 的 `Portal`，弹层被挂到 `document.body` 下、与遮罩**平级**，shadcn 的 Select
默认只给定位层 `z-50`。于是弹层**照常渲染**（截图里看得到、DevTools 里也在），却整块
压在 `z-99` 之下——指针事件全落在遮罩与日志行上，弹层收不到任何点击。

用户读到的「看不到菜单」是弹层被盖住的外观，读到的「切不了 / 翻不了页」是同一个原因
的交互后果（点击没落到目标上）。

#### 7.21.1 契约：弹层定位层的 z 必须**严格高于**遮罩

层级必须给在**定位层**（`positioner`，Portal 的宿主），不是 Popup：Popup 自己的
`z-50` 只在定位层建立的 stacking context **内部**比较，改它越不出这一层。

本仓库把这条写成可断言的常量（`src/components/studio/logs/log-panel-layers.ts`，
第①层纯派生，无 React 无 DOM）：

| 常量                          | 值       | 用途                     |
| ----------------------------- | -------- | ------------------------ |
| `LOG_PANEL_OVERLAY_Z`         | 99       | 面板模态遮罩             |
| `LOG_PANEL_POPUP_Z`           | 199      | 面板内 portal 弹层定位层 |
| `isPopupLayerAboveOverlay(z)` | `z > 99` | 判据（**相等也算违规**） |

`SelectContent` 因此新增 `positionerClassName` 透传口子（`src/components/ui/select.tsx`），
调用方（`LogPanel` 的 `OriginSelect`）按契约传 `LOG_PANEL_POPUP_Z_CLASS`。
默认仍是 `z-50`——不在模态遮罩里的普通下拉不需要更高层级。

> 为什么要求**严格**大于：同 z 时层叠顺序由 DOM 决定，弹层先挂、遮罩后挂就必然被盖住。
> 「有时候点得动、有时候点不动」比稳定失效更难查，契约直接把相等归为违规。

#### 7.21.2 标题徽标不再复述来源与总数（**已被 §7.24.1 取代**）

同一次反馈里的「红框中两部分重复了」指头部右边那块胶囊：它写着
`全部来源 · 1822 · 警告 1 · 错误 1`。当时把它减到「只报警告与错误、全为零不渲染」。

> **这一条不再是现状**：减过之后它仍与级别按钮上的同名计数重复（同一项数据的
> 两次渲染），用户五审时又圈了一次。§7.24.1 把**整块删除**，计数只留级别按钮
> 一处。读这一节只当历史。

#### 7.21.3 测试：为什么必须有一条不靠 jsdom 的

jsdom 不做布局与层叠，也**不实现 `elementFromPoint`**——「弹层画出来了但被遮罩压住」
在 jsdom 里与正常弹层完全无从区分。所以这里用两层：

| 层                      | 文件                       | 断言什么                                                                                              |
| ----------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------- |
| 单元（jsdom）           | `log-panel-layers.test.ts` | 常量关系（严格大于、相等/Nan 判违规）、class 与常量一致、解析器只认纯数字 `z-<n>`（对齐规范 03 §3.2） |
| 单元（jsdom）           | `LogPanel.test.tsx`        | 面板实际把契约 class 传给了**定位层**（Popup 的父节点），且遮罩用的是同一份常量                       |
| 端到端（真实 Chromium） | 见 §7.21.4                 | `elementFromPoint` 命中弹层、点得动候选、切完来源能翻页                                               |

#### 7.21.4 现场复核方式（真实浏览器）

这类问题**不能用单测证明**，复核时按下面的步骤在真实 Chromium 里量：

1. 用 `@tailwindcss/postcss` 从 `src/app/globals.css` 编译出真实 CSS
   （Tailwind 会 warn 未知工具类但不阻断，产物里若缺某条规则，样式就静默失效）；
2. `esbuild` 打包一个只渲染 `<LogPanel />`（pre-seed store）的页面；
3. Playwright 打开后：点开来源下拉 → 在弹层矩形内多点 `document.elementFromPoint`
   （含四个角与中点），断言命中都在弹层子树内；再真的点一个候选、切完来源后点
   「更早的一页」，断言来源切换与翻页都生效。

修复前后在同样的步骤下：修复前所有采样点命中遮罩 / 日志行，点击候选会一直
「被其它元素拦截」（Playwright 的报错原文即 `<div class="flex items-start …"> from
<div id="root"> subtree intercepts pointer events`），切不了来源；修复后采样点全部落在
弹层内，候选可点、来源可切、翻页正常。

> 顺带钉住一条容易踩的级联陷阱：`SelectContent` 的 `w-auto min-w-max` 与默认的
> `w-(--anchor-width)` 都是**同权重单类**，生效的是**后出现**的那条（Tailwind 按
> 属性/工具类顺序产出）。上表里的四列布局依赖 `w-auto min-w-max` 最终生效；去掉
> `w-auto` 会让弹层被压回扳机宽度（约 90px），四列数字挤成一团——而单测看不出宽度。

### 7.22 面板排布与滚动的返工：下拉归位、翻页恢复、内容不再自己动（#262 三审）

§7.21 解决「弹层被遮罩压住」之后，用户又提了四条，看上去是四个小毛病，
其实是**两处结构性问题**加两处排布问题：

| 用户原话                                                                                                       | 性质   | 根因                                                                    |
| -------------------------------------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------- |
| 「下拉右侧有很多空白，需要让下拉移到右边，给左边的日志类别和条数留下较大空间」                                 | 排布   | 搜索框吃了 `ml-auto`，把下拉顶在级别按钮旁边，多出来的宽度全留在中间    |
| 「下拉顶在窗口最上方，要让它和下拉按钮底边对齐」                                                               | 排布   | `alignItemWithTrigger` 让弹层去覆盖扳机；头部贴着窗口顶端时只能向上生长 |
| 「日志这里没法翻页」                                                                                           | 结构性 | 「有新日志」的计数在**封顶时恒为 0**，页脚那个出口永不出现              |
| 「日志到上限还继续产生新内容，面板不断移动，想复制某一项十分困难，甚至无法选择，刚选择就刷新把我的选择弄没了」 | 结构性 | 第 1 页窗口随新日志整体前移 → React 卸载首行节点 → 选区随节点消失       |

#### 7.22.1 行头：计数在前，搜索与下拉一起靠右

`.h-12` 行头的 DOM 顺序现在是：

```
[标题 + 警告/错误徽标] [级别按钮×5（类别 + 计数）] [flex-1 空白] [搜索框] [来源下拉] [操作按钮]
```

要点是那个 `flex-1` **必须在搜索框之前**。放在它后面（或干脆不给，只让搜索框继续
吃 `ml-auto`）都等于什么都没改：搜索框留在原位、空白挪到右边，用户看到的那块红框
一点没少。判据写进了 `LogPanel.test.tsx`（DOM 顺序）与 e2e（`boundingBox().x` 顺序

- 级别按钮与下拉之间的间距 > 120px），因为这类问题**单测量不出宽度**。

#### 7.22.2 下拉弹层：与扳机底边对齐，且不向上翻转

两条一起改才成立：

| 参数                   | 值                 | 作用                                           |
| ---------------------- | ------------------ | ---------------------------------------------- |
| `alignItemWithTrigger` | `false`            | 弹层不覆盖扳机，从扳机**下面**开始             |
| `collisionAvoidance`   | `{ side: "none" }` | 撞到视口底部也**不翻到上面**，改为滚动弹层自身 |

`SelectContent` 因此新增 `collisionAvoidance` 透传口子（`src/components/ui/select.tsx`），
默认行为不变（普通下拉照旧会自动翻转）。于是弹层顶边恒等于扳机底边
（`sideOffset` 4px），**与窗口位置无关**——这正是用户要的那句「弹出下拉菜单的最上方
和下拉按钮的最下方对齐即可」。

`SelectPositioner` 会把定位结果写在定位层的 `data-side` / 弹层的 `data-align-trigger`
上，因此这两条在 jsdom 里就能断言（§7.22.5）；真实坐标由 e2e 量。

#### 7.22.3 第 1 页锚定窗口：内容不再自己动，选区不再被冲掉

这是本轮最深的一处。第 1 页原本取时间线的**尾部 200 条**，而日志每 2s 轮询一次：

- 每来一条新行，这 200 条的窗口就**整体前移一格**；
- React 于是卸载最上面那一条、挂上新的最末一条；
- 用户框在首行里的文本**随节点一起被卸载**——**滚动位置甚至没动**，选区就没了。
  这正是用户说的「刚选择就刷新把我的选择弄没了」（在真实 Chromium 里量到的就是这个，
  不是滚动造成的）。

修法是给第 1 页一个**锚点**（`LogStoreState.anchorId`）：

| 概念                                              | 含义                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------- |
| `anchorId`                                        | 用户「正在看的那一段」的头一条 id                                   |
| `selectFirstPageWindow(logs, anchorId, pageSize)` | 以锚点起取 200 条；返回 `truncatedFromEnd` = 窗口之后（更新的）条数 |
| 重取时机                                          | 打开面板 / 点「回到最新」 / 换页 / 切筛选 / 搜索 / 用户自己滚到底部 |

锚定之后窗口原地不动、DOM 节点不重建，**选区自然留住**；想追最新可以亲手往下滚，
也可以点页脚那个出口。

配套的两条：

1. **贴底只追到基线**（`followBaseline`）。旧行为是「时间线一变就
   `scrollTop = scrollHeight`」，判据没错、错在它**每两秒就成立一次**：内容每隔两秒
   整体上移一次，用户刚框住的文本立刻被滚走。现在贴底改为按
   `data-log-index` 滚到「已看过的那一条」，新行在下面累积。
2. **正在框选就什么都不做**（`selectionInsideLogs`，在 `log-row-style.ts`，
   第①层纯函数）。贴底前问一句选区是否落在 `[data-log-text]` 子树里，
   是就跳过这次滚动——拖动过程中浏览器会随滚动改锚点，滚动会直接打断框选。

三层各挡一类：**窗口不重建**（根治）→ **滚动不追新**（防内容整体移动）→
**框选期间不滚**（防打断拖动）。前两层在 store，第三层在视图。

#### 7.22.4 环形缓冲截断不推进 `revision`

`appendFileLogs` 判断「有没有新行落板」用的是**身份**，不是长度：

```ts
const landed = new Set(logs.map((e) => e.id));
const hasNew = fresh.some((e) => landed.has(e.id));
```

不能用「长度有没有变」：时间线封顶后，新行会顶掉同样多条最旧的行，长度恒等于
`MAX_LOG_ENTRIES`——明明有新日志，长度却说他「没有」。这一条同时决定两件事：

- `revision` 只在真的落了新行时推进；
- 贴底基线的推进同样只认新行，内容不会被每两秒一次的轮询反复拉动。

#### 7.22.5 测试：哪一层能证明什么

| 层                      | 文件                         | 断言什么                                                                                                                                                                                        |
| ----------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单元（jsdom）           | `log-store.test.ts`          | 锚定窗口不动 / `truncatedFromEnd` 递增 / 锚点被挤出时退回尾部窗口；截断不推进 `revision`；基线只由显式动作推进；「有 N 条新的日志」按窗口计数（含封顶场景）                                     |
| 单元（jsdom）           | `log-row-style.test.ts`      | 选区判定的五种形态（行内文本 / 行元素 / 别处文本 / 折叠光标 / 取不到选区）                                                                                                                      |

### 7.23 面板四审：启动/启动器日志丢失 + 级别筛选与行头空白（#262 四审）

用户这一轮说了两件事，各自有独立的根因：

| 用户原话                                                               | 性质   | 根因                                                                                                  |
| ---------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------- |
| 「启动和启动器日志丢失」                                               | 结构性 | 会话起点被当成**整条时间线**的裁剪线，而启动器的头几行写在锚点（`dev-launcher.log` 的 mtime）**之前** |
| 「顶部还有较大空白区域，全部/警告/错误这些挤在一起，可以占用大些空间」 | 排布   | 五个筛选按钮被钉在 `w-8`，行头富余宽度被一个**无名** `flex-1` 空白 div 吸走                           |

#### 7.23.1 会话裁剪逐来源判定：覆盖重建的来源不参与

`dev-launcher.log` 的 mtime = 本次启动时刻（§7.15），但启动器进程
（`start-tauri-launcher.log`）在它被创建**之前**就写下了 python / exe / cwd /
探测 Node 这些行。拿这个起点去裁**整条时间线**，这些本次启动最早、最该被看到的
行会被当成「上一次运行的残留」丢掉——面板上「启动」「启动器」两个来源恒为空，
正是用户读到的「启动和启动器日志丢失」。

| 来源                                     | 文件形态                                                                     | 是否参与裁剪 |
| ---------------------------------------- | ---------------------------------------------------------------------------- | ------------ |
| `app-runtime`                            | 追加写、不轮转，混着前几次运行                                               | **是**       |
| `app`（`nextjs-panel-<pid>-<ts>.log`）   | 按进程命名，但服务端取「目录里最新的一份」，本次未落盘时会读到上一进程的文件 | **是**       |
| `launcher`（`start-tauri-launcher.log`） | 每次运行覆盖重建（`open(..., "w")`）                                         | 否           |
| `dev`（`dev-launcher.log`）              | 每次运行覆盖重建                                                             | 否           |
| console / tauri / system                 | 运行期生成，时刻即「现在」                                                   | 否           |

判据收在 `log-store.ts` 的 `isSessionScopedOrigin` 一处（可独立断言），
`dropStaleEntries` 逐条问它；服务端 `/api/logs/current` 的 `resumable` 分支
（此前算了却没人用）同步只对累积来源下发 `sessionStart`。**两层都要兜**：
服务端没给起点时客户端不该裁覆盖重建的来源，服务端给了起点时同样不该裁
（`LogPanel`/store 的用例把两条都钉住）。

> 为什么不能「服务端不给起点就完事」：`app` 来源需要起点（可能读到上一进程的
> 文件），因此起点是**逐来源**的属性，不是一个全局开关。

#### 7.23.2 行头：筛选按钮整组吃掉富余宽度，不留无名空白

DOM 顺序（沿用 §7.22.1 的分工）：

```
[标题] [级别按钮×5（flex-1 容器，每钮 flex-1 basis-0）] [搜索框] [来源下拉] [操作按钮]
```

三条要点，缺一不可：

1. **按钮等分容器**：每个按钮 `flex-1 basis-0`（不再是 `w-8`），标签与计数
   **同行**排布、按钮 `h-9` 吃满行头（此前 48px 行头里塞两行文本，按钮只有
   32px 高）。
2. **容器自己就是那块弹性空间**：它 `flex-1`，因此右侧那组被顶到最右。
   **不要再加第二个 `flex-1` 空白 div**——两个 `flex-1` 会平分富余宽度，
   等于把一半空间又还给空白（用户看到的红框就是这么来的）。
3. **`min-w-56` 是折行判据**：`flex-wrap` 的换行单位是容器本身，可用宽度不足
   224px 时五个按钮整组落到第二行并吃掉整行宽度。比「每个按钮各自 `min-w` 后
   硬挤」好在：无论多窄，标签都保持可读，不会退化成只剩一列竖字。

#### 7.23.3 测试：哪一层能证明什么

| 层                      | 文件                         | 断言什么                                                                                                                                                                                 |
| ----------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单元（jsdom）           | `log-store.test.ts`          | `isSessionScopedOrigin` 的判据表；launcher / dev 的行早于起点仍保留；跨运行来源的旧行被裁；同 batch 里两类各按各的规则                                                                   |

### 7.24 面板五审：计数只留一处，级别色给标签文字（#262 五审）

用户这一轮给了一张行头特写，说了三句：

| 用户原话                                                                         | 性质   | 根因                                                                                                                   |
| -------------------------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------- |
| 「警告/错误显示重复了，左侧那两个去掉」                                          | 冗余   | 标题旁那块灰底胶囊写的 `警告 n · 错误 n` 与级别按钮**同源**（同一个 `originCounts`），同一项数据两处出现               |
| 「右侧的警告文字改成黄色，错误改成红色」                                         | 可读性 | 级别色此前只落在**数字**上（`CountChip` 的 `alarming ? "· n"` + 级别色），标记词「警告」「错误」本身是灰的             |
| 「每个都保留显示文字和四位数字的宽度即可。不要因为宽度不够导致文字显示成省略号」 | 布局   | 截图里的 `警… 539`：按钮 `min-w-0` + `overflow-hidden` + 标签 `truncate` 三者叠加 → 标签被切成省略号、数字被挤到下一行 |

#### 7.24.1 一项数据只说一次

标题旁那块胶囊从 §7.21.2 起已被减到「只报警告与错误」，但它与级别按钮仍然是
**同一组数字的两次渲染**。用户圈出的「重复」就是它。现在**整块删除**：

| 信息                    | 唯一出口                  |
| ----------------------- | ------------------------- |
| 各类别条数（含 `全部`） | 左侧五个级别按钮          |
| 完整分类数（含 `信息`） | 各按钮的 `title` 悬浮说明 |
| 当前来源                | 右侧来源下拉的扳机        |
| 分页与保留量            | 页脚                      |

行头第一行因此只剩「标题 + 五个按钮 + 搜索 + 下拉 + 操作」，标题行的横向空间
不再被一个恒在的徽标吃掉。

#### 7.24.2 级别色给标签文字，不给数字

配色表 `LEVEL_LABEL_STYLES`（`LogPanel.tsx`）：

| 级别    | 类               | 说明                     |
| ------- | ---------------- | ------------------------ |
| `all`   | `text-gray-100`  | 中性                     |
| `debug` | `text-gray-500`  | 中性                     |
| `info`  | `text-cyan-300`  | 与日志行正文的 info 同色 |
| `warn`  | `text-amber-300` | **黄**（用户明写）       |
| `error` | `text-rose-300`  | **红**（用户明写）       |

三条口径：

1. **颜色挂在按钮上、由标签文字继承**，不挂在数字上。用户扫的是「警告」这两个字；
   数字（`4ch` 定宽）固定 `text-gray-600` 中性灰，避免一行里出现两个互相稀释的
   高亮块。
2. **`CountChip` 不再接收 `level`**：它过去按级别给数字染色（`error` 红 / `warn` 黄 /
   其余灰）。颜色职责移到标签后，这个参数就是死代码——留下来只会让下一个人以为
   数字也该带色。`LogLevel` 的导入也因此从「给 Chip 用」变成只在候选列定义里用。
3. **零条目也着色**：它表达的是「这一格是警告」，不是「这里有 0 个问题」。
   「有没有问题」由同一格里的数字回答（`0` 与「切过去是空的」互相印证）。

#### 7.24.3 「文字 + 四位数字」是固定预算，永远不省略

`警…` 是三个条件同时成立的结果：

| 条件         | 旧值              | 现值                | 作用                                                                             |
| ------------ | ----------------- | ------------------- | -------------------------------------------------------------------------------- |
| 按钮最小宽   | `min-w-0`         | `min-w-fit`         | `min-w-fit` 取**内容固有宽度**；`min-w-0` 允许容器压到忽略固有宽度，于是标签被切 |
| 按钮溢出裁剪 | `overflow-hidden` | 去掉                | 它是 `text-overflow: ellipsis` 生效的前提之一，留着等于给省略号留后门            |
| 标签         | `truncate`        | `whitespace-nowrap` | `truncate` 直接声明「切了打省略号」                                              |
| 数字列       | 无宽              | `w-[4ch]`           | 「文字 + 四位数字」是固定预算，数字位数再多也**不缩不省**                        |

不省略的代价是窄窗口下整组可能横向溢出：这交给行头的 `flex-wrap` 接住
（`min-w-56` 是折行判据，见 §7.23.2），而不是靠切字。**判据是「文字完整」而不是
「一定塞得下」**——这一轮用户给的是前者。

#### 7.24.4 测试：哪一层能证明什么

| 层                      | 文件                         | 断言什么                                                                                                                                                                                                                                                                                                    |
| ----------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单元（jsdom）           | `LogPanel.test.tsx`          | 按钮无 `truncate` / `overflow-hidden` / `min-w-0` 且有 `min-w-fit`；标签 `whitespace-nowrap`；数字列 `w-[4ch]` + `tabular-nums` + 纯数字；警告类含 `text-amber-300`、错误类含 `text-rose-300`，数字列固定 `text-gray-600`；标题旁不再有 `rounded-full` 胶囊，且计数只来自级别按钮的 `textContent` / `title` |
| 端到端（真实 Chromium） | `e2e/critical-flows.spec.ts` | 五个按钮宽 ≥ 56px；按钮与其两个子元素的 `scrollWidth <= clientWidth`（真正的不省略判据）；警告 / 错误的计算色**不同**且分别落在黄 / 红区间（用 2D 画布换算成 sRGB——Tailwind v4 可能给 `lab(...)`，直接切字符串会算错）；数字列颜色 ≠ 标签颜色；标题行第一行里不含 `警告 n` / `错误 n`                       |

三条判据全部落在真实浏览器上。

### 7.25 面板六审：分类要「不漏」，复制要「按行」（#262 六审）

用户这一轮说了两句，各自指向一条**结构**上的缺口，而不是样式：

| 用户原话                                                                                                       | 性质         | 根因                                                                                                                |
| -------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------- |
| 「现在缺少分类，有的日志只在全部页签才显示，这种也要有自己的分类或是归入其他分类」                             | 分类不是划分 | 一半的日志行**没有文件来源**（`origin` 为 `undefined`），下拉里既没有它们的名字，选中任何来源又都会把它们整批藏起来 |
| 「日志多了我想复制报错文本还是复制不了，我刚选中内容就刷走了，需要每条日志后面加一个复制按钮，可复制日志内容」 | 出口粒度不对 | 唯一的复制出口是标题栏的「复制**全部**日志」——要一行的人拿到两千行，还得自己在里面搜                                |

#### 7.25.1 分类必须覆盖每一行：`bucketOf` + 守恒判据

面板里的行有两个来源：**文件**（`launcher` / `dev` / `app` / `app-runtime`）与
**运行期**（浏览器 console 拦截、Tauri 事件、全局未捕获错误）。后者的 `origin`
是 `undefined`，而来源筛选过去是这么判的：

```ts
const originOk = origin === "all" || entry.origin === origin;
```

于是这类行**只在 `all` 下成立**：选中任何一个来源，它们整批消失；而下拉里又
没有它们的名字（下拉的候选由 `ORIGIN_LABELS` 手工列，只有那四个文件来源）。
用户读到的是「有的日志只在全部页签才显示」，而界面上没有任何地方能看出
「还有一批行没被任何分类覆盖」。

修法是把「归类」变成一条**函数**，而不是散在判据里的比较：

```ts
export const CONSOLE_ORIGIN = "console" as const;

/** 有文件来源的行 → 它自己的来源；没有的 → 「控制台 / 全局错误」桶。 */
export function bucketOf(entry: Pick<LogEntry, "origin">): LogOriginFilter {
  return entry.origin ?? CONSOLE_ORIGIN;
}
```

- `LogOriginFilter` 从 `NonNullable<LogEntry["origin"]> | "all"` 扩成
  `… | "console" | "all"`——「控制台 / 全局错误」是一个**真分类**：有名字、
  有计数、按它筛得出这批行；
- 计数（`computeOriginCounts`）与过滤（`computeFiltered`）**都**走 `bucketOf`。
  两处各写一份判据必然漂移，漂移的表现正是「下拉上写着 5 条、切过去只有 3 条」
  这类不再可信的数字（§7.19.3 同一条理由）；
- 顺带修掉一个**计数错误**：这类行过去只计入 `all`（`table.all.all += 1` 之后
  直接 `continue`），于是「全部」按钮上的数字大于各分类之和，按分类找过去永远
  对不上。现在它进自己的桶。

**判据是守恒**：逐个分类的条数之和 = 「全部来源」的条数。它把「有没有行落不进
任何分类」变成可断言的等式——将来再加一类来源却忘了给它建桶，这条会红。
`log-store.test.ts` 断言到**逐级别**（不只是总数），e2e 在真实浏览器里读下拉
每项的 `sr-only` 纯文本摘要求和（不读自绘的四列：那是视觉产物，读它等于把用例
绑在排版上）。

> 文案写「控制台 / 全局错误」而不是「其他」：它回答的是「这批行是谁写的」，
> 让用户切过去之前就知道会看到什么（`ResizeObserver loop…`、未捕获的 Promise
> 拒绝都在这里）。

#### 7.25.2 复制必须能按行：出口粒度对齐诉求

「复制」此前只有**整页**一个出口（标题栏那个 `Copy` 图标）。用户要的是
**一行**——他刚看到一个报错，想把它发给别人；拿到两千行之后还要自己搜，
而「搜索 + 框选 + 复制」的每一步都可能被新日志打断（§7.22.3 的锚定窗口正是
为这件事做的，但**根源是出口粒度不对**：要一行就不该给整页）。

行尾现在有一个复制按钮（`RowCopyButton`）：

- 写的是**这一行**：时刻（全日期 `MM-DD HH:mm:ss.mmm`，与「复制全部」同口径）、
  级别、正文，拼装函数 `formatEntryForClipboard` 就是「复制全部」逐行用的那个
  ——两个出口共用一份口径，不会出现「单条复制的格式和全部复制的不一样」；
- **显形时机**：默认 `opacity-0`，`group-hover` 与 `focus-visible` 才显形。
  日志是「长时间盯着看」的界面，一个常在的按钮列会在每行末尾多出一块常驻色块，
  把正文的右边界切碎；`focus-visible` 保证纯键盘用户也点得到；
- **反馈按行独立**：成功显示「已复制」、失败显示「复制失败」，1.2s 后复原，
  不需要全局 toast（连点两行不会互相覆盖）。**失败必须说失败**——写不进去却
  报「已复制」，会让用户把一次失败的复制当成成功，到粘贴时才发现是空的，
  而那时原文可能已经翻页翻走了。

> 它同时让「选区」这件事不再关键：不必先框住文本（框到一半可能被滚动/新日志
> 打断），点一下就拿走整行。§7.22.3 的锚定窗口仍然需要（用户仍可能想复制**半个
> 屏幕**的内容），但「复制一行」这条最常见的路径不再依赖它。

#### 7.25.3 测试：哪一层能证明什么

| 层                      | 文件                         | 断言什么                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单元（jsdom）           | `log-store.test.ts`          | `bucketOf` 的判据表（无来源 → `console`）；`computeOriginCounts` 里 console 桶逐级别计数；**守恒**（各分类之和 = `all`，逐级别）；`setOrigin("console")` 只筛出 console / tauri / system 的行且条数与计数一致；`formatEntryForClipboard` 带全日期、带级别、多行正文原样保留                                                                                                              |
| 单元（jsdom）           | `LogPanel.test.tsx`          | 每条行尾都有复制按钮；点一下写进剪贴板的**就是这一行**（含 `[ERROR]`，且不含邻行的文本）——这里借 `userEvent.setup()` 装的剪贴板替身读回写入内容，量的是「写了什么」而不是「调用过没有」；写失败时显示「复制失败」且不显示「已复制」（覆盖顺序必须**先 `setup()` 再覆盖**，反了会被 setup 自己的替身盖掉、用例变成永远成功的假绿）；「控制台 / 全局错误」能单独筛出来，且计数与内容同口径 |

`opacity-0` 的按钮与正常按钮无从区分，命中测试只有浏览器做得了；剪贴板也要
真权限（`context.grantPermissions(["clipboard-read","clipboard-write"])`）。

> 一个现场踩到的坑记在这里：`console.error` 会让 Next dev 的**错误浮层**也渲染
> 一份同样的文本，且那是个隐藏节点——按文本全局找再 `toBeVisible` 会一直等到
> 超时。e2e 里读日志正文一律用 `[data-log-text]` 限定在面板行内。
