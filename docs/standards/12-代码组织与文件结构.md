### 12.2 Barrel Export 规范

```ts
// ✅ 分组注释 + 统一路径风格（components/studio/index.ts）
// ── Layout Shell ──
export { AppShell } from "./AppShell";
export { TopBar } from "./TopBar";

// ── Canvas & Workflow ──
export { CanvasArea } from "./CanvasArea";

// ── Shared UI ──
export { ModalDialog } from "./ui/ModalDialog";
```

**规则**：

- barrel 文件只做 re-export，不含逻辑。
- 路径风格统一（本项目用 `~/components/studio` 别名）；同一 barrel 内不混用相对/别名路径。
  **别名只有一种前缀：`~`**（`@/` 非本仓库约定，见 §12.8 的 R13）。
- 内部重构（拆子目录）对外 API 不变 → barrel 稳定消费方零感知。

### 12.4 注释规范：只写「当前代码的 Why」

> **核心原则**：注释记录**当前代码为什么是这样**，不记录**代码是怎么变成这样的历史**。
> 历史交给版本控制 —— `git log` / `git blame` / commit message / PR 描述 / CHANGELOG。

#### 12.4.1 该留：决策与约束（Why）

代码只说 What，注释才解释 Why。以下信息**高度就近**，三个月后的维护者改到这行就能看到，
从而避免把已被否决的方案改回去：

| 该写                   | 示例                                                                        |
| ---------------------- | --------------------------------------------------------------------------- |
| 架构 / 技术选型决策    | "用 Zustand 而非 Context：日志每秒数十次更新，Context 会触发全树 re-render" |
| **否决过的方案及原因** | "不用底部抽屉：压缩画布可用空间，且与 MiniMap / 状态栏重叠"                 |
| 反直觉代码的动机       | "SSE 断线不手动重建 EventSource：浏览器自动重连，close 会丢帧"              |
| 隐式契约 / 前置条件    | "此字段由后端 runner 写入，前端只读不写"                                    |
| 权衡取舍的边界值       | "300 条上限：低于此值用户感知不到丢失，高于则内存占用明显"                  |

其中「**否决过的方案**」价值最高 —— 它回答的是"为什么不用 B"，而这正是 `git log` 查不到、
且最容易被后人重蹈覆辙的信息。

#### 12.4.2 不该留：作者 / 日期 / 修改流水

| 不该写进代码                               | 应该放哪                                                                                                   | 原因                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 作者（`R-ardot122`）、日期（`2026-08-31`） | `git log` / `git blame`                                                                                    | 天然已有；写进注释会随代码搬迁而过期失真 |
| "谁改了什么"流水                           | Commit message / PR 描述                                                                                   | 同上，且重复维护成本                     |
| 旧方案的完整代码 / 前后对比                | `git` 历史                                                                                                 | 无信息增量，只增加阅读负担               |
| 大段 changelog                             | `CHANGELOG.md`（仅记录用户可感知的对外差异，见 [13.10](13-提交与-code-review.md#1310-changelog-记录规范)） | 面向发布说明，不是代码读者               |

#### 12.4.5 一句话判据

写注释前自问：

> **"这条信息，三个月后的维护者在 `git log` 里也能查到吗？"**

能查到 → 删掉；只有当前决策者知道的「为什么」 → 留下。

### 12.5 工具函数与组件目录分离

| 目录                    | 放什么                                                                                                                                      | 不放什么                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `lib/`                  | **跨端逻辑层**：纯函数与框架无关工具（`isVideo`、Zod schema、`timeAgo`）、Zustand store 实现、网络客户端，以及**声明的** Node-only 领域编排 | React 组件、视图层 import、未声明的 Node 内建 import |
| `config/`               | 常量与静态配置（`src/config/`）                                                                                                             | 业务逻辑                                             |
| `server/`               | 服务端逻辑（db client、repository、服务，`src/server/`）                                                                                    | 客户端代码                                           |
| `trpc/`                 | tRPC router / context / 受保护 procedure（`src/trpc/`）                                                                                     | 业务组件                                             |
| `components/studio/ui/` | 无业务依赖的通用基础 UI（`ModalDialog`、`DarkSelect`）                                                                                      | 业务组件（`HistoryList`、`AgentPanel`）              |
| 组件目录内 `hooks/`     | 单组件私有的自定义 hook（如 `use-project-manager.ts`）                                                                                      | 跨功能复用 hook                                      |

> **注意**：本项目**没有**顶层 `src/hooks/`、`src/stores/`、`src/types/` 目录（与主规范 §2.1 一致）。跨功能复用的 hook 若确需共享，就近放入 `lib/` 或组件目录，禁止新建顶层目录制造分裂。

#### 12.5.1 `lib/` 不是「纯工具」，它是跨端逻辑层（ISSUE #572 第 6 项）

`lib/` 曾在本章写作「纯工具函数（无 React、无服务端依赖）」，实际却是「剩下的一切」：
进程编排（`comfyui/**`、`film/orchestrator.ts`、`drizzle-studio/**`）、文件系统、
数据库仓储都在里面。**规范描述的是理想，与代码不一致的规范比没有规范更糟**——
按它写代码的人会把「服务端编排」当成违规，而现状没有任何一条判据支持这个判断。

修正后的口径（可执行的部分收在 §18.2 / §18.4）：

- `lib/` = **跨端逻辑层**：被 `components` / `app` / `server` 共同依赖的**地基**，
  承载「全平台复用」的逻辑。其中既有纯函数，也有 Node-only 领域编排。
- 判断一个模块属于哪一侧，**看它的声明而不是目录名**：`import "server-only"` /
  `.server.ts` / 都不带（纯 Node 宿主），三选一由 §18.4 规定、由
  `tests/lib-node-only-declarations.test.ts` 强制。
- **服务端领域编排的落点**：先问「它是否只服务端用」——是，就按 §18.4 声明后**留在
  `lib/`**（`lib/comfyui/**` 就是这种形态，它同时被 Next 服务端与启动编排加载）；
  需要视图层与纯 Node 宿主**共用同一份实现**时，也必须留在 `lib/`（`lib/llm/secrets.ts`
  由 MCP 宿主与 Next 两侧共用，下沉到 `server/` 会让 MCP 拖进整个 Next 服务端图）。

> 一句话：**`lib/` 的分界不是「纯不纯」，是「谁依赖谁」**——它永远在最底层，
> 因此不得 import 视图层（§12.7）；而它是不是 Node-only，由声明回答。

### 12.6.1 变量命名硬约束（对齐主规范 §3）

- **禁止单字母变量**（循环索引 `i`/`j`/`k`、catch 参数 `e`、占位符 `_` 除外）。
- 事件参数 `e` 需语义化（`event`/`evt`）；状态简写 `s`、接口数据 `d`、动态 import `m` 等一律改语义名。

### 12.7 循环依赖预防（机器强制，ISSUE #574）

- 组件目录内的 `index.tsx` 不反向 import 父级业务模块；跨功能复用走 `components/studio/ui/` 或 `lib/`。
- Zustand store 不 import 组件；组件订阅 store。
- `lib/` 不 import `components/`；`components/` 可 import `lib/`。
- **`lib/` 与 `server/` 的引用逐个登记**（判据：`tests/lib-server-imports.test.ts`）。
  `lib` 是被 `server` / `components` / `app` 共同依赖的地基，新增对 `src/server/**`
  的依赖必须先裁决并登记在测试的 `REGISTERED` 里（清单只许变短，已消除的条目必须删掉）。
  两类不算越界：`lib/core/**`、`lib/db/**` 本身就是 element `server`（取
  `~/server/db/schema` 是**同层**引用）；测试里与源码串一致的 `vi.mock(...)` 跟着
  源码一起改。裁决与清单见规范 §18.10。
- **`src/**` 内不得存在模块循环依赖**（含自环、含 type-only 回引）。判据由
  `scripts/check-circular-deps.cjs` 在 pre-commit（第 18 步）与 CI
  （`Module circular dependencies ratchet`）强制。

**为什么必须机器化**：这两条原则此前只写在规范里、没有判据，于是 `src/lib` 内
真长出了 2 组环，而它们**只靠一句注释维持**：

```
src/lib/comfyui/{executor-cli,executor-finalize,executor-scheduler,executor-ws}.ts
  —— 收口（finalize）结束要「让队列继续跑」→ import scheduler；
     调度（scheduler）要执行任务 → import cli / ws；
     cli / ws 要结算 → import finalize。四方递归。
src/lib/comfyui/{client,instance-port,status}.ts
  —— status 要探端口 → import client；client 要按进程快照取地址 →
     import instance-port；instance-port 要读注册表 → import status。
```

环的危害不是「跑不起来」，而是**跑起来的样子取决于 import 顺序**：某个模块
在自身求值途中被对方的模块体读到一半，拿到的是 `undefined`，表现为
`undefined is not a function` —— 而报错行号落在**调用点**、与真正的成因相隔
几个文件。更糟的是它随打包器 / 动态导入时机漂移，本地复现不了。

**判据为什么用强连通分量（SCC）而不是「找一条环路」**：SCC 与遍历起点无关
（结果稳定，才能做棘轮基线），且天然把「同一个环的不同走法」归成一个分量 ——
否则 A→B→A 与 A→C→A 会被报成两条、数字随顺序漂移。

**修法：让依赖方向单向，而不是「两边一起改」**。本仓库用过的两类手法，可直接照抄：

| 手法                     | 适用                                                    | 实例                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **下沉叶子模块**         | 环里有一段「谁都不依赖」的公共部分                      | `probe.ts`（`probeComfyAtPort`/`probeBaseOnce`）、`executor-history.ts`（`fetchHistoryEntry`/`ComfyHistoryEntry`）、`redact-secret.ts`、`workflow-node-types.ts` |
| **依赖倒置（回调注入）** | 依赖是「向后收口 → 向前续跑」这类**动作**，物理上分不开 | `executor-continuation.ts`：收口侧只调 `kickQueue()`，调度层在模块体里注册实现                                                                                   |
| **共享类型下沉**         | 环是 type-only 回引（子件要用父件的类型）               | `workflow-node-types.ts`：类型不需要「属于谁」，只需要「被谁共用」                                                                                               |

**三条容易踩的细节**：

1. **type-only 回引也算环**。`import type` 在编译后被擦除，但它**仍然**是
   「子件依赖父件的定义」—— 类型下沉到类型模块（§18）即解，代价是零。
2. **注意目录 barrel**。`import { X } from "./CanvasNode"` 解析到的是
   `CanvasNode/index.tsx`，而它 `export { CanvasNode } from "./CanvasNode"` ——
   子件引 barrel 就等于引父件。子件应直接引具体文件
   （`./CanvasNode/CanvasNodePrimitives`）。
3. **依赖倒置的注册点必须在模块体**，不能放进某个函数里：注册必须先于任何任务
   被处理（入口链 `enqueue → ./executor → ./executor-scheduler` 保证了这一点）；
   放函数里会让「先收口、后首次出队」的路径拿到空回调。回调缺失时也**不许静默
   空转** —— 本仓库既有 3s 安全网心跳兜底，缺注册时另打一条 warn。

### 12.8 文件组织卫生（2026-08-29 审查新增）

- **禁止时间戳备份文件进 `src/`**（如曾出现的 `workflow-detail_20260829_121552_764.ts`）。版本
  回退靠 git 历史，重构前需要安全网就开分支；此类文件已清理，勿再产生。
- **运行时产物与本地工具目录已 gitignore**：`/log/`、`/run/`、`/temp/`、`/python-venv/`、
  `__pycache__/` —— 运行产物不入仓库，也不要在 `src/` 里写运行时文件。
- **新增 git-忽略的产物/临时目录时须同步 eslint ignores**：`.gitignore` 与
  `eslint.config.js` 顶层全局 `ignores` 需保持一致——凡 `.gitignore` 新增忽略的
  产物/临时目录（`coverage/`、`out/`、`dist/`、`node_modules.old/`、`.pnpm-store/`、
  `log/`、`run/`、`test-results/`、agent 索引目录等，可能落 `.ts/.tsx/.js` 或物理存在含

### 12.8.0 import 别名只有一种：`~`（ISSUE #640，机器强制）

**判据一句话**：`src/**` 与 `e2e/**` 的静态模块说明符以 `@/` 开头即违规——一律写 `~/`。

**它不是「风格偏好」，因为写错的代价是零**：`tsconfig.json` 的 `paths` 里同时有

```json
"paths": { "~/*": ["./src/*"], "@/*": ["./src/*"] }
```

`@/*` 是 create-t3-app 脚手架留下的历史项。于是 `import { cn } from "@/lib/utils"`
**能编译、能跑、类型也对**——唯一的代价是「同一件事从此有两种写法」，而且它不会
自己停下来：新人（与生成器）照最近的邻居抄，漂移面积只会变大。ISSUE #640 的时点是
**`@/` 573 处 / `~/` 2 518 处**。

**高发区是 `src/components/ui/**`**：`shadcn add <comp>` 生成的组件默认写 `@/`
（§16.3 已点名），而 `ui/` 是「工具生成、尽量不手改」的目录——靠人在 review 里
逐行改不现实。所以口径是**生成后顺手改**，判据由门禁兜住。

| 约束                                         | 理由                                                                 | 门禁 |
| -------------------------------------------- | -------------------------------------------------------------------- | ---- |
| `src/**`、`e2e/**` 的 import 一律 `~/`       | `@/*` 是脚手架历史项，留着它等于允许两种写法长期并存                 | R13  |
| 动态 `import("@/…")` / `vi.mock("@/…")` 同罚 | 它们是同一个「模块说明符」，只认 `from` 会留下大半个缺口             | R13  |
| 注释里的 `@/…` **不判违规**                  | 注释里写「旧写法是 `@/…`」正是在解释这条规则的来由（§12.4.1 的 Why） | —    |

**为什么把注释排除在外**：这条规则的 Why 本身就要提到 `@/`。把注释也判成违规，
等于逼着下一个人删掉唯一的解释——本仓库反复踩过「判据把自己需要的解释一起拦掉」。

判据由 `scripts/check-import-alias.cjs` 承担（R13），回归测试
`tests/check-import-alias.test.ts`；已接入 pre-commit 与 CI。**不要**改用
eslint 的 `no-restricted-imports`：它按 package 名匹配，而 `@/` 是 paths 别名，
在 pnpm 布局下 `module.source` 为 `null`——本仓库已有过这类「写了但静默不生效」的
门禁（见 `eslint.config.js` 里 drizzle 那条的注释）。

### 12.8.1 窗口标题行让位（ISSUE #310，机器强制）

页签搬到窗口标题行后，标题行是**应用级 chrome**：任何铺满**整个视口**的浮层都会把它
整条盖住——页签看不见、右上角的最小化/最大化/关闭也点不到。

判据（一句话）：**凡 `fixed` 且 `inset-0` 的顶层浮层，顶部都必须让位给标题行**，
写法统一为 `top-title-bar right-0 bottom-0 left-0`（`bottom-0` 必须显式，否则靠内容
高度撑开、拉伸不到底）。

- 取定位只用两处，不要手写：`overlayClass("modal", extra)`（模态弹窗 / 抽屉 / 遮罩，
  不铺满）与 `fullScreenLayerClass(z, extra)` / `FullScreenLayer`（全屏视图，铺满内容区）。
  判据本身是纯函数，在 `src/lib/full-screen-layer.ts`（规范 17 第①层），视图层只消费。
- 标题行高度定在 `globals.css` 的 `--spacing-title-bar`：tailwind v4 **只有
  `--spacing-<name>` 命名空间会生成间距类**，自定义名（如 `--title-bar-height`）产出
  0 个类、让位静默失效。
- **门禁**：`scripts/check-title-bar-clearance.cjs`（pre-commit 第 3 步 + CI
  `Title bar clearance`）扫描 `src/components/**`、`src/app/**`，命中 `fixed inset-0`
  即阻断。豁免仅 3 条，逐条写在脚本 `EXEMPT` 里并注明理由（判据模块自身的注释、装饰
  背景层、注释引用旧写法）；**新增豁免必须在脚本里写明「为什么它不是内容浮层」**，
  否则等于把门禁关掉。
- 判据自测在 `tests/check-title-bar-clearance.test.ts`（临时仓库跑真脚本，
  断言该拦的拦、不该误伤的放过），E2E 回归见 `e2e/critical-flows.spec.ts`
  「打开设置 / 打开应用日志面板后应用页签仍可见可点」。

> 为什么单独设门禁而不是靠 Code Review：`fixed inset-0` 是全项目最通用的弹窗写法
> （历史存量 25 处），首轮只改了「全屏视图」，弹窗类立刻二次回归。**靠人肉逐个文件翻的
> 判据必然漏**，能机器判的就别写进人脑。

### 12.8.2 内嵌第三方页面（iframe）先判「能不能嵌」，能开就自己开（ISSUE #310）

让出标题行解决的是「本应用自己的浮层盖住页签」；**被内嵌的页面自己能不能显示**是另一
类问题。这里踩过两次坑，成因与结论都必须写死。

**① 成因曾被记错。** 早先文档把空白页签记成「ComfyUI 发 `X-Frame-Options: DENY`，
跨源必然被拒」。**这个成因是错的**：ComfyUI（`server.py`）与 aiohttp 都不发这个头
（已用真实中间件实测复核）。真正的拦路虎是：ComfyUI 在**未开 CORS** 时挂的是
`create_origin_only_middleware()`，它对跨源请求（`Sec-Fetch-Site: cross-site`，
或回环地址下 `Host` 域名 ≠ `Origin` 域名）**直接返回 HTTP 403**（反 CSRF：防随机
网页 POST 127.0.0.1 排队）。iframe 内嵌正是跨源请求，403 响应体为空 → 一片白。
出错时把成因记错，会让修复方向整个偏掉（上一轮就因此退到了「另开窗口」）。

**② 开关握在自己手里，别绕道。** ComfyUI 是本应用 spawn 的，启动参数带上
`--enable-cors-header` 就会改挂 `create_cors_middleware()`——跨源不再 403，并回
`Access-Control-Allow-Origin`（`src/lib/comfyui/lifecycle-derive.ts` 的
`withEmbedClearanceFlag` / `COMFY_EMBED_FLAG`，在 `buildSpawnArgs` 里统一注入、
幂等不重复）。**正常路径下 ComfyUI 一定能被内嵌**，不应该出现「打不开就弹第二个
窗口」这种绕道（用户明确要求「不要打开另一个窗口，我只要多页签的形式」）。

因此约定：

- **探测必须模拟 iframe 视角**：`probeComfyEmbeddable` 的请求要带 `Origin` 头。
  裸探测（无 `Origin`）会拿到 200，把「会被 403」误判成「可嵌」——这正是上一轮
  观测盲区。判读优先级：`403` → 明确不可嵌并点明该开 `--enable-cors-header`；
  `Access-Control-Allow-Origin` 有值 → 可嵌；再退到 CSP `frame-ancestors` /
  `X-Frame-Options`；拿不到任何放行证据时**按不可嵌处理**（不赌）。
- **判据在服务端**：`src/lib/comfy-embed.ts` 纯函数（`judgeEmbeddable` /
  `frameAncestorsAllows` / `parseXFrameOptions`），经 tRPC `setting.comfyEmbeddable`
  暴露（宿主页把 `window.location.origin` 传上去做同源判定）。为什么不能放页面上：
  跨源读不到被嵌页响应头，iframe 的 `error` / `load` 事件都不带原因，「被拒」与
  「内容为空」在 JS 里长得一样。客户端网络层收口 `src/lib/comfy-tab-client.ts`。
- **「打开查看」这条决策路径只有两档，且都留在同一个窗口**：
  `decideComfyTabOpen` 返回 `embed`（内嵌页签）或 `blocked`（**仍在页签内**渲染
  可读说明：成因 + 下一步）。这条路径**不允许**另开独立窗口、也**不允许自动跳
  系统浏览器**——那违背「像文件管理器那样多页签」的目标。`blocked` 只用于
  「外部实例不受本应用参数控制」这类边缘情形。
  页签模型:`shell-tabs-store` 的 `ShellTab.blockedReason`，渲染见 `ShellTabs.tsx`
  的 `TabBlockedNotice`。
- **系统浏览器是用户主动点的并列出口，不是自动回落**（§12.8.3）：设置页另有
  「在浏览器打开」按钮，点它才跳浏览器；`openComfy()` 那条路径永远不碰浏览器。
- **新增任何内嵌第三方页面（iframe）时照此办理**：先探测、再决定渲染什么，
  不要无条件渲染 iframe —— 空白页签是最难排查的失败形态（没有报错、没有出口）。
- 回归测试：`src/lib/comfy-embed.test.ts`（判决表逐条钉住，含 403 与「探测必须带
  Origin」）、`src/lib/comfyui/lifecycle-derive.test.ts`（开关注入幂等）、
  `src/app/(main)/settings/hooks/use-settings-page.test.ts`（页签形态三例）、
  `e2e/critical-flows.spec.ts`（可嵌渲染 iframe / 不可嵌给说明，两条都断言不弹窗；
  另有「在浏览器打开」不碰页签一条，见 §12.8.3）。

### 12.8.3 「在浏览器打开」是与页签并列的出口，不是回落

12.8.2 定下「点『打开查看』只出页签」，那条结论容易被顺手读成「本应用永远不许调
系统浏览器」——**这是过度解读，会把用户真正需要的出口一起删掉**。此处把边界写清：

- **禁止的是「自动回落」**：内容嵌不进去就悄悄把用户甩到浏览器（或弹第二个窗口），
  用户既没得到内容、也不知道发生了什么。这是 12.8.2 要杜绝的形态。
- **允许的是「用户主动点的并列出口」**：同一个地址再交给系统默认浏览器打开，
  服务用户放大查看 / 装浏览器插件 / 多屏铺开的场景。它与页签内嵌**并存**，
  不替换、不切换页签、不影响页签那套行为。
- **落地位置**：设置页 ComfyUI 状态行的「在浏览器打开」按钮
  （`SettingsPageView.tsx`）→ controller hook `use-settings-page.ts` 的
  `openComfyInBrowser` → tRPC `setting.comfyOpen` →
  `src/lib/comfyui/lifecycle.ts` 的 `openComfyUi` → `src/lib/open-in-browser.ts`
  （`spawn` 命令 + 参数数组，不经 shell 二次引号解析）。
- **地址由服务端自己探**（`openComfyUi` 内部先 `probeComfyUi()`），不采信前端
  state 里的旧 `base` —— 用户点按钮时可能已经隔了很久，端口可能已经变了。
  这也是这个按钮不复用 `setting.openExternal` 的原因：那条端点的地址完全由
  调用方给定，前端拿着过期地址就会打开一个空白浏览器页。
- **视图层不新增 IO**：按钮只调 controller hook 暴露的 action，符合 §17 四层范式。
- 回归：`src/app/(main)/settings/hooks/use-settings-page.test.ts`（「在浏览器打开」
  三例：成功不碰页签 / 未运行的提示 / 打开失败的提示）、
  `e2e/critical-flows.spec.ts`（点它不新增也不切换页签、不弹窗）。

### 12.8.4 内嵌方的跨源限制要在「外壳」解决（WebView2 参数，ISSUE #310）

12.8.2 解决的是「**被嵌方愿不愿意**被嵌」（探测 → 判决 → 可读说明）。但还有一层
在**外壳自己**身上，探测**永远看不到它**：

**现场**：ComfyUI 已经在运行、地址也对、探测判「可嵌」，页签里却只有一句

```
已阻止此内容。请与网站所有者联系以解决此问题。
```

**成因**：应用级页签把 ComfyUI 内嵌进**同一个 WebView**，而两者不同源（端口不同
即跨源）。WebView2 默认按 Chromium 的「不同源不可嵌」执行，直接拒绝渲染该 iframe。
它和 12.8.2 那两个成因的区别是**谁来执行**：403 / XFO / CSP 都是被嵌方发出来的，
服务端探测得到；这一条是宿主自己执行的，探测侧永远是「一切正常」——所以只能修外壳。

**修法**（内嵌被谁拦就修谁，两段都要在）：

- **服务端放行**：ComfyUI 由本应用 spawn 时注入 `--enable-cors-header`（幂等），
  不发 XFO / frame-ancestors，跨源请求不被 403；
- **嵌入方放行**：应用页自己的 CSP 必须有 **`frame-src`** 放行 ComfyUI 的本地源
  （`next.config.js`：`frame-src 'self' http://127.0.0.1:* http://localhost:*`，
  与 tauri.conf.json 的 frame-src 同口径）。frame-src 不写会**回退到
  `default-src 'self'`**，跨端口即跨源被拒——这层拦截发生在嵌入方页面，
  WebView2 的 `--disable-web-security` 也豁免不了（它只关同源策略，不动 CSP）。
  `frame-ancestors 'none'` 是本应用不被别站内嵌的反点击劫持，保持不变。

**两条死路（都已实证并移除/放弃，别再走）**：

- exe 同级 `app.exe.manifest` 的 `per_app_arguments`（#445）：不是 WebView2
  官方文档认可的机制（learn.microsoft.com 无此通道），实测参数到不了浏览器
  进程（`msedgewebview2` 命令行无该开关）；`build-launcher` 清空重建
  `start-tauri/` 时该文件还会被抹掉。manifest 机制已整体移除；
- `--disable-web-security`：即便经官方通道（`additionalBrowserArgs`）真的
  下发到浏览器进程（已实证可达），也救不了这个症状——它只关同源策略，
  CSP `frame-src` 该拦还是拦，反而把壳内全部页面的隔离拆了。

**排障实证手段**：起壳后查 `msedgewebview2` 命令行（确认浏览器进程参数）、
`curl -sD - -H "Origin: http://127.0.0.1:3100" -H "Sec-Fetch-Dest: iframe"`
ComfyUI 地址（确认服务端没拦）、`curl -sD -` 应用页地址（确认 CSP frame-src
在放行列表里）。拦嵌入式 iframe 的三方：被嵌方响应头 → 嵌入方页面 CSP →
壳参数，逐层排除。

**门禁**：`tests/comfyui-embed-csp.test.ts` 锁住 frame-src 放行列表、
`frame-ancestors 'none'` 不被放宽、以及 manifest 旧机制不再回流。

**顺带修掉的一个「判不出来偏要说可嵌」**：壳的 main 窗初始 URL 是 `about:blank`，
页面把 `window.location.origin` 传上来时是字符串 `"null"`。`URL` 对非特殊 scheme
会把端口解析成 0，于是 `isSameOrigin("about:blank", "http://localhost:8080")`
返回 **true** —— 判据把「完全不知道」当成「同源、必然可嵌」，页面于是无条件塞
iframe。现在 `judgeEmbeddable` / `probeComfyEmbeddable` 在任一侧不是 http(s) 时
一律判**不可嵌**（且不发无意义的探测请求），回归见 `src/lib/comfy-embed.test.ts`
的「非 http(s) 源一律判不出」一组。

**失败也要可读、可自查**：不可嵌时页签内的说明里**必须带地址**
（`ShellTab.blockedUrl`）+ 一句「也可以到 设置 → 创作后端 点『在浏览器打开』」。
理由：只剩一句「看不了」时，用户和排查者都无法判断是**外壳**拦的还是 **ComfyUI**
拦的；把地址复制到浏览器能打开 → 拦的是外壳（本条），也打不开 → 拦的是 12.8.2。

### 12.8.5 壳里的 HTML5 拖放：原生处理器会「吃掉」DOM 拖放事件（ISSUE #616）

12.8.2 / 12.8.4 解决的是「页签里的页面**能不能显示**」。这一条解决显示之后的下一个
问题：页内的 HTML5 拖放（ComfyUI 拖入图片 / 工作流）能不能收到事件。

**现场**：应用内打开的 ComfyUI 拖不进图片，而**同一个 ComfyUI 地址在浏览器里整窗
打开拖放正常**；页签本身显示完好、日志无报错，看起来像是「ComfyUI 的拖入功能时好
时坏」。

**成因**：宿主窗口默认挂着 **WebView2 的原生拖放处理器**（wry 的
`drag_drop_handler_enabled` 默认 **true**）。Tauri 自己的 API 文档把这条因果关系
写得很直白——`WebviewWindowBuilder::disable_drag_drop_handler` 的说明是
「Disables the drag and drop handler. **This is required to use HTML5 drag and drop
APIs on the frontend on Windows.**」。处理器一接手，Chromium 就不再走自己的拖放
路径——`dragover` / `drop` **不派发到 DOM**，文件被换成 wry 的回调 `on_drag_drop`，
而本应用没有注册它。页签里的 ComfyUI 完全靠 `drop` 事件的 `dataTransfer.files`，
于是拖进去毫无反应。**「浏览器正常、应用内不正常」这条对照本身就是判据**：两者唯一
的差别就是这一层壳。

**修法**：主窗 builder 显式 `.disable_drag_drop_handler()`（`src-tauri/src/lib.rs`
的 `create_main_window`，函数上方有完整说明）。三点必须一起记住：

- **在宿主窗口上关，不是给 iframe 关**：命中测试落在宿主那个 WebView（`main`）上，
  iframe 只是它内部的一块区域；被拖进来的文件由宿主这一层决定交给 DOM 还是交给
  原生处理器。ComfyUI 自己的独立窗口（`open_comfyui_window` 建的 `comfyui` 窗）
  不承载 iframe，保留默认即可。
- **可以放心关**：本应用没有任何一处消费原生文件拖放——项目画布与工作流库的拖放
  都是**页内拖元素**（自定义 dataTransfer），与文件拖入无关；壳侧也没有注册
  `on_drag_drop`，没人监听 `tauri://drag-drop`。关掉它 = DOM 恢复正常语义 + 少一层
  原生处理器，纯收益。
- **必须重编 Rust 壳**：`cd src-tauri && cargo build --release --features custom-protocol`。
  这类壳侧行为修复只改前端跑旧二进制等于没改（同 12.8.4）。

**门禁**：`tests/comfyui-embed-csp.test.ts`（同族还有页签内嵌的 CSP `frame-src`
放行断言）——那一行 `disable_drag_drop_handler` 被删掉就红，因为没有类型系统能拦住它。

**新增任何「壳里套第三方页面」的容器时照此自检**：先在**浏览器**里把同一地址试一遍
拖放；浏览器正常而应用内无反应，就把嫌疑按「壳参数 / 宿主窗口行为 → 应用页 CSP →
被嵌方响应头」的顺序排，别先去翻被嵌页面的代码。

### 12.11 源码里禁止内嵌控制字符（NUL 让整个文件变二进制，机器强制）

**判据一句话**：`src/**` 的 `.ts` / `.tsx` 源码里，**不得出现制表符 / 换行 / 回车以外的
控制字符**（NUL 及其它 C0 码位、DEL、C1 区）。要表达一个 NUL，写**转义形式** `"\u0000"`
（那是 6 个可见字符），不要往文件里塞一个真的字节。

**为什么这不是洁癖**：源码里带一个真的 NUL 字节，git 与工具链会把这个文件**整体**
当成二进制——而「被判成二进制」是一堆**静默**后果的开关：

| 环节                   | 带 NUL 时的表现                                                         |
| ---------------------- | ----------------------------------------------------------------------- |
| `git diff`             | 只回一句 `Binary files a/… and b/… differ`，**改动内容一个字都看不到**  |
| `git show --stat`      | 该文件行数栏显示 `Bin 0 -> 0 bytes`（或其他 bin 统计），评审拿不到 diff |
| `grep -rn` / `ripgrep` | **默认直接跳过**整个文件，`grep -rn "某符号" src` 永远搜不到它          |
| 编辑器 / 代码浏览器    | 不语法高亮、不显示行号，部分模式下整文件被当成乱码                      |

最坏的一档是**评审失效**：一份带 NUL 的改动在 PR 里「看不出改了什么」，而 CI 全是绿的
（`tsc` / `eslint` / `vitest` 都照常读得懂这个字节），于是问题要到很久以后才被发现。

**来源与真实事故**：这类 NUL 几乎都不是有意写进去的，而是**用 NUL 当占位符哨兵**留下的。
本仓库 `src/lib/comfyui/markdown.ts` 的行内代码暂存就是这种写法——它用 `\0CODE<n>\0`
把已渲染的 `<code>` 片段藏起来，好让后续几步正则「看不见」代码正文。

**替代写法（同构，可读性与评审都回来）**：哨兵只需要满足「**接下来跑的正则命中不了它**」，
这一点用一个可打印的形式同样成立。`markdown.ts` 现在用 `<数字 id>`：纯 ASCII，
既没有反引号、也没有 `*` `_` `[` `&lt;`（后续那几组正则的全部触发字符），
隔离效果与 NUL **逐条相同**，而 `git diff` 与 `grep` 都恢复可用。

```ts
// ❌ 用真的 NUL（文件从此是二进制，git diff 只回「Binary files differ」）
return `\0CODE${idx}\0`;            // 源码里是一个 0x00 字节
text.replace(/\0CODE(\d+)\0/g, …)

// ✅ 可打印哨兵：隔离效果同构，文件保持纯文本
return `<${idx}>`;                  // 正文是先 escapeHtml 过的，只有正文能产生字面量 <n>
text.replace(/<(\d+)>/g, …)
```

> **选哨兵形状时的通用判据**：列出**接下来还要跑的每一组正则**，哨兵必须一个都不命中；
> 同时要确认「用户内容不可能伪造出同样的形状」——本处正文是先 `escapeHtml` 过的，
> 用户写 `<0>` 到了这一步是 `&lt;0&gt;`，永远撞不上恢复用的 `<(\d+)>`。
> 两条都过了，这个形状就和 NUL 一样安全，而且不把文件变成二进制。

**门禁（R12）**：`scripts/check-file-structure.cjs` 扫描 `src/**` 的 `.ts` / `.tsx`，
按**码位**（而不是按字节串匹配）判定，命中即阻断并点名 `文件:行 → U+00xx`。豁免
只有制表符 / 换行 / 回车（源码里的正常排版）。规则在 `pre-commit` 第 2 步与 CI
`File structure rules` 步骤各跑一次；回归测试见 `tests/check-file-structure.test.ts`
的 R12 用例组（真的往临时工作区写 NUL 字节，断言被拦；转义写法与制表符放行）。

> **为什么从「按字符串找 `\0CODE`」改判「按码位找控制字符」**：前者只认得某一种
> 哨兵形状，换一个形状就静默失效；后者是这条规则真正的判据——**文件里有没有不可见的
> 控制字节**，与它被用来干什么无关。判据写成形状，等于把门禁挂在实现细节上。

### 12.12 跨文件重复块（同一份实现被复制成两份，机器强制）

**判据一句话**：同一个仓库里，**两份实现逐行重合超过 75%** 且各自都在 60 行以上，
就是一对「孪生」——要么抽成一个共享模块让两份各自只留差异，要么说明其中一份该删。
由 `scripts/check-code-duplication.cjs` 在 pre-commit 与 CI 强制。

**为什么必须机器判定**：重复代码在 review 里是**最容易被放行**的东西——单看每一份
都「没毛病」（命名清楚、注释完整、测试通过），只有把两份并排比较才发现是同一段。
而「并排比较」这件事人不会每次都做，机器会。

**真实事故（ISSUE #536 P2）**：本仓库有两对，都是同一模式：

| 一对孪生                                                                | 规模         | 为什么会写两份                                                           |
| ----------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------ |
| `lib/workshop/api-channel.server.ts` ⇄ `server/workshop/api-channel.ts` | 84% 逐行相同 | 一个要 `import "server-only"`，一个跑纯 Node MCP，**不能**带 server-only |
| `api/llm/test-usage/route.ts` ⇄ `api/llm/test-usage/query/route.ts`     | 84% 逐行相同 | 提交与「继续等待」两个动作                                               |

第二份的注释当时还**明说**了这件事（「复刻 `@/lib/workshop/api-channel.server` 的
生图/视频能力」）——动机可以理解，但「复制 84%」不是解法：生图请求体、超时、错误
文案、结果提取全在两处各存一份，以后改协议要改两处，**漏一处就是静默行为分叉**
（两个入口对同一上游发出不同请求，而没有任何门禁看得见）。

**正确修法**：把协议实现抽到一个**纯逻辑模块**（`api-channel-core.ts`），两个入口
只注入各自的 IO 差异 —— Next 侧注入 `server-only` 的落盘与 `remoteModel` 表查询，
MCP 侧注入纯 Node 读文件。共享内核里**不含**任何一侧的传输层代码。
`test-usage` 那对同理：抽到 `lib/llm/usage-test.server.ts`。

**判定口径（v1，刻意保守）**：

- 只扫 `src/**` 的 `.ts` / `.tsx`（不含测试、快照）；
- 逐行归一化：去首尾空白、丢空行与整行注释 —— 缩进与注释差异**不算**差异；
- 对每一对文件求「行数少的那个有多少行能在另一个里找到」（**集合式**，不比顺序）；
- 比例 ≥ 75% 且两边都 ≥ 60 行才算一对。

集合式的好处是**零误报**（不会因为「碰巧有 20 行相同」就报）；代价是它只认得出
「整份复制」而认不出「局部大段复制」—— 后者交给阈值更低的后续版本，现在先把
历史上真实发生过的这一档堵住。

**棘轮**：结果记在 `scripts/.code-duplication-baseline.json`，新增孪生对一律阻断，
修掉后执行 `--update` 收紧（CI 用 `--strict`，未收紧也失败）。判据留在**比例**
上而不是「这两个文件曾经是孪生」上 —— 后者换个文件名就静默失效。

**与 eslint 分层规则的分工**：`eslint.config.js` 管的是「谁可以 import 谁」
（依赖方向）；本条管的是「同一段逻辑有没有被写两遍」（内容重复）。两者互不覆盖。

#### 12.12.1 门禁够不到的那一档：小函数的跨层复制（ISSUE #535）

§12.12 的判据是「逐行重合 ≥ 75% **且两边都 ≥ 60 行**」。这个下限是刻意的（避免
「碰巧有 20 行相同」的噪音），但它留了个**死角**：**十几行的小工具函数被抄成三份，
一条门禁都看不见** —— 无论 R5（文件行数）、§12.13（函数行数）还是 §12.12（重复块），
全都够不着，而 `eslint` 的分层规则只管依赖方向、更看不见它。

**真实实例（ISSUE #535）**：两个纯取值函数 `strParam` / `numParam` 被逐字抄了三份，
各自约 4 行、连名字都三处不同：

| 位置                                                 | 名字                          | 层     |
| ---------------------------------------------------- | ----------------------------- | ------ |
| `components/workshop/ShotStudio.tsx`                 | `strParam` / `numParam`       | ③ 视图 |
| `components/workshop/hooks/use-workshop-pipeline.ts` | `paramString` / `paramNumber` | ② 逻辑 |
| `lib/workshop/character-portrait-client.ts`          | `strParam` / `numParam`       | ② 逻辑 |

三份之间**没有任何 import 边**，所以循环依赖检测（§12.7）也看不见。

**危害不是「重复」本身，是缺省值跟着被复制了多份。** 三份调用点各自写死
`28 / 7 / "euler_ancestral" / "normal"`；这组值要调（换默认采样器、换步数）时，
漏改任何一份的表现是「**同一次生图的三个入口参数不同**」——不报错、不留日志，
只体现在出图结果上。

**人工判据**：一个函数若同时满足「**无 React、无 IO、纯取值/换算**」与「**语义与
名称完全一致**」，它就只能有一个落点——`src/lib/`（`lib/` 是被视图层与逻辑层共同
依赖的**唯一**安全方向）。收敛后的实例：`lib/workshop/param-coerce.ts`
（`paramString` / `paramNumber` / `paramInt` + `DEFAULT_GEN_PARAMS`）。

**顺带修掉的一个静默错值**：三份副本都用 `typeof value === "string" ? Number(value)`
解析数值，而 **`Number("")` 是 `0` 不是 `NaN`**——参数表里留了个 `""`（用户清空输入框）
会被解析成 `steps = 0`（画面全黑），而不是回落到缺省值。中央实现显式拦掉空串，
与 `lib/error-message` 的「空串 = 没有值」同一口径（那里 `new Error("")` 会渲染成
空白提示条，是同一类 bug 的另一处实例）。

> **不是所有「看起来像」的都该合**。`components/workshop/hooks/use-file-upload.ts`
> 的 `errorMessage(err)` 同样长得像 `lib/error-message.ts` 的中央实现，但**签名不同**
> （没有 fallback 参数、返回可空）—— 硬合会把「空串回落」与「调用点兜底」两层含义
> 搅在一起。判据里的「语义与名称完全一致」是必要条件：**签名不同就是不同的函数**，
> 此时宁可留着两份。

> **为什么不给这一档做门禁**：「两个函数是不是同一个」机器判不出来（改名、等价重构、
> 参数顺序不同都构成反例），把阈值降到十几行只会把噪音引回来。这一档由 Code Review
> 与 §13.1 自查清单兜，判据靠**知道该往哪放**（`lib/`）而不是靠脚本拦。

### 12.13 函数长度上限（文件有人管，函数也得有人管，机器强制）

**判据一句话**：函数体超过 **400 行** 即进「拆分候选」清单；按**文件**的
「超阈值函数数」记棘轮，**只许降不许升**。由 `scripts/check-function-length.cjs`
在 pre-commit 与 CI 强制。

**为什么不能只靠 R5**：R5 管的是**文件**行数（超 900 行提醒）。这两条维度不同，
缺口很实在 —— 一个文件完全可以「行数没超但函数超了」，而更糟的是 R5 连文件都漏时
（历史口径只扫 `src/components/`），**全仓库最大的那个函数就完全没有任何护栏**：
`settings/SettingsPageView.tsx` 的 `SettingsPageView` **单函数 2186 行**，塞了约 15
个设置分区，任何改动都要先在这两千行里定位，而「能不能拆」没有任何机器信号。

**两层的分工**：

| 门禁        | 管什么                  | 判据                                                                          | 行为        |
| ----------- | ----------------------- | ----------------------------------------------------------------------------- | ----------- |
| R5（§12.8） | **文件**行数            | `src/**` 超 900 行，按文件计数（§12.13.3）                                    | 提示 + 棘轮 |
| §12.13      | **函数**行数（TS/TSX）  | `src/**` 函数体超 400 行（含无名字的 IIFE / 回调体，见 §12.13.2），按文件计数 | 提示 + 棘轮 |
| §12.13.1    | **函数**行数（Rust 壳） | `src-tauri/src/**` 函数体超 120 行，按文件计数                                | 提示 + 棘轮 |

三条都**只提示存量、阻断增量**：存量交给排期（清单本身就是那张排期表），增量交给
棘轮（不得静默长出第二个巨型文件 / 巨型函数）。

**400 这个数字不是拍的**：本项目 400 行以上的函数共 **22 个**（含 §12.13.2 纳入无名字
块体后新亮出的 2 个跨行签名组件），正好是「人工排期拆得完」的规模；降到 200 会让 40 个
函数一起亮，清单变噪音，没人会照它排期。

**技术判据（踩过的坑）**：括号配对**只认 `()` `{}` `[]`，不认 `<` `>`**。TSX 里的
泛型参数（`TaskProgressNode | undefined`）与 JSX 标签都是不配平的尖括号，一旦参与
计数，累计深度会漂成负数，**函数尾永远找不到** —— 泄漏表现是「一个 TSX 文件只报
0~1 个巨型函数」这种静默漏报。三种圆括号在 TS/TSX 里总是配平的。字符串 / 模板 /
注释里的括号同样要跳过（否则 `"}"` 这种字面量会把函数尾切错）。回归测试见
`tests/check-function-length.test.ts`（含「字符串里的括号不参与配对」一例）。

**棘轮口径按文件计数、不按函数名**：用名字做键会让「改名」被当成新增；用数量则只
关心「这个文件里还有几个巨型函数」，拆掉一个就少一个。

**棘轮不许被静默放宽**：基线与脚本各带一个**判据版本**（`RULE_VERSION`）。只有判据
本身变了（例如把无名字的块体纳入统计）才允许 `--update` 一次性重记，其余情况数字只许
下降 —— 否则 `--update` 就成了「这条先放宽一下」的后门。判据变更后未重记的基线会被
直接拦下（旧数字与新计数不是同一个量，比对没有意义）。

#### 12.13.1 Rust 壳的函数长度（`src-tauri/**`，机器强制）

上面那条门禁**只扫 `src/**` 的 TS/TSX**，Rust 侧完全没有同类护栏 —— 于是
`src-tauri/src/lib.rs` 的 `run()` 里塞了近 300 行的窗口 / 托盘 / 协议 / sidecar
编排，而「能不能拆」在这条链路上**没有任何机器信号**（ISSUE #536 P4）。
`scripts/check-rust-function-length.cjs` 补齐这个维度，与 JS 侧同构：按**文件**的
「超阈值函数数」记棘轮（`scripts/.rust-function-length-baseline.json`），只许降不许升。

**阈值是 120（不是 400）**：两侧代码的「自然长度」不同 —— TS/TSX 有大量 JSX 与类型
声明，单个组件函数几百行尚可读；Rust 侧是结构化编排，**120 行已属「该拆了」**，这也
正是 P4 报过长的口径。用 400 会让 `run()` 那 278 行整段落在阈值下面 —— 门禁在、
却对本次要修的实例一声不吭。

**判定细节与 JS 侧的差异**：声明形态认 `fn name(` / `pub fn` / `pub(crate) fn` /
`async fn` / `unsafe fn`；括号状态机额外要处理 Rust 特有的两种字面量 ——
**`r#"…"#` 原始字符串**里的括号、以及 **`'` 的两义性**（字符字面量 `'x'` 要跳过，
生命周期 `'a` / `&'a str` 不能当引号，否则状态机错位）。泛型尖括号
（`Vec<Option<T>>`）与 JSX 同理由**不参与配对**保证。重构后全仓最长的 Rust 函数是
`run()` 的 79 行，阈值 120 留有余量。回归测试见
`tests/check-rust-function-length.test.ts`。

#### 12.13.2 回调体与 IIFE 同受约束（ISSUE #570 第 7 项，机器强制）

**判据一句话**：**无名字的块体**（立即调用 IIFE、事件回调、闭包参数）与具名函数
**走同一阈值、同一棘轮** —— 「一个函数的行数」这件事不因它有没有名字而不同。

**为什么必须补这一半**：原判据只认「有名字的声明」（`function f` / `const f = (…) =>`），
于是**把超长逻辑塞进 IIFE 或回调里能整条绕过门禁**。这不是假设 —— 本仓库实例：

| 位置                                                                     | 形态         | 行数      |
| ------------------------------------------------------------------------ | ------------ | --------- |
| `lib/comfyui/lifecycle.ts` 的 `ensureComfyUiReady`                       | 外层具名函数 | 405       |
| ↳ 同函数内的 `st.starting = (async () => {…})()`                         | **IIFE**     | 288       |
| ↳ 同 IIFE 内的 `stdout` / `stderr` / `exit` 三个 `on(…)`                 | **回调**     | 合计约 40 |
| `lib/comfyui/workflow-detail.ts` 的 `cacheJson(k, ttl, async () => {…})` | **闭包参数** | 278       |

外层那条能被抓住，**里面的 288 行却完全隐形** —— 而真正让这个函数不可读、不可测的
正是那 288 行（见本小节下方的「等待循环与事件回调」）。同源的还有
`executor-cli.ts` 的 4 个 30~98 行回调、`drizzle-studio/lifecycle.ts` 的 80 行 IIFE。

**技术判据**：识别 `=> {` 与无名字的 `function (…) {` 两种头（具名头另行识别，避免把
签名里的类型注解 `(msg: string) => void` 当成回调）；**长度从声明行算起**（签名占了 7 行
时那 7 行也属这个函数）；具名与匿名**嵌套时两条都报** —— 它们要拆的方式不同：外层按
职责切分支，内层直接提成具名函数，只报外层会让内块继续在「外层已经很糟」的掩护下膨胀。
字符串 / 模板 / 注释里的 `=>` 与 `function` 一律先剥离（否则文档与调试文案会误报）。

**这一条同时补掉了另一个静默漏报**：原判据的两条正则要求「名字 + 同一行的 `(`」，于是
**签名跨行的具名函数也看不见** —— `export const WorkflowSubgraphNode = React.memo(function
WorkflowSubgraphNode({ data, selected }: { … }) {`（638 行）与
`GlobalStepLogPanel`（454 行）就是这样一路合法存在的。新判据按「声明行 → 配平后的函数体
`{`」定位，跨行签名与 `React.memo(function …)` 包装都在射程内（这两条是本次重记基线时
新亮出来的存量，已登记进拆分清单）。

**推荐写法：等待循环与事件回调用「策略注入 + 具名纯函数」拆**

这两类超长块体的共同点是「同构的多分支」与「捕获大量外部状态」。拆法是固定的两步：

1. **同构的等待循环 → 一个接受策略对象的函数**。两条分支各自实现「拉起 → 等待就绪 →
   判死 → 超时收尾」时，循环体只留差异（探测方式、判死判据）作为参数：

   ```ts
   /* 循环只有一份；keepAlive 与 bound 的差别全在 wait 与 isDead 里。 */
   async function waitForComfyReady(opts: {
     wait: () => Promise<string | null>;   // 探测一次，返回就绪 base 或 null
     isDead: () => Promise<boolean>;       // 判死（进程消失 / 保活进程未出现）
     deadline: number | null;
     onDeadSeen: () => string;             // 判死时的可行动文案（唯一一处）
   }): Promise<EnsureResult> { … }
   ```

   错误文案**收敛到一处**（原文案在两条分支里逐字重复了两遍，改一句要改两处）。

2. **事件回调 → 导出的具名纯函数**。回调之所以「不可测」，是因为它闭包捕获了
   `st` / `recentOutput` / `log` 这些宿主状态；把状态与端口显式传进去，它就成了可
   单测的普通函数：

   ```ts
   /* 导出即可直接调用，无需真实子进程。 */
   export function buildOutputSink(deps: {
     pushRecent: (line: string) => void;
     appendRuntimeLog: (line: string) => void;
   }): (chunk: Buffer) => void { … }
   ```

**正向案例**：`lifecycle-derive.ts` 已把启动判决表抽成纯函数（覆盖率 90%）。本条的
拆分是同一手法往「等待循环」与「事件回调」上的延伸 —— 判据是**能不能在测试里直接调它**，
而不是「拆成几个文件」。

**拆分已落地（ISSUE #570 第 1~6 项）**，基线随之收紧（22 → 20）。三处手法可照抄：

- **同构等待循环 → `waitForComfyReady(opts)` 接受策略**（`comfyui/lifecycle-wait.ts`）：
  keepAlive 与 bound 两条路径只注入 `probe` / `isDead` / `earlyExit`，超时文案收敛到一处；
  drizzle-studio 的同类 IIFE 也复用它，不再各写一遍轮询。
- **事件回调 → 导出的具名函数**：`createOutputSink(deps)` / `createRecentOutputLedger()` /
  `createChildExitHandler(deps)` 把 `st` / `recentOutput` 等宿主持有量改为显式传参，
  于是「截断到 500 字符」「留底 60 行」无需真子进程即可断言。
- **`cacheJson(…, async () => {…})` 闭包 → 具名 `buildWorkflowDetailJson(input)`**：
  闭包体只调一次又不返回对象，缩进与外层脱节；提为具名函数后语义与调用点分离。
- **comfy-cli 流解析 → `comfyui/executor-cli-stream.ts`**：stdout 按行聚合 envelope
  （`createCliEnvelopeParser`）、stderr 过滤与限行（`createCliStderrSink`）、envelope
  收口（`createCliFinisher`）各自成函数。**面板 `log` 与成功/失败收口一律经参数注入**：
  直接 import `runner-state` / `executor-finalize` 会经 `core/repository` 拖进 DB，
  使这些函数无法脱离 `.env` 单测 —— 而「能直接在测试里调它」正是本条的判据。

#### 12.13.3 文件行数棘轮的「行数口径」陷阱（ISSUE #637，机器强制）

R5 的棘轮口径是**按文件的超限行数**记账（`scripts/.file-size-baseline.json`，只许降不许升），
由 `scripts/check-file-structure.cjs --strict` 在 CI 判定。**难点不在棘轮本身，而在「行数」这个量**。

**行数不是内容量。** R5 数行数用的是逐行状态机（`split("\n").length`），不重排、不合并行长、
不做任何归一化 —— 于是同一段逻辑的行数完全取决于**它写得多紧凑**。一次全库 prettier 治理
（把紧凑的单行参数表 / 对象字面量展开、按宽度拆行）能让「一个字都没改」的文件凭空多出几十行。

**现场（ISSUE #637）**：`LogPanel.tsx` 的基线 1102 记于全库 prettier 治理**之前**；
治理后同一文件（内容未增）已是 1236 行。此后任何人**一行都不碰它**，CI 也报
`R5 超限文件继续变大(… → 1102 → 1236 行)` —— 棘轮把「格式口径变化」读成了「这次改动
让文件变大」，而作者无从下手：要他为了过门禁把已格式化的文件再压缩回 1102 行，等于让
门禁否掉 §13 的 prettier 口径。

**修法：比对前按 `baselineRev` 同口径重数。** 基线自带记它那一刻的修订号，判定时用
`git show <rev>:<file>` 取基线版本的内容、按**今天同一套计数**重数出 `baseLines`，
再与当前行数比较 —— 判据是「这个文件在**同口径**下比基线那一刻多没多」：

- 基线记录 `baselineRev`（`--update` 写入）；
- 文件在基线版本里不存在（本次新增）/ 基线缺 `baselineRev`（旧基线）/ git 不可用
  → 退回基线上的记录值（与历史行为一致，也不静默漏放）；
- 判据版本 `R5_RULE_VERSION` 抬到 3（旧数字与新口径不是同一个量，须一次性重记），
  再抬到 4 —— 见下面的「基线修订号必须可达」。

**不要改成「全仓整体行数比」换算**（试过，实测不行）：prettier 是**逐文件**重排，各文件的
展开倍率差异极大（同一批 9 个超限文件里既有 0.958 也有 1.130），全仓比例约等于 1.0 ——
换算后对 `LogPanel.tsx` 仍判「变大 136 行」，即该口径解决不了它要解决的问题。

#### 12.13.3.1 基线修订号必须可达（ISSUE #653，机器强制）

同口径重数有个**前提**：基线里那个 `baselineRev` **还在当前检出里**。而它记的通常是
**分支提交**（`--update` 写在特性分支上），合入后不再有 ref 指向，一次 `git gc` 就把它变成
不可达对象 —— 此后 `git show <rev>:<file>` 一律失败。

失败时的表现与根因**完全不像**：同口径重数静默退化成「拿记录值直接比」，而记录值记在
**另一个格式时代的源码**上，于是判据退回版本 3 要消灭的那个「跨格式时代相减」。

**现场（ISSUE #653）**：`LogPanel.tsx` 基线 `988` 记于 `116666f`（已不可达），该文件今天按
同一套计数口径是 993 行，**一个字都没改**。CI 报的却是
`R5 超限文件继续变大(… → 988 → 993 行)` —— 谁看了都会去拆文件，而真实动作是重记基线。

| 情形                                               | 判据                                                                                | 可行动作                                       |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------- |
| `baselineRev` 可达                                 | 按它同口径重数出 `baseLines`，与实际行数比                                          | 真有膨胀才拆文件                               |
| `baselineRev` 可达、但该文件当时不存在（本次新增） | 退回记录值                                                                          | 先拆分                                         |
| `baselineRev` **不可达**                           | **单独报**「基线修订号 … 在本检出里取不到」，并显式说明比的是两个格式时代的绝对行数 | `git fetch --unshallow` 后 `--update` 重记基线 |
| 基线缺 `baselineRev`（旧基线）                     | 退回记录值                                                                          | `--update` 补上                                |

判据拆开的意义是**报错指向正确动作**：不可达 ≠ 文件变大。`--update` 时也会确认一次新记的
修订号在本检出里可用，浅克隆 / 只取单分支的 CI 上会提示先 `git fetch --unshallow`。

回归测试在 `tests/check-file-structure.test.ts` 的「R5 行数口径随 baselineRev 重数」一组
（真 git 仓库造「基线版本 / 当前」两态）：基线数字记少 → 同口径重数后放行；内容未变 → 放行、
再真加 20 行 → 阻断；基线版本无此文件 / 旧基线无 `baselineRev` → 退回记录值；**修订号不可达
（含内容同时变大的情形）→ 只报「取不到」并指向重记基线，不含「继续变大」**。

### 12.14 本机服务端点收口到单一事实源（机器强制）

**判据一句话**：默认端口、回环主机、服务 Base URL 只允许在
`src/lib/endpoints.ts` 定义一次；别处一律 import，禁止再写字符串字面量。

**真实事故（ISSUE #536 P3）**：`http://localhost:11434/v1` 一度散落在 **5 个文件**
（设置页 placeholder、`repository-user.ts` 的入库默认值、`llm/server.ts` 的 env 兜底、
`db/schema.ts` 的列默认值、`server/workshop/llm.ts` 的 MCP 兜底），
`http://127.0.0.1:8188` 又散落在另外几处。改一次默认端口要改多处，漏一处的表现是
**静默的行为分叉**：设置页显示 11434、实际请求打到另一个默认值上 —— 两边都不报错。

**该模块的两个硬约束**：

1. **零依赖、零 `server-only`** —— 它同时被浏览器组件（设置页 placeholder）、
   Next 服务端（API route / repository / DB schema）与纯 Node 的 MCP 进程读取，
   任何一侧引入运行时依赖都会把另两侧带崩；
2. **只放「默认值本身」，不放「怎么解析用户配置」** —— 解析（env → DB → 请求覆盖）
   各自在自己的层里做，不混进这一层。

**回环主机用 IPv4 显式写法**：`LOOPBACK_HOST = "127.0.0.1"` 而不是 `localhost` ——
Node 的 fetch 会把 `localhost` 先解析成 IPv6 `::1`，而 ComfyUI / Ollama 默认只监听
IPv4，表现为「`curl localhost:8188` 通、程序连不上」这类难查的 ECONNREFUSED
（细节见 `comfyui/client.ts` 的同类说明）。

**改这里的值之前先 grep 一遍**：本模块存在的意义就是让那次 grep 只需要一次。

### 12.15 死代码的裁决口径：先查「有没有人自己实现了同一件事」（ISSUE #573）

**判据一句话**：发现零调用 / 零覆盖的抽象时，**不许直接删**，先 grep 全库回答
一个问题 —— **「本该用它的人，是不是自己写了一份等价的？」** 三种结论各有唯一答案：

| 现场                                                       | 结论     | 判据                                                             |
| ---------------------------------------------------------- | -------- | ---------------------------------------------------------------- |
| 别处有**等价的实现**（同一 code / 文案 / 结构被抄了 N 份） | **接线** | 这是「本应复用却自己实现」，删掉等于把 N 份复制永久化            |
| 无等价实现，但属**跨领域通用**能力，且已有明确的落地时机   | **保留** | 保留必须在 Issue 里写明「谁在什么时候会用」，不写就是删的理由    |
| 无等价实现，且只是「可能有用」的通用抽象                   | **删除** | 需要时再引入 —— 引入一个抽象的成本远低于长期维护一个误导性空抽象 |

**第一条为什么排在最前**：这类死代码的危害不在「占行数」，在**它的存在本身在骗人**。
`ensure/route.ts` 曾写 `{ error: { code: "auth.required", message: "未登录或会话已失效" } }`，
而 `core/errors.ts` 的 `AuthError` 默认值**逐字相同** —— 但那时 `AuthError` 零调用、
`code` 里还写着「配合 `./api` 的 `toErrorEnvelope()`」而 `./api` 模块**根本不存在**。
于是每个新 route 都照着抄第 19 份，改一句文案要改 18 处。**只有把两边接起来，
「唯一事实源」才成立**；纯删除会把「18 份副本」从「有替代品」变成「没有替代品」。

**第二条的时间尺度**：`core/events.ts` 的 `eventBus` 零 `publish` 时看起来也像死代码，
但领域事件（`task.succeeded` / `project.updated`）是**跨模块解耦**的通用机制，且
现状已有具体缺口 —— 任务终态靠 `store.emitter`（按 taskId 分桶的进程内
`EventEmitter`）推给 SSE，**新增一个「任务完成时也做别的事」的消费者就得改执行层**。
这就是保留它的理由：不是「以后可能有用」，是「现在就有第二个消费者无处安放」。

**第三条的反面**：`core/result.ts`（89 行 `Result` / `Ok` / `Err` / 守卫 /
`mapResult` / `flatMapResult` / `unwrapOr`）全库零引用，而各处边界用的是**判别式联合**
`{ ok: true, base, detail } | { ok: false, detail }`（`lifecycle.ts`、
`llm/usage-test.server.ts`、`agent/types.ts`）—— 成功分支还携带领域字段，
与 `Result<T, E>` 的单值 `value` 形状**并不通用**：塞进泛型只会把 `base` / `detail`
压成 `T` 再让调用方断言回来。所以那是**另起一套**，不是「本应复用却自己实现」→ 删。

**接线时必须把抽象放在对的层**：`core/errors.ts` 保持**零框架依赖**（它同时被
Next 服务端与纯 Node 宿主读取），`NextResponse` 的适配放在
`src/server/lib/error-response.ts`。把 `next/server` import 进 `core/` 会让
「核心层可被任意宿主复用」这条前提静默失效。

**拒删的门槛与拒接线的门槛一样高**：只有「别处已有等价实现」与「已有明确落地时机」
两种理由能保住一段死代码；「以后可能会用」不够。裁决结论要写进 Issue 的清单，
写不出理由的条目按删除处理。

**防回潮**：接线后必须有机器判据。本条的实例是
`src/server/lib/error-response.test.ts` —— 它断言 `src/app/api/**` 里不再出现
`error: { code: ... }` 字面量（**它当场抓到第 19 处**：`custom-nodes/route.ts` 的
`custom_nodes.read_failed`）。没有这道门禁，接线只是「这一轮接上了」，下一个人照旧会抄。

### 12.16 零消费导出（死代码）的机器判据（ISSUE #573 第 9 项，机器强制）

**判据一句话**：**地基层**（`src/lib/**` + `src/trpc/**`）的**值导出**
（函数 / 常量 / 类 / 枚举）若在**生产消费方**（`src/**`、`scripts/**`、`e2e/**`）
与**它自己的测试文件**里都除声明处之外**零引用**，即判定为零消费，必须登记进
棘轮基线（只许降不许升）；新增一个即阻断提交。由 `scripts/check-dead-exports.cjs`
在 pre-commit 与 CI 强制，基线 `scripts/.dead-exports-baseline.json` 当前
**0 个**（见下「基线归零之后」）。

**「谁算消费方」是判据本身，必须与判据口径一致（ISSUE #565复议）**：判据此前
只拿**数量**说话（`symbol` 在引用方范围里出现 ≤ 1 次），而引用方范围**不含
任何测试** —— 于是「同文件单测逐条锁住的纯函数」被永久判成零消费，34 个登记项
里绝大多数是这么攒出来的。现在两张表都是判据：

| 消费方                                                                       | 算不算 | 为什么                                                                                                              |
| ---------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------- |
| 生产源码（`src` / `scripts` / `e2e`）                                        | **算** | 唯一能证明「生产路径真的会走到」的证据                                                                              |
| **模块自己的测试文件**（`src/lib/x/y.ts` ⇄ `src/lib/x/y.test.ts` / `tests/y.test.ts`，以及**任何 import 了该模块**的测试） | **算** | 纯函数被同域单测逐条锁住时，它的可观察行为的确在跑；且这**不可能误伤真死代码** —— 真死代码不会有人为它写测试       |
| `tests/**` 里**只是提到**该名字的其它模块的测试                             | 不算   | 把整个 `tests/` 当消费方 = 判据退化成「有没有人写过这个名字」；按 **import 关系**判定才是精确的                     |

> 「测试算不算消费方」只定义这一处，脚本与本文同口径。

**基线归零之后的证据问题**：清单为空时，「当前清单为空」**不再能证明扫描器在
工作** —— 一个永远返回空的扫描器会让所有断言全绿。因此脚本提供
`--verify <rel>#<Symbol>` 单条精确复核（打印「有消费 / 零消费 + 依据」），
回归测试用它钉住「真的被消费的符号必须报有消费」这条反向锚点，而不是只断言
「清单为空」。

§12.15 给了「发现死代码时该接线的还是该删的」这套裁决口径，但它此前**只有口径、
没有判据** —— 实到「导出但零外部引用」566 个的清单是人工读出来的，而那份清单里
**绝大多数是同文件内使用的 props 类型**（`type` / `interface`），根本不是死代码。
所以本条的扫描范围刻意**只认值导出**：

| 形态                                           | 是否纳入   | 为什么                                                                                       |
| ---------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------- |
| `export function` / `const` / `class` / `enum` | **纳入**   | 值导出零消费 = 生产路径永远走不到（§12.15 第三条）                                           |
| `export type` / `interface`                    | **不纳入** | 绝大多数是「同文件内使用的 props 类型」，纳入等于把判据变成噪音（566 个清单里 90% 来自这里） |
| `export * from` 转发                           | **不纳入** | 是否被消费由被转发模块自己判，转发处重复计数会让同一件事有两个数字                           |

**为什么按「符号」记账、且基线要反向核对**：与重复块 / 函数长度 / 文件行数 /
环依赖同一口径 —— 棘轮只许降不许升，且「登记项已失效」必须当场删掉。某个符号
后来被接上线（或直接删掉）时，基线里那条如果留着，清单就成了一份**会静默漂移的
豁免表**（§18.4 的同款教训）：它看起来在记账，实际已经不对应任何事实。

**为什么只扫「地基层」（`src/lib/**` + `src/trpc/**`）**：`src/components/**` 的
`export` 大量供 shadcn 式「同域消费」与 barrel 转发，判据在那里必然误报；而
`src/lib` 与 `src/trpc` 才是被 `server` / `components` / `app` **共同依赖的地基**
（§18.2），「零消费」在那里才是真问题。

**`src/trpc` 是 ISSUE #565 补进扫描范围的**：`src/trpc/server.ts`（RSC 的
`api` + `HydrateClient` 整条链路，`createHydrationHelpers` + `createCaller` +
`cache(getQueryClient)`）在全库（含 `tests` / `scripts` / `e2e`）**零引用**，
却因为原判据只扫 `src/lib` 而长期活着 —— 一条完整的死链路躺在客户端入口目录里，
没有任何机器判据管它。实测 `src/trpc` 的 4 个值导出（`createQueryClient` /
`api` / `TRPCReactProvider` / `vanillaApi`）**全部有消费方**，把该层纳入扫描
**零误报**，因此并入同一判据（同一份清单只定义一次，不再另起一份会各自漂移的
「trpc 死代码扫描」）。这条死链路按 §12.15 第三条**删除**：全库没有等价的
手写实现（不存在「本应复用它却自己写了一份」），也没有明确的落地时机 ——
本应用的服务端页面只渲染外壳，数据一律走客户端 `~/trpc/react` / `~/trpc/vanilla`，
`src/app/workspace/page.tsx` 更把视图全部 `dynamic(..., { ssr: false })`，
RSC 预取在这套「客户端拉取」形态里没有位置，「以后可能用」不构成保留理由。

**基线归零（34 → 0）是怎么做到的**：那 34 条被逐条按 §12.15 复核过。
复核时实测出一个共同结构 —— **清单本身在骗人**：绝大多数条目的性质是
「注释说它有用，判据说它没人用」，而结论从来不是「注释对」也不是「判据对」，
而是**两边都不对，缺的是把它们接起来的那一步**。三类处理：

| 类别                              | 数量 | 处理                  | 实例                                                                                                                                                                                                     |
| --------------------------------- | ---- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 别处有等价实现（本应复用却自己实现） | 3    | **接线**              | `emptyProject()` ← 视图里手写的 `DEFAULT_META`；`sanitizeModeValue()` ← 视图里手写的 `"text"`；`NEXTJS_PANEL_LOG_PREFIX` ← 路由里手写的 `"nextjs-panel-"` 前缀                                                    |
| 纯视觉/开发期反复，产品里没有位置  | 1    | **删除**              | `workflowArdot` 的调试标签：`WorkflowNodeArdot` 是「对齐设计稿的纯视觉测试节点」（无 data / 无 handlers），没有调试价值，却要为它维护一条渲染链路                                                          |
| 「以后可能会用」的通用抽象         | 30   | **删除**              | `shouldReportReady(p) === (p !== null)` 这类**一行转发**、`hasDesktopMarker` / `isDesktopInstall` 这类「组合调用判断 kind」的语法糖、`MODEL_REGISTRY` 整族（画布早已改成选工作流库工作流）、`log-paths` 里那批**实际由脚本侧各自拼路径**的常量 |

三类里最值得记住的是第三类 —— 它们全都**长得像基础设施**，这正是它们能长期
躺着的理由。判据只有一句：**留着的理由必须写得出「谁在什么时候用它」**，
写不出即删（§12.15 第二条）。「它是通用工具」「以后做 X 会用到」都不是理由。

**退出方式**（与其它棘轮一致）：把符号接上线、或删掉，然后
`node scripts/check-dead-exports.cjs --update` 收紧基线。**新写的零消费导出没有
退出通道** —— 要么接上消费方，要么不要写。回归测试见
`tests/check-dead-exports.test.ts`。

### 12.17 出口纪律：barrel 不转「假承诺」，基类不做横切（ISSUE #565）

两个位置的「注释与现状相反」被机器判据收口（pre-commit 第 23 步 / CI
`Core barrel & repository base discipline`，回归测试
`tests/core-barrel-entry-discipline.test.ts`、`tests/repository-base-purity.test.ts`）。

**① `src/lib/core/index.ts` 不再 `export *`。**

它曾是四个 `export *` 的转发，模块文档写着「所有 server 端模块统一
`import { ... } from "@/lib/core"`」—— 而**全库只有 2 处**真的这样导入，实际
口径是深路径（`@/lib/core/repository` 等）。判据三条：

- **不许 `export *`**：它把整层的加载代价（pino + zod + Drizzle 表定义 +
  `server-only`）与「谁依赖了哪一份」一起转给引用方，也让转出的符号**漏出**
  §12.16 的零消费判据（该脚本刻意不认 `export *`）。
- **每个转出符号必须有消费方**：没有消费方的转发 = 一条「看起来有用」的出口。
- **新代码一律走深路径**：只有「类型 + 值都来自同一层且确实要它们的合集」时才用
  别名（现存一处：`src/lib/skills-seed.ts` 取 `SkillSeed`）。

**为什么这条要从「注释约定」升级成判据**：`export *` 与同层模块的组合会造出
**一个靠「没人这么写」才不成立的环** —— `core/index` → `core/logger` →
`lib/app-runtime-log` → `lib/log-paths`，而 `log-paths`（同层）若从 barrel 取用，
环就闭合。§12.7 的环检测只认**真实存在的边**，抓不到「一写就成环」的潜在组合；
回归测试用一个合成图把这个反例钉住，说明「判据保留在这里的理由」。

**② `repository-base.ts` 是纯机械 CRUD 基类。**

它曾在 `create` 里打一条 `log.debug("create", { id })`。这不是「日志实践」，而是
把**日志口径钉在基类**上：每个子类想记点有信息量的东西时只能自己再加一条；同时让
这一个模块在**没有日志设施**的宿主（测试、纯 Node 脚本）里也必须连带加载日志实现
（pino + 脱敏 + 写盘镜像）。判据两条：基类不许 import 日志实现（`./logger` /
`pino` / `app-runtime-log`），不许 import 上层（唯一允许的 `~/server/**` 依赖是
`~/server/db/schema` 的表类型定义，那是数据层同层成员）。

需要留痕的写入由**子类按自己的语义**记 —— 例如任务状态机在
`repository-task.ts` 里记状态迁移，那才是有信息量的那一行（§12.4 的「只写当前
代码的 Why」同样适用于「该不该在这里打点」）。

> **通用口径**：把横切关注点（日志、错误上报、埋点）放进**基类**，换来的是
> 「所有子类都被记成同一种形状」+「基类的每个宿主都必须具备那套设施」。基类只
> 该翻译「实体 ↔ 表 ↔ 主键」这类机械关系。
