### 15.2 组件质量评分参考

评审/自审组件时，按以下维度给分（每项 0-2 分，满分 20）。**14 分以下建议重构后再合入**。

| # | 维度 | 2 分 | 0 分 |
|---|------|------|------|
| 1 | 单一职责 | 一个组件一件事，行数 ≤200 | 600+ 行干 8 件事 |
| 2 | 状态归属 | 状态放对层（Zustand/tRPC/useState） | Context 存高频状态 / 双写 |
| 3 | 性能 | 大列表虚拟滚动、动画用 transform | 5000 行一次性渲染 / 动画 width |
| 4 | 类型安全 | 无 `any`，API 响应 Zod 校验 | `as Record<string,any>` 堆砌 |
| 5 | a11y | 可交互元素有 label、模态焦点管理 | 图标按钮无 label、模态无焦点陷阱 |
| 6 | 错误处理 | ErrorBoundary 隔离 + 降级 + toast | 白屏崩溃 / 静默吞错 |
| 7 | 样式一致性 | Design Token/语义色、lucide 图标 | 魔法值散落、内联 SVG 堆砌 |
| 8 | 测试/可验证 | 关键逻辑有测试或手动验证记录 | 无测试、无验证说明 |
| 9 | 可读性 | 注释解释"为什么"、无内联 IIFE | 废话注释、JSX 内嵌完整业务逻辑 |
| 10 | 空态/边界 | 空态引导 + 边界值处理 | 空白 / 超长输入未截断 |

**分级**：
- **18-20 分**：标杆组件，可作为团队范例引用。
- **14-17 分**：合格可合入，记录改进点后续优化。
- **<14 分**：需重构（拆分/状态迁移/补测试）后再 Review。

### 15.6 疑难排查记录（随问题归档，对齐主规范 §11）

- **子工作流卡死 / 前端无响应**：先查日志归档（`LogProvider` + 磁盘分层），再对照主规范 §11.1 排查清单（画布、comfyui 子进程、ws 通信）。
- **换行符全文件 diff 噪声**：确认仓库 LF 统一，提交用 `git -c core.autocrlf=false add`（见 [13.7](13-提交与-code-review.md#137-换行符与提交噪声lf)）。
- **git-lfs 提交挂起**：Windows 环境加 `-c filter.lfs.process=` 绕过参数（见 [13.8](13-提交与-code-review.md#138-windows-git-lfs-提交)）。
- **Linux/CI 装依赖失败（better-sqlite3 原生模块）**：`pnpm install` 走 node-gyp rebuild 编译
  better-sqlite3 时，若构建机缺 make/gcc/g++（无 build-essential）会直接失败。这不代表代码或依赖问题，
  只是缺编译工具链。在跑 `pnpm install` 前先 `apt-get install -y build-essential`（Ubuntu/Debian）或
  `base-devel`（Arch）即可；better-sqlite3@13 内置 prebuild 二进制可复用，编译脚本仅兜底。
  若日后重启平台侧流水线，构建镜像务必挑带编译工具的（`node:24` 的 Debian 骨架就自带
  make/gcc/g++），这样 `pnpm install --frozen-lockfile` 不必额外装包；缺工具链的表现是
  安装阶段就红，而不是「装完了但跑不起来」。
- **子工作流内部节点「标题丢失 / 参数名串位 / 右上角编号对不上」**：下钻到子图内部时，
  节点标题与参数名各有独立的取值链，改了一处最容易漏另一处 —— 排查时按三条线逐条走：
  ① **标题**走 `friendlyNodeTitle(classType, title)`，`title` 来自 `graph[id]._meta.title`，
  而子图解析（`workflow-subgraph-parse`）必须像顶层路径一样把 raw 节点的 `title` 带过去，
  否则作者名丢掉、退回类别名（`PrimitiveInt` → "Primitive Int"）；
  ② **参数名**走 `label → localized → name`，其中 `label` 会被「子图暴露口作者名回收」
  结果覆盖，那张表**必须按 `节点id::槽位名` 记账** —— 同一子图里多个同类节点的内部槽位名
  天然重名（四个 `PrimitiveInt` 的入参都叫 `value`），只按槽位名记账会被后写的暴露口覆盖，
  表现为某个节点的参数名变成别的节点的作者名；
  ③ **右上角编号**分两套语义：项目画布按画布节点列表顺序显示短序号 `#1/#2…`，
  工作流编辑器画布显示**真实节点 id**（`#1670`，与 JSON 查看器 / 执行日志 / ComfyUI 报错
  逐字一致）。两者都叫「右上角编号」，改其中一处时务必确认另一处不在同一个组件里共享实现。
- **画布上「隐藏一个端口圆点」把整条线弄没了（error#008）**：React Flow 的边靠 `sourceHandle` /
  `targetHandle` 去两端节点的 `handleBounds` 里找锚点，**找不到就整条边丢弃**并打
  `Couldn't create edge for source handle id: …`（`error#008`）。所以任何 `<Handle id="…">` 的
  渲染条件，都会连带决定「引用它的那些边画不画得出来」。想「不显示但仍要连线」时，**只能做视觉降级
  （缩小 / 降透明度），不能条件卸载**。排查与判据见 `WorkflowEditorCanvas` 的 `handleError`
  （它把「视口裁剪」造成的假告警与真正缺 handle 的告警分开），改完先确认控制台没有新的 `error#008`。
- **画布上「线不接端点、有的口拖不动也落不下（而且没有任何提示）」**：与上一条同属 `handleBounds` 家族，
  但成因不是「handle 被卸载」，而是**端点坐标压根没重算过（陈旧）**。React Flow 的落点几何只在
  **节点元素尺寸变化**时重算（它给自己挂了一层 ResizeObserver 去调 `updateNodeInternals`），而节点对象里的
  `width` / `height` 会被写进节点 DOM 的**内联样式**、且 `handleBounds` 量到之后**仍然取声明值**
  （`getNodeInlineStyleDimensions`）—— 于是「尺寸由内容撑开」的节点外框被钉死在声明高度上：内容长高不触发
  观察、`handleBounds` 停在第一次测量的坐标，边就从卡片半空出发 / 落在圆点旁边；**首帧之后才出现的端点**
  更是从未登记，而 React Flow 起手就是按它找 handle（`getHandle` 取不到即**静默 return**，连
  `onConnectEnd` 都不回调），于是表现为「拖不动，也没有提示」。
  **两条判据**：① 尺寸由内容决定的节点只用 `initialWidth` / `initialHeight` 声明**首帧**尺寸（量到即撤，
  外框改由内容决定），只有「尺寸就是声明值」的空节点（如撑画布高度用的背景板）才写 `width` / `height`；
  ② 端点**清单**变化时（IO 到位 / 换模式 / 只读 ↔ 可连线）主动重算一次（`useUpdateNodeInternals`），
  别指望元素尺寸一定会变 —— 恰好等高的替换不会。回归见 `use-library-wire-flow.test.ts` 的
  「首帧尺寸的声明方式」与 `WorkflowLibraryCanvas` 的 `useHandleInventoryRefresh`。
- **子工作流里「暴露口接进去的那条线从来没连上」（`Couldn't create edge for target handle id: "in"`，ISSUE #441）**：
  与上一条**同源但方向相反** —— 上一条是「handle 被条件卸载了」，这一条是「边指向了一个压根不存在的
  handle」。边界连线（外层暴露口 → 内层节点某一参数行）的落点由 `target_slot` 解析，而 ComfyUI 在部分
  导出路径上给的是**控件序号**（跳过 `model`/`negative` 这类纯连接口），与内层节点 `inputs[]` 的位置是
  **两套下标空间**。错位之后槽位名解析成空串，客户端按兜底写成字面量 `in`，画布上并没有这个 handle。
  **判据**：槽位名只能来自「哨兵边记下的关联」这一事实，不重新猜下标口径 —— `boundarySlotsByNode` 把
  `target_slot` 归拢出来交给 `parseSubgraphSlots`，判定与槽位名同源（同一份 `resolveInputSlots`），
  因此不会出现「解析到一行、实际渲染在另一行」。两条配套约定：① 解析不出槽位名时**不产出这条边**
  （`buildBoundaryLinks` 里直接跳过，别让它变成指向不存在 handle 的边）；② 跳过必须**点名上报**
  （`reportDroppedBoundaryLinks` 写应用日志：哪条边、哪个节点、哪个槽位），否则「线没画出来」与
  「本来就没连」在界面上逐字相同。改动前后都用 `src/lib/comfyui/workflow-subgraph-parse.test.ts`
  的「暴露口的槽位名必须是画布上真实存在的那一行」用例组回归（旧实现下三条用例会失败）。
- **打开工作流 / 子工作流后视口停在空白处，有节点的位置在视野外（ISSUE #394）**：画布聚焦
  （`fitToContent`）此前在「第一帧 + 第二帧」各算一次包围盒就收手。问题在于 React Flow 的节点尺寸是
  **挂载后测出来的**，而画布开着视口裁剪——第一帧里只有「上一个视图留下的那块视口里」的节点会被量到
  尺寸，其余仍是 0。把这块**局部测量结果**当成整张图的范围去 fit，算出来的缩放自然与真实内容无关。
  修法是：**测量是分批到达的，聚焦必须反复算到收敛**——每一帧重算包围盒，直到整个 bbox 都被量到
  （范围不再扩大）或连续若干轮不再增长为止，每轮都下发一次视口；纯算式抽到
  `workflow-editor/subgraph-viewport.ts`（`normalizeBounds` / `computeFitViewport`，有单测）。
  两条判据一并记住：① 测量为 0 的节点**不能按 0×0 参与**包围盒，要退到节点声明的 `style` 尺寸
  （折叠节点靠这条才在范围内）；② 坐标一律按**卡片顶边**参与（React Flow 的 `position` 口径），
  与实测尺寸同一套坐标系，混用「body 顶边」会让兜底路径算出整体偏移的框。另外自动聚焦每次进图只做
  一次，作者把节点拖出视野后需要出口——画布右上角「🎯 居中」按钮只动视口、不改数据。
- **打开子工作流仍然没聚焦（收敛算对了，但这一帧从没排上）（ISSUE #394 第二轮）**：上面那条修完
  后用户反馈「还是和之前一样」。根因不在算式，而在**排程被 cleanup 吃掉**，是一条通用的
  React effect 陷阱，任何「按图 key 只做一次」的副作用都要防：

  ```
  commit N   下钻进子图 → 聚焦 effect 按新 key 排下一帧 rAF（还没触发）
  commit N+1 节点整批同步（setNodes）→ nodes.length 变化 → 聚焦 effect 重跑
             cleanup 先取消 commit N 那一帧未触发的 rAF
             重跑时若「已聚焦」在**排程时**就写死 → 被拦住、不再补排
  ⇒ 图被记成「已聚焦」，视口却留在上一份图（截图停在父工作流的左上角）
  ```

  判据与修法：**「已做过」的记账必须记「真的做完了」，不能记「排过程了」。** 具体到本处，
  `createFitOnceScheduler`（同在 `subgraph-viewport.ts`）把「排程」与「已聚焦」分开——
  `markPending(key)` 允许同一 key 重复调用（被 cleanup 取消的那次能补回来），
  `markSettled(key)` 只在**视口真正下发、且测量收敛（`done`）之后**才调用；提前在首帧记账也不行，
  首帧可能还在量上一份图的节点，会把这帧的范围错当成本图的。排查同类问题的路数：先把 effect 的
  `console`/单测打点铺在「effect 进入 / cleanup / 回调真正执行」三处，看是**算式错**还是
  **这一帧根本没排上**——两者的现象（视口没动）一样，但改法完全不同。回归保护见
  `workflow-editor/FitOnOpen.test.tsx`（用真实 effect 时序复现「key 变 + 节点数变」的两次 commit，
  旧写法下断言失败）。
