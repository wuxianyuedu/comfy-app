## 8. 异步与副作用

> 异步逻辑是 bug 高发区（竞态、内存泄漏、错误处理）。本章给出数据获取、副作用清理、并发控制的规范。

### 8.1 竞态请求：用 cancelled 标志或 AbortController

```tsx
// ✅ 方案 A：cancelled 标志（useEffect 内常见）
useEffect(() => {
  let cancelled = false;
  (async () => {
    const data = await fetchData();
    if (cancelled) return; // 组件已卸载或依赖变化，丢弃旧结果
    setData(data);
  })();
  return () => { cancelled = true; };
}, [dep]);

// ✅ 方案 B：AbortController（标准方案，可真正中止 fetch）
useEffect(() => {
  const ctrl = new AbortController();
  fetch("/api/tasks", { signal: ctrl.signal })
    .then((r) => r.json())
    .then(setTasks)
    .catch((e) => { if (e.name !== "AbortError") console.error(e); });
  return () => ctrl.abort(); // 卸载/依赖变化 → 中止请求
}, [dep]);
```

**判断**：简单"丢弃旧结果"用 `cancelled` 足够；需要节省带宽/避免后端无效计算用 `AbortController`。

### 8.2 tRPC / React Query 条件查询

```tsx
// ✅ 用 enabled 控制查询时机；用 isSuccess/isPending 派生 UI 状态
const detailQ = api.task.detail.useQuery(
  { id: detailId ?? "" },
  { enabled: !!detailId } // id 为空时不发请求
);
const detail = detailQ.isSuccess ? detailQ.data : null;
const loading = detailQ.isPending;
```

**规则**：不要用 `if (!id) return null` 包裹整个组件来跳过查询——让 `enabled: !!id` 控制，组件结构保持一致。

### 8.3 乐观更新

```tsx
// ✅ tRPC mutation + 乐观更新
const deleteTask = api.task.delete.useMutation({
  onMutate: async ({ id }) => {
    await queryClient.cancelQueries({ queryKey: api.task.list.getQueryKey() });
    const prev = queryClient.getQueryData(api.task.list.getQueryKey());
    // 乐观移除
    queryClient.setQueryData(
      api.task.list.getQueryKey(),
      (old: { tasks: Task[] } | undefined) =>
        old ? { ...old, tasks: old.tasks.filter((t) => t.id !== id) } : old
    );
    return { prev };
  },
  onError: (_err, _vars, ctx) => {
    // 失败回滚
    if (ctx?.prev) queryClient.setQueryData(api.task.list.getQueryKey(), ctx.prev);
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: api.task.list.getQueryKey() });
  },
});
```

**规则**：乐观更新必须配 `onError` 回滚 + `onSettled` 失效重拉，保证最终一致性。

### 8.4 禁止 monkey-patch 全局 API

```tsx
// ❌ 错误：monkey-patch history.pushState（BrowserStatusBar 旧写法）
history.pushState = function (...args) {
  originalPushState.apply(this, args);
  update();
};

// ✅ 正确：用 Next.js 的 usePathname() / useSearchParams()
const pathname = usePathname(); // 路由变化自动 re-render，无需手动监听
```

**原因**：monkey-patch 在 StrictMode 下执行两次会互相覆盖原始引用；多个实例挂载会冲突；`popstate`/`hashchange` 已能覆盖多数场景。

### 8.5 useEffect 依赖与清理

```tsx
// ✅ 依赖完整 + cleanup 清理副作用
useEffect(() => {
  const handler = () => setMenu(null);
  window.addEventListener("pointerdown", handler);
  return () => window.removeEventListener("pointerdown", handler);
}, [menu]); // menu 变化重新绑定
```

**规则**：
- 依赖数组写全（eslint `react/exhaustive-deps` 开启）。
- 所有订阅（`addEventListener`、setInterval、外部库监听）必须在 cleanup 中取消。
- `setInterval` 必须 `clearInterval`；轮询组件卸载时停止。

#### 8.5.1 「依赖写全」的反面：不稳引用会把「跑一次」变成「每次渲染都跑」（ISSUE #1803）

上一条规则的反面同样致命，而它**不会**被 `exhaustive-deps` 拦下（依赖写全了，
只是那条依赖本身不稳）：**`useQuery` / `useMutation` 返回的对象、以及依赖它们的
`useCallback`，每次渲染都是新引用**。把它们放进数组 ⇒ effect 每渲染一次跑一次 ⇒
effect 里的写动作（mutation / refetch）完成又触发渲染 ⇒ **自激成循环**。

实测三种形态（同一根因，都发生在「挂载时拉一次」这类 effect 上）：

| 现场 | 表现 |
| ---- | ---- |
| `useEffect(…, [syncMut, loadModels])`，`loadModels` 依赖 `listQ` | 静置时 `model.sync` 每 10~12ms 一次（6 秒 505 次），当时打开的视图每秒重渲染上千次 |
| `useEffect(…, [load])`，`load` 依赖 `configQ` | 弹层打开后 `model.configList` 每 25ms 一次（5 秒 194 次） |
| `useEffect(…, [load, loadModelTags])`，两者都依赖各自 query 对象 | 工作流库静置时 `workflow.list` 每秒约 21 次 |

**修法**：把这类 effect 的**语义**写清楚 —— 它们要的是「挂载时跑一次」，
所以依赖数组就该是 `[]`，而「最新一份实现」收进 ref：

```tsx
const loadRef = useRef<(() => void) | null>(null);
useEffect(() => {
  loadRef.current = load; // 每次渲染同步最新一份（写在 effect 里，不在渲染期赋值）
});
useEffect(() => {
  const t = setTimeout(() => void loadRef.current?.(), 0);
  return () => clearTimeout(t);
  // eslint-disable-next-line react/exhaustive-deps -- 语义就是挂载一次，见 §8.5.1
}, []);
```

三条边界：
- ref 的赋值写在**另一个 effect** 里，不写渲染期（并发渲染下渲染期赋值是禁止的副作用）；
  mutation 的 `mutate` 本身是稳定引用，不必进 ref。
- 这种 `eslint-disable-next-line` 是**合规用法**（与 §8.6 禁止掩盖
  `set-state-in-effect` 不同）：它表达的是「我知道依赖写全了会坏，这就是我不要的」，
  注释里必须写清原因。
- **判据**：拿真实浏览器量一次「静置 N 秒的网络请求数」。这类缺陷的表现是
  **零交互下也在持续打请求**，而单测（不重渲染的 `renderHook`）看不见 ——
  所以每个「挂载时拉一次」的 effect，回归测试要显式 `rerender()` 几轮并断言
  请求计数不增长（实例：`use-model-library.test.ts`）。

### 8.6 避免 useEffect 内 setState 触发循环

```tsx
// ❌ 错误：effect 里 setState 且依赖含该 state → 无限循环
useEffect(() => { setCount(count + 1); }, [count]);

// ✅ 正确：用函数式更新 + 条件守卫，或放到事件回调里
useEffect(() => {
  if (shouldIncrement) setCount((c) => c + 1);
}, [shouldIncrement]); // shouldIncrement 是独立 boolean 状态
```

**React 19 注意（强制）**：React 19 严格 hooks 规则已移除 set-state-in-effect 豁免，**effect 内同步 `setState`（含函数式更新）会触发 `react/set-state-in-effect` lint error**。上述"✅ 正确"示例若在 effect 内同步提交仍会报错，需改用主规范 §4.6 的两种规范写法：

```tsx
// 规范写法一（渲染期对比 + 渲染期 setState，React 19 允许且自动重渲染）
const [count, setCount] = useState(0);
const latestRef = useRef(0);
if (latestRef.current !== shouldIncrement) {
  latestRef.current = shouldIncrement;
  setCount((c) => (shouldIncrement ? c + 1 : c));
}

// 规范写法二（setTimeout 延迟到 render 提交后，纯 effect 场景）
useEffect(() => {
  const t = setTimeout(() => setCount((c) => c + 1), 0);
  return () => clearTimeout(t);
}, [shouldIncrement]);
```

禁止用文件级 `/* eslint-disable react/set-state-in-effect */` 掩盖违规；lint 修复与功能改动分提交。

### 8.7 异步错误处理统一

```tsx
// ✅ 顶层 await 用 try/catch；事件回调里 catch 静默错误需注释原因
async function loadData() {
  try {
    const data = await fetchData();
    setData(data);
  } catch (err) {
    toast.error("加载失败", err instanceof Error ? err.message : String(err));
  }
}
```

**规则**：用户可感知的失败用 `toast.error` 提示；静默忽略只在确实无影响时（如非关键日志加载），且必须注释说明。

### 8.8 并发请求：用 Promise.all / Promise.allSettled

```tsx
// ✅ 独立请求并发，缩短总耗时
const [tasks, projects] = await Promise.all([
  fetchTasks(),
  fetchProjects(),
]);

// ✅ 部分失败不影响其他（加载历史日志等多文件场景）
const results = await Promise.allSettled(files.map((f) => fetchFile(f)));
results.forEach((r, i) => {
  if (r.status === "rejected") console.warn(`加载 ${files[i].name} 失败`, r.reason);
});
```

### 8.9 有序性与并发写纪律

> 来源：#3884 有序性专项审计（#3891~#3913 逐单修复）。写任何「共享状态 + 异步」的代码，按下面四条逐条对照；典型后果是**状态回退**与**已取消的操作又被执行**（已取消订单又被发货）。

**① 终态写入必须条件更新（CAS），不许无条件覆盖**
任务 / 成片 / run 这类带终态的状态列（`SUCCEEDED/FAILED/CANCELLED`、`DONE/FAILED/CANCELLED`、`done/failed/cancelled`），写回必须带「仅当当前状态仍在允许的来源集合内」的条件（同一条 `UPDATE` 的 `where` 里判，SQLite 单写者下原子）。无条件整列覆盖会把用户在长动作期间写入的暂停 / 取消回退成运行中。对终态的重复操作（取消已取消的、失败已失败的）按**幂等返回**处理。仓库内样板：`repository-task-impl.ts` 的 `writeGuard`、`repository-film.ts` 的 `claimGenerating / claimComposing / markDone`、`repository-production.ts` 的 `updateRunGuarded`。

**② check-then-act 必须原子化或先占位**
「先读 → 判断 → 再写」两步之间隔着 `await` 时，并发调用会双双通过判断——重复提交计费任务、重复建行、击穿并发上限。修法三选一：判断与写入收进同一条条件 `UPDATE`；整个读-改-写跨度包进程内互斥（`~/lib/async-mutex` 的 `AsyncMutex` / 按 key 的 `KeyedAsyncMutex`）；或去重账本**先占位后完成**（创建前先写 promise / marker）。样板：工坊编排的 `sessionMutationMutex`、派发循环的 `dispatchMutex`、`createSession` 的先占位。
⚠️ `behavior: "immediate"` 事务只串行化**写段**：读-改-写之间夹着外部调用（LLM / 生图 / ffmpeg）时，事务覆盖不了整个跨度，必须用 mutex 或在锁内重读。

**③ 异步回调只读「发起时快照」，禁读共享可变状态**
`.then` / `await` 之后的回调里读共享 ref / 模块级变量（`xxxRef.current` 这类），拿到的是**完成时刻**的值——后发先至的第二次调用早已把它改写。发起时先 `const target = 共享值` 捕获，回调一律用捕获值；跨条目共享的 `setState`（日志面板这类）在 effect 里配 `disposed` 标志或 `beginStaleRun`（§16.2.4.34），`await` 返回后先判本轮是否已作废。样板：`use-file-upload`、`use-task-step-log-stream`。

**④ 轮询必须带轮次令牌；SSE 消费必须全窗去重**
轮询回调持 `seqRef`，只接受**最新一次发起**的响应（慢响应不得把旧快照盖在新快照上；样板：`use-runtime-log-source`）。`/api/tasks/[id]/stream` 每条新连接（含 EventSource 自动重连）都会把日志**全量回放**——消费端一律走 `tailWindowAppendUnique`（`~/lib/page-window`）按 `(t, msg)` 全窗判重，不要自己写「只扫尾部 N 条」的窗口去重（回放长度远超尾窗）。样板：`use-task-log-stream`、`workflow-run-store`、`stepLogCache`。

这四条**不设启发式自动扫描门禁**（会误报一片，见 [12.18](12-代码组织与文件结构.md#1218-复用优先写之前先查缺能力补地基不造第二轮子) 末段）；承重处在两处——Code Review 的「并发与有序性」维度（[13.4](13-提交与-code-review.md#134-code-review-重点维度)）与上面点名的既有判据出口。新代码触碰共享状态、终态列、轮询或 SSE 时逐条自查。

### 8.10 重试与轮询纪律

> 来源：#3888 可重试性专项审计。全库逐处核对后**没有**发现「无上限 / 无退避 / 对非幂等下游盲目重试 / 超时层层放大」的现行违例 —— 地基已经收口：Node 侧「一次等多久」只有 [`~/lib/retry-policy`](../../src/lib/retry-policy.ts) 一份（具名策略 + `backoffDelayMs`），SQLite 撞锁循环只有 `sqlite-busy-retry.ts` 一份（只认锁族错误、穷尽原样抛出），Rust 壳轮询只有 `poll_clock.rs` 一份（墙钟预算 + 两段退避）。新写重试 / 轮询按下面五条对照，别再各写一份裸循环。

**① 次数必须有界，或挂在墙钟预算上**
无上限重试是重试风暴与雪崩的种子。两种合法形状：**有界次数**（`attempt < N`，N 写进具名策略，如 `HISTORY_READ.maxAttempts`）或**墙钟预算**（`deadline` / Rust `PollClock`；**退避不缩短预算**——预算是时刻差，不是「次数 × 间隔」，`poll_clock.rs` 有测试钉住这句）。`while (true)` / `for (;;)` 只允许两类：**读流到 `done`**（那是消费不是重试），以及**常驻消费进程内标记**（`PollClock::forever`，须注明为何永不过期）。

**② 退避形状二选一，并把「为什么」写在策略名旁边**
`fixed`：对端**一定就绪、只是慢一拍**（刚提交的任务、停止后的探针）——退避只会让结果更晚到。`exponential`：对端**可能长时间不可用**（WS 重连）——别一直砸它。这是场景判定不是偏好；拿不准读 `retry-policy.ts` 文件头那组对照。

**③ 多个进程 / 客户端会同时撞同一资源 ⇒ 开抖动**
一群 Next worker 同时切 WAL、桌包双进程抢写锁，同步的重试拍会继续撞在一起。`backoffDelayMs` 的 `jitter`（`"full"` / `"equal"`，缺省 `none`）是这一格的地基；单客户端对单服务的重试不必开。**新增多进程竞争场景的重试，默认开 `equal`。**

**④ 只重试幂等 / 可重入的操作**
确认「失败的那一次没有留下半态」才许自动重试：SQLite 撞锁重试成立的前提是失败事务已整体回滚（#2586）。带副作用的下游（提交任务、发消息、扣额度）不确认幂等就**不自动重试**——重试决定留给调用方或用户（`task.retry` 是显式业务动作，不是循环）。

**⑤ 超时预算要罩住里面的重试，不许层层放大**
外层等待预算 ≥ 内层单次超时 × 次数 + 退避总和。探针单跳用 `AbortSignal.timeout(单次预算)`，总预算用 deadline 判。反例形状：「外层 5s 超时里跑 10 次 × 2s 的重试」——外层永远等不到内层收敛。本仓样板：`waitForComfyReady` 的 deadline、`ci-ga-verdict-readout` 的 45m 预算 + 连续未认领熔断。

这五条同样**不设启发式自动扫描门禁**（同 [8.9](#89-有序性与并发写纪律) 的理由）。自查入口是审计用的 grep 清单——`retry|重试|backoff|jitter|maxAttempts|while \(true\)|for \(;;\)` 命中后**人工逐处判**它是重试、读流、还是文件名避让；Code Review 的「异步与副作用」维度（[13.4](13-提交与-code-review.md#134-code-review-重点维度)）照此核对。

### 8.11 可终止性纪律

> 来源：#3889 可终止性专项审计（#4003~#4008 逐单修复）。写任何「等外部 / 起子进程 / 占内存」的代码，按下面五条逐条对照；典型后果：线程打满（async 形态 = 并发槽 / 互斥被永久占住）、OOM、进程残留锁住文件。

**① 一切「等外部」的等待必须有预算**
fetch 用 `AbortSignal.timeout(单跳预算)`（样板：`src/lib/comfyui/client.ts` 每个调用、`src/server/workshop/llm.ts` 的 180s、launcher `classifyProbe` 的 2.5s）；包 promise 用 `~/lib/with-timeout` 的 `withTimeout` / `withTimeoutResult`；子进程挂看门狗，超时走 `onTimeout` 收尾（样板：custom-nodes `spawnCapture` 的 `killChild`、console 的 `MAX_RUN_MS` 看门狗）。**外层 deadline 罩不住内层无预算的单跳**——单跳自己也要有界（[8.10](#810-重试与轮询纪律) ⑤ 同族）。

**② 取消信号必须传播到真正干活的那一层**
入口的 `req.signal`（客户端断开）要传进上游 fetch 与子进程：流式响应的 `ReadableStream` 要实现 `cancel()`；SSE / ndjson 路由在 abort 时停表、杀子进程、发终帧。样板：`tasks/[id]/stream` 的 cleanup 三路径收口、console 的断开 `runner.cancel()`、`/api/llm` 把 `req.signal` 传进 `streamLLM`。**UI 的「停止」只翻状态不算取消**——步内挂起的等待收不到信号（run-engine 的取消只在步间生效，就是这一格的反例）。

**③ 内存队列与缓存必须有界**
只增不减的数组 / Map 要有上限与淘汰（样板：`runner-state` 的 `LOGS_MAX_LINES` / `LOGS_MAX_TASKS` LRU、`stepLogCache` 的 256 条 LRU、`event-loop-watch` 的 20 条环形）。生产快于消费要有背压或丢弃策略（日志尾窗 `tailWindowAppend`），不许「先存下来再说」。

**④ 常驻循环要能退**
轮询循环带 deadline 或 max ticks（样板：film `watchLoop` 的 `WATCH_MAX_ITER`、run 循环的 `MAX_TICKS`、`poll_clock.rs` 的墙钟预算）；`while (true)` / `for (;;)` 只允许三类：读流到 done、字符串收敛（每轮严格变短）、**有 earlyExit / isDead 出口且语义是「等到进程退出或用户停止」的常驻等待**（须注释写明为何无硬超时，样板：lifecycle-launch 的手动启动语义）。订阅退订后要停表（样板：`queue-signal` 最后一个退订 `stopTimer`）；依赖外部巧合的重排（如 `use-narrow-nav` 的首帧对账）要有次数上限。

**⑤ 子进程与请求的生命周期要绑死**
凡是「为一个请求拉起的子进程」，客户端断开或超时都必须回收：登记进可回收的账本（dev-launcher 的 `spawned` + `reapAll`），**不 `detached` 逃逸进程组**；回收统一走 `killProcessTree`（硬规则 3）。`unref()` 只解决「不吊住事件循环」，不解决「不留孤儿」——两者要分开对待。

**自查 grep 清单**（命中后人工逐处判，不设启发式门禁，同 8.9 / 8.10 的理由）：`while \(true\)|for \(;;\)|setInterval\(|new Promise\(|await fetch\(|spawn\(|addEventListener\(|new EventSource\(` ——逐处回答四问：**什么时候停？谁取消它？内存涨到多大算到头？进程 / 连接随谁退场？**答不上来就是本节的候选违例；Code Review 的「异步与副作用」维度（[13.4](13-提交与-code-review.md#134-code-review-重点维度)）照此核对。

### 8.12 一致性与双写纪律

> 来源：#3890 一致性（双写）专项审计（#4019~#4026 逐单修复）。写任何「同一份事实落在两处」的代码（DB 列 ↔ 内存缓存、DB ↔ 磁盘文件、localStorage ↔ 服务端镜像、主表 ↔ 冗余列），按下面五条逐条对照；典型后果：脏读、缓存与库长期不一致、用户内容被旧值静默覆盖。

**① 先答「谁是权威」，再动手**
单一事实源先定下来：另一份存储是**投影 / 缓存**（可随时重建，样板：`runner-state` 的内存日志是工作集、`task.logs` 是落库投影；工坊草稿的权威在 production，`workshopSession` 是同事务镜像）。两份都「算权威」等于没有权威——漂移只是时间问题。

**② 同一事实写两处，必须同事务或同语句**
跨表 / 跨行的双写收进 `db.transaction(…, { behavior: "immediate" })`（样板：`workshopSession` ↔ `production` 同事务、`saveLlmSettings` 跨表同事务）；能并成一条条件 `UPDATE` 的就不要两条。两次独立写之间就是失败窗口——写完 A 写 B 失败，A 就成了无人对账的孤儿。

**③ 缓存 / 内存副本不得先于持久化更新**
更新顺序必须是「先落盘（权威）、后改缓存（投影）」；持久化失败要**回滚缓存或失效指纹**（样板：`app-settings` / `api-channel` 的先写盘后对齐指纹）。反例形状：先 `cache = next` 再 `writeFile`，写失败后指纹仍命中旧文件，本进程永远返回从未落盘的「新值」。

**④ 跨店读写带版本或指纹对账**
本地副本与服务端镜像各带 `updatedAt`（或内容指纹），恢复时取**较新的一侧**、迟到写拒绝覆盖较新镜像（样板：canvas-store 的 `adoptServerProject`、工坊草稿的版本对账 + 服务端 ifNewer）；「本地为空才采用服务端」不是对账——它放行陈旧本地值反写。多个写者改同一份大 JSON 列时，先拿内容写锁、锁内重读再合并（样板：`withProductionContentLock`）。

**⑤ 外部调用与本地写之间必须有补偿出口**
先写本地行、再调外部服务（ComfyUI / LLM / ffmpeg）的顺序，失败路径要么取消外部产物、要么把本地行标失败（样板：enqueue 的 cancelTask、orchestrator 的 markFailed + cancelTask 补偿、reaper 对账）；「外部已花费、本地没记录」这一格没有任何补偿可做，只能靠提交前的顺序与幂等闸防住。

**自查 grep 清单**（命中后人工逐处判，不设启发式门禁，同 8.9~8.11 的理由）：`localStorage\.setItem|writeStorageJson|writeFile\(|cache = |\.set\(.*cache|patchContent\(|replaceLogs\(|upsert` ——逐处回答三问：**这份事实的权威在哪？两份写入是否同事务 / 同语句？一边失败时另一边怎么回到一致？**答不上来就是本节的候选违例；Code Review 的「并发与有序性」维度（[13.4](13-提交与-code-review.md#134-code-review-重点维度)）照此核对。
