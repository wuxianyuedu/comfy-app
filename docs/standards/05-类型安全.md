## 5. 类型安全

> 本项目使用 TypeScript 7（strict）+ Zod 4。类型安全的目标是：编译期捕获数据结构变更、避免 `any` 静默吞错。

### 5.1 禁止 `any` 和 `as Record<string, any>`

```tsx
// ❌ 错误
const data = response as Record<string, any>;

// ✅ 正确：Zod schema 校验
import { z } from "zod";
const ResponseSchema = z.object({
  files: z.array(z.object({
    name: z.string(),
    size: z.number(),
  })),
});
const parsed = ResponseSchema.parse(response);
```

**例外**：与第三方库交互、渐进迁移阶段可局部用 `unknown` + 类型守卫，`unknown` 比 `any` 安全（必须窄化后才能用）。

### 5.2 禁止 eslint-disable 堆砌

```tsx
// ❌ 错误：12 个 eslint-disable 说明类型系统已经在尖叫
/* eslint-disable @typescript-eslint/no-explicit-any */
/* eslint-disable @typescript-eslint/no-unsafe-assignment */

// ✅ 正确：修复类型问题，而不是静音
```

**允许的局部禁用**：仅在调用第三方无类型 API 时，用行内 `// eslint-disable-next-line` 单行禁用 + 必须附注释说明原因，禁止文件顶部批量禁用。

### 5.3 用 ReturnType 推导组合 hook 的返回类型

```tsx
// ✅ 正确：实现改了类型自动跟
export type IOEditContextValue = ReturnType<typeof useIOEditContext>;
```

### 5.4 枚举用 union type（字符串字面量），不用 enum

```tsx
// ❌ 错误：enum 生成反向映射，包体积/ tree-shaking 不友好
enum Status { Pending = "pending", Running = "running" }

// ✅ 正确：union type + as const 派生（单点维护）
const STATUS_LIST = ["pending", "running", "done", "error"] as const;
type Status = typeof STATUS_LIST[number]; // 派生，单点维护
```

### 5.5 API 响应一律 Zod 校验

```tsx
// ✅ tRPC 已内置 Zod input/output schema；REST 端点手动校验
const TaskListSchema = z.object({
  tasks: z.array(TaskSchema),
});
type TaskList = z.infer<typeof TaskListSchema>;

// 在 fetcher 边界校验一次，内部全链路类型安全
async function fetchTasks(): Promise<TaskList> {
  const res = await fetch("/api/tasks");
  return TaskListSchema.parse(await res.json());
}
```

**收益**：后端字段增删/改名时，前端在**数据入口**就报错，而不是在某个深层组件里 `undefined` 崩溃。

### 5.6 类型守卫与窄化

```tsx
// ✅ 自定义类型守卫
function isTask(item: unknown): item is Task {
  return typeof item === "object" && item !== null && "id" in item && "status" in item;
}

// 使用
const tasks = rawList.filter(isTask); // 类型自动窄化为 Task[]
```

### 5.7 避免 `as` 断言绕过检查

```tsx
// ❌ 错误：as 断言把类型问题推迟到运行时
const view = card.id as WorkspaceView;

// ✅ 正确：用类型约束让编译器帮你校验
const QUICK_ACTIONS: Array<{ id: WorkspaceView; ... }> = [ ... ];
// 或运行时校验
function isWorkspaceView(v: string): v is WorkspaceView { ... }
```

### 5.8 `unknown` vs `any` 选择

| 场景 | 用 |
|------|---|
| 外部输入（fetch/JSON.parse/event） | `unknown`，然后 Zod 校验或类型守卫窄化 |
| 确实任意结构（如动态 className 合并） | `any` 仅在工具函数内部，对外仍返回具体类型 |
| 第三方无类型 API | `// @ts-expect-error` 单行 + 注释，或用 `unknown` 包裹 |

### 5.9 索引访问与首字符截取

tsconfig 开了 `noUncheckedIndexedAccess`：索引访问的结果一律是 `T | undefined`。按"首字符"截取文本也不要用 `s[0]`——空串得 `undefined`，emoji/代理对会取到半个字符。

```tsx
// ❌ 错误：name="" 时渲染空白；"😀" 取到高代理半字符
<span>{name[0]}</span>

// ✅ 正确：Array.from 按码点拆分 + 显式兜底（参考 AgentPanel.tsx 头像）
const initial = Array.from(name.trim())[0]?.toUpperCase() ?? "A";
<span>{initial}</span>
```

**规则**：`s[0]` / `s.slice(0, 1)` 只可用于确定 ASCII 的场景；面向用户展示的字符截取一律 `Array.from(s)[0]`（或 `[...s][0]`）+ `??` 兜底。

### 5.10 `no-unnecessary-condition` 的四种去向（ISSUE #2919）

`typescript/no-unnecessary-condition`（oxlint type-aware）报的是「按类型看，这个条件恒真 / 恒假」。
本仓的类型大量来自 `JSON.parse as X` / `unknown` 收窄原语 / zod `looseObject` / 手工 JSDoc ——
**「类型比运行时窄」是设计如此**，所以这条规则的命中默认是「类型的锅」不是「代码的锅」。
每处命中只允许落进下面四格之一，并在 PR 描述里逐条说明落哪一格、为什么：

| 格 | 判据 | 动作 |
|---|---|---|
| **① 类型修好** | 值真的可能缺失，只是声明写得比运行时窄（后端回包、`spawnSync` 出参、`RegExpExecArray` 分组、JSON 解析结果…） | 把 `\| null` / `\| undefined` 补回声明处；`?.` / `??` 原地保留 |
| **② 真多余** | 同一作用域里刚判过、或分支已把值窄化掉 | 删条件 / 删死分支 |
| **③ tsc 要** | 运行时确实恒非空，但编译器不建模（如正则必需分组的 `m[1]` 是 `string \| undefined`） | 保留，并在行尾一行注释写明「这处是给 tsc 看的」 |
| **④ 落账禁用** | 值是闭包 / 回调里写的标志位那类，规则的控制流分析看不到写入点 | `// oxlint-disable-next-line typescript/no-unnecessary-condition -- <一行理由>` |

两条判据冲突时**归 tsc**：`scripts/gates/check-scripts-typecheck.cjs` 把 tsc 那侧判成硬闸（新增零容忍），
所以「规则说多余、tsc 说必需」的行一律保留，走第 ③ 格。

第 ④ 格不许扩成「懒得判」：一条禁用 = 一条理由，理由要写「运行时为什么仍可能走到另一支」，
写不出来的就去查类型来源（那就是第 ① 格）。

### 5.11 接口契约与兼容纪律（ISSUE #3907）

「调用方拿到的形状 / 码 / 语义不许漂」。写或改任何 tRPC 路由、REST route、
SSE/ndjson 通道、MCP 工具时，按下面六条逐条对照：

**① 错误信封只有两套口径**：REST 纯错误走 `errorResponse`（`{error:{code,message}}`）、
带业务字段的失败走 `apiErrorBody`；tRPC 路由抛 `TRPCError`。**业务前置不满足**
（缺数据、状态不允许）必须是 `PRECONDITION_FAILED` / `NOT_FOUND`，不许裸抛
`Error` 落成 500——客户端要能按码分支「该不该重试」。同一条件在同一族端点里
用同一个码。

**② 枚举与入参 schema 单源派生**：状态 / 档位词表定义一次（lib 或 schema 层导出
常量），类型与 zod 都从词表派生；服务端能发出的值，客户端的 union 必须认。

**③ 列表端点必答分页与截断**：有 `take` 就有 `skip`/`cursor` 与 `hasMore`
（或 `total`）；静默截断（返回不足还装作「就这些」）是契约违约。排序带
tiebreaker（同毫秒批量写入的行序才稳定）。

**④ 批量接口必答部分成功语义**：按项明细（每项的成败 / 跳过原因），失败可
归因、可决定重试；不许把「已完成」「撞活动任务」「坏项」混进同一个 `skipped`。

**⑤ 传输层形状由真实链路的测试钉住**：tRPC 的传输是 superjson——Date 到
浏览器仍是 Date；wire 契约测试用 superjson 往返建模，不按「JSON 序列化后的
想象」写判据。

**⑥ 同族端点的鉴权、幂等应答、请求体校验口径对齐**：同资源族的每条路由
同一鉴权闸；坏请求（畸形 JSON / 表单）一律 400 + 可读文案；重复删除返回
一致的幂等标记（`alreadyGone`）。
