## 11. 测试与可观测性

> 商业级项目需要可验证的质量保障。本章给出测试分层、行为测试重点、埋点与日志可观测性规范。

### 11.1 测试分层

| 层级 | 工具 | 覆盖范围 | 示例 |
|------|------|---------|------|
| 单元测试 | Vitest | 纯函数、工具函数、Zod schema | `format.ts`/`suggestFix.ts` |
| 组件测试 | Vitest + Testing Library | 组件渲染、交互、a11y | `TaskCard` 点击/空状态 |
| 集成测试 | Playwright | 关键用户流程（端到端） | 创建任务→生成→查看历史 |
| 视觉回归 | Playwright screenshot | 关键 UI 的像素基线：xyflow 画布、空态、弹窗、Tailwind 断点、深色主题 | 画布布局/配色、弹窗尺寸 |
| 类型检查 | tsc --noEmit | 全项目类型安全 | CI 强制 |

### 11.2 行为测试优先

```tsx
// ✅ 测行为（用户能感知的），不测实现细节
import { render, screen, fireEvent } from "@testing-library/react";
import { TaskCard } from "./TaskCard";

test("点击任务卡片触发 onOpen", () => {
  const onOpen = vi.fn();
  render(<TaskCard task={mockTask} onOpen={onOpen} />);
  fireEvent.click(screen.getByRole("button", { name: /查看任务/ }));
  expect(onOpen).toHaveBeenCalledWith(mockTask.id);
});
```

**规则**：
- 用 `getByRole`/`getByLabelText`（a11y 友好）而非 `getByTestId`（最后手段）。
- 断言用户可见结果，不断言内部 state/`useStore` 调用细节。

### 11.3 测试覆盖重点（商业级）

| 场景 | 必测 |
|------|------|
| 空状态 | 列表为空时的引导 UI 渲染正确 |
| 加载/错误态 | loading skeleton / error toast 触发 |
| 边界值 | 超大输入、超长字符串截断、空字符串 |
| 交互 | 按钮点击、键盘快捷键（Ctrl+Shift+L） |
| 竞态 | 快速切换/连续点击不崩溃、状态最终一致 |
| a11y | `axe` 静态分析 + 键盘可达性手动验证 |

### 11.4 Zustand store 测试

```tsx
// ✅ store 可在测试中直接调用，无需渲染
import { useLogStore } from "./log-store";

test("addEntry 保留最近 MAX 条", () => {
  const store = useLogStore; // hook 上挂 getState/setState/subscribe
  for (let i = 0; i < 2500; i++) store.getState().addEntry({ level: "info", message: String(i) });
  expect(store.getState().logs.length).toBe(2000);
  expect(store.getState().logs[0].message).toBe("500"); // 旧的被丢弃
  store.getState().reset?.(); // 清理，避免跨用例污染
});
```

### 11.5 埋点与可观测性

```tsx
// ✅ 关键用户行为埋点（如"创建任务""导出工作流"）
analytics.track("task_created", { source: "homepage", workflow: "z-image" });
```

**规则**：
- 仅记录行为事件 + 非敏感上下文（来源页面/工作流类型），**不记录 prompt 原文、文件路径等敏感内容**。
- 埋点失败不影响主流程（try/catch 包裹）。
- 开发环境可关闭埋点（`if (process.env.NODE_ENV === "production")`）。

### 11.6 console 拦截可关闭

`LogProvider` 的 console 拦截在生产环境可关闭，避免性能开销/循环风险：

```tsx
// ✅ 仅开发环境 + Tauri 桌面端启用拦截
const ENABLE_LOG_INTERCEPT = process.env.NODE_ENV === "development" || isTauri();
useEffect(() => {
  if (!ENABLE_LOG_INTERCEPT) return;
  // ... 拦截逻辑
}, [addEntry]);
```

### 11.7 CI 质量门禁

CI 门禁命令以 package.json 脚本为准，与 [13.5](13-提交与-code-review.md#135-ci-门禁) 同一套，避免两处重复维护：

```
PR 合并前必须通过：
✅ pnpm typecheck            （tsc --noEmit）
✅ pnpm lint --max-warnings 0 （零错误零警告）
✅ pnpm test                 （vitest run）
✅ pnpm build                （生产构建）
✅ playwright test           （E2E，关键流程）
✅ playwright test e2e/visual （视觉回归像素基线，见 §11.8）
```

**规则**：CI 失败阻断合并；本地 pre-commit hook（lint-staged）做轻量 lint + typecheck。


### 11.8 视觉回归（像素基线）

> 目标：捕获**布局/像素级退化**（配色、间距、尺寸、深浅色、响应式断点被无意改动），
> 这是 DOM 快照/行为测试都覆盖不到的防线。

#### 方案选择（避免两套基线维护成本）

仓库采用 **Playwright `toHaveScreenshot`** 作为唯一视觉基线方案，不引入
Chromatic / Vitest browser mode / 第二套截图工具。理由：

- 仓库已装 `@playwright/test` 并用于 E2E，复用同一浏览器基础与 webServer，无额外运行时。
- Chromatic 依赖 Storybook 基建与云服务，本仓库没有 Storybook，落地成本高。
- Vitest browser mode 需为截图单独装配浏览器驱动，且与 E2E 工具栈割裂。

**基线范围**（以「用户会看」为准，**只锁定关键 UI**，不追求全组件覆盖）：
xyflow 画布布局/节点配色、空态/空画布提示、弹窗/浮层尺寸、Tailwind 响应式断点、
深色（`.dark`）与浅色主题对比。

#### 基线用例约束

```ts
// ✅ e2e/visual/*.spec.ts 示例：锁定登录页明/暗两态
import { test, expect } from "@playwright/test";

test("登录页深色基线", async ({ page }) => {
  await page.addInitScript(() => document.documentElement.classList.add("dark"));
  await page.goto("/login");
  await expect(page).toHaveScreenshot("login-dark.png", { fullPage: true });
});
```

**规则**：
- 视觉用例**不碰随机/时变内容**（时间戳、动画、加载中骨架屏、由 DB 驱动的列表），
  否则基线必 flaky。需要时先 mock / 用固定 fixture 数据，把渲染内容钉死。
- 基线 PNG **提交入库**；用例改动导致基线变更时，用
  `pnpm exec playwright test --update-snapshots` 重录基线，并在 PR 描述里标注
  「视觉基线已更新：<原因>」，供 reviewer 人工核对 diff。
- 失败产物（actual/diff PNG）落在 `test-results/`（已在 .gitignore 忽略），仅本地/CI 排查用。
- 基线维护是**人工 review 的核心对象**：CI 只负责「不一致即失败」，是否采纳新基线由人决定。

### 11.9 DOM 快照边界：不要拿快照当结构基线

**现状问题**：`src/components/studio/**/__snapshots__/*.snap`（Vitest DOM 快照）
把整棵渲染 DOM dump 成文本，**易碎**——任何无关 class/标签/CSS 变量变更都会
击穿全部用例，且与真正的布局/像素退化无关，误报成本高。

**边界与迁移方向**：
- `toMatchSnapshot()`/`toMatchInlineSnapshot()` **禁止新增用于断言整棵 DOM 结构**。
- 判断准则：**只断言用户可见结果**（`getByRole`/`getByText` + jest-dom 匹配器，
  见 §11.2），**不要**用整棵 `container` 快照代替行为断言。
- 存量 `.snap` DOM 快照按 §11.2 迁移为「组件断言用户可见结果」，迁移完毕的
  测试删除对应 `.snap` 文件；**迁移期间不得新增** DOM 结构快照。
- 布局/视觉层面的防退化职责移交 §11.8 的 Playwright 像素基线，不在 Vitest 层用
  DOM 快照重复承担。
