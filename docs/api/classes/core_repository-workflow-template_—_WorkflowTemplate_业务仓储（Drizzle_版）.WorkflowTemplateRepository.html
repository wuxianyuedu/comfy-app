    findSourceMetaForUser

    • findSourceMetaForUser(
          userId: string,
          id: string,
      ): Promise<WorkflowTemplateSourceMeta | null>

      「这条工作流有没有绑着一个本地源文件」那一段元数据 —— 真投影。

      这里原本是一个 findByIdForUserSelect(userId, id, _select?: unknown)： 参数名承诺投影、实现里 select() 全列取，三个调用点还在按迁移前的 布尔投影写法传 { id: true, sourcePath: true } —— 类型层一声不响 （unknown + 调用点不做校验），实际每次详情加载都把 rawJson 与 positions 这两个大 JSON blob 拖出来一遍（台账 F13：同一个 unknown 签名让 train.cancel 从迁移起每次 500，这一处是它的性能版兄弟）。 现在投影是真的列清单，方法名也不再承诺一个它不做的能力。

    listForUser

    • listForUser(
          userId: string,
          opts?: { orderBy?: SQL<unknown>[]; where?: SQL<unknown> },
      ): Promise<WorkflowTemplateListRow[]>

      列表页要用的列 —— 显式投影，不是 select()。

      为什么不写 select()：它把每一列的整份值都取出来，其中 positions （每个节点的坐标数组）与 rawJson 都是大 JSON blob，而列表页对 positions 一个字都不看。全字段读法让 SQLite 把整行物化、驱动再把 几 MB 的字符串跨过 C++ ↔ JS 边界，堆压力与 GC 全落在一次轮询上。

      rawJson 必须留：可执行性判据（hasRawContent）与紧凑预览 （buildWorkflowPreview）都以它为真值来源，去掉它列表就答不出 「这条能不能跑」。positions 是唯一能整列省掉的大字段。

      mock 边界：~/server/db 的测试替身走的是内存实现，列投影在类型层 收窄、在行为层只影响读了多少 —— 见 repository.test.ts 的断言。

      • opts: { orderBy?: SQL<unknown>[]; where?: SQL<unknown> } = {}
