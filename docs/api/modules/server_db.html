    Module server/db

    db.ts -- Drizzle instance over the async @libsql/client driver.

    Connects to db.sqlite via @libsql/client (DATABASE_URL looks like file:./db.sqlite). In development the singleton is parked on globalThis so Next dev hot reloads do not reopen the connection on every re-evaluation.

    Why libsql (was better-sqlite3): better-sqlite3 is a synchronous driver -- any slow SQL, big Zod safeParse, or index scan pinned the whole Next server event loop and amplified every backend slowdown (see MEMORY notes). libsql speaks the same SQLite file format and ships a native async client, so we keep the schema, the file layout and Drizzle's libsql adapter and stop blocking the loop. Same WAL / foreign_keys pragmas as before.

    NOTE (keep this file ASCII-only): it sits on the build-time module graph and Next's error code frame renderer computes highlight spans by byte offset, panicking (end byte index N is not a char boundary) when a span lands inside a multi-byte character -- which takes the whole next build down with a Rust panic that points nowhere near the real cause. See docs/standards/launch-and-build.md sec.5.
