    Module core/logger — 全应用日志的**唯一实现**（pino）

    logger.ts — 全应用日志的唯一实现（pino）

    本模块曾是「零依赖自研日志器」：自己拼行、走 console.log/error、没有任何 脱敏。而仓库另一侧 src/server/lib/logger.ts 是 pino（带 REDACT_PATHS + 密钥值形状守卫 + ERROR 镜像进应用日志面板）。于是同一件事出现两条互不相通的 通道，直接后果有三条：

    1. 同一件事两种口径：LOG_LEVEL 的读法、级别集合、输出形态各自实现一遍；
    2. 安全契约不成立：repository-base.ts 的 log.debug("update", patch) 若某天多带一个 token 字段，旧实现会原文落盘 —— pino 那条通道有 redact 兜底，这条什么都没有（规范 07 §7.18.2.1 的脱敏契约在这条通道上失效）；
    3. 观测通道不完整：console.* 不进 ERROR 镜像（面板「应用运行」那一路 看不到），排查时「明明有 error，面板却一片空白」。

    上一轮把它改成「服务端 pino 的薄封装」，消除了通道分叉，但实现仍是两份同层 模块（lib/core/logger ⇄ server/lib/logger），只是其中一份转发给另一份。 本轮把实现（level/redact/镜像/pretty 的全部配置）合并到本文件， src/server/lib/logger.ts 改为一层兼容转发（既有导入路径逐字不变）。

    为什么实现落在 lib/ 而不是 server/

    lib 是被 server / components / app 共同依赖的地基，而日志是典型的 横切关注点。放在 server/ 会让地基反过来依赖上层：lib 侧每一处要写日志的 模块只能 import { logger } from "~/server/lib/logger"（实测曾有 11 条这样的 越界边，只能靠清单逐个登记，见 tests/lib-server-imports.test.ts）。实现落在 lib/core 后方向天然正确：lib → lib，server → lib。

    本模块不带 server-only（规范 §18.4 第三类）：它被 Next 服务端与纯 Node 宿主同时加载，加上 server-only（入口就是一句 throw）会让 scripts/*.mjs 的启动编排直接崩 —— tests/lib-node-only-declarations.test.ts 会核这一条。

    两条写入路径，脱敏各管一段

    · pino 流（nextjs 文件 / stdout）：由下面的 REDACT_PATHS 按字段名擦； · ERROR 镜像（log/services/app-runtime.log，面板可见）：不经 pino redact，由 ./redact-secret 的值形状守卫在写入边界擦，且只写文本 字段、绝不整包 JSON.stringify（规范 07 §7.18.2.1 / AGENTS 硬规则 16）。
