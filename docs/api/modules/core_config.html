    Module core/config

    config.ts — 集中式、类型化、经过校验的应用配置（Config 模式）

    为什么需要它

    代码库里 process.env.X 散落在几十处，存在三个问题：

    1. 拼写风险 —— process.env.DATABSE_URL 不会报错，只会在运行时悄悄用错值；
    2. 类型不明 —— 环境变量永远是 string | undefined，用到时才 parseInt，易出错；
    3. 默认不统一 —— 同一端口在 dev / build / script 里各自写死，难维护。

    本模块在进程启动时一次性解析并校验全部配置，输出一棵不可变的、强类型的 AppConfig 树。任何模块都应 import { config } from "@/lib/core" 后读取， 而不是再直接读 process.env。

    设计要点

    • 使用 zod 做 schema 校验：缺失给默认值、非法值给出可读错误（启动时即失败， 而非运行到一半才崩），符合「fail-fast」商业级实践；
    • 全部字段只读（Getter 返回基本类型，无 setter），避免运行期被意外改写；
    • features 子对象集中承载开关型配置（特性开关 / feature flags）， 便于灰度与排障；
    • 与 ./container 配合：配置本身作为首个被注册的服务。

    校验失败行为

    若环境变量值非法（如 COMFYUI_BASE_URL 不是合法 URL），模块加载即抛出 带字段名的可读错误，配合启动脚本的日志可立即定位，而不是在第一次请求时崩溃。
