    • applySqlitePragmas(
          target: SqlitePragmaTarget,
          pragmas?: readonly string[],
      ): Promise<void>

      把那份清单应用到一条连接上，撞锁按预算重试。

      为什么开机这几条要单独有出口（ISSUE #1282）： 三处站点（Next 主库、工坊库、执行宿主）此前各自写一遍 for (const pragma of SQLITE_PRAGMAS) await client.execute(pragma) —— 循环体逐字相同（§12.18 该收口），而更麻烦的是它没有容错： PRAGMA journal_mode = WAL 在一份还没切到 WAL 的库上要独占锁， 而 next build 会为 collect-page-data 起 7 个 worker 进程，每个都走一遍这个循环。 实测（7 个独立进程同时打一份刚建的空库）：3/8 抛 SQLITE_BUSY，异常从模块顶层 await 浮出 worker、被 Next 聚合进 Failed to collect page data for /api/trpc/[trpc] —— 报错行还落在无关路由上。干净检出上表现为「第一次 pnpm build 必失败、再跑一次就好」， 而 CI 每次都是干净检出。

      重试只认锁族错误（复用 isSqliteBusyError）：认不出原因就原样抛， 不把「只读挂载 / 磁盘满」一类真故障拖成几次同样的尝试（与 executor-write-retry 同纪律）。

      站在这里而不是各站点自己包一层：三处站点要的是同一件事，各写一遍就必然漏一处 （执行宿主那侧今天有 timeout 预算，Next 两处刻意没有 —— 预算的取舍见文件头， 与「开机这几条要不要重试」是两个独立决定，后者三处都要）。

      Parameters

      • target: SqlitePragmaTarget

        已建好的连接（@libsql/client 的 Client）。

      • pragmas: readonly string[] = SQLITE_PRAGMAS

        要应用的清单，默认就是本模块那份；只为测试留出注入点。

      Returns Promise<void>

      Throws

      非锁族错误、或重试穷尽后，抛出原错误（调用方据此失败得看得见）。
