      断开那条：给时刻 + 去向，能拿到原因就当场给。

      原因为什么不再是「等恢复那条」

      探活走的是应用服务自己的 HTTP，服务一不在那条通道必然不通——所以经 HTTP 读 run/app-service-exit.json 的那条路（GET /api/dev/last-exit）在读的这一刻 确实不通。但记录本身已经在进程结束那一刻落在盘上了，读不到它纯粹是因为 选错了通道：壳进程活得好好的，它读这个文件不经过任何应用服务 （get_app_service_exit，见 ~/lib/shell/app-service-exit 的 fetchCurrentDisconnectExit）。

      所以现在的形态是： · 拿得到（壳内，且记录确实是这一次写的）→ 当场把原因与动作写进来； · 拿不到（非壳环境 / 旧壳 / 这次断开没留下记录）→ 说清「这一刻拿不到」， 并指向恢复那条。不编一个「未知原因」——那等于把规范 §10.3.1 要消灭的 静默又请回来。

      旧行为（无论拿不拿得到都只说「原因写在 run/app-service-exit.json，恢复时给」） 是 ISSUE #1915 的现场：用户手里明明有原因（文件就在那儿），界面上却一个字都没有。
