    • whichCommand(
          name: string,
          __namedParameters?: WhichCommandOptions,
      ): string | null

      在 PATH 上解析可执行文件，返回可直接 spawn 的绝对路径。

      为什么必须自己解析：Windows 上 Node 的 spawn 不认 PATHEXT —— spawn("pnpm") 直接 ENOENT，必须给 pnpm.cmd（或它的绝对路径）；而 Linux 上给 pnpm.cmd 又同样 ENOENT。写死平台后缀会在「一种平台能用、另一种静默失败」，因此按 PATH × PATHEXT 自己扫一遍。

      但「扫到一个同名文件」不等于「能跑」：Node 的 spawnSync 在 Windows 上 不解析 shebang（libuv 直接 CreateProcess 传文件路径），所以 pnpm（corepack 那只无扩展名的 shim，本质是 #!/usr/bin/env node 的脚本）被 spawn 时一律 EACCES/ENOEXEC —— 用不了。而 PATHEXT 的顺序又把 .CMD 排在最前，于是同一目录里 「能跑的 pnpm.ps1 / 能跑的 pnpm」会被跳过，选中的偏偏是跑不起来的那个 （.CMD 只有 cmd.exe 会解释它）。表现是 pnpm -v 探测失败、stderr/stdout 全空、 启动器只报一句「未知错误」——看起来完全像 corepack 缓存损坏，实际是路径选错了。

      因此判据分两层：① executableExts() 定优先顺序（真正有可执行形态的扩展名 在前，executableKind 判不出形态的垫底）；② 取候选后做一次 usableCommand() 确认（fs.accessSync + ENOEXEC 回退），选第一个真的能跑的。
