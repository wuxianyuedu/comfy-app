      • cancel: function
        • cancel(taskId: string): Promise<TaskWriteOutcome>

          用户取消：写 CANCELLED + finishedAt。

          归属例外的唯一一处（ADR §14 D4）：取消这个动作只活在 Next 进程里，而 host 名下的行也必须能被取消，所以这里刻意不叠 ownedBy(owner)——叠了就等于 把「Next 取消 host 任务」这条合法路径堵死。跨归属的只有状态标记： 「kill 在飞执行」仍归 owner 自己做（host 的 reconcileCancelled / inline 的自己名下 cliProcs），非 owner 不越界碰执行细节。

          终态守卫照常叠：对已结束的任务点取消不该把 SUCCEEDED 翻成 CANCELLED。

      • claimNextQueued: function
        • claimNextQueued(mode: TaskClaimMode, take: number): Promise<string[]>

          队列领取（P3 §5 ADR §6/§7 Phase 3-A）：单语句 UPDATE ... WHERE id IN (SELECT ... ORDER BY createdAt LIMIT ?) RETURNING id。

          原子性由 SQLite「单写语句内子查询同语句求值」保证：inline/host 两个领取方 各自最多领走互不重叠的行。刻意不用 db.transaction + 先 SELECT 后 UPDATE： 本实现要同时跑在三种宿主（better-sqlite3 同步测试库 / libsql http / libsql file）上，async 事务回调在同步驱动上于 continuation 之前就 COMMIT， 原子性静默失效。

          归属谓词跟 ADR §6：host 只领显式 'host' 的行；inline 领 NULL（历史行与 未带归属的建行）与 'inline'。领取时把 claimedBy 覆写为 mode，NULL 行由此转为显式归属；reaper 分片（listStale* 的 owner）用同一归属谓词。

      • listStaleUnownedQueued: function
        • listStaleUnownedQueued(
              cutoff: Date,
              take: number,
          ): Promise<
              { claimedBy: string; createdAt: Date; id: string; workflowName: string }[],
          >

          reaper 扫死信 QUEUED 行（ISSUE #1204 起的口径）：QUEUED + finishedAt IS NULL + createdAt < cutoff + promptId IS NULL + 不属于任何已知归属片。前四条不变，第五条从 ownedBy(owner) 换成它的补集： pull 模型（ADR §14 D1 第二刀）下「QUEUED 且无 promptId」只剩一个意思—— 还没被领（等槽 / 等宿主起来 / 等 ComfyUI 就绪），那是健康的等待态，归领取 循环负责，不是回收器该判死的形状。这条规则原先针对的形态（raw 路径在 POST 给 ComfyUI 之前不翻 RUNNING、不写 promptId）已随「唯一提交实现 = comfy-cli + 领取即单语句原子翻 RUNNING」消失，留着它反而会先把新宿主 boot 第一拍还没来的 遗留行判成失败（实测：boot 诊断数出 hostShardQueued=1，1.4s 后同一行 FAILED）。 NULL 归 inline（见 ownedBy），所以只有「写着归属、却不在这两个值上」的行才算 无主——正常数据永远不匹配，本条因此退成畸形行的兜底出口。
