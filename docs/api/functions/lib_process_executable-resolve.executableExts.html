    Function executableExts

    • executableExts(
          env: ProcessEnv | Record<string, string | undefined>,
          platform?: Platform,
      ): string[]

      候选扩展名的优先顺序（不是一个集合，顺序即判据）。

      顺序取自「Node 能不能直接起它」： · ""（无扩展名，如 corepack 的 pnpm shim）与 .EXE —— 真正的可执行形态， Windows 上由 CreateProcess 直接起； · .PS1 —— 必须经 powershell -File 起（由 executableKind 判出来，见下）； · .CMD / .BAT —— Node 起不了（它是给 cmd.exe 的批处理脚本），只能垫底： 同一个目录里既有 pnpm.cmd 又有可用的 pnpm 时，选前者必然 EACCES； · PATHEXT 里其它扩展名（.COM / .VBS / 自定义）排最后，保持「用户配了就用」。

      .PS1 是无条件候选，不看 PATHEXT（ISSUE #1961）

      上面那三步里，.PS1 此前与 .CMD / .BAT / .COM 一样要 PATHEXT 声明才进得来 —— 而 Windows 系统的默认 PATHEXT 从不含 .PS1（PowerShell.exe 不是靠 文件关联启动的，.ps1 也不在「敲名字就能跑」的那一类里）。于是：

      · corepack 摆在 .tools\pnpm\<ver>\bin 的那三个形态里，只有 .ps1 能被 Node 起得来（无扩展名 shim 是 shebang、libuv 不解析；.CMD 是批处理、 只有 cmd.exe 解释）； · 候选表里却没有 .ps1 ⇒ whichCommand() 一个都选不出 ⇒ 返回 null ⇒ 上层报「PATH 上没有任何可用的 pnpm 形态」，而能跑的那个就摆在旁边。

      实测（自托管 Windows 节点，PATHEXT=.COM;.EXE;.BAT;.CMD;.VBS;…）： pnpmInvocation() 返回 null，而同目录的 pnpm.ps1 一直在盘上 —— 「工具链自证」因此报 pnpm 不可用，整条流水线在第 1 秒就停。

      判据因此改成：.PS1 与无扩展名 shim 一样，是本仓自己要找的形态，不由 PATHEXT 决定。理由与「为什么必须自己解析 PATH」同源（见 whichCommand 的注释）： PATHEXT 描述的是「cmd.exe 敲名字会试哪些后缀」，而这里问的是 「Node 能起得来哪些形态」—— 两个问题不同，答案也就不能共用一份。

      POSIX 只有一种形态（无扩展名），此函数退化为 [""]。
