      跑一次异步动作，并把结果接到反馈通道上。

      三件本函数一次给全的事

      1. 失败路径一定有可见出口（硬规则 4）：catch 里统一走 errorMessage(e, failureText()) —— 网络层原文（「Unexpected token '<'」） 由 ~/lib/error-message 翻译成人话，调用处不必再判一次。 finally 里清忙由调用处负责（忙标记是它的状态）。
      2. 成功静默是显式的：successText 缺席 = 成功不报（合法）， 给了就一定会报 —— 收口前那二十余处里，「成功静默」与「忘了写成功分支」 在代码上完全一样。
      3. 结果信封按同一口径读：ok ?? triggered ?? true（第三种来源 tRPC 不抛即成功）。readResultEnvelope: false 则完全不看返回值。

      返回值而不是抛错

      失败不向外抛：调用处大多需要「失败了就回滚本地乐观更新 / 刷新列表」， 那需要一个返回值而不是一个需要再包一层 try 的异常（收口前 patchModes / patchModelTags 正是这么写的，而 resyncWorkflow 那个漏了回滚 —— 差别只在「有没有再包一层」）。

      典型调用形态（成功报 toast、失败回滚列表）： 先给出 report（成功调 toast.success、失败调 toast.error）， 再 await runAsyncAction(发起调用的箭头函数, { report, failureText, successText }) —— 它返回的 { ok, detail } 用来决定要不要 void load() 回滚列表。 完整示例见 use-workflow-actions 的 patchModes。
