    • resolveCommandInvocation(
          file: string,
          args?: string[],
          __namedParameters?: WhichCommandOptions,
      ): ResolvedInvocation

      把一行「用户想跑的命令」解析成这台机器上真能起得来的形态。

      与控制台的关系：控制台的输入框只做「空格 + 引号」的分词（parseConsoleLine）， 分词之后拿到的 file 是用户写的名字（pnpm / git / node）， 而这个名字在 Windows 上多半不是一个能直接 spawn 的路径 —— 直接交给 spawn 就是那条 spawn pnpm ENOENT（ISSUE #1327 的现场）。所以起进程前 必须过这里一次。

      resolved: false 表示「PATH 上查无此命令」——不改写 command，调用方 据此给出可读出口（说清「找不到这个命令」与去过 PATH 找过），而不是把一个 裸名字丢给 spawn、拿回一句信息量很低的 ENOENT。

      ⚠️ 探针不拿 args 去起（ISSUE #1977 第八轮）

      上一层（usableCommand / commandInvocation）判「这个候选起不起得来」的方式是 真起一次，而它喂的参数就是这里的第二入参。于是「调用方要跑什么」与「探针喂什么」 被合成了一件东西 —— 后果是探针把真命令整条跑了一遍：

      · resolveCommandInvocation("node", ["scripts/e2e-run.mjs", "--grep=@critical"]) ⇒ 探针真的起了一次 node scripts/e2e-run.mjs --grep=@critical（stdio: "ignore"、 30s 上限），Playwright 的 webServer（pnpm start + 假 ComfyUI）随之被拉起来； · spawnSync 超时只收直接子进程，那些孙子进程留在端口上接着跑 —— 真那一跑 再起来时撞见「端口已有人应答」，而这一步的结论被读成「解析成功」； · 更大的形态：.cnb.yml 里每一条 node scripts/… / pnpm run build 都在 被执行两遍（一遍探针、一遍真跑），pnpm install 那一格尤其危险 （探针把安装砍在半路，留下残缺的 node_modules）。

      判据是探针参数与调用参数解耦：探针恒用一条廉价、无副作用的参数 （默认 ["--version"]；usableCommand 只读 error.code，非零退出也算「起得来」， 所以 --version 退非零的形态不会被误判）。第二入参因此在语义上只剩一件事 —— 拼进最终命令行，一个字节都不改写。

      需要带宿主参数才能应答的候选（py 启动器那种：裸 py --version 是「列出 已装版本」并退非零）走 probeArgs 显式给 —— 那是 python-resolve.ts 那条链的 事，它直接调 whichCommand()，不经过本函数。
