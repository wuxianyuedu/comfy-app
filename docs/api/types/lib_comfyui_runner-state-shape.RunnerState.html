    executedWorkflow

    executedWorkflow: Map<string, unknown>

    本次执行实际提交给 ComfyUI 的工作流 JSON。RAW 载荷存 patched（liblib subgraph 格式，未展开，含画布覆盖）；API 载荷存 execution-graph 收拾后的图。 任务完成后落盘到 generated/.../workflow.json，便于工作流模板后续改动 时仍能完整复现本次生成结果（种子已存 manifest.seed + TaskImage.seed）。

    第二个用途（ISSUE #1202 收口时登记）：WS 的 executing / progress 帧只带节点 id，日志那行「▶ 节点 [3] 采样器（KSampler）」与落库的 progressNode.classType 都靠这一份认类名 —— 必须是提交那一刻的图才与帧里的 id 对得上（画布原件会被 覆盖注入与剔除改动）。两种形状怎么认见 graph-node-class.ts。

    finalized

    finalized: Set<string>

    「终态已落库」标记（与 settled 的「终态已认领」区分）。 同一个 taskId 可能被多条收口路径尝试写终态：正常 executor 路径、 看门狗超时、reaper 孤儿回收。settled 只保证「谁先认领」，但认领失败 的一方若直接调用 finalizeFailure（不走 claim）仍会二次写库，把先写入 的失败原因覆盖掉——用户就会在「执行日志」（经 SSE 拿到的第一份原因）与 「应用日志 / DB」（被后写入覆盖的第二份原因）看到互相矛盾的结果。 这里给「DB 终态写入」单独加一把一次性锁：首个写入者落库，其余直接跳过， 保证两处永远显示同一个失败原因。

    lastNodeByTask

    lastNodeByTask: Map<string, { classType: string; node: string; t: number }>

    按节点记录完成情况。ComfyUI 发 executing 且 data.node !== null 时， 把（节点 id, classType）记在这里；下一条 executing 的 node 为 null 到达时，用记录下来的值打出「✔ 节点 X (classType) 完成」。 这样日志面板给用户的是按节点的时间线，而不只是「开始了」的标记。 仅 API 格式路径需要这一对日志；comfy-cli 路径自己会打（见 executor-ws）。

    pendingDispatch

    pendingDispatch: Set<string>

    本进程已领取、尚未收口的任务（P3 §5 ADR §14 D1 的第二刀：取代原来的 内存队列 queue 与计数器 active）。 它是「这一行归本进程在飞」的唯一内存足迹，三处都读它：并发槽位判据 （MAX_CONCURRENCY）、reaper 的进程内认领检查、取消时的归还。 为什么是 Set 而不是计数：计数答不了「这一条是不是我的」，而孤儿判决要的 正是后者（旧实现靠 queue.some(...) 回答，队列没了就得另找依据）。

    queuedEntries

    queuedEntries: Map<string, LogEntry[]>

    taskId → 本轮排队期写下的行（等待原因那类）。领取会重开 logs（重跑不混 上一轮的尾巴），这份登记让领取那一刻把本轮已经写过、且已经落库的行接回去， 否则「⏳ 等待 ComfyUI WebSocket 连接就绪…」会被抹掉——回收器不再兜底判死排队 行之后，那句是唯一说明「这条在等什么」的出口（ISSUE #1206）。 由 logWhileQueued 写、takeQueuedEntries 取走即清。
