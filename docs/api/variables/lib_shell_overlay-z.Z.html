    浮层层级（z-index）的刻度表 —— 规范 16 §16.2.5。

    背景（ISSUE #672）：同一件事（下拉浮层）曾在 MultiSegmentPopover 是 9999、WorkflowSeedModeButton 是 9999 配 9998 遮罩、SelectMenu 又是 9999，而节点 JSON 浮层用 9000/9001，全屏抽屉散落 10005/10020；状态栏 10000、消息中心 10020 —— 谁也说不清「它比谁高」， 新增一层只能再编一个更大的数。

    P2 先把自搓浮层收拢到 ui/ 原语并定下两条刻度；P4 发现余量仍有 7 处自成 一档（9998 / z-10000 / z-10020 / z-80 / z-60 / studio/logs 的 z-99+z-200），于是把刻度补成一张成体系的表：每一档都对得上一类 真实存在的浮层关系，而不是「再把魔数换个名字写进对象里」。

    数值同时定义在 src/app/globals.css 的 @theme（供 z-overlay / z-popup / z-modal / z-canvas-ui 等工具类使用），两处必须一致 —— 由 tests/overlay-z-scale.test.ts 钉住。放在 lib/shell：它是客户端可达 的跨端定层常量，lib/core 在 eslint 的 boundaries 里是 element server， 视图层引不得。

    ── 四条判据（与规范 §16.2.5 同源）─────────────────────────────

    1. modal 不进 1000~1200：那是 React Flow 给节点选中态（约 1010）与 悬浮态（1180，见 globals.css）留的位，应用模态插进去会和节点争层级。
    2. popup > modal：挂在 body 的下拉由模态内部的控件打开 （ui/select / ui/popover / ui/dropdown-menu 都是 portal 到 body）， 低于模态就等于「点得开、点不中」—— 同 §16.2.5 里日志面板那条回归。
    3. 画布内部的层级不属于本表：指针/事件只在自己容器的层叠上下文里比较， 与视口浮层不在同一维度；它们从 base 起排是为了「同一个容器内部的关系 有名字」，而不是「要和模态比高低」。
    4. chrome 严格高于其余所有档：标题行是应用级 chrome，它的可点性 由层级保证 —— 几何让位（top-title-bar，规范 12 §12.8.1）只保证「不被 盖住 / 压暗」，挡不住第三方往 body 注入的整视口遮罩。base-ui 的 InternalBackdrop（modal 打开时渲染）就是 position: fixed; inset: 0; z-index: auto; pointer-events: auto 的一层，它不受本仓库让位规则约束： 标题行若停在 z-index: auto，后出现的定位元素必然在命中测试里压过它 （实测：设置页「启动日志」全屏后窗口按钮整排点不动，ISSUE #310 第三次回归）。
