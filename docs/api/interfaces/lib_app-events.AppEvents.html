    Interface AppEvents

    全部应用事件的名字与载荷表。

    新增事件 = 在这里加一行（名字与载荷类型写在同一处），然后在派发侧 emitAppEvent("…", payload)、读侧 subscribeAppEvent("…", handler)。 不要在别处再写一遍事件名字符串 —— 判据 P61 会拦下视图 / 逻辑 / 服务端里裸写的 new CustomEvent("…") 与 addEventListener("…")。 也不许只写一端 —— tests/app-event-pairing.test.ts 要求这一行的每一条 都既有派发方又有订阅方（认字面量，也认 export const X = "…" 常量的间接写法）。

    comfyapp:canvas-sync-changed

    "comfyapp:canvas-sync-changed": undefined

    画布的服务端镜像状态变了（某条被永久拒收、或某条重新同步成功）。 载荷：无 —— 状态本身可查（~/lib/project-canvas/sync-notice 的 listSyncNotices()），读侧在挂载时也要读一次：本模块不排队重放， 而写镜像的入口不止画布那一页（工作区首页新建、画廊删除都会发镜像）， 那些页面上没有提示器 —— 只靠事件的读侧必然漏掉那一次。

    comfyapp:custom-nodes-updated

    "comfyapp:custom-nodes-updated": undefined

    自定义节点注册表被重新灌入（画布挂载时那一次、以及每次解析收尾后的那一次）。 载荷：无 —— 结论本身可查（~/config/custom-nodes 的 getCustomNodesRegistryState()：版本号 / 节点数 / 有没有拿到清单）。

    为什么读侧必须在挂载时先读一次再订阅：本模块不排队重放，而最早的一次灌入 就发生在画布挂载的 effect 里（WorkflowEditorInner 调 refreshCustomNodes()）， 那一刻订阅还没建立 —— 只订阅不读表的写法，会让「首屏节点数为 0、再进来才有」 这类现象永远说不清是谁的锅。

    曾经这条链上有过一份同名事件、只有派发方没有订阅方（当年的订阅方是画布的 添加节点菜单，后来那个菜单不在了），于是它是一个「没人听的广播」—— 台账 E9 记的就是它。现在订阅侧在 ~/components/studio/canvas/use-custom-nodes-registry。

    workspace:navigate

    "workspace:navigate": { view: string }

    请求工作区切到某个视图。载荷：视图 id（WorkspaceView）。

    为什么用事件而不是 props：触发方（工坊右栏的「资源库」卡）与持有视图状态的 容器（app/workspace/page.tsx）之间隔着 WorkshopPipeline / WorkshopAside 两层，为一条「跳过去」的链接穿三层 props 不划算；订阅侧也只有一处。

    载荷刻意写成 string 而不是 import WorkspaceView：本模块在 src/lib， 不得反向依赖视图层（§18 硬规则 22）—— 合法性由订阅侧按已有枚举收敛。
