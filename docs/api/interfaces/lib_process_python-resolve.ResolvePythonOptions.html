    Optionalprobe

    probe?: UsabilityProbe

    「起得起吗」的探针，默认真权限位 + 真 spawnSync。

    为什么要这个注入口（与 kill-process-tree.ts 的 COMFYAPP_TASKKILL 同一条口径）： 本模块判的是另一种平台上的事（POSIX 的执行位、内核解析 shebang）， 而 Windows 开发机上这两样都造不出来 —— 实测：Windows 上 fs.accessSync(X_OK) 对 0o755 / 0o644 / 0o444 / 0o000 一律通过（权限位不参与判断）， 而把一个真 .exe 改名成无扩展名再 spawn 得到的是 ENOENT（CreateProcess 不认）。 于是「POSIX 上找到就用绝对路径」「没执行位要与起不来分开报」这几档在本地只有两个 下场：整组 runIf(!win32)（= 这台机器上零执行者，台账 E7 记的形状）， 或者为「它本来就不可能红」而通过（更糟：绿灯是假的）。 注入探针后这张表在两端机器上判同一个结论；Windows 那几档照旧走真探测 （批处理不起、.ps1 落宿主、MZ 头当二进制），因为那些在本机是真造得出来的。 ⚠️ whichCommand 的记忆化键不含 probe（只有 name + PATH + PATHEXT + platform）： 同一个 PATH 上换探针又指望换结论，会读到上一条的缓存 —— 换探针的用例先 clearWhichCommandCache()。

    OptionalprobeArgs

    probeArgs?: string[]

    whichCommand 在「真起一次确认」时喂给候选的参数（默认 ["--version"]）。

    为什么要有它：同一个命令的可用判据不是统一的。python 那类解释器要的是 「能不能答 --version」，而 py 启动器裸着跑是「列出已装版本」并退非零 —— 候选名一样、判据不一样。此前 whichCommand 把这一格写死成 --version， 于是带宿主参数的候选（py -3）只能由调用方自己再包一层，或者干脆漏掉这一档 （ISSUE #1959 第二轮：门禁探的面与流水线自证探的面因此漂成两份）。 记忆化键里也不含它 —— 同一条 PATH 上「py --version 不成立、py -3 --version 成立」会被读成同一条缓存，换 probeArgs 的用例请先 clearWhichCommandCache()。
