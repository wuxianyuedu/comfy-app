# 耗时基线复测：开发盘与 CI 搬到 ReFS 之后（2026-10-21）

> 机器 = `LAPTOP-45M82AAB`，16 逻辑核。检出 `G:\ComfyAPP\comfy-app-t3-branch2`、pnpm store
> `G:\.pnpm-store\v11`、runner `G:\runner\data\orange-ci`、缓存槽 `G:\ci-cache\comfy-app-t3`。
>
> **`G:` 是 ReFS**（卷标「开发」，100G）。旧那批读数时代的 `F:` 是 NTFS（卷标「数据」），
> 而**两卷在同一块物理盘**上（Disk 1 = WDC SN730 1TB NVMe；`C:` 在另一块 SL7000 2TB）。
> 所以本账里所有「倍率」都是**文件系统之间**的差，不掺硬件。
>
> ⚠️ 引用规则：下面每个数都带 ①盘/文件系统 ②冷态或暖态 ③当时有无并发 job。
> 缺任一项就按「不可引用」处理（与 `2026-10-16-hook-baseline-map.md` 那句「秒数是量级不是承诺值」同口径）。

## 一句话结论

搬盘没有把这条链变慢——**元数据密集的那一族反而快了 2–4×**。真正变的是两件事：
① 每日档被**两条与搬盘无关的在红**挡住（接槽×Turbopack、bundle-budget 棘轮），所以那几格的旧读数
如今连「当日唯一执行者」都没有了；② 冷态/暖态那一格的跨度**比文件系统差大得多**，
同一份「不接槽装依赖」在 25 分钟内是 216s → 88.5s → 48.8s，而 NTFS 的旧读数是 51s。

⇒ **这一格结案：既不治、也不切。** 理由是形态而不是大小：这三笔不是「白载了什么东西」

且这是「税」不是「总账」—— 墙钟的大头在断言侧那三格，它们同样是真 gate 工作（全库 prettier、
全 story 的 axe），一样不能换。

⚠️ **别再为这件事重开一轮**：读数会随版本漂，但这一格的结论不依赖漂的那部分 ——
它依赖「税 = 动作」这个形态判断。要复量只需一条命令：`pnpm test:coverage:tracked`，
它自己会打那两行榜（分文件耗时 + 装载税）。

## 取数与复跑手法（这一轮真正可复用的三件）

- **逐格墙钟不用解析日志**：`cnb build get-build-status -v --repo <slug> --sn <sn>` 的
  `data.pipelinesStatus[<sn>-001].stages[]` 每项带 `name/status/duration`（毫秒）。终态集合里
  红是 `error`（不是 `failed`）。
- **节点原始读数在本地 stream-log**：`G:\runner\data\orange-ci\stream-log\<sn>-001.log`（JSONL）。
  ⚠️ 每条的 `runtime` 是**该 stage 自己起点以来**的毫秒、会反复归零：stage 时长取组内 `max(runtime)`，
  job 总时长取 `max(time)-min(time)`；`type:"cmd" && taskType:"user"` 那行是 runner **实际执行**的命令行原文。
  `time` 是 UTC，本地 +8。
- **免提交探针有两个必须先满足的前提**（这两条都是从红里读出来的，不是文档里推的）：
  内联 `--config` 的 YAML **必须带分支键那一层**（`master:` → `api_trigger:` → 流水线数组）；
  只写 `api_trigger:` 会得到 422 `CONFIG_EVENT_EMPTY … no api_trigger event config for branch master`，
  话术像「没配置」，其实少一层。第二，**探针要带自己的 `lock.key`**：照抄 `.common` 里那条
  `pr-$CNB_PULL_REQUEST_IID` 会在非 PR 事件上退化成 `pr-`，于是**任何一次 push 流水线都会把探针
  `cancel-in-progress` 掐掉**（实测 `cnb-ta7-1k5d5234e` 死在这里，尾格 `cancel`）。
  另有一条量具层的坑：把整份 `.cnb.yml`（54KB）当参数递给 `cnb` 垫片会 `Argument list too long`，
  剥掉注释后的 4.4KB 可以过。

### 5. #2132 那笔账认掉了：+45 B 在两跑之间变成 +539 B，而它全落在同一个块里

认账必须在**当前 master 的产物**上做 —— 上一轮那份产物是 `aa2123c8` 时代构建的，中间 `src/` 又动过，
直接拿它 `--update` 会把一份过期读数记成基线。所以先重跑 `pnpm run build`（HEAD `a2afa733`，退 1 在
这一格，正是例外流程要求的「先判该不该认」）：

```text
[bundle-budget] 当前：文件数 221 · raw 9675.5 KB · gzip 2277.7 KB
  基线：文件数 221 · raw 9674.1 KB · gzip 2277.2 KB（生成于 2026-10-21）
  gzip 总量上升：2277.2 KB → 2277.2 KB（+539 B）
  基线修订号：d752ed11（其后本检出上有 44 次提交）
新增内容 2 个（gzip 合计 31.9 KB，指纹在基线里找不到）；同时消失 2 个（合计 31.4 KB）⇒ 并排净差 +539 B
```

**#2141 那条改好的读数在这里第一次承重**：同一笔账在本节第 2 段还是「新增内容 2 个，最大的 30.6 KB」，
现在并排给出消失合计与净差 ⇒ 净差 539 B 与上面那句「总量上升 539 B」**自洽**，读的人不必再自己减一遍
（旧形态下那句「新增 30 KB」会让人以为要压回 30 KB，而真正的账是 539 字节）。

逐文件账在 `--update` 之前**用另一把尺独立复算一次**（同一份基线 + 同一份产物，两个量具同读数）：

| 分块槽 | 基线 | 当前 | 该槽净差 |
| --- | --- | --- | --- |
| 画布 / 生成那条共享块 | `1gwk4_2404t7w.js` 31 250 B | `3gpd4ke-0618r.js` 31 789 B | **+539 B** |
| 动态加载清单块 | `23lm6v2wi7sjz.js` 877 B | `2zf-46-2phjlo.js` 877 B | **0 B** |

⇒ **539 B 全部在同一个块里**；清单那一半只是把改名后的块名抄了一遍（它内部第一行就写着
`static/chunks/3gpd4ke-0618r.js`），这两读恰好相等是巧合，**不是**「清单块恒 0」——
上一轮它是 +1 B。

归因窗口比 #2132 立案时窄得多：`d752ed11..HEAD` 共 44 笔主干提交，但**动过 `src/` 的只有 3 笔**，
`pnpm-lock.yaml` 与 `next.config.js` **一笔没动**（所以这不是「拉进来一个新依赖」那一类）。三笔逐个定性：

| 提交 | 动了 `src/` 的什么 | 会不会进客户端图 |
| --- | --- | --- |
| `b2138660` #2118 | `src/app/api/custom-nodes/route.ts` + `src/lib/process/python-run.ts` | 不会：API 路由与 Node 宿主件 |
| `f5f9e05e` #2123 | `src/lib/media/task-images-client.ts` 换 zod 运行时镜像 | 会 |
| `32010475` #2140 | 新增 `CanvasNode/generate-payload.ts` + `lib/workflow/workflow-generate-input.ts` | 会 |

**#2140 那一半钉得住**（块内证据，不是拿体积猜身份）：`workflow-generate-input.ts` 里
`缺少要执行的工作流` 与 `这条记录的入参与当前形状不符` 这两串中文，全仓 `src/` 里只出自这一个文件，
而 221 个块里只出现在 `3gpd4ke-0618r.js` 这一块。
**#2123 那一半本轮没有复算**：它靠的是同一份基线下**两档读数之差** —— `aa2123c8` 报 +45 B、
`a2afa733` 报 +539 B，而这两个 revision 之间只有一笔动过 `src/`（就是 #2140）⇒ 增量 494 B 归 #2140，
剩下的 +45 B 沿用 #2132 / §13.5.4 里那一轮的定位。今天这根针只钉得住前者，`isCover` / `localPath`
这类列名在别的客户端模块里也有，不足以单独把 #2123 钉进这一块。

**为什么认**：这三笔买的正是「客户端在运行时知道线上要什么形状」。#2123 之前是 `as unknown as`
—— 列被改名时表现不是报错，是相册永远空；#2140 之前是 `payload as GenerateInput`
—— 少写一个必填键时界面上只剩一句「生成失败」。台账 E4 那条线的全部意义就是把这两条 cast 换成
一份服务端与客户端**共用**的 schema，而「共用」在这里必然意味着它被打包进客户端。
量级：539 B = 总量的 **0.024%**，文件数 221 ⇄ 221（没有多一次请求，raw 侧 +1 483 B）。
已按 §13.5.4 走 `pnpm run check:bundle --update --allow-increase`，新基线锚点落 `a2afa733`（主干可达），
重跑 `pnpm run check:bundle` 绿。

顺带一条对第 2 段的订正：那里说「新增两个分块（最大 30.6 KB）」是**判据当时的原话**，
它已被 #2141 改掉 —— 现在那两行合并成一句带净差的读数。旧句子留着不改，是因为它记的是
**那一天屏幕上真的写了什么**；要拿它推体积构成，读本节这一段。

## 同日（10-22 傍晚）：时刻第二次挪 —— `0 2 * * *` → `0 0 * * *`，它换到什么、赔什么

业主拍的第二挪（#2114 出路 3 那一半的第二次执行）。**本页立案 4 那句「任何固定小时都是抛硬币」
没有被推翻**，这一挪换的仍是硬币面；不同的是这次把两面各自的读数算出来了：

| 时刻 | 查得到的四晚里醒着的晚数 | 依据（入睡时刻，本地） |
| --- | --- | --- |
| `04:00` | 2 / 4 | 10-18 那晚 00:37 就睡了、10-20 那晚 06:09 才睡 ⇒ 这两晚 04:00 在睡 |
| `02:00` | 3 / 4 | 10-18 在睡；10-19 / 10-20 / 10-21 醒 |
| `00:00` | **4 / 4** | 四晚入睡时刻 00:37 / 07:09 / 06:09 / 04:00:36，**都在 00:00 之后** |

⇒ 出勤这一格 00:00 确实赢，但两条边界必须跟这句话一起留着：

- **样本只有四晚**。10-22 那次 `02:00` 缺勤（本页「次日」一节第 1 条：`02:00:18` 落下来、
  `Prepare` 0.3s `error`、平台侧 `labels: []`）对应的入睡时刻没查到 ⇒「4/4」不是保证，
  这台机的睡眠边界跟着「人什么时候收工」走（立案 4 的原话）。
- **赔掉的是另一条前提**。§13.5.21 / §13.5.23 把重档放到每日那一跑，靠的是
  「没有并发 PR、**机器是空的**」；而 `00:00` 恰是这台开发笔记本最可能还在被人用的时刻。
  所以这一挪的性质不是「修好了」，是**把一个失效换成另一个失效**：
  缺勤（根本没有读数）换成污染（读数里混着人在用机）。
  污染那一侧的第一份量已经取到 —— 同一格 `单跑构建·同步数据库表结构`
  独跑 **12.7s**（`cnb-723-1k5h25hkt`）、与另一档重叠 **99.3s**（`cnb-omb-1k5hfmlij`）；
  而 `安装依赖` 那格独跑本身就跨 135.9 / 197.3 / 269.5s，重叠那次的 232.9s 落在区间内 ⇒
  **量具没把冷/暖与并发分开，所以这里只证形状、不报倍数**。
  ⇒ 明天起，每日那一跑里某一格变慢**不许**照旧登记成判据回归，先分清当时那台机上还有谁。

同批动的现役时刻：`.cnb.yml` 事件键 + 它旁边那段注释（「这个点换过一次」→「换过两次」）、
`AGENTS.md`、`docs/standards/11`、`docs/standards/13`（18 处）、`scripts/ci-cache-slot.mjs`
那句 26h TTL 的理由。**历史数据一律没动** —— 本页立案 4 的逐晚表、
`changelog.d/2114-daily-run-moved-to-0200.md`、以及规范里那句「04:00 缺勤 2 次、02:00 缺勤 1 次」，
它们记的是当时量到的事。

时刻本身仍然**没有判据在守**：`tests/no-platform-ci-config.test.ts` 只认「分钟段与小时段是单值」
= 每天一次，不认具体几点 —— 这是 §13.5.23 明写的已知边界，不是这次的疏漏；而它正是
「在册 ≠ 出勤」缺的那半条（#2114 出路 1）还没落地的证据。下一次派发（`0 0 * * *` 的第一落点）
若仍缺勤，就该做出勤判据，不再换时刻。
