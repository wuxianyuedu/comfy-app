## 10. 错误处理与降级

> 商业级应用要"优雅降级"而非白屏崩溃。本章给出错误边界、降级策略、用户提示规范。

### 10.1 三级降级策略

| 层级 | 策略 | 示例 |
|------|------|------|
| L1：功能降级 | 某子功能失败，整体页面仍可交互 | shiki 高亮失败 → 纯文本行号渲染 |
| L2：组件隔离 | 单个组件崩溃，不影响其他区域 | React ErrorBoundary 包裹画布/面板 |
| L3：全局兜底 | 整页崩溃兜底页 | `app/error.tsx` / `app/global-error.tsx` |

### 10.2 React Error Boundary

```tsx
// ✅ 类组件实现 Error Boundary（React 目前仅类组件支持）
class ErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error: Error) { console.error("ErrorBoundary caught:", error); }
  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}

// 使用：包裹独立区域
<ErrorBoundary fallback={<PanelFallback />}>
  <InspectorPanel />
</ErrorBoundary>
```

**规则**：画布/面板/第三方组件（shiki/JsonView）等独立区域用 ErrorBoundary 隔离；不要把整个页面包在一个 Boundary 里——那样等于没隔离。


### 10.3.1 降级不得静默（#389）

**跳过调用与「不报错」不是同一件事。** 把一次失败降级成「本次不生效」保住了页面
可交互，但用户看到的是功能**悄无声息地失灵**——比白屏更难排查。凡是走 L1 降级的
路径，都要回答两个问题：

1. **为什么降级**：这条原因在运行时是否可知？可知就采集下来（不要靠猜）。
2. **用户能做什么**：给一句可执行的动作，而不是只陈述现象。

范例（ISSUE #389「陈旧实例」）：store 动作不在当前实例上时跳过调用，同时判定
「页面是否还跑着旧代码」，把「重载一次即恢复 + 重载不会丢工作」通过应用内通知
送达（toast 一闪而过 + 消息中心留底）。机制见
[launch-and-build §4.3](launch-and-build.md#43-陈旧实例运行图落后于源码时的可观测性issue-389)，
用户侧说明见 [guide-stale-code.md](../guide-stale-code.md)。

```tsx
// ✅ 降级 + 可见出口：跳过调用，但把「为什么、怎么办」讲清楚
if (typeof state[action] !== "function") {
  console.warn(`[wf-stores] 动作 ${action} 在当前 store 实例上不存在，已跳过本次调用`);
  reportStaleStoreAction("missing-store-action"); // → 应用内通知（去重在通知层）
  return false;
}

// ❌ 静默降级：用户只会看到「点了没反应」
try { state.newAction(); } catch { /* 忽略 */ }
```

### 10.4 异步错误提示规范

```tsx
// ✅ 用户可感知的失败用 toast；错误含可读信息
async function cancelTask(id: string) {
  try {
    await cancelTaskMutation.mutateAsync({ id });
    toast.info("已发送取消请求");
  } catch (err) {
    toast.error("取消失败", err instanceof Error ? err.message : "请稍后重试");
  }
}
```

**规则**：
- 错误信息给用户看的部分要**友好可读**，技术细节（stack）只进 console/`ErrorBoundary`。
- 网络错误统一提示"网络异常，请检查连接"，不暴露内部错误码。

### 10.5 空状态设计

```tsx
// ✅ 空状态给出"下一步引导"，而非空白
{filtered.length === 0 ? (
  <div className="grid min-h-[300px] place-items-center rounded-2xl border border-dashed border-white/[0.08]">
    <div className="text-center">
      <p className="text-lg font-medium text-gray-300">暂无任务记录</p>
      <p className="mt-1 text-sm">在创作台生成内容后，历史记录会显示在这里。</p>
      <button onClick={onNewProject}>新建画布项目</button>
    </div>
  </div>
) : ...}
```

**规则**：空状态必须说明"为什么是空的"+"下一步做什么"，降低用户困惑。

### 10.7 表单/输入容错

- 用户输入非法值（如 seed 超 INT 范围）→ 前端校验提示 + 后端校验兜底，不信任前端。
- 文件上传：校验类型/大小，超限给出明确提示"文件超过 50MB，请压缩后重试"。
- `JSON.parse` 用户输入：try/catch + 友好错误定位。

### 10.7.1 用户可见错误文案：详情与「动作前缀」各只有一个出口

失败路径要「有日志 + 用户可见出口」（硬规则 4），而**用户看到的那句话**由两段
拼成，两段各自只有一个出口：

| 段 | 出口 | 它管什么 |
|----|------|---------|
| **详情** | `~/lib/error-message` 的 `errorMessage(e, fallback)` | 从 `unknown` 抛值里取值，并把网络层原文（`Unexpected token '<'`）翻成人话 |
| **动作前缀** | 同模块的 `errorText(e, action, fallback?)` | 「是哪个动作失败了」＋统一的分隔符；详情取不到时**只兜详情**，动作名一定在结果里 |

```ts
// ✅ 两段式，分隔符只有一处定义
errorText(e, "读取配置");              // "读取配置：连接被拒绝或中断，…"
errorText(e, "镜头 2 提交失败");       // 动作名可以带上下文
// ❌ 四处各写一遍（规范 16 §16.2.4.45 的 P42 硬闸会拦）
`读取配置失败：${String(e)}`            // String(e) 对 `new Error("")` 产出 "Error"、
                                        // 对对象抛值产出 "[object Object]"
```

`e instanceof Error ? e.message : String(e)` 这一类手写兜底**一律改走 `errorMessage`**：
它不只是拼串，还承担网络层翻译（`fetch failed` → 「网络请求失败，请检查应用服务
是否正在运行」）—— 绕开它等于让一部分落点把英文原文摆给用户。

**没写动作名的地方**（`errorMessage(e, "保存失败")`）是合法的：结果本就正确。
但它**表达不了**「动作 + 详情」两段式，需要时改用 `errorText`。

### 10.8 上报与可观测性（已接入 Sentry）

- 项目已安装 `@sentry/nextjs`（v10+）；关键错误用 `captureException` / `console.error` 上报，非关键错误不上报。
- 错误上报含上下文（任务 id、操作类型），便于排查但**不含敏感信息**（prompt 原文、文件路径脱敏）。
- 埋点/上报失败不影响主流程（try/catch 包裹）。

### 10.9 服务端错误出口的唯一形态（ISSUE #573）

**REST Route Handler 不许手写错误信封。** 统一走 `src/server/lib/error-response.ts`：

```ts
import { errorResponse, unauthorizedResponse } from "~/server/lib/error-response";

if (!user) return unauthorizedResponse();              // 401 结构化信封
try { ... } catch (e) { return errorResponse(e); }     // AppError 用其 code/httpStatus
```

信封形状 `{ error: { code, message, details? } }` 由 `lib/core/errors.ts` 的
`toErrorEnvelope()` 决定（**唯一事实源**），`error-response.ts` 只做
「核心层零框架依赖 → Next 适配」这一层。`AppError` 子类自带 `code` 与 `httpStatus`：

| 需求 | 写法 |
|---|---|
| 未登录 / 会话失效 | `unauthorizedResponse()`（= `new AuthError()`） |
| 资源不存在 / 不属于当前用户 | `errorResponse(new NotFoundError("任务不存在"))` → 404 |
| 入参校验失败 | `errorResponse(new ValidationError("..."))` → 400 |
| 外部依赖（ComfyUI 等）不可用 | `errorResponse(new IntegrationError("..."))` → 502 |
| 兜底（未分类） | `errorResponse(e)` → 500 / `"internal"`，**不下发 stack** |

**接线前的现场**：15 个 route / 19 处各自手写
`{ error: { code: "auth.required", message: "未登录或会话已失效" } }` —— 与
`AuthError` 的默认值**逐字相同**，改一句文案要改 18 处，且新 route 会照着再抄一份。
`toErrorEnvelope` 当时零生产调用方，文档里还引用了根本不存在的 `./api` 模块。

**门禁**：`src/server/lib/error-response.test.ts` 断言 `src/app/api/**` 下不再出现
`error: { code: ... }` 字面量。接线当时它就抓到遗漏的第 19 处
（`custom-nodes/route.ts` 的 `custom_nodes.read_failed`）—— 没有这道门禁，
「接线」只是这一轮接上了，下一个人照旧会抄。

> **`ValidationError` 的实现状态**（2026-09，ISSUE #672）：上表的「入参校验失败」
> 一行**长期只有文档、没有实现** —— `core/errors.ts` 当年按「无生产调用方不立类」
> 的裁决把九个状态码子类一并删掉之后，这条就只剩对照表。于是各 REST 路由又回到
> 手写 `NextResponse.json({ error: "请求格式错误" }, { status: 400 })`（**信封形状
> 与其余错误不一致**：那里是 `{ error: { code, message } }`）。
>
> 现在 `ValidationError` 已补进 `core/errors.ts`，第一个真实调用方是
> `~/server/lib/request-body` 的 `readJsonRecord`（规范 16 §16.2.4.44 的入参
> 收窄出口）—— 按本文件的裁决，**这时才值得立类**。新增 REST 端点请一律走
> `readJsonRecord`，不要自己拼 400 字面量。

**为什么适配层不在 `core/`**：`core/errors.ts` 必须保持零框架依赖，它同时被
Next 服务端与纯 Node 宿主（`scripts/*.mjs`、MCP 进程）读取；把 `next/server`
import 进 `core/` 会让「核心层可被任意宿主复用」静默失效。
