## 2. 性能规范

> 本章覆盖渲染性能、内存、主线程、动画四个维度。性能问题要"测量优先"，但以下为预防性的强制规则。

### 2.1 列表/日志必须有上限

```tsx
// ❌ 错误：无限追加，内存泄漏
setLogs((prev) => [...prev, ...entries]);

// ✅ 正确：环形缓冲，保留最近 N 条
const MAX = 2000;
setLogs((prev) => {
  const next = [...prev, ...entries];
  return next.length > MAX ? next.slice(-MAX) : next;
});
```

### 2.1.1 无限历史与虚拟滚动（无上限场景兜底）

> **前提**：2.1 的"内存上限"是默认规则。本节只在业务**确实要求查看全部历史**（如全量日志审计、历史记录导出预览）时适用。核心原则——**内存有上限，磁盘无上限**。

#### 技术底线：内存与磁盘分离

严禁把全量数据一次性保留在 State/Redux/Zustand 中。即使使用虚拟滚动，State 里的数组过大也会导致 `useMemo` 过滤、`filteredLogs` 遍历等逻辑每次全量扫描而卡顿。

| 层 | 策略 | 上限 |
|---|---|---|
| 内存（State） | 只保留热数据（最近 N 条）+ 虚拟滚动可见窗口 | `MAX_IN_MEMORY`（如 50,000 条，按机器性能调） |
| 磁盘/后端 | 超出的部分落盘；搜索"全部"时按需从文件/DB 读取 | 无上限 |

#### 实现要点

1. **虚拟滚动**：行数可能达数万/数十万时，用 `@tanstack/react-virtual` 只渲染视口可见区，DOM 节点数恒定。
2. **单行长度限制**：单行超长（巨大 JSON/二进制转文本）单独渲染也会卡，超过阈值（如 10,000 字符）应截断/折叠。
3. **超大滚动高度兜底**：浏览器对 `scrollHeight` 精度有上限（约 33,554,400px / 2²⁴）。当 `估算总高 = count × estimateSize` 超过阈值（如 8,000,000px）时，按比例压缩映射，牺牲极端情况下的物理滚动精度换取整体稳定。

```tsx
// ✅ 无上限场景：内存上限 + 虚拟滚动 + 后端全量搜索
import { useVirtualizer } from "@tanstack/react-virtual";

const MAX_IN_MEMORY = 50_000; // 虚拟滚动可承载的内存上限

// 1) State 仍限制内存渲染上限（防初始加载炸裂）
setLogs((prev) => {
  const next = [...prev, ...entries];
  return next.length > MAX_IN_MEMORY ? next.slice(-MAX_IN_MEMORY) : next;
});

// 2) 虚拟滚动列表
function LogList({ logs }: { logs: LogEntry[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: logs.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 22, // 预估单行高度
    overscan: 10,           // 预渲染缓冲，防快速滚动白屏
  });

  return (
    <div ref={parentRef} className="h-full overflow-auto">
      <div style={{ height: `${virtualizer.getTotalSize()}px`, position: "relative" }}>
        {virtualizer.getVirtualItems().map((row) => (
          <div
            key={row.key}
            ref={virtualizer.measureElement}
            style={{
              position: "absolute", top: 0, left: 0, width: "100%",
              height: `${row.size}px`,
              transform: `translateY(${row.start}px)`,
            }}
          >
            {logs[row.index]?.message}
          </div>
        ))}
      </div>
    </div>
  );
}

// 3) 搜索：内存未命中 → 走后端全量检索（磁盘）
async function searchAll(query: string): Promise<LogEntry[]> {
  const needle = query.trim().toLowerCase();
  const local = logs.filter((l) => l.message.toLowerCase().includes(needle));
  if (local.length > 0) return local;
  const res = await fetch(`/api/logs/search-all?q=${encodeURIComponent(query)}`);
  return res.json(); // 后端从磁盘归档逐文件扫描
}
```

> **与 2.6 的关系**：2.6 是"大列表必须虚拟滚动"的总纲；本节是 2.1 在"无上限/全量历史"这一特殊场景下的**兜底细则**（内存上限 + 磁盘分层 + 滚动高度兜底 + 单行截断）。
>
> **落地实例（日志面板，ISSUE #609 八审）**：时间线本身不设条数上限（用户要能往前
> 翻完整段），"同时挂载多少"由 **虚拟滚动** 兜住——一页 2000 行只渲染视口内的
> 几十行，撑开滚动条的是**估算总高**（超 `scrollHeight` 精度上限时按比例压缩）。
> 行高是常量（不换行 27px / 每多一行 +18px），因此不需要动态测高这一轮额外测量。
> 细节与判据见 [07 §7.28](07-日志系统.md#728-面板八审满页-2000-行改成虚拟滚动609)。

### 2.2 搜索/过滤用 useMemo，依赖明确

```tsx
// ✅ 正确
const filteredLogs = useMemo(() => {
  const needle = search.trim().toLowerCase();
  return logs.filter((entry) => {
    const levelOk = filter === "all" || entry.level === filter;
    const searchOk = !needle || entry.message.toLowerCase().includes(needle);
    return levelOk && searchOk;
  });
}, [logs, filter, search]); // 依赖明确，不漏
```

**注意**：`useMemo` 只在依赖不变时复用结果。若过滤函数引用了组件外部的**可变**变量（如模块级 `let` 计数器），需纳入依赖或改为参数传入，否则可能读到过期值。模块级**常量**（`const MAX = 2000`）是稳定引用，无需进依赖。

### 2.4 避免在 render 阶段调用 setState

```tsx
// ❌ 错误：render 中同步 setState 导致额外 re-render（且 React 19 会报 lint）
if (prevQuery !== query) {
  setPrevQuery(query);
  setHitIndex(0);
}
```

**React 19 强制规范**（对齐主规范 §4.6）：`set-state-in-effect` 已不再豁免，effect 内同步 `setState` 同样报 `react-hooks/set-state-in-effect`。两种规范写法：

```tsx
// ✅ 规范写法一：渲染期对比 + 渲染期 setState（React 19 允许，遇冲突自动重渲染）
const prevQueryRef = useRef(query);
if (prevQueryRef.current !== query) {
  prevQueryRef.current = query;
  setHitIndex(0);
}

// ✅ 规范写法二：setTimeout 延迟到 render 提交后（纯 effect 场景）
useEffect(() => {
  const t = setTimeout(() => setHitIndex(0), 0);
  return () => clearTimeout(t);
}, [query]);
```

禁止文件级 `/* eslint-disable react-hooks/set-state-in-effect */` 掩盖违规。

> **案例归档**：该模式的实战应用与一次外部审查的误判分析见
> [CanvasNode 审查归档](../guides/reviews/2026-08-30-canvasnode-review.md)——
> 带守卫的渲染期 setState 是官方推荐写法，勿以"额外 re-render"为由改成 effect（会引入
> 提交后闪烁）；其正确适用前提是 prev 守卫 + 同组件状态。

### 2.7 动画用 transform/opacity，不动画 layout 属性

```tsx
// ❌ 错误：动画 width 触发 layout + paint
transition-all duration-300 ease-out
  ? "w-[360px]" : "w-0"

// ✅ 方案 A：外层 transform 滑入，内层固定宽度
<aside className="transition-transform duration-300 translate-x-0">
  <div className="w-[360px]">{children}</div>
</aside>

// ✅ 方案 B：grid 列宽过渡（不影响内部内容布局）
grid-template-columns: ${open ? "360px" : "0px"} 1fr;
```

**动画决策表：**

| 要动画的视觉变化 | 推荐属性 | 触发成本 |
|---|---|---|
| 位移（滑入/抽屉） | `transform: translateX/Y` | 合成器，无 layout |
| 淡入淡出 | `opacity` | 合成器，无 layout |
| 尺寸变化（面板伸缩） | `transform: scaleX` 或 grid 列宽 | 优先 transform |
| 颜色/背景 | `background-color` / `color` | paint only |
| **避免** | `width` / `height` / `left` / `top` / `margin` | 触发布局重排，最贵 |

> **与主规范 §4.4.3 的调和**：右侧 Inspector 面板显隐采用主规范 §4.4.3 已落地的 **CSS transition 宽度过渡**（`transition-all` + `w-(--panel-right-width)` + `pointer-events` 切换），属于面板级例外；通用规则（本表）仍优先 `transform`/`opacity`，元素级动画禁止动画 `width`/`height`。

> **列表条目级增删/重排（AutoAnimate）**：当需要给「列表条目增 / 删 / 排序换位」这类批量 DOM 重排加平滑过渡时，可用 [`@formkit/auto-animate`](https://auto-animate.formkit.com)（`useAutoAnimate`）。它基于 **FLIP** 用 `transform: translate` 位移 + `opacity` 淡变补间，**不走** `width`/`height`/`left`/`top`/`margin`，与本节「元素级禁止动画 layout 属性」一致。
- 适用范围：**列表条目级**增删/手动重排（如历史任务卡片排序切换、筛选移除）。**不适用**于画布（`@xyflow/react` 有自己的渲染/动画机制）、面板级宽度过渡（见上文主规范 §4.4.3 例外）。
- 参数约定：`useAutoAnimate({ duration: 250, easing: "ease-out", disrespectUserMotionPreference: true })`；`options` 仅在首次挂载生效，需用 `useMemo` 固化。已去掉「尊重系统减弱动画」的限制，允许适量过渡动画（`duration` 保持在 250ms、`ease-out` 的轻量档，不以大位移/长时长制造晕动）。
- 选点原则：默认 `duration: 250` + `ease-out`，只做小范围试点（如 `HistoryList` 的任务卡片列表），验证符合本表后再推广。

#### 2.7.1 「表现 vs 性能」的裁决口径（存量 8 处的实测结论）

本节是**取向**不是禁令：动画对表现有正收益，**允许**用 —— 判据是
「**表现收益是否盖过性能代价**」，而不是「碰了 layout 属性就一律改成 transform」。
强行把所有宽度过渡拆成 `transform: scaleX` 会引入内容变形（`scaleX` 缩放子元素
文字/图标）或额外 DOM 层，有时**比让它重排更贵**。因此下表逐条定性现存站点，
按「触发频次 × 受影响子树 × 是否脱离文档流」三个量级裁决：

| 站点 | 动画属性 | 触发 | 裁决 |
|---|---|---|---|
| `ui/progress.tsx`（`progress-indicator`） | `width` | 进度推进（秒级节流更新） | **保留**：细条（`h-1`）、宿主为单实例进度条，重排子树只有条内填充；改 `scaleX` 会缩到圆角端点 |
| `ui/sidebar.tsx:271`（`sidebar-gap`） | `width` | 点击折叠（一次） | **保留**：空 `div`、零内容、脱离视觉焦点 |
| `ui/sidebar.tsx:283`（`sidebar-container`） | `left`/`right`/`width` | 点击折叠 / 移动端抽屉 | **保留**：`fixed` 定位、脱离文档流；重排**只影响它自己**，不波及主内容 —— 这正是官方基元的折叠语义 |
| `ui/sidebar.tsx:462`（`sidebar-group-label`） | `margin`/`opacity` | 点击折叠（一次） | **保留**：`-mt-8` + 淡出是「收折一行」的最小表达，同一子树随侧栏一起动 |
| `ui/sidebar.tsx:561`（`sidebar-menu-button`） | `width`/`height`/`padding` | 点击折叠 / 图标档覆盖 | **保留**：图标档是官方基元核心交互，改 `scale` 会让图标与文字一起变形 |
| `ui/navigation-menu.tsx:118`（`Positioner`） | `top`/`left`/`right`/`bottom` | 切换菜单项时弹层跟随锚点 | **保留**：重定位发生在**浮层内**（`Portal`）、与主文档流隔离；`data-instant:transition-none` 已给「不该有动画」的路径留了直落 |
| `ui/navigation-menu.tsx:124`（`Popup`） | `width`/`height` + `opacity`/`transform` | 弹层开关（内容尺寸随菜单项变） | **保留**：属**面板级**宽度过渡，与上文主规范 §4.4.3 例外同口径；纯 `opacity`/`transform` 无法表达「容器随内容长大」 |
| `canvas/RgthreeBodies.tsx`（旁路开关滑块） | `left` | 点击旁路（一次） | **保留**：10×10 小圆点、位移 12px @120ms、单实例；改 `translateX` 收益与代价都可忽略 |

**裁决结论：8 处全部保留，不改。** 共同特征是「用户显式触发（点击）+ 一次性 + 受影响
子树小或脱离文档流」——**不是**连续帧动画，也不是在长列表里滚动重排。真正要拦的是
**每帧都动 layout**（拖拽/滚动跟随、输入实时改宽度、`infinite` 关键帧驱动尺寸）
与**在大子树上动 layout**（动一次让几百个节点重新布局）。

> **别和 [06 §6.7](06-无障碍访问-a11y.md#67-动画与过渡) 混修**：那条是 `prefers-reduced-motion`
> 的降级账（晕动症，WCAG 2.3.3），本条是渲染成本的账，两者**同一处站点、不同判据**，
> 改一处不要顺手改另一处（06 的存量账原文也写了这句话）。

**判定流程（新写动画时自问）**：

1. 触发是谁？**用户显式点击 / 一次性状态切换** → 走「保留」路径；**每帧跟随 / 无限循环** → 必须换 `transform`/`opacity`。
2. 动画的子树多大？**自己一层或脱离文档流** → 可以动 layout；**波及几十上百节点** → 换写法。
3. 有更强的替代吗？`transform`/`opacity`/grid 列宽**能表达同一视觉**就优先用它（本表第一段）；表达不了（容器随内容长大、`scaleX` 会变形内容）→ **保留 layout 过渡并在此登记**。

### 2.8 避免主线程长任务：分片 + setTimeout 让出

```tsx
// ✅ 正确：大文件高亮分片，片间让出主线程
const processChunk = () => {
  if (cancelled) return;
  const slice = lines.slice(start, start + CHUNK_LINES);
  // ... 处理 slice
  if (chunkIndex < totalChunks) {
    setTimeout(processChunk, 0); // 让出主线程一帧
  }

```

**适用场景**：shiki 语法高亮大文件、JSON 树深度遍历、大量 DOM 节点批量创建。分片粒度以每片 < 16ms（一帧）为目标。

### 2.9 图片/视频资源

- **缩略图用 `MediaThumbnail`** 统一封装，视频类型走 `<video>` + `preload="metadata"` + `poster`，避免自动播放加载整段视频。
- **大图懒加载**：`loading="lazy"` + 固定宽高（防布局抖动 CLS）。
- **Object URL 及时释放**：`URL.createObjectURL(blob)` 用完后在 `finally` 里 `URL.revokeObjectURL(url)`，防止内存泄漏。
- **导出下载**：用 `Blob` + 临时 `<a download>` 触发，不要直接 `window.location.href = blobUrl`（会跳转/内存不释放）。

### 2.10 React.memo / useMemo / useCallback 使用准则

| 工具 | 何时用 | 何时不用 |
|------|--------|---------|
| `React.memo` | 列表项组件、纯展示子组件、props 引用稳定时 | 组件内部本身很轻、props 每帧都变 |
| `useMemo` | 派生计算开销大（大数组 filter/map）、依赖稳定的值 | 简单 `a + b`、依赖频繁变化 |
| `useCallback` | 回调作为 memo 子组件的 prop、依赖稳定 | 只在组件内使用的临时回调 |

**核心**：优化工具的代价是代码复杂度。先测性能瓶颈（`Performance` 面板 / React Profiler），再针对性优化，避免"防御性 memo 全量铺开"。

### 2.11 画布性能模式（@xyflow/react，对齐主规范 §6.1）

画布是本项目最重渲染区域，默认开启以下模式：

```tsx
<ReactFlow
  onlyRenderVisibleElements={true} // 视口外节点不渲染
  nodesDraggable={nodes.length < 200} // 节点多时禁用拖动
  minZoom={0.1}
  proOptions={{ hideAttribution: true }}
  nodeTypes={nodeTypes} // 模块级常量，不内联
>
```

- **节点组件 memo 化**：`React.memo` 包裹节点组件，props 只传稳定引用。
- **订阅收敛**：节点内部高频状态只订阅最小粒度 selector，不在节点层订阅整棵画布 store。
- **边惰性化**：`defaultEdgeOptions={{ type: "smoothstep" }}`，用 `useEdgesState` 控制，避免边对象每次 render 重建。
- **颜色/样式模块级常量**：节点颜色表、尺寸常量放模块顶部，禁止每次 render 重建对象字面量。
- **视图状态用 `useReactFlow` 局部读取**：`viewport`/`zoom` 不进全局 store，避免画布操作触发全树渲染。
