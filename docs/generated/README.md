# 产品文档（Comfy-APP-T3）—— 索引与使用规则

> 本目录是**产品功能与需求的唯一口径**：一个功能「是什么、做到什么程度算做完、
> 现在什么状态」以本目录为准；「怎么实现」以 `docs/standards/` 开发规范为准。
> 需求本身要变时改本目录（规则见 §5 变更控制）—— 后续开发以本目录为需求基准。

## 1. 定位与读者

| 读者         | 怎么用                                                                 |

| 产品 / 需求方 | 在 `feature-catalog.md` 对编号提增删改；在 `feature-specs.md` 写验收口径 |

| Review       | 对照规格的「行为与验收」判「做完没有」，不凭印象                       |

| 问题                                       | 归哪份                                                                 |

## 4. 怎么用（三条路径）

- **做功能开发前**：catalog 找到需求编号 → specs 对应条读「行为与验收」→ 动手；
  改动使某条需求的状态变化（新上线 / 进灰度 / 退役）时，同批更新 catalog 状态列。
- **写 Issue / PR 标题**：术语用正式名（glossary），可带编号（如 `FR-WP-03`）。
- **发现需求与代码不一致**：代码说了算现状，但**不要就地改文档了事** ——
  先判「是需求变了还是实现偏了」：需求变了改本目录；实现偏了按 AGENTS 硬规则 29
  当场立案（`pnpm ship --new-issue …`）。

## 5. 变更控制（「后续开发以此为准」的落地规则）

1. **编号稳定**：`FR-<域>-<序号>` 一经分配不回收、不改义；需求退役把状态改成
   `已退役` 并注明去向，不删行。
2. **状态四态**：`已上线` / `灰度` / `计划中` / `已退役`（词义见 catalog §1）。
3. **改功能先改需求**：新增 / 改变用户可见行为的功能，同批 PR 内更新本目录
   （catalog 加行或改状态、specs 补验收口径）；只改实现不改行为的不动本目录。
4. **验收口径可核验**：每条需求的「行为与验收」写成能跑命令 / 能指路径的形态，
  不写「体验良好」这类不可判的词。
5. **与规范同批维护**：本目录是 `SCOPED_DOCS` 纳管文档 —— 改了源要同批带
   `docs/generated/` 镜像（`pnpm doc:render`），并由 `pnpm doc:check` 把关
   （口径见 `docs/reference-facts.md` §3）。

## 6. 维护规则

- 新功能域先进 catalog 的分域表，再进 specs 补详述；一篇写不下再拆，别挤爆一节。
- 文档里的路径 / 命令以仓库现状为准；发现漂移按 §4 第三条处理。
- 本目录**不写实现细节**（代码示例、分层规则、门禁口径归规范），只写
  「做什么、怎么算做完」。
- 本目录的登记与校验范围见 `scripts/doc-facts.cjs`（`SCOPED_DOCS` /
  `SCOPED_DOC_DIRS`）与 `docs/README.md` §1 文档体系总览。
