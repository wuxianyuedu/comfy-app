## 11. 测试与可观测性

> 商业级项目需要可验证的质量保障。本章给出测试分层、行为测试重点、埋点与日志可观测性规范。

### 11.1 测试分层

> 命名口径（2026-09-04 对齐，见 #8）：「集成测试」一词历史上混指两种完全不同的东西，
> 容易误导。现拆成 **前端集成（Vitest 层，走真实 tRPC 管线）** 与 **E2E（Playwright）**，
> 责任分开。前端组件测试若涉及跨模块数据流（tRPC query/mutation、缓存失效、乐观更新），
> 一律升级为前端集成写法（见 11.3），不得再用「永不 resolve」桩冒充冒烟。

| 层级     | 工具                                           | 覆盖范围                                                             | 示例                                                     |
| -------- | ---------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 单元测试 | Vitest                                         | 纯函数、工具函数、Zod schema                                         | `format.ts`/`suggestFix.ts`                              |
| 组件测试 | Vitest + Testing Library                       | 纯渲染/交互/a11y（不依赖服务数据）                                   | `TaskCard` 点击/空状态                                   |
| 前端集成 | Vitest + RTL + MSW + QueryClient + tRPC client | 组件↔tRPC 数据态流转                                                 | 见 11.3：loading→data→error、表单提交后缓存失效/乐观更新 |
| E2E      | Playwright                                     | 关键用户流程（端到端，真浏览器）                                     | 创建任务→生成→查看历史                                   |
| 视觉回归 | Playwright screenshot                          | 关键 UI 的像素基线：xyflow 画布、空态、弹窗、Tailwind 断点、深色主题 | 画布布局/配色、弹窗尺寸（见 11.8）                       |
| 类型检查 | tsc --noEmit                                   | 全项目类型安全                                                       | 提交门槛强制                                             |

**前端集成 vs E2E 的分界**：

- **前端集成（Vitest）**：本地、毫秒级、可并行，测的是**组件 + QueryClient + tRPC client +
  MSW 网络拦截**这一套客户端数据管线——loading → data → error、缓存失效、乐观更新、
  zustand 交互。**不**起真服务、不连真库。
- **E2E（Playwright）**：起真应用（`pnpm dev`/构建）+ 真 ComfyUI 进程，覆盖跨页面关键流程。
  慢、脆、成本高，只用于少量关键链路。

### 11.2 行为测试优先

```tsx
// ✅ 测行为（用户能感知的），不测实现细节
import { render, screen, fireEvent } from "@testing-library/react";
import { TaskCard } from "./TaskCard";

test("点击任务卡片触发 onOpen", () => {
  const onOpen = vi.fn();
  render(<TaskCard task={mockTask} onOpen={onOpen} />);
  fireEvent.click(screen.getByRole("button", { name: /查看任务/ }));
  expect(onOpen).toHaveBeenCalledWith(mockTask.id);
});
```

**规则**：

- 用 `getByRole`/`getByLabelText`（a11y 友好）而非 `getByTestId`（最后手段）。
- 断言用户可见结果，不断言内部 state/`useStore` 调用细节。

#### 11.2.1 闸门类判据：拒绝必须发生在副作用之前

鉴权 / 归属 / 路径包含 / argv 注入 / 状态码契约这类逻辑，**测法与业务分支不同**：
它们的失败形态不是「结果不对」，而是「不该发生的动作发生了」。所以一条合格的闸门用例
必须同时打两句话，只断状态码等于没拦住（请求已经跑出去了）：

```ts
// ✅ 拒绝 + 副作用没发生
await expect(caller.workflow({ id: "task-b" })).rejects.toMatchObject({
  code: "NOT_FOUND",
});
expect(rmMock).not.toHaveBeenCalled(); // 磁盘一次都没动

// ✅ 注入类：不但要拒，还要钉住「合法那一路的 argv 形状」
expect(args).toEqual([
  "-u",
  SCRIPT,
  "--out",
  MANIFEST,
  "--report-out",
  REPORT,
  "--only-pkgs",
  "A,B",
]);
//                                   ↑ 位置与内容都不许被客户端挪动

// ❌ 只断状态码 —— 已经 spawn 出去了，400 也照样把文件覆写了
expect(res.status).toBe(400);
```

配套的口径（每条都是装机时被照出来的，不是设计时想出来的）：

- **反向验证是判据精确性的证据**，不是覆盖率：把归属判定短路 / 从净化器里删掉一个字符 /
  摘掉包含判据，**恰好**对应的那几条变红。红得多说明判据含糊，一条都不红说明这条用例是装饰。
- **「勾销必须与判据同批」**（台账 A 系列的复算教训，§13.5.8 的同一族）：安全项被关闭时，
  台账里那一条必须能指出「哪个文件的哪条用例在钉它」。`8740948` 一次修了 A2/A3/A6/A7/A10
  五条、并把它们登记成待办、且没留任何执行者 —— 表现就是后来人读到一张「已知还缺」的清单，
  按它去设计防线，而代码其实早就不是那样了。
- 失败路径的处置**留在调用点、判据只写一份**（§12.12）：`taskOutputDir()` 返回 `null`，
  打开 → `FORBIDDEN`、删除 → 什么都不删、落盘 → 硬失败，三种处置都是业务决定；
  把「抛错」做进共享层就等于替三个调用点各做了一次他们没要的决定。
- **一条口径要把它的所有落点列出来再收**（A5 复算的教训）：「URL 协议只许 http(s)」当年补在
  「服务端会去 fetch 的两个地址」上，而**危害最大的那条**（`setting.openExternal` 把请求方给的
  地址交给系统浏览器）根本不在那份名单里。所以收到地基时先 `grep` 一遍同类入参
  （`z.string().url()`、`openUrl*`、`spawn(... url)`），把落点数写进模块注释 ——
  「收了几处、还有几处没收」必须看得见，否则下一条同族洞又会当成「已经修过了」。
- **加了属主判定，就要回头审缓存指令**（A13 的同一批）：产物读取口原本写的是
  `public, max-age=31536000, immutable` —— 那两个字面量在只判路径时是无辜的（内容对谁
  都一样），一旦响应开始依赖「你是谁」，`public` 就等于授权共享缓存把 A 的产物回给 B，
  代码里那道闸写得再对也只剩形式。所以判据的**实际出口常常在响应头里而不在 `if` 里**，
  这类用例必须把响应头一起断言（本仓库的写法：`/^private\b/` + `immutable` 同条断言，
  把 `private` 改回 `public` 恰好红一条）。
- **判据装在 handler 上 ≠ 请求会走到 handler**（A13 的最后一环，也是最容易漏的一环）：
  `public/**` 由 Next **按静态文件直接发出**，不经过任何 route handler。产物正好落在
  `public/generated/` 下，所以只在 `route.ts` 里加会话与归属判定时，同一个文件在两个
  URL 上给两个答案（实测，`loginRequired` 开着、无会话）：
  `/generated/<taskId>/img_0.png` → **200** 原图，`/api/generated/<taskId>/img_0.png` → 401。
  口径：**给「按路径读文件」的口子加判据时，先问这个前缀还有没有别的服务方式**
  （静态 public、`assetPrefix`、桌包的自定义协议都算），并把「两种形状必须同一个答案」
  写成用例。机制上唯一的落点是 `src/proxy.ts`（`next.config.js` 的 `rewrites()` 返回
  扁平数组时属于 `afterFiles`，实测压不过 `public/` 里的真文件 —— 那是个配置看着在写、
  实际一个字都没挡的形态）；而 proxy 这一层自己的静默档在 `config.matcher`：
  沿用下来的那条通配把**带点的路径整个排除**，产物 URL 个个带扩展名，
  删掉显式的产物前缀条目后 `proxy()` 里一行代码都不动、判据一次都不执行、零报错。
  **这一族的收口方式排在后面一层**（台账 A13 残留，已关）：能被静态直发的位置上
  根本不该放需要判据的东西 —— 产物根搬到仓库根的 `generated/` 之后这条旁路不存在，
  proxy 那层降级成「让老形状的 URL 仍然走闸」的兼容层，漏配 `matcher` 的表现也从
  「绕过闸门」变成「这条路 404」。给这类「补了一层绕行」的判据写用例时，
  顺手把「这层哪天可以撤」记进注释与台账，否则它会以安全层的身份一直活着。
- **错误码是判据的一个独立维度，而覆盖率满档不代表它被判过**（⑨ 第二刀，台账 E8）：
  同一句「查不到」写成 `throw new Error("… not found")` 与 `new TRPCError({ code: "NOT_FOUND" })`
  在**行覆盖上是同一行**，但前者被 tRPC 归成 `INTERNAL_SERVER_ERROR` ——
  于是「越权与不存在同形」这条口径在状态码层根本没成立（两边都 500，看着一样纯属巧合），
  客户端也拿不到能分支的码。`material` 的用例对「库里没有这一行」那两支确实判了
  `code: "NOT_FOUND"`，但对「分类不在枚举里」只写了 `rejects.toThrow("Invalid folder")` ——
  而那几处实现是 `throw new Error`， caller 边界留着原文，于是**消息判到了、码没判**，
  分支覆盖 100% 也拦不住。闸门类用例的断言形状因此应当是
  `rejects.toMatchObject({ code: "…" })`（或把错误码抽进比较函数里比两个 id 同不同形），
  只看 `.toThrow(原文)` 等于把状态码那一维交给巧合。
  **落点是 lint 不是新的 `check-*.cjs`**：`eslint.config.js` 对
  `src/server/api/routers/**/*.ts` 禁 `ThrowStatement > NewExpression[callee.name!="TRPCError"]`
  （B 组每次提交都跑、报错直接指行号，不必再养一份会静默失效的清单），
  并由 `tests/router-error-envelope.test.ts`（固定清单）判「存量为零 + 扫描面非空 + selector 真的会响」
  —— 第三层用 eslint 自带的 `Linter` 现场验，因为**「配置写在」与「配置在跑」是两件事**（§11.7 同源）。
- **挂载即欠执行者，而粒度必须是 procedure 不是 router**（⑨ 第四刀，台账 E3 收口）：
  一份 router 有测试文件，推不出它的每条口都被调用过 —— `workflow.test.ts` 34 条用例在场，
  `workflow.detailFull` / `workflow.subgraph` 两条口仍然零执行者。反过来，零执行者的口也
  不等于「该补测试」：`customNode.list` 的 `nodes` 是写死的 `[]`（真实现在 REST 侧，同数据
  两个门、tRPC 这一个是假的）还顺手把整个 settings 回给客户端，`post.getLatest` 的注释写着
  「OWASP A01：要求已登录」而 `loginRequired` 默认 `false` 让那句等于没写、且没有
  `createdById` 过滤 —— 给死口写用例就是把它焊死，本批的处置是**定性后删除**。
  所以判据的对象是**挂载动作本身**：`tests/trpc-surface-executors.test.ts`（固定清单）
  枚举 `appRouter._def.procedures`，要求每条都出现在「import 了该 router 文件闭包」的测试里
  的调用形态。三条口径：① **闭包**（聚合 router 把 procedure 拆在兄弟文件里，只认挂载文件
  会把执行者判丢）；② 「文件提到过这个 router」不算，得出现 `proc(` 调用形态；
  ③ 扫描面本身非空 + 用合成的 `ghost.*` 反证四种形态 —— 三条缺一条，判据就会在空输入上假绿。
- **「对编译器按下静音键」的动作本身要能被机器看到**（F13 的收口形态）：
  `as never`、`select?: unknown` 这类写法的语义是「这里我不检查了」，而它坏掉时的表现
  不是报错而是**一声不响**——`train.cancel` 从 Prisma→Drizzle 迁移起每次 500、
  `findByIdForUserSelect` 的投影参数是空气（承诺窄读、实际整行拖两个大 JSON blob），
  两件事都隔着几个月、都全绿。判据不能写成「禁用 `as never`」（转发第三方 API 签名时
  确实要给个交代），要写成 **`AS_NEVER` 逐处登记表**：按「文件 + 该文件内出现次数」记账、
  每处必须写「为什么不能改成把类型收对」；新增未登记即红，登记的那处不见了也即红
  （表失去记账能力就是白表）。同一张表里可以留着两处「已知欠账」的条目，
  但**理由必须写成欠账**（MCP 写侧入参没校验那一处就是这么记的），并另开台账项。
  登记用「文件 + 次数」而不是行号：行号会在无关改动里漂，漂了的登记项等于一张对不上账的表。
- **把静态通道折进 handler 那天，要逐条清点静态服务白送的能力**（A13 残留的第二条，`Range`）：
  产物根从 `public/generated` 搬到 `generated/` 之后，所有字节都只走 `/api/generated/[...path]`
  这一条 handler —— 归属闸是补上了，但**`Range` 顺手没了**：`public/**` 由 Next 直发时
  浏览器 seek 是白送的，而 handler 里一句 `fs.readFile` 只会整份 200 回全量。
  这类「不是回归、是搬家时掉下来的东西」最难被自己的 diff 照出来（没人写坏它，
  只是新代码没继承旧能力），所以口径是：**折叠静态通道时，把 `Accept-Ranges`、条件请求
  （`ETag` / `If-Range`）、`HEAD`、编码这几条逐个点名**，要留的留、明确不留的写进注释说明为什么。
  本条落地时的两个判据形状值得抄：① 分段请求必须**复用同一串权限判定**（每条拒绝用例
  都顺手带一个 `Range` 再打一遍，防止「读哪一段」那层长出第二套权限逻辑）；
  ② 短读时 `Content-Range` 要与 body 一起收窄 —— 承诺 6 个字节而只给 2 个，
  客户端会照着承诺去拼出一个坏产物，比回 404 更糟。
- **有执行者 ≠ 有消费方，同一份挂载面要判两维**（⑨ 第四刀的第二维，台账 E3′）：
  `material.*` 那三扇门有 18 条归属用例、门槛登记到 95/100/95/80，而素材库面板从头到尾走的
  是 REST 的 `/api/materials`（`src/lib/media/materials-client.ts`）。一条**只有测试在调**的口
  不是「安全」，是「可以烂掉而没人红」：它与真门是同一套判据的两份实现（§12.12 的孪生对），
  界面永远碰不到那份漂移。所以消费方维度与执行者维度共用一份挂载面：
  `src/**` 的**非测试**代码里必须点名它 —— 先过 `stripComments`（注释里提一句不算用它），
  再认三种形态（`api.ns.proc`、`api.ns["proc"]`、`RouterInputs["ns"]["proc"]`），
  且定义这条口的文件闭包不算它自己的消费方。找不到就必须在 `ZERO_CONSUMER` 里登记
  「谁将来接它」，登记表**双向不陈旧**（口没了登记还在 = 红；消费方接上了登记还在 = 红）
  并带长度棘轮 —— 让这张表变长的唯一合法路径是先动台账。
  **收口那天要看一眼覆盖率有没有掉档**：门删掉后 `materials.ts` 的分支覆盖从 80 掉到 78.43
  （`check:all` 当场红），因为那些清洗与包含分支一直只被那扇门的用例**顺带**走过 —— 活着的
  REST 门送进来的全是合法入参，129 字符的 scope、`..`、`a<b>.png`、隐藏文件、单条 stat 失败
  这些形状一个都进不来。正确补法是**给判据层自己一份按判据组织的用例**（`materials.test.ts`），
  而不是把那条死门找回来当覆盖率的水泵。
  装这一维时顺带照出**另一族洞**：客户端里有 3 条真请求打向根本不存在的 handler（`/api/skills`、
  `/api/images`、`/api/file/<name>`），而调用点一句 `catch {}` 或 `MediaThumbnail` 的空 `src`
  就把 404 咽成「没有数据」—— 于是「选完图看不到图」这类反馈被当成形状解析问题修了两轮，实际没好。
  同族还有第 4 条：一个**只是长得像 REST 地址**的 sessionStorage 键（真实请求早改成 tRPC 了），
  它不发请求，但会骗过下一个读代码的人、也会让地址判据一直红在假阳性上。
  判据已随之装成硬闸（`tests/rest-endpoint-targets.test.ts`，进固定清单：地址字面量 → `src/app` 目录形状，外部服务地址与 RPC 通道基址走带原因的显式登记表），四条的逐条处置见台账 E3‴。
- **用例的期望值要从语义推，不能从实现抄**（⑨ 第五刀，台账 A8 第二段）：
  `compose-steps.ts` 的 `clipPathOf` 把库里存的 `/api/generated/…` 解析成
  `public/api/generated/…`（只剥前导斜杠、没剥 `api/` 段），于是「合成成片」对每一条镜头必败；
  而这条**被断言反过来钉成期望** —— 旧用例写着 `expect(...).toBe("/proj/public/api/generated/films/x.mp4")`。
  表现是「这份纯函数有测试、全绿」，实际是测试在替 bug 签名，比没测试更糟：
  它把错误的形状变成「改一下就会红」的既成事实，后来人只能顺着它再抄一遍。
  两条口径：① 断言「形状」时必须答得出**为什么是这个值** —— 本例的正解不是字面量，而是
  「写侧 `taskOutputUrl()` 存什么，读侧就该解回同一个文件」这一条**同源往返**
  （`output-paths.test.ts` 因此直接往临时目录落一个真文件再解析回去）；
  ② 同一份布局/协议的第二份实现**由机器禁止**，不靠 review 记住
  （`tests/artifact-layout-single-source.test.ts`：五种被禁形状、扫描面非空自证、
  每种形状各有一个实例真能被照出来、外加一条**跨语言成对**判据钉住 PowerShell 里那份
  `comfyapp://` 允许根 —— 它在所有 TS 检索面之外，搬根那天不会跟着动）。
- **尽力而为的镜像要按「重试有没有用」分档，而「有出口」不等于「发过一条事件」**（台账 A3 第二段）：
  `canvas-store` 把画布镜像到服务端时写的是 `catch {}`，注释理由正当（「网络不稳时绝不阻塞
  本地优先的界面」）—— 但**归属闸装上之后多出了一格它从来没覆盖过的失败**：
  `FORBIDDEN` 是「这份内容服务端永远不会收」，与「此刻拿不到服务端」在用户那边是两件事
  （前者换端口就看不见自己的画布且再试一万次也不会好，后者下一轮自动保存自然会补上）。
  三条口径：① 分类用**错误码**而不是文案（`~/lib/error-message` 新增 `errorCode()`，
  与日志那一份共用同一条取值链 —— 靠匹配文案则文案一改判决就错）；「4xx 都算被拒」也不对，
  `TIMEOUT`/`429`/5xx 是「现在别打这么勤」，判成拒收就是每次 dev server 重启都弹一条假故障；
  ② 出口要落在**可查的状态**上，不能只广播一条事件：本仓库的 `emitAppEvent` 明确承诺
  不排队重放，而**写这份状态的入口不止一处**（工作区首页新建项目、画廊删除镜像都会改它，
  而那些页面上没挂提示器）—— 那一次的广播没人接，所以只订阅必然漏；
  所以读侧必须「挂载时先读表，再订阅变化」，这一格要单独有用例钉住（把挂载时那次读表删掉，
  恰好只有那一条红）；③ 去重要按「同一条画布的同一句原因」而不是只按 id，
  原因变了要重新说一次（用户照着提示改完名字，界面上不能还留着旧的）；
  ④ **界面上那句必须读得懂，原文与码走日志那一行**。`errorText()` 对 `BAD_REQUEST`
  会原样回出 zod 的 JSON 形状（`too_small` / `inclusive` / `path` 那一坨），
  把它塞进 toast 等于把内部结构甩给用户 —— 「有用户可见出口」的那一半是**读得懂**。
  按码翻成人话（`FORBIDDEN` → 「这个画布编号已经属于别的用户，改个名字另存一份就能保住」），
  翻不出的码走已翻译的原文而不是硬编一句好话；同一行日志再带上 `rawErrorDetail(e)`
  （含 `code=…`）—— 界面上看不见码，日志里就得能查回是哪个码拒的。
  顺带一条只有落笔时才知道的事：**浏览器侧的 lib 模块要留这行日志只能走 `console`**
  （pino 那条是服务端通道，打进浏览器包既跑不起来也会点着
  `client-bundle-node-builtins` 那条判据），而 `tests/single-logger-channel.test.ts`
  默认禁止 `src/lib` 直写 console。正解是按它自己的机制把**这一个文件**登记进豁免清单
  （首行 `"use client"`、且三条判据逐条答得出），不是放宽判据、更不是整目录免检。
  同族判据见 E9：一条通道**两端都要在场** —— 只有派发的广播与只有监听的口都是静默的，
  装机时一次照出三条，逐条处置必须与判据同批。

#### tRPC 桩：协议是 JSON Lines，不是 JSON 数组（ISSUE #1442）

**要喂数据就用 `e2e/support/trpc-stub.ts` 的 `stubTrpc()`**：

```ts
await stubTrpc(page, {
  "task.list": { tasks: [{ id: "a", createdAt: new Date(), … }], total: 1 },
});
```

它按客户端**真正读的协议**产出响应，所以内容是能进到界面上的。别自己 `route.fulfill`
拼信封——那条路会**静默失灵**。

**为什么**：客户端是 `httpBatchStreamLink`（`src/trpc/link.ts`），它发
`trpc-accept: application/jsonl` 协商，服务端由 `jsonlStreamProducer` 回一段
**JSON Lines**（`content-type: application/json` + `transfer-encoding: chunked`）
—— `[{result:{data:…}}]` 这个数组是**另一条协议**（非流式）的形态：

```
{"json":{"0":[[0],[null,0,0]]}}                  ← head：批里 0 号槽指向 0 号流
{"json":[0,0,[[{"result":0}],["result",0,1]]]}   ← 0 号流：槽位 → result 是 promise
{"json":[1,0,[[{"data":0}],["data",0,2]]]}       ← 1 号流：result.data 也是 promise
{"json":[2,0,[[{"tasks":[]}]]]}                  ← 2 号流：真数据（含 superjson meta）
```

消费端 `jsonlStreamConsumer` 的契约是「**第一行**是 head（按 `batchIndex` 索引的对象），
其后每行是 `[chunkId, status, data]` 的 async chunk 定义」。喂数组进去时它被整段当成
**一行** = head，而 head 本该是对象 → `decodeChunkDefinition` 拿到的形状对不上 →
`type` 落空 → 槽位静默变 `undefined`，**全程不抛错**。所以现场是「四种信封形状行为
完全一致、坏 JSON 也一样、控制台零报错、`loggerLink` 照样打 `<< query`」——
界面上只是照旧显示真数据（看起来像「桩没生效」）。

三个连带事实：

- **每行都必须是 `{"json": …}` 信封**（服务端 `serialize` 后 `JSON.stringify`）；
  裸数组行同样解不开；
- **`superjson` 的 `meta` 要作用在整行上**：`meta.values` 的路径带 chunk 前缀
  （实测 `2.0.0.tasks.0.createdAt`）。把数据单独序列化再拼回
  `[chunkId, status, …]` 会丢前缀，`Date` 过线后还原成字符串，客户端
  `row.createdAt.getTime()` 直接抛 `is not a function`。helper 里就是整行
  `superjson.serialize`，所以不需要手工写 `meta`；
- **一个 URL 只有一个处理器**（`page.route` 后注册者**先**被调用、它对不认识的 URL
  `continue()` 会把请求放去网络）：所有过程登记在**同一个** map 里，别分两次调用
  —— 与 11.3.1 上面 `stubComfyTrpc` 的注释是同一条纪律。

协议形态由 `tests/e2e-trpc-stub.test.ts` 锁着，判据是**拿 `@trpc/server` 的真
`jsonlStreamConsumer` 读一遍**（不是复刻一份实现），所以 tRPC 升级换协议会在那里变红，
而不是等某条 e2e 变成「数据没进去」的假绿。`e2e/critical-flows.spec.ts` 里那份
`stubBackend` **不喂数据**（只让请求很快答掉、别卡住界面），注释已按这个事实写明。

**这一层能给出什么判据**：需要**特定数据形态**才判得出来的东西 —— 例如队列的
**位次方向**（后端按 `createdAt` 倒序回、执行器 FIFO，视图必须反一次让最早提交的
成为「第 1 位」，`e2e/queue-monitor.spec.ts`）。真库凑不出这个形状，而它是最像
「只有看屏幕才发现」的错误。

#### 覆盖率棘轮

门禁里覆盖率与单测**共用同一次 vitest 运行**（`pnpm run test:coverage`）：
此前 `pnpm run test` 与 `pnpm run test:coverage` 是两步、同一套五千多条用例跑两遍，
时长与核时都翻倍，而覆盖率本来就跟着这一次运行出（见 13.5.3）。

> **这一步曾经退化成裸 `vitest run`，于是门槛变成死配置**（台账 E2）：平台侧下线后，
> 本地一键门禁 `scripts/quality-gate.mjs` / `.ps1` 的 test 门只剩 `exec vitest run`，
> **不带 `--coverage`** —— `vitest.config.ts` 的 `coverage.thresholds` 里那几十条按实测定的
> 门槛，没有任何自动化路径判定过它们（只有人手动跑 `pnpm test:coverage` 时才判一次）。
> 现在两侧的门禁都带 `--coverage`，并留两条约束：
> ① **覆盖率只在「全量」这一档判** —— 单文件跑 `--coverage` 会把其余路径按 0% 汇总，
> `thresholds` 每一条都刷红（实测单跑一份 `LogPanel.test.tsx` 就报出 `src/lib/workshop/**`、
> `ui/image-viewer.tsx` 等一串 0% 不达标）。所以别把 `--coverage` 挪进钩子的增量档，
> 那一步跑的是几十份用例，门槛必然全红。
> ② **红与覆盖率各自记账**（`vitest.config.ts` 的 `coverage.reportOnFailure`）—— v8 默认在
> 有用例失败时**清掉数据、不产出报告**，于是「一条与覆盖率无关的试用例红」= 门槛静默缺席
> （现场：全量 464 文件 / 2 败，`coverage/` 目录是空的）。修掉这个默认值之后，红照样非零
> 退出，但覆盖率照常汇总并按门槛判。

**给动态段路由加门槛时，方括号必须转义**（同一族的第三种静默失效，实测撞到）：
`coverage.include` 走 glob，而 Next 的目录名 `src/app/api/generated/[...path]/route.ts` 里
`[...path]` 会被当成**字符类** —— 按字面量写进去时条目不匹配任何文件：路由被加载、用例全过，
但报告里**查无此文件**，`thresholds` 就成了空挂的登记（与「只写门槛不写 `include`」同形）。
正确写法是 `src/app/api/generated/\\[...path\\]/route.ts`。给 `[id]` / `[[...slug]]` 这类路由
加门槛时同理。判断办法很朴素：跑完去报告里找这一条在不在，而不是看用例绿不绿。

平台侧用 `testing:coverage` 插件读 `coverage/lcov.info` 上报曲线 ——
**只上报，不在平台侧设 `lines` / `diffLines` 阈值**：平台阈值是绝对百分比，
本仓库走的是「按目录设门槛」的口径，两套数字放在一起必然打架。

**上报必须排在「真的跑完用例」之后，且不许把 script 藏进 `type:` 底下的 `stages:`**：
这两条各自独立，却都会以同一句话收场（插件报「没有找到覆盖率报告文件」）。

- **并行会让插件赶在报告产出前退出**：同一个 stage 里的 `script` 与 `type` 是
  **两个并行任务**，把二者写在一处时，`testing:coverage` 容器会在测试还在跑、
  `coverage/` 尚未产出时就开始找报告文件，而 `breakIfNoCoverage` **缺省为 `true`**，
  找不到即报错退出。现场是该步在 1~2s 内失败（vitest 要 60s+），日志为
  `Error: 没有找到覆盖率报告文件`，整条门禁在测试这一步中断、**vitest 一次都没跑完**。
  探针实测：同一份「找不到报告」的日志配上 `breakIfNoCoverage: false` 即返回 0 ——
  说明失败正是这个缺省值触发的，而不是报告路径写错。
- **`type:` 底下嵌 `stages:` 会被静默丢掉**：平台解析带 `type:` 的 step 时只认
  那一步**自带的** `script`，嵌套那层不生效 —— 构建日志里 vitest 根本没有运行痕迹。

因此本仓库的形态是 `单元测试`（`pnpm run test:coverage`）→ `覆盖率上报`
（`type: testing:coverage` + `pattern`）**两个相邻 stage**：拆分版在真实构建里让插件
拿到了 `/workspace/coverage/lcov.info`（行覆盖率 63.48%），是已验证可行的形态。
原先由 `tests/cnb-pipeline-gates.test.ts` 的「用例在上报之前跑完，且上报步骤不许把
script 藏进 type 底下的 stages」一条把两条口径一起锁住（挪到并行位置、或在
`type:` 底下嵌 `stages:`，都会失败，均已在本地实测）—— 该用例随 `.cnb.yml` 一并
删除（见 13.5.3），两条口径留档在此，日后重启平台侧时按本段重建守卫。

**报告格式是两处必须对上的口径，只改一侧不会红**：插件读的是**磁盘上的文件**，
文件由 `vitest.config.ts` 的 `coverage.reporter` 决定要不要产出。PR #641 把门禁切成
插件上报时漏改了 reporter（当时只有 `text` + `json-summary`），现场是插件在本步开始
1.8s 后以「没有找到覆盖率报告文件」退出 —— vitest **根本没跑起来**，整条覆盖率上报
与「全量 vitest 只跑一遍」的核时收益同时静默失效，而报错行落在与本意无关的位置。
因此 reporter 固定包含 `lcov`。平台侧流水线删除后（13.5.3）这份报告不再有上游
消费者，但**保留 lcov 并留住这条口径记录**：它是「覆盖率接任何外部工具」的通用入口，
删掉会让日后重启上报时重新踩一遍同一个坑（当时的现场是插件 1.8s 就退出，
而报错完全指不出是 reporter 少配了一项）。

**`script` 与 `type:` 必须写在同一条 step 上**（与上一条同源，`.cnb.yml`
删除后仅作口径记录）：平台解析带 `type:` 的步骤时**只认那一步自带的 `script`** ——
把 `script: pnpm run test:coverage` 藏在 `type` 底下的 `stages:` 里，那一句会被
静默丢掉（构建日志里 vitest 根本没有运行的痕迹），插件才在 1.8s 后报同一个
「没有找到覆盖率报告文件」。`/workspace`（`CNB_BUILD_WORKSPACE`）在脚本任务与
插件/内置任务之间是**共享**的（平台文档「执行环境与文件共享」：未配 `image` 的
脚本任务在流水线容器里跑，配了 `image` 的脚本任务与插件任务在独立容器里跑，但
`/workspace` 与 `docker.volumes` 声明的目录在任务间可见），所以「先跑用例、再
上报」写在同一步读得到报告文件。日后重启上报时按这条写，别再踩一遍。

`vitest.config.ts` 的 `coverage.thresholds` 按**目录**设硬门槛，不设全局门槛

### 11.8 视觉回归（像素基线）

> 目标：捕获**布局/像素级退化**（配色、间距、尺寸、深浅色、响应式断点被无意改动），
> 这是 DOM 快照/行为测试都覆盖不到的防线。

#### 方案选择（避免两套基线维护成本）

仓库采用 **Playwright `toHaveScreenshot`** 作为唯一视觉基线方案，不引入
Chromatic / Vitest browser mode / 第二套截图工具。理由：

- 仓库已装 `@playwright/test` 并用于 E2E，复用同一浏览器基础与 webServer，无额外运行时。
- Chromatic 依赖 Storybook 基建与云服务，落地成本高；而**本仓库已接入的 Storybook
  （ISSUE #1381，`pnpm storybook`）只做组件工作台与 a11y 报告，不接 Chromatic** ——
  引入第二套云端像素基线正是本节要避免的成本。
- Vitest browser mode 需为截图单独装配浏览器驱动，且与 E2E 工具栈割裂。

> **Storybook 与本节的关系**：两者判的**不是**同一件事，不互相替代（ISSUE #1381）。
> Storybook 是「单个组件在受控 props 下的形态」（开发期预览、a11y 违规、明暗两态），
> 像素基线是「真实页面在真实栈上的布局/配色/断点」——后者才是回归的防线。
> 因此本节「唯一视觉基线方案 = Playwright `toHaveScreenshot`」的口径**不变**。
>
> **这条分工本身有判据**（`tests/visual-storybook-division.test.ts`，进固定清单）——
> 之前两侧各管一边、**没有一条盯着「哪件事该由谁做」**，而边界被越过去时不会红：
> 给 story 加 `toHaveScreenshot` 会在 Storybook 的 webServer 上长出**第二套像素基线**
> （判定口径与 `e2e/visual` 完全不同）；接 Chromatic 会多一笔云服务依赖；而
> `e2e/visual/` 被清空或只剩一页是**减法型**失效（删东西比加东西更容易过 review）。
> 判据三向：Storybook 侧不许出现截图断言 · 不许引入第二套像素工具 ·
> 本节声明的基线范围档（深浅两态 / 响应式断点 / 空态）各有落点。**不判「覆盖几个页面」**
> —— 本节已定调「只锁定关键 UI，不追求全组件覆盖」，数字型门槛会逼着人录一堆脆基线。
>
> **组件覆盖率也有判据**（与本节无关，同属「数字写在文档里就会过期」那一族）：
> `tests/storybook-component-coverage.test.ts` + `scripts/storybook-check.mjs` 现算
> 「`ui/` 下有多少组件被 story import 到」，与 `scripts/.storybook-coverage-baseline.json`
> 比 —— **只许升不许降**，分母（可预览文件数）变了要同批回答问题。口径与理由表的
> 门槛见 [16 §16.2.3.5](16-shadcn-ui与表单校验.md#16235-组件覆盖率是棘轮判据不是文档里的一句话)。
>
> 另外，**故事文件自己的写法**也有判据（与本节无关，但同属「不构建失败却一片白」那一族）：
> 枚举清单要从 props 派生、不能从 `cva()` 的返回值上取（`cva()` 返回的是函数，
> 运行期没有 `.variants`；Storybook 会在**加载期**抛 `Cannot read properties of
undefined`，表现是「侧栏列着故事、画布一片空白」）。判据是
> `tests/storybook-cva-variant-source.test.ts` 与 `node scripts/storybook-check.mjs`，
> 口径见 [16 §16.2.3.4](16-shadcn-ui与表单校验.md#16234-故事里的枚举清单从-props-派生不要从-cva-的返回值上取)。

**基线范围**（以「用户会看」为准，**只锁定关键 UI**，不追求全组件覆盖）：
xyflow 画布布局/节点配色、空态/空画布提示、弹窗/浮层尺寸、Tailwind 响应式断点、
深色（`.dark`）与浅色主题对比。

**当前落点**（"档档有落点"由 `tests/visual-storybook-division.test.ts` 判，见上）：

| 声明的档            | 落点                                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 深浅两态对比        | `login.visual.spec.ts` 的 `login-desktop` / `login-desktop-light`；`workspace.visual.spec.ts` 的 `workspace-desktop-dark` / `workspace-desktop-light` |
| Tailwind 响应式断点 | `login.visual.spec.ts` 的 `login-mobile`（`devices["iPhone 13"]`）                                                                                    |
| 空态                | `models.visual.spec.ts` 的 `models-empty`（`model.list` 桩成空列表）；`canvas.visual.spec.ts` 的 `canvas-empty`（空项目的空画布引导卡）               |
| xyflow 画布         | `canvas.visual.spec.ts` 的 `canvas-filled`（四张真节点 + 三条真连线 + 真视口）                                                                        |
| 弹窗/浮层尺寸       | `overlay.visual.spec.ts` 的 `overlay-log-default` / `overlay-log-wide`（同一浮层的默认档与加宽档，两档宽度由 `boundingBox()` 断言）                   |

公共前置收在 `e2e/visual/support/page-baseline.ts`（`unstableChromeMasks` /
`setTheme` / `settle` / `clearProjectIndex`）—— 五份 spec 各抄一份就是 §12.12 的孪生对。

**两档的钉法**（它们各有一条别的屏没有的坑）：

- **画布**：React Flow 的画面由「视口 × 节点画布坐标」两件事一起定。视口是
  `fitView` 异步算出来的（组件里双 rAF），所以 `canvas.visual.spec.ts` 在截图前
  **等它收敛**（连续两次读数相同算停下），而不是读第一帧 —— 实测第一帧是过渡值
  （`matrix(0.99…, 12.07, 10.06)` vs 收敛值 `matrix(0.929…, 118, 100.13)`），
  拿它当基线等于截一张过渡态。另外**边能不能画出来取决于端口在节点上真的存在**：
  本画布只有「每个节点右侧 `output`」与「`picture` 左侧 `inputImage`」两种，
  写成别的组合时 React Flow **静默不渲染**那条边（不报错、画布只是少一根线），
  所以用例把边数也钉住（4 节点 / 3 边）。
- **浮层尺寸**：被测对象是**两档宽度**，不是浮层里那堆内容。日志面板的行是逐帧在
  长的（时间戳、跑 id、错误计数），拿它当基线对象就是本节明令禁止的「时变内容」；
  所以用例打开后把来源切到**恒定 0 行的那一档**（`壳侧编排`，它读的是双击启动留下的
  `log/launcher/shell-launch.log`），正文落空态、计数全 0；页脚那颗 `服务 <bootId>`
  徽标逐次启动都不同**且是变宽的**（用它的 `title` 只遮徽标本身时，遮罩带宽度会跟着
  随机串变 —— 实测连续两次跑出 40 像素差异、且只在遮罩那一条），所以遮的是**整条定高
  页脚**。两档宽度由 `boundingBox()` 断言（默认档 `w-6xl` = 1152、加宽档
  `calc(100vw-16px)` ≥ 1152+128），因为 ISSUE #720 那次静默失效正是**宽度没变**。

#### 基线用例约束

```ts
// ✅ e2e/visual/*.spec.ts 示例：锁定登录页明/暗两态
import { test, expect } from "@playwright/test";
import { setTheme, settle, unstableChromeMasks } from "./support/page-baseline";

test("登录页暗色档基线", async ({ page }) => {
  // ⚠️ 别用 `documentElement.classList.add("dark")`：它绕过 `next-themes` 直接改 DOM，
  // 水合时被 Provider 的偏好覆盖，而且**表达不出 light 档**。写 `theme` 键走的是
  // 用户真会走的那条路（`ThemeProvider` 的 storageKey）。
  await setTheme(page, "dark");
  await page.goto("/login");
  await settle(page, "登录以同步你的作品");
  await expect(page).toHaveScreenshot("login-desktop.png", {
    fullPage: true,
    mask: await unstableChromeMasks(page),
  });
});
```

> ⚠️ **页面级基线的数据依赖必须桩掉或清干净**：「跑一下看看」得到的基线若随「这台机器
> 的 DB / localStorage 里有什么」变，它就不是基线 —— 那不是「红先定性」能救的。
> 本仓库两处实测形态：`models` 屏渲染的是真实模型库（`stubTrpc` 把 `model.list` 桩成
> 空列表才有确定的空态）；首页「最近项目」区取决于 `canvas-store` 的项目索引
> （`clearProjectIndex` 按前缀清 localStorage）。

**规则**：

- 视觉用例**不碰随机/时变内容**（时间戳、动画、加载中骨架屏、由 DB 驱动的列表），
  否则基线必 flaky。需要时先 mock / 用固定 fixture 数据，把渲染内容钉死。
- 基线 PNG **提交入库**；用例改动导致基线变更时，用
  `pnpm exec playwright test --update-snapshots` 重录基线，并在 PR 描述里标注
  「视觉基线已更新：<原因>」，供 reviewer 人工核对 diff。
- 失败产物（actual/diff PNG）落在 `test-results/`（已在 .gitignore 忽略），仅排查用。
- ⚠️ **基线文件名带平台，因此「换了机器 = 没有基线」**：`toHaveScreenshot` 的默认
  文件名含 `-<platform>`。像素层**保留**（口径：布局 / 配色 / 尺寸这类退化只有像素抓得住，
  `getComputedStyle` 那类跨平台断言补的是另一张网），代价是**每个真正执行像素回归的环境都得
  有自己的那一套**。当前登记两档：`-win32.png`（开发机，`pnpm dev` 口径）与
  `-linux.png`（容器 / 类 CI 环境，`CI` 为真 ⇒ `pnpm start` 口径，需先 `pnpm build`）——
  两档都用同一份 spec 录出、实测同一命令连跑两次零差异。**基线是按 webServer 口径录的**：
  Next 的 dev 指示器那个 mask 目前遮不住（宿主的 bounding box 是 0×0，见下一条），于是
  `pnpm dev` 与 `pnpm start` 的像素互不相同 —— 在某一档跑像素时，`CI` 的真假要与该档基线
  录制时一致，否则报的是「dev 指示器那块差异」而不是界面变形。原先入库的 `-linux.png` 曾在
  `#6538809` 删掉（录于全局状态栏出现之前、也没有 mask 规则，与当时 spec 已不是同一件界面
  —— **留一份对不上现状的基线比没有基线更坏**）；这一档后来按「同一份 spec 重录成套 PNG +
  同批登记 `SUPPORTED_PLATFORMS`」的姿势恢复。缺档的表现也不是「那一档没跑」，而是
  **判失败并顺手把新生成的 PNG 写进 `*-snapshots/`**（那里不被 .gitignore 忽略），于是留下
  半套基线。这条现在有判据：`tests/visual-baseline-pairing.test.ts` 按
  `e2e/visual/*.visual.spec.ts` 自扫（不维护 spec 清单），核对「每个截图名 × 每个登记平台
  都有 PNG」「PNG 全部被 git 跟踪」「没有未登记的平台后缀、也没有查无此名的孤儿基线」三头，
  登记在提交前的固定守护清单里。
  **「本机没有基线」这件事另有一层**（本条此前只写「换了机器 = 没有基线」，而它要的处置
  一直只写在文档里）：那三头判的是**仓库里那几套基线的形态**，不回答「**运行这台机器**
  会不会一跑就红」—— 在没登记过像素平台的机器上，它们照样全绿（那是如实回答，不是漏判）。
  现在这个问题由 `pnpm check:visual` 的**前置判决**回答（见下面「按需跑」那条），
  清点内核与那三头判据**同一份**（`scripts/visual-baselines.mjs`，§12.12）。
- ⚠️ **「页面不依赖后端」不等于「像素可复现」**：根布局给每个页面挂着全局
  `BrowserStatusBar`，里面有**实时帧率与系统时钟**，Next 的 dev 指示器也在左下角 —— 三者都
  不是被测界面却逐帧在变，桌面端 fullPage 因此永远取不到两张稳定截图，报的是
  `Failed to take two consecutive stable screenshots`（实测差异约 90 个像素，就是 FPS 那两位
  数字）。写视觉用例先把这类 chrome 用 `mask` 掉：见 `e2e/visual/login.visual.spec.ts` 的
  `unstableChromeMasks`（按 `aria-label` 取状态栏；dev 指示器按存在与否追加）。**判据是同一
  命令连跑两次都绿**，不是 `--update-snapshots` 那一次「写成功」。
  ⚠️ **但「dev 指示器按存在与否追加」目前遮不住它**：Next 把这个角标挂在 `nextjs-portal` 的
  **shadow root** 里，且宿主元素 `position` 不占位，`boundingBox()` 实测 `0×0` —— 而 Playwright
  的 `mask` 是按元素 bounding box 画的，0×0 等于什么都没遮（实测 win32 基线的左下角仍留着那个
  「N 1 Issue」角标）。所以屏掉 dev chrome 这件事**暂时靠「不在 dev 口径下录基线」来达成**，
  不是靠这条 mask；真要让它成为 mask 能遮住的元素，得连同 win32 基线一起重录。
- 三种走法按情形选：
  ① UI 改动导致基线合法变更 → `pnpm exec playwright test e2e/visual --update-snapshots`
  重录，且**同一截图名在登记平台里成套提交**（不许只提其中一张）；PR 标注
  「视觉基线已更新：<原因>」；
  ② 只想验证「算出来的样式对不对」（颜色 / 层级 / 尺寸这类）→ **别用像素**，
  在 e2e 里读 `getComputedStyle`，天然跨平台（参考 `e2e/theme-token-consumers.spec.ts`）；
  ③ 只是路过跑了一下 → `git status` 清掉生成的未跟踪 PNG（留着它会顶掉「入库」那条判据）。
- 新增一档执行环境（linux 容器 / macOS）时，**先用同一份 spec 在那档录出成套 PNG，再同批**
  改 `tests/visual-baseline-pairing.test.ts` 的 `SUPPORTED_PLATFORMS`：只登记平台不录基线 =
  那一档一跑就红；只录基线不登记平台 = 被孤儿判据点名。两种半套都比「没有那一档」更费人。
  **恢复已被删掉的那一档也走同一条路** —— 把旧 PNG 贴回来不算：`#6538809` 删掉 `-linux.png`
  是因为它与当时的 spec 已不是同一件界面，恢复 linux 档的姿势是「在该档用当前 spec 重录成套
  PNG + 同批把 `linux` 加回 `SUPPORTED_PLATFORMS`」，不是把旧图还原。
- ⚠️ **「某一档缺几张」是一个必然出现、且必须能被提前命名的状态**（`PENDING_PLATFORMS`）：
  新增截图名会让**某一档缺那几张**，而像素是平台渲染的产物 —— 只能在**那一档的机器上**
  录（在 linux 上录一份改名叫 `-win32` 是**造假**，不做）。本仓库的自动化执行环境
  （NPC 工作区 / CNB 容器）都是 linux，所以 win32 档的补录只能由 Windows 开发机完成。
  `scripts/visual-baselines.mjs` 的 `PENDING_PLATFORMS` 把这件事登记成**一条有主的账**：
  判据对登记档的缺失**放行**，但立刻用**双向不变式**盯住它 ——
  ① 登记的平台不在 `SUPPORTED_PLATFORMS` 里 = 孤儿登记；
  ② 登记的平台**已经不缺**任何基线 = 该删登记而没删（补录那批的漏网，这条最关键：
  少了它，这张表就退化成赦免名单，**下一次**真丢了基线照样放行）；
  ③ `reason` 写得太短（"稍后处理"）也算红 —— 下一个人要知道去哪台机器补。
  `scripts/pixel-run.mjs` 的前置判决在那一档给出「正在待重录」而不是「从没登记过」——
  两种状态的动作不一样（前者补几张、后者要整套录完再登记平台）。
- ⚠️ **「基线按 webServer 口径录」这条现在有数据、也有判据**（此前只在文档里写了一句
  「`CI` 的真假要与该档录制时一致」，**录基线那一档完全不校验它** —— 而验基线那一档不受
  缺基线那闸拦是它的本分，所以口径这条口子一直开着）：`scripts/visual-baselines.mjs` 的
  `PLATFORM_RECORDING` 把「每档录于 `dev` 还是 `start`」登记成**数据**（`SUPPORTED_PLATFORMS`
  从它派生，两处不会漂）；`scripts/pixel-run.mjs` 起 webServer / 浏览器**之前**先核
  「本机 `CI` 的真假换算出的口径」与「该档登记的口径」是否一致（`checkRecordingEnv`），
  不一致直接拦下（退出码 3）并给出置法。为什么录基线档也要拦：口径不符时 `--update`
  会**成功**——生成一套看着正常的 PNG，自洽、不当场红，只在以后某次真差异里混进来、
  还指不出是它。`pnpm check:visual --dry-run` 会把「本档登记为哪条 / 本机实走哪条」一起打出来。
- ⚠️ **「待重录」的账会在改像素层时被点名**（只提醒、不阻断）：那张登记表是**放行**的，
  所以改像素层的人不会从任何判据里听到「还欠着」——缺的账只剩一句给人读的 `reason`。
  `scripts/visual-gate.mjs`（改了 `e2e/visual/**` 才跑那一步）因此顺手打印一行：哪几档
  还缺、只能在哪台机器补、补完连同登记一起删。**不阻断**是刻意的：补录只能在那一档的
  机器上做（本仓库的自动化执行环境都是 linux），阻断等于让所有人卡在一个只有少数人能解
  的账上——那比漏掉更费人。
- ⚠️ **「判据存在」不等于「判据拦得住」，所以它现在有执行者**：`tests/visual-baseline-pairing.test.ts`
  已在 `scripts/affected-tests.mjs` 的固定守护清单里（每次提交都跑），而「改像素层的提交必须
  显式跑一次 vitest」这句**不再只是文档口径**——`scripts/visual-gate.mjs`（pre-commit D 组）在
  暂存改动命中 `e2e/visual/**` 或 `playwright.config.ts` 时，判**本次要跑的清单里那条判据在不在**：
  不在就直接阻断。清单与 C 组同源（`resolveAffectedTests`，§13.5.8），所以「有人把这条判据从固定
  清单里摘掉」当场被拦，而不是等到下一次像素层出事才发现判据没有执行者。
  这一条要拦的动作是「拿 e2e 的通过数当像素层结论」——`--grep @critical` 一条视觉用例都不含
  （视觉 spec 没有 `@critical` 标签，而 §11.7 按需验证清单点名的正是它），跑绿了证明不了像素层没坏。
  现场是 #6538809：那一批删掉 `-linux.png` 两张基线、同时把 `SUPPORTED_PLATFORMS` 收成 win32，
  提交者从 e2e 读数得出的「像素层没事」与像素层的实际判决无关（实测在 Linux 容器上跑
  `pnpm test:e2e`，两条视觉用例报的是 `A snapshot doesn't exist at …-linux.png, writing actual`）。
  本步**不另起一次 vite**（C 组已经起了，钩子那一档只起一次冷启，§13.5 的口径）：它判的是
  「本次提交带不带像素判决」，不是「你有没有手跑 vitest」——后者是一句无法观测的话。
- **「按需跑」现在有入口、也有定性（`pnpm check:visual`）**：上面那条门禁只判「带不带判决」，
  它**刻意不跑像素**（起 webServer + 浏览器会与钩子里的 A/B/C/D 抢资源，普通提交也不该付）。
  真要跑像素时走 `scripts/pixel-run.mjs`（`pnpm check:visual`；Windows 双击入口是
  `scripts/quality-gate.ps1 -Mode visual`，登记在 launch-and-build §9.5 的对照表）：
  - 它**同批跑两次**——像素档（`e2e/visual`）+ 配对判据（`tests/visual-baseline-pairing.test.ts`）。
    少一次就等于「交出一批基线而『基线成套且入库』不在这一轮里判」，那正是 #6538809 的形态。
  - **默认只在当次检出自证、不落盘**：基线是人工 review 的核心对象，顺手写 PNG 等于把
    review 对象变成执行的副产品。落盘要显式 `--update`（`pnpm check:visual:update`），
    且这台机器要**连跑两次都绿**才算「像素可复现」——录一次成功只证明「这次写成功了」。
    ⚠️ **这句承诺对「缺基线」不自动成立，得显式争取**：Playwright 的 `updateSnapshots`
    **默认就是 `'missing'`**（`playwright test --help` 自己写着「Running tests without the
    flag defaults to "missing"」）—— 不带任何开关，缺的那几张也会被写进 `*-snapshots/`。
    所以检查档一律显式传 `--update-snapshots=none`（`CHECK_UPDATE_MODE`），录基线档
    （`--update`）才放开。否则「默认不落盘」是一句对已有基线成立、对**缺基线**恰好不成立的
    话 —— 而缺基线正是最需要它成立的时候（在没登记过的平台上跑一次，工作区里就多出半套
    未入库的 PNG，那正是上面判过「比没有更费人」的形态）。
  - **起任何东西之前**先答「**本机这个平台有没有成套基线**」（`checkLocalBaselines`）：
    命名带平台 ⇒ 这是一个必然会出现、且代价为零就能提前命名的状态。没有就**不启动**
    webServer / 浏览器，直接按「平台没登记（先录再同批登记）/ 登记了但缺几张（补录）」
    给出文件清单与动作，退出码 2。此前的形态是：先付一遍构建 + 起服务 + 起浏览器，
    再从 Playwright 的输出里读出「这台机器没有基线」，还得自己认出那一句说的是这件事。
    清点内核在 `scripts/visual-baselines.mjs`，与配对判据**同一份**（§12.12）——
    两处各抄一份的话，「判据说基线成套」与「像素档说本机没基线」必然对不上账。
  - 它把**红的定性**一起给出来（三条实测形态各有各的动作）：`A snapshot doesn't exist at
…-<platform>.png` = **这台机器没有基线**（按上面那条登记平台 + 成套录，别当回归去改业务
    代码）；`Failed to take two consecutive stable screenshots` = 页面里有逐帧 chrome（加 mask，
    放宽阈值只会让基线失去意义）；diff 数字 = 这才是退化。认不出的形态一律先按 §11.13 隔离
    重跑定性 —— 「红先定性」是硬动作，不是可省的一步。前置判决拦下时不必再走这三档定性：
    它是零代价的**前置**答案，不是从输出里反推的推断。
  - 它**不进 `check:all`**：像素档的代价与「结论只在录过基线的那台机器上成立」（基线名带平台）
    两条一起决定了它不属于「日常该完整跑一遍」那一档，与 E2E `@critical` 同属 §13.5.4 的按需层。
    ⚠️ **这条口径现在也有执行者**（此前只是文档里的一句话）：`GATES.visual` 带 `run: false`、
    `.ps1` 那侧带 `Run = $false`，两侧都写着「不在 `all` 里」的注释，而**没有任何判据按名字
    钉住它**。实测漏法：把那一档挪进默认档（去掉 `run: false`）**同时新增任意一个按需档**，
    `tests/ps1-consistency.test.ts`（此前唯一会解析这张表的判据）照样全绿 —— 它盯的是「按需档
    集合非空、且两侧一致」，只要还剩一个就成立。于是「像素档混进 `pnpm check:all`」全绿通过，
    代价是每次一键门禁都起 webServer + 浏览器（且结论只在录过基线的那台机器上有效）。
    判据现在是 `tests/pixel-run.test.ts` 的三条（进固定清单）：**按入口**（`args` 里那个
    `pixel-run.mjs`）而不是门禁名判 —— 改名就能绕过的判据等于没有 —— 两侧都判，
    外加「解析器不是空转」（两侧都真解析出条目、默认档集合一致）。两个解析器与
    `ps1-consistency` 共用一份 `tests/helpers/quality-gate-gates.ts`（§12.18）。
- ⚠️ **「换了基线」这件事本身此前没有任何判据，而它真出过事**（ISSUE #1282 的实测）：
  入库的 `-linux.png` 有几张与当时环境差 **1 像素**（文字整体下移一行），而三个判据
  一个都看不见 ——
  ① `playwright test --update-snapshots` **总是绿**（它把基线改写成当次实况，
     「写成功」被读成「像素可复现」）；
  ② `tests/visual-baseline-pairing.test.ts` 只核「截图名 × 平台**成套且入库**」，
     不核「这套 PNG 现在还跑得绿」；
  ③ `pixel-run.mjs` 的 `--update` 档按设计**不拦缺基线**（那是它的本分）。
  于是「录一版、把仓库基线换成它」这条路上一个判据都没有，而换掉的是**别人的档**：
  真正执行像素回归的那台机器下一次一跑就红，红的原因（1 像素）还得现场看图才能定性。
  防线是**新鲜度账**（`scripts/visual-freshness-gate.mjs`，pre-commit D 组）+ **跑绿即记**
  （`scripts/pixel-run.mjs`）。这一条走过一次弯路，两次的形状都记下来 —— 它说明「欠账」
  这个词会把人引向什么样的机制：
  - **弯路（已撤）**：先做的是一张「换基线 ⇒ 领一张自证欠账」的表 —— 动过基线 PNG 的提交
    必须同批带来 `scripts/.visual-reproduce-ledger.json`。它的**方向反了**：把成本压在
    「**换基线的人**」身上，而这条红的真正受害者是「**信任这批基线的人**」；而且它记的是
    「我换过」这个**动作**，不是「它现在还绿」这个**状态** —— 于是一张空白欠条能合法地
    停留在仓库里，直到下一个人去那台机器上跑。它连同 `--record` 一起撤掉了（ISSUE #1282）。
  - **现在的形状**：每一**登记**档都必须有一条**新鲜度记录**
    （`scripts/.visual-baseline-freshness.json`），写清**谁 / 什么时候 / 按哪条命令复核的**
    —— 缺一条 = 这一档还停在「录过就算数」。记录由 `pnpm check:visual` **跑绿即记**
    （`pixel-run.mjs` 的 `recordFreshness`），所以账上的日期就是「上一次真跑过」的**事实**，
    而不是一句承诺。
  - **`--update` 不记、红着不记**：「录基线」只是「这次写成功了」（§11.8 反复写着
    它与「像素可复现」是两件事），而红着的时候记一条「我跑过」会把「跑过」与「跑绿过」
    混成同一件事 —— 两个都是这条账要防的形态。
  - **`PENDING_PLATFORMS` 那一档不要求新鲜度记录**：它缺几张基线、只能在那台机器上补录，
    「上次自证」对它是句不成立的话。两张表各管一件事 —— pending 管**数量**、新鲜度管**时效**。
    强行要求一条只会逼人填一句假读数。
  - ⚠️ **刻意不做墙钟阻断**：像素回归的结论只在**录过基线的那台机器上**成立（基线名带平台），
    而本仓库的自动化执行环境都是 linux —— win32 档的复核只能在 Windows 开发机上做。
    拿时钟去阻断等于让所有人卡在一个**只有少数人能解**的账上（与前一条 pending「只提醒、
    不阻断」同味）。所以纪律收在**可观测的形状**上（有主、写清、不挂空档），
    「多久没跑算旧」由人看着每次提交打出来的读数决定 —— 判据不下一个会随机器与运气变化的阈值。
  - **钩子里不跑像素**：`pixel-run.mjs` 要起 webServer + 浏览器，与钩子里的 A/B/C/D
    抢资源（§13.5 的并行预算是实测敏感项）。钩子只做它做得到的那件事 —— **每档都得有主**。
- 基线维护是**人工 review 的核心对象**：自动化只负责「不一致即失败」，是否采纳新基线由人决定。

### 11.9 DOM 快照边界：不要拿快照当结构基线

**现状问题**：`src/components/studio/**/__snapshots__/*.snap`（Vitest DOM 快照）
把整棵渲染 DOM dump 成文本，**易碎**——任何无关 class/标签/CSS 变量变更都会
击穿全部用例，且与真正的布局/像素退化无关，误报成本高。

**边界与迁移方向**：

- `toMatchSnapshot()`/`toMatchInlineSnapshot()` **禁止新增用于断言整棵 DOM 结构**。
- 判断准则：**只断言用户可见结果**（`getByRole`/`getByText` + jest-dom 匹配器，
  见 §11.2），**不要**用整棵 `container` 快照代替行为断言。
- 存量 `.snap` DOM 快照按 §11.2 迁移为「组件断言用户可见结果」，迁移完毕的
  测试删除对应 `.snap` 文件；**迁移期间不得新增** DOM 结构快照。
- 布局/视觉层面的防退化职责移交 §11.8 的 Playwright 像素基线，不在 Vitest 层用
  DOM 快照重复承担。
- **快照形态的选择（vitest 5 起）**：上面禁的是「拿快照当 DOM 结构基线」这件事，
  不是快照本身。三类产物各有各的落点 —— 小、稳定、与人读的代码贴在一起 → 内联快照；
  短且一次性 → `toMatchSnapshot`；**大块、需要被人工 review 的真实产物**
  （生成物、结构清单）→ **`toMatchFileSnapshot("path/to/out.txt")`**：它把基线写成
  一个**能独立打开、能单独 diff 的真文件**，而不是 `.snap` 里一段转义过的字符串 ——
  review 对象从「测试文件的附属物」变回「产物本身」，这正是 §11.8 那条
  「基线是人工 review 的核心对象」想要的性质。

### 11.9.1 文件快照（`toMatchFileSnapshot`）：给「大块且人读」的产物用

判据是**产物形态**而不是产物大小 —— 满足下面两条就走文件快照，不满足就别用：

1. **大块**：内联成字面量会把 diff 挤成一团、把测试文件撑成不可读；
2. **人读**：它的**内容变化本身就是 review 对象**（一个新名字、一条被删的声明），
   而不只是「和上一版不一样」。

两类典型落点：

- **生成物**：`docs/generated/**` 这类「源 → 产物」的文本（本仓库这类同步判据目前
  走 `*.cjs --check` 脚本，不在 vitest 里）；
- **结构清单**：从源码**解析出来的那份事实**。实例是 `@theme` 声明的 token 清单
  （`tests/theme-tokens-compile-source.test.ts`）—— 149 个名字，少一个的表现不是
  「某条用例红」而是「某个 `bg-*` 类编不出来、界面上那处颜色悄悄回退到兜底」，
  而「这一版到底声明了哪些」只有人读得出来。

三条边界：

- **基线要入库、要能单独 diff**。放在 `__snapshots__/` 下、名字带扩展名
  （`.txt` / `.json` / `.html`），让它像产物一样被打开 —— 不要放进 `.snap`。
- **先钉「解析本身有效」再比清单**。清单从源码解析出来时，解析规则失灵的表现是
  **空清单照样通过**（快照变成空文件）。所以在比对之前先断言解析面非空
  （本仓库那条写的是 `declared.size > 50`），否则这条判据是一条会静默失效的清单
  （同 §11.13.1 那条「判据自己也不许依赖不受控的输入」）。
- **更新走 `-u`，且要限范围**。`pnpm exec vitest run -u` 不带文件参数会**全量**跑并
  把项目里所有快照一起写掉 —— 只想录一份文件快照时，参数里带上那个文件
  （`pnpm exec vitest run -u tests/xxx.test.ts`）。

### 11.10 Tauri 壳薄层测试与业务边界

> 桌面壳（`src-tauri/**`）只做「薄壳」职责（窗口、custom-protocol、崩溃兜底、
> 进程树清理、日志出口）。给它一层**可重复的冒烟级自动化**守壳级能力，同时用硬
> 边界把业务/画布/数据流挡在 Web 层测——**业务逻辑一旦沉进 src-tauri 就难测且
> 难回滚，属反模式**（对齐 [launch-and-build.md §1 分层职责](launch-and-build.md)）。

#### 11.10.1 壳级能力清单（只测这些）

| 能力                  | 验证方式                                                                                                              | 关联规范                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 启动出窗口            | tauri-driver / Playwright 连 WebView2，断言应用窗口就绪、能加载 splash 或主界面                                       | §1                         |
| custom-protocol 注册  | 探测 `comfyapp://` 协议可用（壳编译带 `custom-protocol` feature 后启动页/资源内嵌，非 devUrl 导航）                   | §2 / §5「Edge 错误页」条目 |
| 崩溃兜底 / 进程树清理 | 强杀壳进程后断言 `taskkill /PID <pid> /T /F` 能整树回收，无 node/pnpm 残留锁端口                                      | §3                         |
| 日志出口              | 断言启动日志按 §4 布局落到 `log/`（按次命名 + 轮转），无固定名日志被锁死                                              | §4                         |
| 窗口/启动页重编一致性 | 改动 src-tauri 后必须 `cd src-tauri; cargo build --release --features custom-protocol` 重编，再跑冒烟，避免跑旧二进制 | §5 / §7                    |

#### 11.10.2 工具与跑法（薄、不引入全套矩阵）

- 推荐 **tauri-driver**（WebDriver2 协议）+ 少量 Playwright WebView 客户端；或在
  无法起 tauri-driver 的环境退化为「脚本层冒烟」：直接校验壳二进制时效、
  custom-protocol 编译产物与日志出口。
- 冒烟脚本按次命名 + 轮转，落在 `log/`，不引入新的固定名日志文件（防残留句柄锁死）。
- 壳冒烟只在改 `src-tauri/**` / `tauri.conf.json` / `splash-assets/**` 的 PR 上跑，
  不进每次提交的默认 `pnpm test` 矩阵（Windows + 重编开销大）。

#### 11.10.3 业务边界（硬规则）

| 属于壳测试                                    | 不属于壳测试（去 Web 层）                |
| --------------------------------------------- | ---------------------------------------- |
| 窗口/启动页/协议注册/崩溃兜底/进程树/日志出口 | 画布、节点渲染、数据流、tRPC、表单、状态 |
| 冒烟 + 错误兜底                               | 业务行为、覆盖率爬坡                     |

**规则**：业务主体始终在 Web 层（Vitest/组件/Playwright 见本章 11.1~11.7）测；
`src-tauri` 只允许出现窗口/导航/进程编排，禁止写入业务逻辑。新增含 postinstall
构建脚本的 Rust/原生依赖，同步更新 `pnpm-workspace.yaml` 的 `allowBuilds`。

#### 11.10.4 壳冒烟质量门禁

**已经机器化的部分**：`.githooks/pre-commit` D 组的 `scripts/shell-gate.mjs`
（判据由 `tests/shell-gate.test.ts` 锁 —— **锁的是哪两半要说清**：触发面 + 合并采纳过滤一直是真跑的；
而下面 1/2/3 这三条**判决出口**在 ISSUE #1356 之前只有「抠源码文本」的断言
（`toContain("whichCommand")` 加一段 `toMatch(/return 1;\s*\n…/)`），断言的是「源码长这样」而不是
「跑起来会退 1」，加一行注释就红、判决坏了却不红。现在判决抽成可注入的
`runGate({ staged, root, cargoRunner })`，由夹具（一次性检出 + 受控 mtime + 注入的 cargo 结果）
把四条出口与「判出问题 ⇒ 非零退出」这条传导**执行**出来，三条变异各自恰好红一条）。
它只在**暂存改动命中壳的四类输入**
（`tauri.conf.json` / `build.rs` / `src/` / `splash-assets/`）时才做事，然后问两件事：

1. 有 `src-tauri/src/*.rs` 改动 → 跑 `cargo test`。这是壳里 37 条 `#[test]`（端口推导、
   单实例哈希分桶、进程回收、项目根上溯…）**唯一的执行者** —— 此前全仓没有任何一步跑过它，
   `cargo test` 只出现在文档正文里，表现就是「Rust 侧改坏了，提交与本地钩子全绿」。
   实测本机冷 430s / 暖 40s（37 条本身只跑 0.07s，钱全在编译），所以只在真改了 Rust 时付
   这笔；只改 conf 或启动页时跳过 —— 否则每个前端提交都加一次 Rust 编译，人就会去
   `--no-verify`，判据反而归零。
2. 时效判据**复用** `dev-launcher.mjs` 的 `shellStaleWarning()`（§12.18，不写第二份
   比时间戳的逻辑），从「启动时打一条 WARN」升级成「本次提交改了壳而二进制没跟着重编 → 阻断」。
   ⚠️ 必须条件化：该判据比的是 mtime，而 `git pull` / `checkout` / `stash` 会批量推进源码
   mtime —— 无条件阻断会让「拉了别人改壳的分支」把本地一个没动过壳的提交拦下来
   （`launcher-core/splash-assets.mjs` 里「内容没变就不写盘」就是在护这个数）。只有当暂存区里
   就是本次的壳改动时，这个比较才指向提交者自己。
3. `cargo` 不在 PATH 时**不放行**，给出 rustup 指路 —— 改了 Rust 却编不了，等于没验证。

**仍然是人工的**（没有判据，别当成已闭环）：

```
✅ src-tauri 改动后启动冒烟通过（启动 / 协议 / 清理 / 日志出口，清单见 11.10.1）
✅ 业务仍由 Web 层测试覆盖（pnpm test / pnpm test:e2e 不受影响）
```

改动 `src-tauri/**`、`tauri.conf.json`、`splash-assets/**` 后未重编壳视为不合格
（对齐仓库根 [AGENTS.md 硬规则 5](../../AGENTS.md)）—— 这一句现在由上面第 2 项在提交时拦，
不再只靠人记。

### 11.11 可观测/日志契约（Logging Contract）

> 商业级要防「静默失败」：日志/错误/会话这些横切面一旦格式漂移或被误改，
> 排查与告警会集体失明。为此把关键契约固化成自动化测试，格式或边界被改坏时由门禁拦截
> （本地 `pnpm exec vitest run` 与 `.githooks/pre-commit`，见 11.7）。

**契约测试落点**（与 11.5 埋点纪律同源，扩展为「代码即契约」）：

| 契约                      | 测试文件                        | 断言要点                                                                                                       |
| ------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| pino 输出格式             | `src/server/lib/logger.test.ts` | 每条日志是单行合法 JSON，含 `level/time/msg` 标准字段，采集端可直接解析分流                                    |
| pino 脱敏                 | 同上                            | `password/token/secret/apiKey/req.headers.*` 落 `[Redacted]`，明文绝不出现在日志行                             |
| PII/prompt 原文不落盘     | 同上                            | `prompt/negativePrompt/email/phone` 默认脱敏，即便代码误塞进结构化字段也不泄露（把 11.5 纪律下沉到日志层兜底） |
| auth/会话边界             | `src/server/api/trpc.test.ts`   | better-auth 未登录 → `ctx.user=null`；会话命中已有/新邮箱 → 取库中或自动建号                                   |
| authedProcedure demo 兜底 | 同上                            | `ctx.user=null` 时注入 `demo@comfy.app`，本地单用户可用                                                        |
| rateLimitedProcedure 分支 | 同上                            | 同 key 超窗返回 `TOO_MANY_REQUESTS`；不同 key 独立计数                                                         |
| 错误上报不静默            | `src/server/lib/audit.test.ts`  | 敏感操作审计写库失败仍 `logger.error("audit_write_failed")`，杜绝把错误吞掉                                    |

**单点事实来源**：redact 路径集中定义在 `src/server/lib/logger.ts` 的
`REDACT_PATHS`，并经 `createPinoLogger({ destination })` 让契约测试与生产共用
同一份配置——格式/脱敏只在 logger.ts 一处定义、处处一致。

**纪律（不可测试的部分靠 review 兜底）**：日志契约能机械拦截「敏感字段落盘」，
但「代码主动往日志塞 prompt 原文」这类行为仍主要靠 11.5 的 review 纪律约束；
契约测试把「一旦误塞会原样落盘」这一事实钉死，提醒调用方保持克制。

### 11.12 本地一键质量门禁（非开发人员可用）

> 开发人员跑 `pnpm typecheck` / `pnpm exec eslint` / `pnpm test` 已经顺手；但对
> 非开发人员（验收、QA、桌面打包复查），一串命令门槛太高。仓库提供**可双击运行的
> 质量验证脚本**，把这些门禁做成黑盒：双击即跑、绿/红一眼可见。

#### 用法

在项目根目录双击（或命令行执行）：

```
双击 tools/start/verify-quality.ps1                       全部三项：typecheck → eslint → vitest
pwsh -File .\tools/start/verify-quality.ps1 -Mode typecheck   仅类型检查（tsc --noEmit）
pwsh -File .\tools/start/verify-quality.ps1 -Mode lint        仅 ESLint（零错误零警告）
pwsh -File .\tools/start/verify-quality.ps1 -Mode test        仅 vitest（自动排除"已知基线失败"文件）
```

**只想跑测试时用 `tools/start/run-tests.ps1`**——门禁是「三项一起跑」的黑盒，
日常改一处代码想只跑一个文件、想复现基线失败、想用 vitest 自己的开关时它都不合适：

```
双击 tools/start/run-tests.ps1                              全部测试（排除"已知基线失败"文件）
pwsh -File .\tools\start\run-tests.ps1 -Full                连"已知基线失败"文件一起跑（复现基线失败）
pwsh -File .\tools\start\run-tests.ps1 src\lib\media.test.ts   只跑指定文件
pwsh -File .\tools\start\run-tests.ps1 -- --reporter=verbose  透传 vitest 参数（`--` 前后一视同仁）
```

分工：`verify-quality.ps1` = 提交前的三道门禁；`run-tests.ps1` = 开发过程中的单测红绿循环。
后者**指定了测试文件就不再追加排除项**——传了具体文件还去 `--exclude`，只会变成
「我明明指定了它却不跑」。逻辑脚本 `scripts/run-tests.ps1` 与门禁共用同一份
`KNOWN_FAILED_FILES`（单点定义在 `scripts/quality-gate-shared.mjs`，不另抄一份 —— 从
`.ps1` 源码里正则解析那份清单曾让「改一次写法」变成「排除项静默返回空数组」，
红/绿从此不可归因，见 §9.5 与 `scripts/check-ps1-consistency.mjs`）。

前置条件：

- 首次双击前需完成一次性文件关联（Windows 默认双击 `.ps1` 是「用记事本打开」而非执行）：
  右键 `scripts\enable-ps1-double-click.ps1` →「使用 PowerShell 运行」。
  详见 launch-and-build.md §8。
- 已装 Node + pnpm，且已在根目录执行过 `pnpm install`（脚本会探测 `node_modules\.bin`，
  未装会给出明确提示而非一串看不懂的报错）。
- **依赖与 lockfile 脱节时会先被拦下**：拉取更新若新增/删改了依赖却没重装，老代码里
  import 的包（如 msw）在新 `node_modules` 里不存在，各项门禁会各自抛一串晦涩的
  `Failed to resolve import xxx`。`quality-gate.ps1` 开跑前会对比仓库根 `pnpm-lock.yaml`
  与 `node_modules\.pnpm\lock.yaml`（pnpm 保存的「最近一次成功安装」快照），不一致即判定
  依赖陈旧，直接给出中文提示并退出，指引执行 `pnpm install`（或重跑 `run-local.ps1`）。
  `scripts/prepare-local-run.ps1` 的依赖检查同样并入该判定，双击 `run-local.ps1` 遇到
  陈旧依赖会主动补装，不再误跳过。参考 `docs/guides/sync-after-pull.md`。
- 桌面壳（`src-tauri/**`）相关改动另走 Tauri 壳冒烟门禁的单独路径（见 11.10 壳小节
  与 launch-and-build.md §5），不并入这套 Web 层质量脚本。

#### 这套脚本守什么

| 门禁项    | 底层命令         | 说明                                                                    |
| --------- | ---------------- | ----------------------------------------------------------------------- |
| typecheck | `pnpm typecheck` | `tsc --noEmit` 全量                                                     |
| lint      | `pnpm run lint`  | 零错误零警告（对齐 11.7）；扫描范围是白名单，见 `eslint.config.js` 顶部 |
| test      | `pnpm test`      | 全量 vitest，**默认排除已知基线失败文件**                               |

**为何 vitest 默认排除"已知失败"**：历史上 task/generate 两个 router 集成测试在
master 基线可复现地失败（与当次改动无关）。若不加隔离，非开发人员一键验证会看到
红色却无法判断是不是自己引入的。脚本把这类文件登记在 `KNOWN_FAILED_FILES`，默认
跳过并单独打印，保证其余用例全绿=可信信号。

> **这张清单现在为空**（终态）。它 2026-09-27 一度有 5 项，全部是「别线的红挡住提交
> 钩子的**增量测试层**」（规范 13 §13.5.8：import 闭包会把别线的红拉到无关提交面前），
> 按机制登记、按机制打印，**每一条都写归属与「别处更强的执行者」**。之后被清空 ——
> 留着比红更糟：**红会挡住提交，静默跳过什么都不会说**，而粒度是文件，一条过期登记
> 会把整个文件的断言从增量面摘掉。
>
> 第一个被删的是 `tests/theme-token-single-source.test.ts`，它留下的教训单独写在这：
> 登记它时给的理由是「裸自定义属性白名单少一条登记」，而**那条理由当时就不成立** ——
> 真正的红因是全库扫描型用例的耗时（8.25s，其中扫描 6.7s）顶到了那时默认的 5s
> `testTimeout`，而它单独跑一直全绿。字阶档 `--text-` 由该线补进白名单、超时预算由
> §11.13 收掉之后就再没红过。**登记理由必须是复算过的事实，不能是「看起来像的原因」** ——
> 理由写错的例外项比没有例外项更糟：修好了也没人来删，同时骗过两个人。
>
> ⚠️ **清空时把「在谁的检出上跑」当成普适事实，会留下反向的坑**（实测，别线）：剩下 4 项
> 里壳与启动器那 3 个文件按 §13.6.2 串行复算确为绿；而
> `tests/turbopack-tracing-excludes.test.ts` **在带 `.next/standalone` 的检出上当时仍然真红**
> （1 败 19 过）—— 它判绿是因为那次复跑**没有本地产物**，用例按既有设计自行跳过。
> **同一条判据换台机器结论相反**，这种「依赖磁盘状态」的产物侧用例（同类的还有
> `check-standalone-contents.cjs`）复算时必须先说清 `pnpm build` 跑过没有；
> 判它绿之前，先确认它有没有真的跑。
>
> **这一类现在有登记表**：`tests/conditional-skip-registry.test.ts`（登记在提交前的固定守护
> 清单里，每次提交都跑）要求每一处条件性 skip 都写明**档位**（`env` 缺工具 / `platform`
> 平台分叉 / `artifact` 缺构建产物 / `manual` 人工挂起）**+ 理由 + 站点数**，产物档那几条
> 必须点名「要先 `pnpm build`」。偷偷多一处没登记的 skip、或登记了却把站点删掉，都在这里
> 变红 —— 于是「全绿 + `N skipped`」里的每一处都能查到它为什么暗、在谁的机器上暗，
> 报数不再依赖人记得住这一节。
>
> **两条附在该项上的说法都要撤回，它们是同一个错的两个面**（2026-09-28 #1220 结案时实测）：
> ① 当时把红归因成「产物里带着 `node_modules/pino-*/docs/*.md` 那批漏项、缺一条
> `./node_modules/**/docs/**` 的 excludes」—— 补上那条 excludes **实测一个文件都不减**
> （excludes 对「全项目 tracing」带进来的整目录条目不做减法，机制见
> [launch-and-build §7.2 第三件事](launch-and-build.md)），减法只在产物层显式删除里发生；
> ② 那个「484 份依赖包文档」本身是**穿符号链接数出来的假账** —— standalone 的
> `node_modules/<pkg>` 是指向本仓库 pnpm store 的链接，产物里的真文件是 0，数到的是开发机
> 的内容。**归因写成「看起来像的原因」，修法就会跟着错一轮。**
>
> 再要登记前先做两件事：① 按 §13.6.2 在干净 master 上复算，确证是别线的红、不是本次
> 改动引入；② 想清楚那条门禁在别处有没有更强的执行者。清单与这段口径的权威副本是
> `scripts/quality-gate-shared.mjs` 的文件头注释。
>
> **本题材的第三次登记留下的教训与前两次不同档**（ISSUE #1282）：`tests/theme-dark-token-cascade.test.ts`
> 的登记词把根因写成了「产物里没有 `.bg-card` 规则」，而实测那条规则一直在，
> 真因是**判据自己的白名单漏了第三种拼法**（`var(--color-card)` 不在 `var(--(card|color-surface))`
> 里）。也就是说：**这条断言在白名单被写下的那天起就不是「性质」而是「拼法的枚举」**，
> 而枚举的漏项与业务回归长得一模一样，没人能从报错里读出「这是判据自己的问题」。
> 它再次印证上面那句「登记理由必须是复算过的事实」—— 而这一轮把它变成了机器判据
> （见本节下面的「第 3、4 条现在不再是靠人记得」），不再依赖下一个人记得较真。

> **登记进 `KNOWN_FAILED_FILES` 的代价要一并认**：`verify-quality.ps1` 的「绿」
> 与全量 `pnpm run test` 不是同一口径 —— 登记项全量模式会跑红（#582 已确认
> 这类历史失败，如 `use-workflow-save.test.ts` 的 `mutate` 断言，另立 Issue 修）。
> 因此「先登记、下轮再修」会让两边长期不一致，登记时**同时写明谁来修**。

#### 新增验证怎么补充（持续维护口径）

1. **新增测试**：只需把测试文件放进 vitest 默认 include（`src/**/*.test.{ts,tsx}`），
   `test` 模式自动收录，**无需改脚本**。
2. **新增一条门禁项**（如 prettier、build、新契约测试命令）：编辑
   `scripts/quality-gate.ps1` 头部的 `$Blocks` 清单数组，按既有条目格式追加
   `@{ Name; Cmd; Args }` 即可；入口 `tools/start/verify-quality.ps1` 无需改动（仅当新增 Mode
   时同步补 `ValidateSet`）。
3. **既有失败被修复**：把该文件从 `KNOWN_FAILED_FILES` 删除，让它回到门禁里被强制
   拦截，避免悄悄退化。
4. 约定：`KNOWN_FAILED_FILES` 只放"确证与本次改动无关的历史基线失败"，任何新失败
   都必须让脚本红起来；不许随手把失败塞进例外列表。

**第 3、4 条现在不再是「靠人记得」**（ISSUE #1282）：`scripts/check-known-failed-stale.mjs`
在 pre-commit 的 D 组里判两头 ——

| 判什么                                 | 为什么                                                                                                                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登记项指向的路径**存在且被 git 跟踪**  | 文件被删/改名/搬目录之后，那条排除项就成了一个**永远匹配不到任何东西**的字符串：静默失效、表面上一切正常。同族现场是从 `.ps1` 源码正则解析这份清单（改一次写法就返回空数组） |
| 登记项**真的还红着**（真跑那几个文件） | 这是「过期」的本体。一条登记之所以有资格存在，仅因为它复现得出别线的红；一旦变绿（别线修好了它），「留着」就只剩「把整个文件从增量面摘掉」这一个效果                         |

**它刻意不判「登记词里写的根因对不对」**：那是一句自然语言，无法观测。上一条现场里
登记词就写错了（写成「产物里没有 `.bg-card` 规则」，实测规则一直在、是判据自己的
白名单漏了第三种拼法），而**写错理由的例外项比没有例外项更糟** —— 修好了也没人来删，
同时骗过两个人。机器判不了散文，但能判**结论**（它现在还红吗）；结论错了散文必然跟着错。

代价口径（§13.5.8）：清单为空是**常态**，此时本步零耗时零输出直接退出；非空时才真跑，
而清单按定义只有个位数条目 —— 跑的是那几份文件，不是全量。

⚠️ **本判据本体第一版自己就踩了它要拦的那个坑**（留在这，因为它是最贵的一条教训）：
第一版用 `--reporter=basic` 起 vitest，而这个名字在 vitest 5 已被删 ⇒ vitest 以
`status 1` 退出、**一行用例都没跑**，而判决把那个 1 读成了「登记项还红着」，给出一个
假绿的 `[ok]`。根因是**退出码同时承载两种截然不同的事实**（「跑完且红」与「压根没跑」），
只读它必然把后者读成前者；而 `spawnSync` 的 `error` 守卫抓不到它 —— 子进程**正常退出**了，
只是退非零。⇒ 「跑过」这个读数必须来自 vitest 自己写下的结构化产物（JSON 结果文件 +
里面有用例数），不能来自退出码。两条反假绿用例（起不来 / 零用例）与 `--self-test`
都钉着这一条。

##### 11.12.1 「空表是终态」留下的那一档，现在有了执行者

上一节那句「清单为空是常态、零耗时退出」是**代价的正确取舍**，但它同时留下一个空档：
**判据的「真跑那一档」在干净仓库上从来没有被执行过**（空表 ⇒ 直接 `return 0`），
而它唯一的自证入口 `--self-test` **一个执行者都没有**（全仓 grep 不到调用点）。
这与 §13.5.4 那句「按需跑是没有执行者的话」是同一族：**机制在场、没人敲它。**

两个洞都是实测出来的，而且**各自的盲区互为补集** —— 所以两个都得有执行者：

| 变异（真跑过） | `tests/known-failed-stale.test.ts` | `--self-test` |
| -------------- | ----------------------------------- | ------------- |
| `--reporter=json` 改成 `jsonx`（模拟 vitest 升级改名） | ✅ **11 条全绿**（用例喂夹具，看不到真命令） | ✅ 当场红 |
| `judgeStillFailing` 改成恒 `return { exitCode: 0 }` | ✅ 红（喂夹具，抓得到） | ❌ **假绿**（旧版只有红侧） |

第二条暴露的是自证自己的缺陷：它原本只验「红的那条判成红」——而**放行是判据的默认
动作**，判据恒放行时红侧当然也放行。能证明它**还会拦**的，只有一条它必须拦下来的输入。
所以自证现在同一次真跑里放**两只探针**：红侧（必然红 ⇒ 判据必须说「还红着」）+
绿侧（必然绿 ⇒ 判据必须说「已经过期」，**对照组**），代价不翻倍。

执行者是新门禁 `scripts/known-failed-selftest-gate.mjs`（pre-commit D 组），与
`visual-gate.mjs` / `shell-gate.mjs` **同形**：触发面窄（只碰了这套机制本身才做事 ——
登记表 / 判据本体 / 钩子接线），普通提交零输出零耗时；命中才付一次真跑（实测 ~0.9s）。
它判的不是「你有没有手跑自证」（一句无法观测的话），而是**这次改动有没有带着一个
还活着的「真跑那一档」进历史**。

顺带收紧了判决的口径：清单非空时它是**多条**，而原先读的是**整场退出码**（「有没有
任意一条红」的粗糙代理）—— 一条红会让同批里已经全绿的条目也被判成「还红着」，于是
**「该删的过期登记」正好判不出来**，与本判据的立案动机正面冲突。现在逐份读
`testResults[].status`（vitest 写的是**绝对路径**，登记表写的是相对路径，判决里归一化比对）。

### 11.13 用例超时预算：并行变红不等于回归

**判据一句话**：一条用例在全量并行下报 `Test timed out in Nms` 时，先用
`--no-file-parallelism` 隔离重跑再定性——**串行也红才是真红**，串行绿的是预算不够
或资源争用。把「红」直接当回归去改业务逻辑，是本仓库最常见的一类假修。

**为什么默认值不够**：vitest 的默认预算（用例 5s / 钩子 10s）是按「一个文件几十
毫秒」的假设计量的，而本仓库的门禁用例普遍要 `execFileSync` 真起 Node / git /
prettier 子进程，或对全 `src/**` 做一遍可达性扫描。隔离实测的下限就压在 5s 上下：

| 用例（隔离跑的单条最慢值）           | 实测                                                    | 默认预算下           |
| ------------------------------------ | ------------------------------------------------------- | -------------------- |
| 客户端打包可达性（全 src DFS）       | 5469ms                                                  | **超时**             |
| 库表就绪判据                         | 4770ms                                                  | 贴边（几十 ms 翻车） |
| 死导出清单 `--verify` 自证           | 3729ms                                                  | 通过                 |
| 主题令牌（`beforeAll` 现编一份 CSS） | 收口前 7.2s/文件 ⇒ 现在 0.13s/文件（ISSUE #1336，见下） | 原本钩子 10s 贴边    |

`vitest.config.ts` 里的 `testTimeout: 30_000` / `hookTimeout: 45_000` 就是按
「最慢实测值 ×3.6」给的。**这是天花板不是目标**：用例慢到接近它时该优化用例本身
（收窄扫描面、复用子进程），继续抬这个数等于把「真挂死」的检出时间一起放大。
`it()` / `describe()` 上的显式预算优先级更高，不受全局值影响。

**上面那行「主题令牌」是本节口径的一次兑现（ISSUE #1336）**：两份 theme 判据的
`beforeAll` 各自把 `globals.css` 全量编译一遍（本机裸跑实测 21109ms、vitest 里 7.2s），
满载时排到 `hookTimeout` 之外 ⇒ **整份 suite 红、里面 35 + 18 条用例一条没跑却被记成
skipped**，而串行隔离重跑全绿 —— 典型的争用假红。修法**不是**再抬一次超时（那行注释
自己就反对），而是把编译的输入源固定住：`tests/helpers/theme-tokens.ts` 改成
`source(none)` + 显式 `@source inline(...)` 钉住判据要读的那几条 utility，并把项目自己的
`@theme` 换成 `@theme static`（v4 默认按「全仓哪里用到过」tree-shake 主题变量，判据不该
依赖这件事 —— 只关扫描的第一版把 `--color-primary-strong` 的浅色档摇没了，`sidebar-state-contrast`
当场红一条）。改后单份 suite 实测 0.13–0.2s，产物里**同名变量取值一条没变**（逐条比对过），
`hookTimeout` 保持 45s 没动。反向判据见 `tests/theme-tokens-compile-source.test.ts`。

**预算解决不了的那一类，杠杆是并发而不是继续加预算**：格式化门禁、启动器门禁
那些**已经自带** 30s / 60s 的用例，在默认并发（16 逻辑核上约 15 个 worker）下照样
能饿红 —— 因为每条用例还要再起一份 Node / git / prettier 子进程，超订的部分从
「等 CPU」变成「等子进程」。同一台机器、同一份代码、全量 437 个文件的三档实测：

| 跑法                            | 红文件 | 红用例 | 墙钟 | 说明                         |
| ------------------------------- | ------ | ------ | ---- | ---------------------------- |
| 默认并发 + 默认预算（5s / 10s） | 20     | 42     | 599s | 起点                         |
| 默认并发 + 20s / 30s            | 8      | 18     | 461s | 超时类大幅减少但未归零       |
| `maxWorkers: 8` + 20s / 30s     | 4      | 14     | 659s | **超时类红归零**，剩下全是真 |

`vitest.config.ts` 取第三档。**但「买回红即可归因」这句后来被自己否掉了**——
套件涨到 559 份之后在同一台机器上复跑（master `9392a88f`，ISSUE #1393 的记录）：

| 跑法                                  | 结果                                                                                                                                                                                                                       | 墙钟            |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `pnpm test`（`maxWorkers: 8`）        | 1 份红，且那 1 条是 `Error: Test timed out in 30000ms`（`tests/ui-primitives-coverage.test.ts`），隔离重跑 65/65 绿；另有 1 条未处理错误 `[vitest-pool]: Failed to start forks worker …LogPanel.test.tsx` 把退出码打成非零 | 707s            |
| `pnpm exec vitest run --maxWorkers=4` | **560 files / 6887 passed + 23 skipped，全绿**                                                                                                                                                                             | 1949s（32m35s） |

也就是：**真断言红已经是 0**（`KNOWN_FAILED_FILES` 也就是空数组，那张登记表的规则见 §11.12），但 8 档并没有把「争用形态的红」
买干净 —— 池子起不动 worker 与单条超时都会以「全绿却退非零」的形态回来。
⇒ 第三档买到的只是「红得少」；**判红仍然要先 `--no-file-parallelism` 隔离重跑定性**，
这一句是硬动作，不是可省的一步。
当年那 14 条**与并发无关**的判断仍然算数（它们是启动器 / 壳 / 产物三条线的真实断言失败），
但「还剩产物那 1 条、只在带 `.next/standalone` 的检出上才现形」这句今天不再成立：
本轮就是在**带 standalone** 的检出上跑的，产物线全绿（`tests/standalone-runtime-completeness.test.ts` 9 条）。

**看到「60s 都超时」时不要改成 120s**：那是争用信号，正确动作是按上表核对并发、
或用 `--no-file-parallelism` 先定性。把预算一抬再抬，等于把「真挂死」的检出时间
一起放大，而且下一次没人知道这个数是怎么来的 —— 所以这两个值的注释里写了实测出处。

**还有第三种红：既不是回归、也不是预算不够，而是「断言某个竞态真的发生」的用例不再发生那个竞态。**
实测一次（全量 505 文件并行）：`tests/sqlite-pragma-sites.test.ts > 裸循环在 8 进程同时打新库时会抛
（量具没坏）` 红 1 条，`--no-file-parallelism` 隔离重跑 9/9 绿（该条 3624ms）。它长得像回归（`AssertionError`，不是 `timed out`），但机制与上面那条判据同源 ——
**它把「抢得到锁」当成前提，
而前提的成立依赖调度**——满载时 8 个子进程被排开、彼此错开打开库，锁根本没机会撞。
抬预算对它一点用没有（问题不是慢，是没撞上）。要收就得改构造：给子进程一个**同步屏障**
（都就位后再一起打开库），或把断言从「一定会抛」换成「只要抛过就证明量具有效 + 明确允许
不抛时按跳过记账」。别把它降级成「重试三次取绿」——那等于把量具本身变成会静默失效的清单。
**这条已经按 §13.6.2 复算过基线，结论比「满载抖动」更难看**（下一刀做的，不是写下这条时的猜测）：
同一份量具代码（`git diff` 对 `tests/sqlite-pragma-sites.test.ts` 及其输入的改动为空），
**在主检出上隔离跑 2/2 绿，在 `git worktree add` 出来的干净 master 基线上隔离跑 2/2 红** ——
它不只在满载下失效，换个目录 / 调度就失效。于是判红口径按顺序走三步：
① **先复算基线，而且不必先跑全量** —— worktree 里单跑那一份文件就够；
② 基线也红 = **别线的红**，不为它放宽任何判据，也不由本刀顺手改它的构造（归 #1306 那条线）；
③ 基线绿、本刀红，才回头看自己加了什么负载。
⚠️ 别把「串行绿 = 预算 / 并发」这句现成话直接套到这类量具上 —— 那句管的是**超时**，
而它报的是 `AssertionError`，同一份代码串行也能两边不同结果，说明失效的是前提而不是预算。

**但预算还有第三个维度：带不带 coverage。** 上表两档都是裸 `vitest run`；一旦加
`--coverage`，v8 的逐分支插桩会把重头用例**成倍**拉长，而这一份变慢是**确定性的**，
不是排队等出来的 —— 所以它属于「按实测给余量」那一类，不属于上面那句「争用信号」。
实测同一台机器同一份 `LogPanel.test.tsx`（33 例）：

| 跑法                            | 整文件用例耗时 | 那两条重头用例        |
| ------------------------------- | -------------- | --------------------- |
| 单跑，不带 coverage             | 74.6s          | 均在 45s 预算内       |
| 单跑，带 coverage               | 105.9s         | 25.0s / **34.4s**     |
| 全量并行 + coverage（8 worker） | 176.0s         | 34.4s 那条越过 45s 红 |

该文件的 `vi.setConfig({ testTimeout })` 因此从 45s 抬到 **120s**（= 单跑带 coverage
的最差实测 ×3.5，与全局那个「最慢实测 ×3.6」同一条公式）。**这不改变真正的解法**：
那两条用例要真塞过 `LOG_PAGE_SIZE`（2000+50 条）才能证明「不止 2000 条封顶」，
成本在渲染侧 —— 把 2000 行的渲染成本降下去（虚拟化 / 收窄种子）才是终点，抬预算只是
别让它把「覆盖率档」变成一条永远的红。抬之前先按本节第一句定性：**串行不带 coverage
也红才是真红**。

### 11.13.1 判据自己也不许依赖「现生成、不入库」的输入

「精确化判据」还有一面：**收窄编译面 / 缩小扫描范围时，别顺手把一条「只有跑过某条
命令才存在」的文件当判据的地基**。判据依赖生成物时的表现很坏 —— 在作者机器上绿
（他跑过那条命令），在干净检出上恒红，而红的是**从那份基线分出去的每一次提交**。

一个实例（台账 E15）：

| 实例                            | 判据依赖了什么                           | 干净检出上的形态                  | 修法                                                                                   |
| ------------------------------- | ---------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------- |
| Storybook 生成件（ISSUE #1409） | 被引方 `import "./generated/app-origin"` | `tsc` 报 **TS2307**（模块不存在） | 生成件从 `.ts` 改成纯数据 JSON，类型与缺省值由**入库**的 `app-origin-defaults.ts` 承担 |

修法的取向是：**不是去补那份生成物（补不完，也不该让判据依赖它），而是让消费方
不再需要它**。第二条经验也在这里：判据收窄扫描面之后必须补一条**在场证明**
（`tsc --listFilesOnly` 打文件清单、点名被引方与那份现造的输入），否则
「include 写错 / 被 `exclude` 挡掉」都会让它**静默空转** —— 换形比原形更需要这条。

同一形态另有第二个实例（ISSUE #1465，同一处的环境声明 `next-env.d.ts`），但它的生成物
属 **Next 生命周期**而不是 Storybook 的产物，所以**它的症状、根因、`exclude` 那个坑与
三条反证的读数一起收在 `docs/standards/launch-and-build.md` §5 的对应行**，本表不列。
（本节留的这条原理仍然适用于它 —— 「别拿自己保证不了的生成物当地基」不挑生成物是谁
写的，挑的是判据依赖了谁。）

### 11.14 等异步落定：`expect.poll` 取代手搓轮询与裸 `sleep`

> 口径：**「等一个条件变成真」一律写 `expect.poll`**；用 `await new Promise(r => setTimeout(r, N))`
> 来等状态落定的写法属于反模式，新增时由 review 拦下（存量按本节逐步收口）。

三种写法的差别有三层，**不要把第二层说成第三层**（下表是按 vitest 5.0.3 实测的，
实测手法见本节末）：

| 写法                                  | 等不到时的输出                                      | 预算从哪来                                                     | 条件成立时 |
| ------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------- | ---------- |
| `await sleep(300)`                    | 无 —— 它是**赌**，赌赢绿赌输红                      | 写死的 300ms                                                   | 照样等满   |
| `vi.waitFor(() => expect(x).toBe(y))` | 最后一次断言的实际值 + diff（**不是**「只报超时」） | `vi.waitFor` 自己的 1000ms 默认，**不吃** `expect.poll` 的配置 | 立即返回   |
| `expect.poll(() => x).toBe(y)`        | 同上 + `message` 标签                               | `vitest.config.ts` 的 `expect.poll` 一处                       | 立即返回   |

**第一层（真正的反模式）**是 `sleep`：它不判条件、只在赌时间 —— 条件早已成立时它照样
等满 300ms，条件永远不成立时也不说差多少。本仓库这批轮询等的是**真的进程动作**
（`spawn` 落地、`sleep` 挂成组长、孙进程被 `taskkill` 收走），赌时间在这里既慢又不稳。

**第二层（本仓库选 `expect.poll` 的理由）是预算的落点，不是报错。** `vi.waitFor` 与
`expect.poll` 都会把**最后一次尝试的实际值**打出来（`toEqual` 时给逐项 diff）——
早期版本的本节曾写成「`vi.waitFor` 拿不到最后一次的实际值」，那条是**错的**（实测
两者都给，见本节末）。真正的差别在于：`expect.poll` 吃 `vitest.config.ts` 里那一处
默认预算，而 `vi.waitFor` **只认自己的 1000ms**（它没有配置层的默认值）。本仓库一大批
轮询等的是真进程动作、实测单次已越过 1s，所以「默认值写在配置里一处」这件事本身就是
选它的理由。

**第三层**是 `message` 标签（`{ message: "残留的孤儿 PID" }`）与回调拿得到的
`AbortSignal`：报错里多一句人说人话的标题。

> **什么时候仍然该用 `vi.waitFor`**：需要在重试里**做事**、而不是只读一个值的时候 ——
> 多步准备、要在回调里 `return` 出结果、或依赖它「每轮自动 `advanceTimersByTime`」这条
> 假定时器集成的（`vi.waitFor` 在 `vi.useFakeTimers` 下自动推进，`expect.poll` 不会）。
> 判据是「我等的是一件事，还是一连串有副作用的动作」。

写法与边界：

```ts
// ✅ 等条件成立（默认预算在 vitest.config.ts 的 expect.poll，见下）
await expect.poll(() => runner.busy()?.runId).toBe("slow");

// ✅ 等一个集合收敛：失败时打出「多的 / 少的是哪几条」，比两条 toContain 有用
await expect
  .poll(() => all.filter((p) => isAlive(p)), { message: "残留的孤儿 PID" })
  .toEqual([]);

// ✅ 一次性逃逸口仍可用：这个条件不靠时间收敛（例如等一个「不会发生的事」）
await expect.poll(() => isAlive(pid), { timeout: 4000 }).toBe(false);

// ❌ 赌时间：等不到也照样走到下一句，红的时候拿不到任何现场
await new Promise((r) => setTimeout(r, 300));
expect(runner.busy()?.runId).toBe("slow");
```

- **默认预算只在 `vitest.config.ts` 写一次**（`expect: { poll: { timeout: 4000, interval: 50 } }`）。
  vitest 出厂的 1000ms / 50ms 是给「内存里的状态翻转」定的，而本仓库一大批轮询等的是
  真进程动作，实测单次就已越过 1s —— 所以默认值按实测抬到 4s，调用点只在确实需要
  更宽 / 更窄时再写 `{ timeout }`。
- **它是余量不是兜底**：一条 `expect.poll` 走到超时说明被等的事根本没发生，
  去查它为什么没发生；**不许把它当成「让慢用例过关」的旋钮**（同 §11.13 那条口径）。
- **纯延时仍然合法**的地方只有一类：被测对象**确实依赖挂钟**、而假定时器又会把被测
  逻辑一起冻住（例如 `vi.useFakeTimers` 下的 `advanceTimersByTimeAsync` 已经是更优解，
  但对真子进程无解）。这类位置的注释里要写清「为什么这里必须是真时间」。
- **收尾资源挂 `onTestFinished`**：起真进程的用例里，「断言失败提前抛出」不该在机器上
  留下一个跑一小时的 `sleep 300`。收尾要挂在 `onTestFinished` 上而不是写在用例末尾 ——
  末尾那句在红的时候根本不执行。

**档位纪律**：`expect.poll` 的引入不是给用例「续命」。同一批收口里，`kill-process-tree`
那组把 400~700ms 的裸 sleep 换成了条件轮询，文件耗时从 ~3.5s 降到 0.5s ——
**条件轮询通常比赌时间更快**，这是它的第二个好处，也是「换成 `expect.poll` 之后还要
不要留原来的超时数」的判断依据：条件成立即返回，不成立才走到上限。

**上面那张表的实测手法**（口径改动必须先复现，别照抄结论）：拿一个必然不成立的
条件各跑一次，把两次报错逐字比 ——

```ts
// A：vi.waitFor
await vi.waitFor(() => expect({ pids: [11, 22] }).toEqual({ pids: [] }), {
  timeout: 200,
});
// B：expect.poll
await expect
  .poll(() => ({ pids: [11, 22] }), { timeout: 200, message: "残留的孤儿 PID" })
  .toEqual({ pids: [] });
```

vitest 5.0.3 实测输出：

```text
A: AssertionError: expected { pids: [ 11, 22 ] } to deeply equal { pids: [] }
B: AssertionError: 残留的孤儿 PID: expected { pids: [ 11, 22 ] } to deeply equal { pids: [] }
   Caused by: Error: Matcher did not succeed in time.
```

即**两者的实际值 / diff 完全同档，差别只在 `message` 与预算来源**。改写本节这类
「谁报错更好」的口径时，先把这段跑一遍再动笔 —— 凭印象写出来的对照表会像上面那条
错误结论一样，被后来的人当依据去改一批用例。

### 11.15 参数化用例：`test.for` 取代 `it.each`

> 口径：新增参数化用例一律写 **`test.for`**；`it.each` 属 vitest 3 时代的写法，存量
> 按本节逐步收口（本仓库已全部转换完，63 处，见 changelog）。

两者最大的差别是**「一行数据」的表示方式**：

| 写法                                           | 每个用例拿到什么         | 一行数据长什么样                                       |
| ---------------------------------------------- | ------------------------ | ------------------------------------------------------ |
| `it.each([[a, b]])("…%s…%s", (a, b) => {})`    | 元素**摊开**成多个参数   | 元组 —— 要么是数组（易与「多个参数」混），要么是模板串 |
| `test.for([[a, b]])("…%s…%s", ([a, b]) => {})` | 元素**原样**作为一个参数 | 任意值；是元组时由回调自己解构                         |

`test.for` 那条「原样进、原样出」是本节的核心理由：**没有隐式摊开**。`it.each` 的
`(a, b) => {}` 与 `([[a, b]]) => {}` 在「一行两列」上看着等价，但一旦数据形状变化
（一列、对象、异步工厂），摊开规则就会让人与类型检查器一起算错 —— 本仓库转换时
`tsc` 恰好逐条指出了每一处形状不匹配，这正说明摊开规则是隐式的。

写法与边界：

```ts
// ✅ 一列标量：回调参数就是那个标量
it.for(["debug", "info", "warn", "error"] as const)("%s 合法", (level) => {});

// ✅ 多列：一行一个元组，回调解构 —— 数据形状在类型上看得见
it.for([
  ["development", true, false, false],
  ["test", false, false, true],
] as const)(
  "%s → isDev/isProd/isTest 互斥",
  ([env, isDev, isProd, isTest]) => {},
);

// ✅ 对象行（`it.each` 做不到）：一行是一个有字段名的东西
it.for([
  { name: "a", ok: true },
  { name: "b", ok: false },
])("$name 的判定", (row) => {});

// ✅ 第二参永远是 vitest 的 TestContext（signal / task / skip / annotate / onTestFailed）
it.for(CASES)("%s", (row, ctx) => {});

// ❌ 旧写法：元素被隐式摊开，形状一改就与类型对不上
it.each([["a", true]])("%s", (name, ok) => {});
```

两条容易踩的：

- **`as const` 不是可选的**。`it.for([["a", 1]])` 的元素类型是 `(string | number)[]`，
  解构出来的每一项都带 `undefined`，于是 `expect(x).toBe(y)` 这类调用会报类型错。
  加了 `as const` 才是只读元组、每列类型确定。这条是转换时 `tsc` 逼出来的，
  不是风格偏好。
- **`test.for` 的模板串形式语义不同**：`` it.for`${() => a} 与 ${() => b}` `` 把每个
  插值**当作独立参数**传给回调（`(a, b) => {}`），而 `it.for([...])` 形式把每个元素
  **原样**传一个参数。两种形式混用时按这一条判，别按 `it.each` 的记忆推。

**为什么不是「必须换」**：`it.each` 没有被废弃，两者都受支持。这条口径管的是
**新增**与**顺手收口** —— 与 §11.14 的 `expect.poll` 同属「升级后把新写法当默认」
这一档，不动那些换了反而更难读的存量。

### 11.16 `test.extend` fixture：把「依赖什么」变成用例的显式入参

> 口径：**一个「这条用例依赖什么环境」的判据，写成 fixture 而不是包装函数 + 裸全局读**。
> 本仓库当前唯一样例是 `tests/helpers/platform-fixtures.ts`（平台与宿主形态）。

三件此前一直靠手工活表达的东西，fixture 把它们收成一处：

| 之前的写法                                                               | 它的问题                                                                                                  |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 整组 `describe.runIf(!isWindowsPlatform())`                              | 一刀切：组里那些判**决策**的用例（不需要真起进程）也跟着不跑，在 Windows 上整组零执行者（台账 E7 的形状） |
| 各处手写 `Object.defineProperty(process, "platform", …)` + `try/finally` | 每个文件各抄一份；且它是**过程式**的 —— 新写一条用例忘了包就静默不切平台，收尾只靠 `finally` 写对         |
| 用例体里裸读 `process.platform === "win32"` 决定跳不跳                   | 「这条为什么没跑」要去用例体里找；同一件事在 `conditional-skip-registry` 里会以几种写法各占一行           |

fixture 之后：**平台与宿主形态是用例签名里的入参**，收尾由 vitest 保证。

写法（`tests/helpers/platform-fixtures.ts` 是参考实现）：

```ts
// 派生 test 对象，不另起一套 API
export const test = base.extend<Fixtures>({
  asPlatform: async ({}, use) => {
    const original = Object.getOwnPropertyDescriptor(process, "platform");
    await use((value) =>
      Object.defineProperty(process, "platform", {
        value,
        configurable: true,
        writable: true,
      }),
    );
    // 收尾在 use 之后 —— 用例 throw 也照样跑到
    if (original) Object.defineProperty(process, "platform", original);
  },
});

// 消费点：「依赖什么」写在用例签名里
platformTest("同步入口在 Windows 上是 /PID …", ({ asPlatform }) => {
  asPlatform("win32");
  // …
});
```

四条纪律：

- **能注入的一律注入，切平台是最后手段**。`process.platform` 是全局状态，只在被测
  代码自己读它、又没给注入参数时才切（`killProcessTreeViaImage` / `killProcessTreeSync`
  正是这种；`killProcessTreeWith` 有 `{ windows: true }` 参数，那条路径就不用切）。
- **不可满足的依赖要显式 skip，不许「为它本来就不可能红而绿」**（同 §11.7 那条
  「绿有两种含义」）。派生 test 上的 `skipIf` 守卫取 fixture 模块导出的**共享常量**
  （本仓库是 `ON_WINDOWS`），不要各处散写裸表达式 —— 下面第五条会说明为什么。
- **fixture 自己的收尾逻辑要有执行者**。本仓库的写法是 `test.fails`：故意抛一条，
  然后下一条断言状态已恢复。这样「恢复逻辑被删掉」会当场红，而不是靠某条永久红被人看见。
- **fixture 层不许静默漏掉站点**。`conditional-skip-registry` 原来只认
  `it|test|describe` 三个标识符，**派生 test 对象（`platformTest`）上的 skip 站点
  整片漏出扫描面** —— 表现不是「这里红」而是「一条静默不跑的用例没人登记」。
  判据放宽成 `\w+` 之后，那条「三种站点形状都要被扫出来」的用例里补了第四条
  执行者（点名 `ON_WINDOWS` × 2）。**改扫描口径就要同批补它的执行者**，否则
  放宽与收窄都无人判。

**边界**：fixture 只服务「同一种环境依赖在多条用例间重复」的场景。一条用例独有的
桩不需要 fixture（就地写更好读）；纯函数 + 显式 `probe` 入参的写法（如
`executable-resolve` 的 `resolveCommandInvocation`）**优于** fixture —— 那是把依赖
做成了真参数，比 fixture 更早、更强。

### 11.17 用例的环境档：目录级默认 + 「环境早退」判据

> 口径两句话：
> ① **默认档按目录声明**（`vitest.config.ts` 的 `projects`），文件头
> `// @vitest-environment jsdom` 继续保留、用于**逐文件覆盖**；
> ② **不许把用例的结论挂在环境的全局默认值上** —— 要覆盖 SSR / 无 `window` 分支，
> 就用 `vi.stubGlobal("window", undefined)` **把条件造出来**；
> `if (typeof window !== "undefined") return;` 这类**环境早退**由
> `scripts/check-test-environment.cjs` 拦下（进 pre-commit D 组）。

#### 11.17.1 这一档的现状是「按目录声明的默认 + 37 处承重文件头」

历史形状是 `vitest.config.ts` 里一句全局 `environment: "node"`，要 DOM 的用例各自
在文件头写一行 `@vitest-environment jsdom`（曾有 **183 份**，现剩 **37 份** —— 账见
§11.17.1.1）。两件都是真的，
但**第二件从来没人判过** —— 少写一行不报错，只是让用例留在 node 档下跑。
表现分两种，坏的那种是静默的：

| 少写文件头的后果                                          | 表现                                            |
| --------------------------------------------------------- | ----------------------------------------------- |
| 用例真碰 `document` / `window`                            | `ReferenceError` 当场红 —— **响的**，会被人修掉 |
| 用例自己写着 `if (typeof window !== "undefined") return;` | 绿，但**一条断言都没跑** —— **静默的**          |

第二条就是本仓库反复踩的那一族（§11.13.1「判据在场 ≠ 判据在跑」、
§11.7「写着 100、报告里查无此文件」）：**绿有两种含义，而这里绿的是坏的那一种**。
实测形态（`use-css-color-token.test.ts`，本次收口前）：

```ts
it("服务端（无 window）返回 null，由调用方兜底", () => {
  /* vitest 的默认环境是 node，没有 document —— 正好覆盖 SSR 分支。 */
  if (typeof window !== "undefined") return; // ← 换个默认档，这里静默通过
  expect(readCssColorToken("--color-note-tint-base")).toBeNull();
});
```

它把「本用例的结论」挂在了**运行环境的一个全局默认值**上。把默认档换成 jsdom
（或本文件哪天被挪进另一个 project）之后，它照样报绿 —— 而 `npm test` 里那一条
`N passed` 里有一份是空的。这条用例**自己的注释**还把那个默认值写成了前提，
于是更没人会去查它。

#### 11.17.1.1 183 处文件头里 **147 处是纯冗余**，只剩 **37 处承重**

分档落地之后，「这 183 处注释怎么办」被当成过一道「动不动」的题，前两轮的结论是
「不动」，理由写成了「178/183 承重」。**那个数字回答的是另一个问题** ——
它是「摘掉**全部**文件头会红多少份」，证明的是「文件头**整体**有作用」，
推不出「**每一份**都有作用」。真正该逐份问的是一句话：

> 这一份文件头，**替目录档兜底了吗**？

- 用例已经落在 jsdom 档的 `include` 里（`JSDOM_TEST_GLOBS` 命中）——
  目录档给出的结论与文件头**完全一致**，这行头是**纯冗余**；
- 用例在混合目录（目录档给 node）—— 文件头是它归属的**唯一**声明，**承重**。

**判据是可执行的，不靠读代码**（`vitest list` 输出的 `[project]` 就是权威归属）：

```bash
# 1. 拿全部用例的真实归属（project 名）
node_modules/.bin/vitest list | grep -oE '^\[(node|jsdom)\] [^ ]+'
# 2. 逐份比「真实归属 == 文件头声明的 env」→ 相等即冗余
```

实测（vitest 5.0.3）：183 份里 **147 份冗余**（目录档已覆盖）、**37 份承重**。
（后来判据③ 落地时又核对了一遍：这条命令算出的承重数是 **37**，当时文档里写的
「36」是**少算一份** —— 那一份正是被漏删的冗余头，见下。）
删掉那 147 份之后**再跑一遍同一条命令**，608 份用例的归属映射**逐行零差异**
（`diff` 为空）—— 这才是「冗余」的严格证明，比「摘掉会红多少份」强得多。

⚠️ **这是上一轮实现的一次未收尾**：目录档加上了，但没回头把「已经被它覆盖的文件头」
清掉 —— 于是同一件事在配置与用例里各写一遍，读的人无从知道哪一份在说话。
分档的价值之一正是「让归属只有一个来源」，留着冗余文件头等于把这个价值又还回去。

**别再把它简化成「183 处都留着」或「都删掉」**：判据是一个**逐份可判的谓词**
（它有没有替目录档兜底），不是一个可以拍板的数字。

⚠️ **当时这一步是手工跑的，所以漏了 1 份。** 147 份是用上面两条命令逐份比出来的，
但**没有任何判据守着它**，于是 `tests/sidebar-selected-state.test.tsx` 被漏下 ——
它是 `.test.tsx`，早由 `tests/**/*.test.tsx` 收进 jsdom 档，文件头是纯冗余。
**「已经查过一遍」不等于「以后不会再长出冗余」**：手工比一次是**快照**，
判据才是**闸门**（同 §11.13.1「判据在场 ≠ 判据在跑」）。现在这条闸门在
`check-test-environment.cjs` 的判据③（§11.17.4），面就是「头与所属档给同一个结论」。

#### 11.17.1.2 判据③：冗余文件头（`check-test-environment.cjs`）

判「文件头与它所属的档给出**同一个结论**」——两处都在说 jsdom / 两处都在说 node。
它和判据②（矛盾）是**互补**的，不是重复：② 抓「两处说了不同的话」，
③ 抓「两处说了同一句话」。两者同一个病根：**归属声明散在多处**。

**不需要跑 vitest**：所属档由解析出来的 `include` / `exclude` 直接算出来
（判据② 的同一套 glob 引擎）。但**结论的权威出处仍是 `vitest list`** —— 离线算一遍
只是为了让它在钩子里可判，所以判据必须**与配置同源**（同一份 `JSDOM_TEST_GLOBS`），
不许自己另写一套匹配规则。

```bash
node scripts/check-test-environment.cjs            # 检查（进 pre-commit D 组）
node scripts/check-test-environment.cjs --report   # 只出待办清单，不判失败
```

两处口径是实测逼出来的（都进了门禁自测）：

- **只判「恰好落在一个档里」的文件。** 两个档都不匹配（`include` 有缝）或都匹配
  （glob 有重叠）时**不判** —— 那是配置本身的问题，在这里报「冗余」是**报错的原因**，
  会把人带偏。实测现状 610 份用例全部恰好落在一个档里。
- **承重的头不许误报。** 「node 档目录里声明 jsdom」是混合目录那 37 份的形态，
  文件头是归属的**唯一**声明。把判据放宽成「有头就报」，实测一次报 **39 处**
  false positive（当场删错 37 份归属声明）。

#### 11.17.2 分档口径：目录级默认，文件头逐文件覆盖

`projects` 两个档（`node` / `jsdom`），进 `jsdom` 档的用例面是 `JSDOM_TEST_GLOBS`。
**只有两种「整目录一致」的形状**按目录声明：

1. 该目录下**全部**用例都要 jsdom（实测 26 个目录，逐个核过）；
2. `.test.tsx` —— 实测 **116/116** 完全相关，读作「渲染用例」这一档。

混合目录（同目录下两种都有，实测 **20 个**）**保持 node 档**，其中要 jsdom 的
继续靠自己的文件头。理由是量化过的，不是偏好：

- 按目录一刀切会把 **260 份 node 用例**误升进 jsdom。而放错的两个方向**不对称**：
  node 档下真碰 DOM 会**当场红**（响的），jsdom 档下跑纯逻辑**不报错、只是变慢**
  （**静默的**）—— 后者没有报错替你说话。
- 反过来，「按目录切」能省掉的注释也只有 **51/183**（其余 133 份与 node 用例同目录，
  文件头必须留）；用 `exclude` 精确摘出少数派则要在配置里写 **57 条 glob**。
  净账是「126 行注释 ↔ 57 行 glob」，**不值当**，而且每挪一个文件都要回来改配置。

#### 11.17.3 四条实测出来的边界（别照直觉推）

- **换掉全局档 ≠ 删掉文件头**。实测（vitest 5.0.3）：文件头的 `@vitest-environment`
  **优先级高于 project 的 `environment`**，`projects` 只决定「没写文件头时跑在哪」。
  把 183 份文件头摘掉跑一遍，**178 份当场红** —— 这一测证明的是「文件头**整体**有作用」，
  **推不出「每一份都有作用」**（§11.17.1.1：按「有没有替目录档兜底」逐份判，147 份冗余、
  37 份承重）。两个数字都要记住：**178 说明别人乱摘头会红，147 说明这批本来就该删**。
  一条实测数字只能回答它自己那个问题 —— 拿它去回答邻近的问题，就会得出「都不动」。
- **扩展名推不出环境**。`.test.tsx` ⇒ jsdom 完全成立（116/116），但还有 **68 份
  `.test.ts`** 也要 jsdom（store / hook / 路由断言里碰 `localStorage` / `document`）。
  别把分档判据写成「看扩展名」。
- **`projects` 继承声明方的 `test` 选项 —— 这一条早先写反过，订正在这里。**
  早先的写法是「`projects` **不**继承声明方 `test` 的选项（实测）」，据此在配置里立了
  一个 `SHARED_TEST_OPTIONS` 常量、两个 project 各 spread 一次。本轮按仓库规矩先去
  **复现那次实测**，结论是**当时那次测量站不住**（vitest 5.0.3）：

  | 配置形状                                                          | `task.timeout`              | `setupFiles`                    |
  | ----------------------------------------------------------------- | --------------------------- | ------------------------------- |
  | `setupFiles` / `testTimeout` 写在**根 `test`**，inline project 只写 `include` | **30000（继承到了）** | **生效（`jest-dom` 匹配器在）** |
  | 同上 + project 上 `extends: false`（负对照）                      | **5000（出厂值）**          | **不生效**（`Invalid Chai property`） |

  ⇒ 「继承」是**机制**（`extends: false` 是关掉它的开关，实测那一档退回 5000 且匹配器消失），
  不是别的东西碰巧生效。当年那 2 条红是真的，但**归因错了**：那时根 `test` 上确实没有那几项
  （后来才抽成常量），红的是「抽出去之后没 spread 回来」，不是「继承失效」。
  所以共享项现在**写在根 `test` 上、一处定义两档都拿**，`SHARED_TEST_OPTIONS` 那一层复制消失。

  ⚠️ **判断「共享项有没有生效」不能只看配置文本**。这次改动的验收口径是两条：
  ① `vitest list` 的 `[project] … > 用例名` **逐行零差异**（7160 条，改前改后同一份）；
  ② `tests/test-config-inheritance.test.ts` 用 **vitest 自己的 `createVitest()`**
  （`vitest/node`）把配置解析出来逐档核 —— **不自己写一份继承规则或 glob 引擎**，
  那是 #1509 的坑（手写 glob 引擎把 `src/components/ui` 误判成「已覆盖」，
  删完当场被 `vitest list` 揭穿）。

  ⚠️ 该用例还判两件「解析值判不出来」的事，各由变异核验钉住：
  · **「声明在根上」≠「解析值恰好对」**：把根上的 `globals: false` 整行删掉，解析结果
    一个字不变（`configDefaults.globals` 本来就是 `false`），只按值判就等于允许它被顺手删掉。
    所以另有一条「共享项必须**声明**在根 `test` 上」。
  · **`environment` 不许抬到根级**：它是这套分档里唯一按档分叉的项，抬上去 = 两档同环境
    （jsdom 档下跑纯逻辑**不报错、只是变慢**，静默的那一侧）。判据按**白名单**判根级项，
    新增一项先回答「它是不是共享项」。

- **`clearMocks` 在 vitest 5 起默认开着 —— 但别拿它当 `restoreAllMocks` 用**（同批实测）。
  vitest 5 的 `clearMocks` 出厂值从「关」变成**开**（`configDefaults.clearMocks === true`），
  实测：同一个 `vi.fn()` 在第一条用例里被调一次，第二条里 `toHaveBeenCalledTimes(0)` 成立；
  而**实现替换不被它还原** —— `vi.spyOn(obj, "f").mockImplementation(…)` 的替换会**跨用例留着**
  （实测第二条里 `obj.greet()` 仍返回「被替换」），还原它的是 `restoreMocks` / `mockReset`。
  仓里现有 **49 处 `vi.clearAllMocks()` 全在 `beforeEach`/`afterEach` 钩子里**、与这个新默认
  重复，**26 处 `vi.restoreAllMocks()` 不重复**。
  **量完的处置是不动**：不删那 49 处 —— 它们和 `tdb.$reset()` / `cleanup()` / `resetRunnerState()`
  同属一个「逐用例复位」钩子，删掉其中一行会把「复位了哪些东西」从钩子里挪到一个远处的配置值上
  （正是本仓库反复踩的「依赖隐式默认值 = 静默」那一族）；而那 26 处 `restoreAllMocks`
  **是承重的**，谁按「反正默认会清」去删它，`spyOn` 的实现替换就会漏到下一个用例。

#### 11.17.4 「环境早退」判据：判据只认环境全局

`scripts/check-test-environment.cjs` 判三件（纯文本、零网络、实测 < 1s）：

1. **环境早退**：用例体内出现「按环境决定跑不跑」的**裸 `return`** —— 一律阻断。
   正解是**把条件造出来**（仓里现成样板：`src/lib/app-events.test.ts` 的
   「无 `window` 时订阅给一个空操作…」那条用 `vi.stubGlobal("window", undefined)`
   - `afterEach(vi.unstubAllGlobals)`）。
2. **目录档与文件头矛盾**：该用例落在 jsdom 档的 `include` 里、文件头却写着 `node`。
   它守的是「挪目录 / 改档」这类改动的可见性 —— **不替用例决定该跑在哪**。
3. **冗余文件头**（§11.17.1.2）：文件头与所属档给出**同一个结论** —— 同一件事有了
   两个来源，改一处漏一处无人察觉。② 抓「两处说不同的话」，③ 抓「两处说同一句话」。

两处口径是实测逼出来的，都写进了判据的注释与用例：

- **`typeof` 后面只认环境全局那几个名字**（`window` / `document` /
  `navigator` / `localStorage` / `sessionStorage` / …）。首版写成「任意标识符」时，
  `function requestUrl(input) { if (typeof input === "string") return input; }`
  被当场误报 —— 那是**类型收窄**，与环境档无关。**一个会误报的判据活不过一次评审**
  （§12.13 的原话：「清单变噪音，没人会照它排期」），所以白名单是判据能立住的前提。
- **只判「jsdom 档里的用例声明 node」**，不判反方向。「node 档目录里声明 jsdom」
  是完全正当的写法（文件头优先级更高）—— 按「与 project 同名」的口径装上去，
  实测一次报 **37 处**，全是混合目录里本该靠文件头指定 jsdom 的 `.test.ts`。

**判据自己不许静默降级**：解析不到 `projects` 的形状时它**判失败**，不退回
「没有目录档」（否则判据② 变成永远空转，而它照样报 OK —— 首版实测就是
`include: []` 却退 0）。同族的 glob 翻译也有个坑：`**/` 必须翻成
「零层或多层目录」，翻成「任意字符 + 斜杠」时 `src/config/**/*.test.ts`
匹配不到 `src/config/x.test.ts`（实测：目录档整条失效）。

#### 11.17.4.1 路由组括号 `(main)` 在 glob 里不转义 = 静默不匹配

`JSDOM_TEST_GLOBS` 里曾有两条**一直在静默失效**的条目：

```ts
"src/app/(main)/settings/components/**/*.test.{ts,tsx}",  // ❌ 匹配的是 src/app/main/…
"src/app/(main)/settings/hooks/**/*.test.{ts,tsx}",       // ❌ 同上
```

picomatch（vitest 的 glob 引擎）把 `(main)` 读成**分组语法**，于是这条 glob 实际
匹配的路径是 `src/app/main/settings/…` —— 那个目录**根本不存在**。表现不是报错，
而是「这两条从没进过 jsdom 档」：`vitest list` 里该目录的用例一直挂在 `node`，
靠自己的文件头撑着（那 3 份 `.test.ts` 因此进了「承重」名单）。转义成
`src/app/\\(main\\)/…` 之后立刻归位（实测：3 份从 `node` → `jsdom`）。

**这条坑仓库里早就写过** —— `vitest.config.ts` 覆盖率那一批的注释、以及
`docs/standards/11` 的覆盖率章节都标了「`(main)` 的括号必须转义，否则条目静默不匹配」，
但**只写在覆盖率那一处**，`JSDOM_TEST_GLOBS` 漏了。同一句话要写在**每个 glob 清单旁边**，
或者更好：让「条目是否真能匹配到文件」变成一条判据 —— 这正是 §11.7
「门槛写着 100、报告里查无此文件」的同一族：**清单条目失效不报错，只是不见了**。

**变异核验**（四条各核一次，都当场红）：把 `vi.stubGlobal("window", undefined)` 换成
环境早退 / 把 jsdom 档里的文件头改成 `node` / 把 `.test.tsx` 的文件头改成 `node` /
把判据③ 改「永假」或放宽成「有头就报」（后者一次报 39 处 false positive）。
判据的门禁自测在 `tests/test-environment-gate.test.ts`（进 C 组固定清单）——
它同时钉住上面几条误报口径（把白名单放宽、把字符串删空、把承重头判成冗余，都当场红）。

#### 11.17.5 这一档**不做**什么

- **不删承重的文件头**：37 份是混合目录里归属的唯一声明（§11.17.1.1）；
  已被目录档覆盖的 147 份冗余**已经删掉**（收尾时漏掉的第 148 份由判据③ 补删，
  §11.17.1.2）—— 「留」与「删」是同一条判据：**它有没有替目录档兜底**。
  这条判据现在是**闸门**而不是一次性盘点：谁往 `.test.tsx` 上再写一行 jsdom 头，
  钩子当场拦下。
- **不按目录一刀切**：会把 260 份 node 用例误升进 jsdom，且那是**静默**的那一侧。
- **不判「这份用例究竟该跑在哪」**：只保证声明之间不自相矛盾。归属由 `include`
  回答，判断由人做。

### 11.18 软断言（`expect.soft`）：只许用在「一张清单逐项判」的循环里

> 口径两句话：
> ① **一张清单逐项判**（扫别名表 / 扫文件清单 / 扫两侧门禁名）→ 用
> `expect.soft`，让报错从「第一个坏的是哪个」变成「坏的都有哪些」；
> ② **顺序依赖的语句** → 必须用硬断言 `expect(...)`。软断言用在那里**比硬断言更坏**
> —— 它会把真正的原因吞掉（见下）。
> 由 `scripts/check-soft-assertions.cjs` 在 pre-commit 强制：`expect.soft` 必须落在
> **循环体里**。

#### 11.18.1 它换来的东西：一次报全，而不是修 30 轮

硬断言在**第一条**失败上停。本仓一大批用例是「扫一张清单、逐项判」的形状 ——
`theme-token-single-source` 的 30 条别名表、`ps1-consistency` 的 5 个关键词 × 两侧、
`sqlite-pragma-sites` 的 3 个站点 × 4 条判据。这些清单只要坏了不止一项，
每一轮都只能看见第一项。

实测（vitest 5.0.3，两条必然失败的断言）：

```
硬断言：× 应为空: expected 1 to be 2          ← 只报第一条
软断言：× 应为空: expected 1 to be 2
        × 第一个元素: expected ...            ← 一次报全部（用例照样红）
```

所以「全面改用 vitest 5 的做法」在这一档的落点不是「写法更短」，是
**反馈的粒度**：30 条清单从最多 30 次「改一处 → 重跑」收成 1 次。

#### 11.18.2 它**不是**「不早停」的通用开关：顺序依赖上它比硬断言更坏

这是本节最要紧的一条，也是实测出来的。软断言失败后**下一行照跑** ——
如果下一行用到了上面那条断言（本该）保证的前提，它会抛一个**与真正原因无关**的异常，
而报告里**只剩那条异常**：

```ts
const arr: number[] = [];
expect.soft(arr.length, "应为空（真正的原因）").toBe(0);
expect.soft(arr[0].toFixed(2), "第一个元素").toBe("0.00");
//            ^ 软断言不早停 → 这里抛 TypeError: Cannot read properties of undefined
```

实测输出：

```
TypeError: Cannot read properties of undefined (reading 'toFixed')
   4|   expect.soft(arr.length, "应为空（真正的原因）").toBe(0);
```

注意第 4 行只是**代码框的行号** —— 那句「应为空（真正的原因）」**一个字都没留下**。
换成硬断言时，报出来的正是它。**在依赖链上，软断言把原因吞掉了。**

#### 11.18.3 判据：`expect.soft` 必须落在循环体里

判据是**形状判据**，不是「该不该软」的语义判断 —— 那件事文本判不了。形状则很好判：
批量上下文就是循环，`expect.soft` 只该出现在 `for` / `for…of` / `while` /
`.forEach` / `.map` / `.flatMap` / `.filter` / `.reduce` 的块体里（含嵌套）。

```bash
node scripts/check-soft-assertions.cjs            # 检查（进 pre-commit D 组）
node scripts/check-soft-assertions.cjs --report   # 只出清单不判失败（盘点用）
```

落在循环外的软断言**一律阻断**，修法二选一：顺序依赖 → 改回硬断言；
本来就是一张清单 → 写成 `for (const x of LIST) expect.soft(...)`。

#### 11.18.3.1 判据走**缩进**，不解析花括号（三条实测逼出来的取舍）

第一版按花括号配对算，连踩三个坑 —— 每修一处都要再加一层词法分析：

| 踩到的形状                                                              | 后果                                           |
| ----------------------------------------------------------------------- | ---------------------------------------------- |
| JSX 自闭合标签 `data-x={v} />`                                          | `/>` 里的 `/` 被当正则开头，后面整段代码被挖空 |
| 箭头函数体直接给正则（`.filter((f) => /from\s+["']pino["']/.test(…))`） | 正则里的引号被当字符串开头，整段跟着错位       |
| 正则字符类里的 `[\\/]`                                                  | 「先遇 `\` 后遇 `/`」把正则提前收尾            |

而**这些都与判据要回答的问题无关**。缩进是仓库里已经由 prettier 保证的事实
（`tabWidth: 2` / `useTabs: false`），判据只问一句「包着我的那一帧是不是循环」：
从站点向上走，遇到第一个缩进更小的行就是一帧；它（连同它的**表头续行**）里有
循环关键字就是批量体，否则把它当下一个起点继续向上。

四条边界都是自测钉住的（`tests/soft-assertion-gate.test.ts`，进 C 组固定清单）：

- **单行形态**：`for (…) { expect.soft(…) }` 里循环与站点**同一行** ——
  向上走永远看不到那个 `for`（它是本行的前缀），所以同行前缀要单独判。
- **折行循环头**：`for (const n of [\n 1,\n 2,\n]) {` —— 关键字与 `{` 隔几行，
  所以帧的表头要**连同续行**一起看，但**只看到块体的 `{` 为止**
  （再往后就是块体内容，算进表头会让「循环之后」的语句被误判成在循环里）。
- **折行的收尾行**（`]) {` / `) {`）不是新的一帧：它与语句头同缩进，
  当成新帧会把 `innerIndent` 降下来、于是语句头被「缩进不小于它」跳过。
- **字符串与注释要挖掉**：判据自己的自测里写着**夹具字符串**，里面就有
  `expect.soft(…)` —— 不挖的话判据会去判自己的夹具（同族的先例：
  `tests/comment-language.test.ts` 里那份 `"// @vitest-environment jsdom"`
  夹具字符串，把 ISSUE #1485 那轮的文件计数从 183 数成了 185）。
- **站点形状要认折行**：prettier 会把长行折成 `expect\n  .soft(preset.command, …)`。
  只认字面量 `expect.soft` 时**那一处整片漏出扫描面** —— 实测：提交前跑格式化之后
  扫描计数从 27 掉到 26，**而判据照样报 OK**。这是「判据在场 ≠ 判据在跑」最纯的
  一种（漏报发生在判据自己的扫描里），所以站点正则是
  `/expect\s*\.\s*soft\s*\(/`，且自测里有折行形态的两条执行者。

**变异核验**（三条各核一次，都当场红）：把一条循环里的软断言挪到循环之后 /
把同行循环删掉（站点随即落到循环外）/ 把折行循环头改成单行后再删掉循环关键字。
判据自己**不许静默降级**：解析不了就判失败而不是放过（同 §11.17.4）。

#### 11.18.4 这一档**不做**什么

- **不判「该不该软」**：那是语义判断，文本判不了。判据只保证「软断言出现在
  有批量语义的位置」，余下的由人做。
- **不把存量硬断言全改成软断言**：只有「一张清单逐项判」那类才值当。
  `it()` 里两条互不相关的断言不在此列（它们不共享一张清单，
  软断言只会让「前一条坏了」这件事不再阻断后一条 —— 那正是 §11.18.2 的坑）。
- **不认正则字面量**：少挖一段的代价只是判定更宽松（漏报），
  这条取舍与 §11.17.4 同源 —— 会误报的判据活不过一次评审。

### 11.19 并发档位（`it.concurrent`）：只在「真让出事件循环 + 无共享可变状态」的地方用

> 口径两句话：
> ① **默认不用** —— 它是本轮盘点 vitest 5 新能力时唯一一条「量完决定不铺开」的。
> 同步阻塞的用例改并发**零收益**（下表），而每条并发用例都要额外论证「它和同文件
> 别的用例没有共享可变状态」；
> ② **真要用，必须同时满足两件**：用例真的在等 I/O（不是 `execFileSync`），
> 且文件里写明隔离声明（`// 并发档：<为什么没有共享可变状态>`）。
> 由 `scripts/check-test-concurrency.cjs` 在 pre-commit 强制后一件，并顺带拦
> 「并发档 × `expect.poll`」这组机制冲突。

#### 11.19.1 它**不是**免费的旋钮：只在用例真的让出事件循环时才买到墙钟

同一件事（起一个睡 300ms 的子进程）× 24 条，vitest 5.0.3 实测：

| 用例形状                     | 串行  | 并发  | 比                 |
| ---------------------------- | ----- | ----- | ------------------ |
| 同步 `spawnSync`             | 7.75s | 7.75s | **1.0×（零收益）** |
| 异步 `execFile`              | 7.73s | 1.71s | **4.5×**           |
| 异步 `execFile` × 8（400ms） | 3.48s | 0.95s | **3.7×**           |
| 异步 `spawn` × 7（350ms）    | 2.68s | 0.85s | **3.2×**           |

`it.concurrent` 让出的是 **JS 栈**，不是被阻塞的线程 —— `execFileSync` 在等子进程
的那段时间里整个事件循环是停的，所以并发无从调度。本仓库门槛自测里最大的那批
（58 份）用的正是 `execFileSync`，对它们改并发 = 换一套新的耦合面，收益为零。

**仓里「扫描型」用例的绝对耗时也都没有可省的余地**（所以这条不靠「把慢的挑出来」）：

| 用例                                             | 实测  |
| ------------------------------------------------ | ----- |
| `lib-node-only-scan.mjs --json`（600+ 模块 DFS） | 198ms |
| 全 `src` + `tests` 逐文件 `readFileSync`         | 47ms  |

⇒ 瓶颈不在 I/O 等待上；并发只会换来一层新的耦合面。

#### 11.19.2 它会把共享可变状态从「各自持有一份」变成「互相踩」——而且踩的是真资源

`sleep` / `waitFor` 那类「谁先跑」的问题还有报错，共享状态串掉的那一类更坏：
失败信息指向与被测行为无关的位置，最难归因。两个实测：

| 文件                                                    | 改法                 | 结果                                                                                                                                                                                                                   |
| ------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tests/executor-host.test.ts`（7 条真起子进程）         | 全改 `it.concurrent` | 红 2 条：`ConnectionFailed("Unable to open connection to local database …: 14")` —— 模块级 `tmpDirs` 被**别人的** `afterEach` 整个 `rmSync` 掉，某条用例的 SQLite 临时库没了。墙钟 3.4s → 1.5s（确实快了），代价是错的 |
| `tests/check-ui-primitives.test.ts`（328 条同步子进程） | 全改 `it.concurrent` | 红 **202** 条，失败信息指向 `seedBaseline` 这类与被测行为无关的位置。墙钟 19.4s → 20.7s（**还更慢**）                                                                                                                  |

注意第一条踩的**不是内存里的变量**：临时目录、SQLite 库、端口这些**真资源**一起串。
所以「有没有共享」的静态判定会误报一片（共享是跨模块的：模块级变量、`globalThis`
上的单例、`mkdtempSync` 的目录、真库、真端口），判据因此只判「有没有声明」，
不判「有没有共享」——**会误报的判据活不过一次评审**（§11.17.4 同源）。

#### 11.19.3 它与 `expect.poll` 在机制上冲突（本节最值钱的一条）

上一节（§11.14）刚把全仓的等待统一收成 `expect.poll`，而它与 `it.concurrent`
**在同一个用例里互斥**。最小复现（vitest 5.0.3，`--no-file-parallelism`）：

```ts
describe("v", () => {
  it.concurrent("另一条", async () => {
    await new Promise((r) => setTimeout(r, 20));
  });
  it.concurrent("站点", async () => {
    let n = 0;
    setTimeout(() => (n = 1), 10);
    await new Promise((r) => setTimeout(r, 20)); // ← 真 timer await
    await expect.poll(() => n).toBe(1); // ← Error: expect.poll() must be called inside a test
  });
});
```

实测矩阵（每格 20 次）：

| 形状                                                         | 结果                     |
| ------------------------------------------------------------ | ------------------------ |
| `it.concurrent` × 2，「站点」**在后**、await 真 timer ≥ 20ms | **20/20 红**             |
| 同上，两条用例**次序反转**                                   | **0/20 红**              |
| `it.concurrent` **只一条**                                   | 绿                       |
| `describe.concurrent` + 普通 `it`                            | 绿                       |
| 串行 `it`                                                    | 绿                       |
| await 的是 `Promise.resolve()` / `setTimeout(0)` / 5~16ms    | 绿（阈值在 20ms 那一档） |
| 同样的站点改用 `vi.waitFor`                                  | 绿（**不受影响**）       |

⇒ **它红不红取决于同文件里别的并发用例有没有先把事件循环让出去**。这是**时序依赖**，
不是共享内存，而且阈值卡在 20ms —— 同一份代码换台机器、换个调度就换一个结论。
判据因此是一条形状判据：**并发档的文件里不许出现 `expect.poll`**，修法二选一 ——
该条改回串行 `it`，或把等待换成 `vi.waitFor`（§11.14 那张对照表已说明：两者在报错上
同档，差别只在预算来源与 `message` 标签，所以这一处换成 `vi.waitFor` 不损失什么）。

#### 11.19.4 判据与它的边界

```bash
node scripts/check-test-concurrency.cjs            # 检查（进 pre-commit D 组）
node scripts/check-test-concurrency.cjs --report   # 只出清单不判失败（盘点用）
```

| 判什么                   | 为什么是它而不是别的                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **并发 × `expect.poll`** | 实测互斥、且红不红由「谁先跑」决定（§11.19.3）—— 文本可判，判的是确定的那一半                                                                                |
| **并发要有隔离声明**     | 「有没有共享可变状态」是语义判断（要真跑才知道），但「有没有人判断过」是形状 —— 声明在场至少让「新增一条用例」这一步必须过一个判断（与 §11.18.3 的取舍同源） |

站点正则 `/(?<![\w.$])(?:it|test|describe)\s*\.\s*concurrent\s*\(/` 要认
**`.` 两侧折行**：prettier 对超长链会折成 `it\n  .concurrent(…)`。
⚠️ 这条是**变异核验照出来的** —— 自测首版造的是「把**参数**折开」（`it.concurrent(` 仍是
行内字面量），于是「把站点正则改回行内字面量」那个变异**照样全绿**，即那一格没有执行者。
**只把参数折开不算折行**。

**变异核验**（五条各核一次，都当场红）：判据① 改永假 / 判据② 改永假 /
站点正则改回行内字面量 / `maskNonCode` 直通原文（不挖字符串）/ 隔离声明放宽成
「有标签就行」（不要求理由非空）。自测在 `tests/test-concurrency-gate.test.ts`
（进 C 组固定清单）。

**两处坑是流程自己照出来的，各记一条口径**：

- **「折行站点」那一格首版没有执行者**：自测造的是「把**参数**折开」
  （`it.concurrent(` 仍是行内字面量），于是「把站点正则改回行内字面量」那个变异
  **照样全绿**。折行要折在 **`.` 两侧**（`it\n  .concurrent(…)`）才钉得住。
- **`maskNonCode` 的插值弹栈首版是错的，而自测全绿**：模板串里 `${…}` 的收口 `}`
  与插值内对象字面量的 `{}` 必须**分开数深度**（给插值层单独一个 `braceDepth`），
  否则插值层不弹栈 —— 从第一个 `${` 往后整段被当成代码，**判据于是去判自己的夹具**。
  发现它的是**提交门槛**（钩子报红、自测绿），不是自测：这是「判据在场 ≠ 判据在跑」
  的又一面 —— **自测绿只证明自测覆盖到的那几条对，不证明判据本体对**。
  修完顺带删掉一个「按栈顶分叉的恢复态」死分支（实测每一格都返回同一个值）。
  ⚠️ 这一格的契约现在**直接钉纯函数**（自测 `require` 那个模块拿 `maskNonCode`
  喂字符串），而不是靠「造个临时仓库跑一遍」—— 它的失效形态在整份文件上
  **不稳定复现**（同一个形状在「前面有没有别的代码」时结论不同，实测）。

#### 11.19.4.1 顺带摘掉一条「会漂的读数」，并把它的执行者搬对位置

同批撞出来的第三件事，与并发无关但同一族（§13.5.10 的近亲）：

|                      |                                                                                                                                                                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**             | `tests/gate-executors.test.ts` 把「步骤位置口径下判据是几份」冻成 `toBe(44)`，本轮新增一份判据就红                                                                                                                                     |
| **为什么冻不得**     | 份数**本来就该**随「新写一份 `check-*.cjs` 还没接钩子」变动 —— 那正是名字族兜底要它可见的东西                                                                                                                                          |
| **为什么又不能只删** | 把「读步骤行」退化成「读全文」时份数 46 → 49，而多出来的三份本来就「有执行者」，`--report` 的点名清单**一个字不变** —— 实测**比总数、比名字都不响**，那正是原断言在拦的东西                                                            |
| **执行者搬去哪**     | 判据自己：`check-gate-executors.cjs` 新增 `PROSE_ONLY_SCRIPTS` 自检，在**它自己算出来的那张表**上反查六个「只作散文举例 / 被 import」的名字。变异核验：把 `gateChainScripts()` 第一段换成读钩子全文，**3 条用例当场红**（原先是 0 条） |

口径与用例的分工因此是：**判据本体自检**（唯一看得见那个差异的地方）+
**用例只钉两件与口径无关的事实**（扫描面非空、两处名单逐字同源）。
「读数写死」的替代从来不是「删掉这条断言」，而是**换一个不随正当变动漂的判据**。

#### 11.19.5 这一档**不做**什么

- **不判「该不该并发」**：那是收益判断，要实测（§11.19.1 那张表就是判它用的）。
- **不铺开既有用例**：本仓库当前**零处**并发站点，判据是纯闸门 ——
  它的对象是「下一次有人想给用例加并发」这一步，不是存量。
- **不静态判共享状态**：跨模块的共享（`globalThis` 单例 / 临时目录 / 真库 / 端口）
  静态判会误报一片，而误报的判据活不过一次评审。声明 + review 是这一维的正确形状。
- **不认正则字面量**：同 §11.18.4，少挖一段的代价只是漏报（可接受的方向）。

### 11.20 类型层断言（`expectTypeOf`）：借 `tsc` 当执行者，判据钉的是「执行者在场」

`expectTypeOf` 是本仓库盘点 vitest 5 新能力时最后三条之一。它**不是「另一种断言」**——
它在 vitest 里没有牙，唯一的执行者在构建配置里。这一节的落点就是那件事。

#### 11.20.1 实测：错的类型断言，vitest 报绿

```ts
// vitest 5.0.3
it("x", () => { expectTypeOf<string>().toEqualTypeOf<number>(); });
```

| 跑法 | 结果 |
| --- | --- |
| `pnpm exec vitest run` | **Tests 1 passed** —— 绿 |
| `pnpm exec tsc --noEmit` | `error TS2344: Type 'number' does not satisfy the constraint '"Expected: number, Actual: string"'` |
| `pnpm exec vitest --typecheck run <普通 .test.ts>` | **仍然绿** |

第三条是关键，它推翻了「加个 `--typecheck` 就有了」这个直觉：`--typecheck` 收的是
`typecheck.include`（出厂值 `**/*.test-d.ts`），**普通 `.test.ts` 根本不在它的收集面**。
而本仓库 `vitest.config.ts` 的 `include` 只匹配 `*.test.{ts,tsx}`，`.test-d.ts` 一份都不收 ——
两个收集面**互不相交**。

⇒ `expectTypeOf` 是「类型层的判据 + 借 `tsc` 当执行者」，而**这一点在用例文件里看不出来**。

#### 11.20.2 实测：`.test-d.ts` 有人管，但**不是**因为 vitest 认它

```
tests/x.test-d.ts（里面是一条错的断言）
  · vitest run                   → "No test files found"（不进收集面）
  · tsc --noEmit --listFiles     → 能数到它两次（被真收进 program）
```

所以 `.test-d.ts` 之所以有用，**不是**因为「vitest 的类型用例约定」，而是因为
`tsconfig.include` 里有 `**/*.ts`（`.test-d.ts` 末尾仍是 `.ts`）。
**执行者是构建配置，不是测试运行器。**

#### 11.20.3 那条静默失效路径（判据要拦的就是它）

实测：把 `tsconfig.include` 从 `**/*.ts` 收窄成 `src/**/*.ts`（测试文件出局）之后

```
  · tsc --noEmit  → 对测试文件里那条错断言一个字都不说
  · vitest run    → 仍然绿
```

⇒ 全仓每一个 `expectTypeOf` **同时变成装饰品，且没有任何一处报错**。
这是「判据在场 ≠ 判据在跑」那一族（§11.13.1 / §11.18.3.1）换了个入口：
**判据写在用例文件里，执行者写在构建配置里**，两者之间没有任何东西把它们拴住。

#### 11.20.4 那它到底该用在哪：`@ts-expect-error` 抓不到的那一侧

`@ts-expect-error` 管的是「这里**必须**有错」。而类型契约有两种破坏方式，它只覆盖一种：

| 破坏方式 | 例子 | `@ts-expect-error` | 正向断言 |
| --- | --- | --- | --- |
| 写错的用法**变合法**（该错没错） | `d.promt`（拼错字段） | ✅ 它自己报红 | 不必 |
| 类型**变宽成超集** | `ShotStatus` 从六个字面量变成 `string` | ❌ **无错可抑制** | ✅ 唯一能钉的 |

第二行的具体形状（本仓库有 20 多处）是「`as const` 元组 → 派生联合 → 用它当索引键的
`Record` / 类型守卫 `value is Xxx`」。**摘掉 `as const` 不需要有人写错代码**，而后果是：

- `ShotStatus` 静默变成 `string`；
- `isProductionStage(value): value is ProductionStage` 静默变成 `value is string` ——
  **交集类型守卫的语义整个消失**，而 tsc 完全接受；
- `Record<Kind, string>`「漏一个成员就报错」的守卫**退化成装饰品**
  （`Record<string, string>` 收下一份只有一半键的字面量）；
- 消费点大多把清单当 `readonly string[]` 用（`.includes` / `.indexOf` / `.length`），
  **宽化在那条路径上无感**。

**运行时断言在这一档上永远看不出区别**（实测：`z.enum` 对两种写法逐条 parse 结果相同），
所以这不是「多写几条用例」能补的。

落点在 `tests/type-level-contracts.test.ts`，变异核过：摘掉 `SHOT_STATUSES` /
`PRODUCTION_STAGES` 的 `as const`，两条断言当场红并打出
`Expected: literal string: done, Actual: string` —— 而**同文件之外那 6 条既有用例全绿**。

#### 11.20.5 判据：`check-type-assertion-executor.cjs`（进 pre-commit D 组）

判两件，纯文本、零网络、实测 < 1s：

| 判据 | 抓什么 |
| --- | --- |
| ① 站点必须在 `tsconfig.include` 面里 | §11.20.3 那条静默路径（执行者在场） |
| ② 认折行站点 | prettier 折开 `expectTypeOf(` 之后仍要扫出来 |

**判据自己不许静默降级**：解析不出 `include` / `include` 是空数组 → 判**失败**
（静默退回「没有 include」会让本判据空转、照样报 OK，与 §11.18.3 首版那个
`include: []` 却退 0 的 bug 同族）。**零站点是合法状态**（它是纯闸门）。

门禁自测 `tests/type-assertion-gate.test.ts`（进 C 组固定清单）跑**真脚本**
（临时仓库 + 只放被测文件 + 一份 tsconfig），八条口径各一条执行者。变异核过：
把站点正则窄化成行内字面量 → 折行那条红；取消字符串/注释挖空 → 夹具那条红。

#### 11.20.6 这一档**不做**什么

- **不铺开到每一个导出类型**：`expectTypeOf` 的价值是「钉住一个**会静默变宽的契约**」，
  不是「给每个类型写一遍」。没有宽化路径的类型写上去只是把定义抄第二遍。
- **不用 `.test-d.ts` 装**：本仓库 `vitest.config.ts` 的 `include` 不收它，于是它会
  **完全不出现在 `vitest list` / 报告 / 覆盖里**。既有的 `.test.ts` 已经能承载类型断言
  （`tsc` 收它、vitest 也收它），多造一个「只在某一侧可见」的文件名族是净负担。
- **不引 `vitest --typecheck`**：实测它对普通 `.test.ts` 无效（§11.20.1 第三行），
  而真要用它就得把 `typecheck.include` 改成 `*.test.ts` —— 那等于全仓再跑一遍 tsc，
  收益为零（A 组已经在跑同一个 tsc）。
- **不把 `tsconfig.include` 判成「必须含 `**/*.ts`」**：判据判的是「站点**所在文件**
  在不在 include 面里」，不是「配置写成某个字符串」。后者会随合理的配置重构
  （比如显式列出 `tests/**/*.ts`）误报 —— 误报的判据活不过一次评审（§11.18.4 同源）。

### 11.21 `ctx.annotate`：注释写得出来，但**读的人**得先在场

`annotate` 是本仓库盘点 vitest 5 新能力时最后三条之一。它看起来像「给用例挂个备注」，
实测下来**四条**都出乎意料 —— 这一节的结论因此不是「怎么用」，而是**先别用它**。

#### 11.21.1 四条实测（每条都反直觉）

**① 第二参数是字符串（type），不是对象**

签名是 `annotate(message: string, type?: string, attachment?)`。照直觉写
`ctx.annotate("理由", { type: "known-failed" })` —— 那个对象会被当成**附件**，当场抛：

```
TypeError: Test attachment requires "body" or "path" to be set. Both are missing.
```

报错讲的是 attachment，而真因是**参数位置写错了** —— 它指不出方向。

**② 它不改结论**

实测：挂了 `known-failed` 注释的失败用例仍然 `Tests 1 failed`、退出码仍是 1。
所以它**替代不了** `KNOWN_FAILED_FILES`（§11.12）那种「先摘掉、再跑」的机制 ——
那一步必须发生在运行**之前**。

**③ 绿的用例上**完全不可见

实测 text reporter：绿的用例带 annotation 时，输出里**一个字都没有**；
只有**失败**用例才会在调用点旁打一行 `↳ known-failed`。
它的可见性完全绑在「这条已经红了」上 —— 给一批**当前是绿的**用例挂声明，
等于写在没人会看的纸上。

**④ 门禁链读不到它**

`--reporter=json` 的产物里既没有顶层 `annotations`、`assertionResults[].meta` 也是空的
（逐键核过）。唯一读得到的是 **programmatic API**：

```js
const mods = await (await createVitest("test", { root, watch: false })).start([file]);
for (const t of [...mods.testModules][0].children.allTests()) {
  t.annotations(); // [{ message, type, location }]
}
```

而本仓库门禁链跑 vitest 的方式是 **CLI spawn**（`run-affected-tests.mjs`）——
与这条通道**天然不兼容**。

#### 11.21.2 那「什么情况下该用」：注释 + 消费方，且注释绑在**已经会红**的用例上

把四条合起来，唯一站得住的用法是：

> 一条**当前就是红**（或按设计会红）的用例，挂一段**给读报告的人**看的理由，
> 并且**有东西真的在读它**。

`test.fails` 那类「按设计失败」的用例是天然落点 —— 它们每次跑都会红，
注释每次都会被打印出来。反过来，给绿的用例挂声明是这一档最典型的**误用**。

#### 11.21.3 判据：`check-annotate-consumer.cjs`（进 pre-commit D 组）

只做一件事：**有站点就必须登记消费方**（`scripts/.annotate-consumers.json` 的
`consumers`，每条写明「谁读、怎么读」）。

| 状态 | 判定 |
| --- | --- |
| 零站点 | 通过（纯闸门 —— 本仓库当前零处） |
| 有站点 + 无消费方登记 | **阻断** —— 「挂一把没人读的注释」比不写更坏，它让人以为这件事有人管 |
| 有站点 + 台账在场 | 通过 |

**刻意不判**「该不该用 `annotate`」：那是收益判断（要实测）。
**也刻意不做**「运行时真去读一遍」的判据：那要起 `createVitest()`，而钩子档已经在
起一次 vitest（C 组），加第二次只为读几行注释 —— 代价与收益不成比例。

判据自己不许静默降级：台账解析不了 / `consumers` 不是数组 → 判**失败**。
门禁自测 `tests/annotate-consumer-gate.test.ts`（进 C 组固定清单）跑真脚本，
八条口径各一条执行者；变异核过两条：站点正则窄化成行内字面量 → 折行那条红；
取消字符串/注释挖空 → 夹具那条红。

#### 11.21.4 这一档**不做**什么

- **不铺开**：本仓库当前零处站点，判据是纯闸门。
- **不替代 `KNOWN_FAILED_FILES`**：粒度确实是「文件」（§11.12 自己写着这是已知的粗糙处），
  但 `annotate` 改不了结论（实测 ②），替代不了「运行前就摘掉」那一步。
- **不当 `conditional-skip-registry` 的第二实现**：那一套（§11.3 附近）已经用
  「档位 + 理由 + 站点数」管着 44 处条件性 skip，且判据在跑；再叠一层并行的
  「声明机制」会变成两个真相来源 —— 正是 §12.18「别造第二轮子」要避免的。
