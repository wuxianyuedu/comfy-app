## 1. 架构与状态管理

> 本章给出"什么状态放哪、谁来管"的决策框架，避免状态归属混乱导致重复存储、竞态和全树重渲染。

### 1.1 全局/高频状态禁止用 React Context

| 场景 | 错误做法 | 正确做法 |
|------|---------|---------|
| 日志面板（每秒数十条更新） | `createContext` + `useState` | **Zustand** 选择性订阅 |
| 画布节点状态（nodes/edges） | Context 存一份 + React Flow 内部一份 | **只让 React Flow 管**，Zustand 只存业务/UI 状态 |
| 多组件共享的 IO 编辑状态 | Context + Provider 嵌套 | **Zustand** `create` + selector |
| 主题/暗色模式（低频、全树） | Zustand | **Context 反而合适**（全树本就要 re-render） |
| 当前用户/会话（读多写少） | 每个页面各自 fetch | **Zustand + tRPC `useUtils`** 或 React Query 缓存 |

**判断标准**：`状态更新频率 × 消费组件数量`。高频 × 多消费方 → Zustand；低频 × 全树 → Context。

```tsx
// ❌ 错误：高频日志用 Context
const LogContext = createContext<LogContextValue | null>(null);
// 每次 setLogs → 所有 useContext(LogContext) 组件 re-render

// ✅ 正确：Zustand 选择性订阅
const useLogStore = create<LogState>((set) => ({
  logs: [],
  addEntry: (entry) => set((state) => ({
    logs: [...state.logs.slice(-2000), entry]
  })),
}));
// 组件只订阅自己需要的字段
const errorCount = useLogStore((state) =>
  state.logs.filter((l) => l.level === "error").length
);
```

### 1.2 Zustand 5 规范

```tsx
// ✅ 新项目直接用 Zustand 5
import { create } from "zustand";

// ✅ 用 selector 精确订阅，避免整个 store 变化导致重渲染
const ioEditMode = useIOEditStore((state) => state.ioEditMode);
const toggleIO = useIOEditStore((state) => state.toggleIO);

// ❌ 错误：一次订阅整个 store 对象（每次返回新引用）
const store = useStore(); // 导致 React.memo 子组件失效
```

**Zustand 最佳实践清单：**

1. **每个领域一个 store**，不要一个巨型 `useAppStore` 装所有状态。
2. **selector 返回原始值/稳定引用**：返回新对象/数组每次都是新引用，会触发重渲染。
3. **派生状态用 `useMemo` 或单独 selector**，不要在每个组件里重复 `state.logs.filter(...)`。
4. **Action 直接定义在 `create` 内**，通过 `set`/`get` 访问状态，无需额外 `useStoreActions`。
5. **SSR/Next.js**：Zustand 默认客户端 store；如需服务端初始化，用 `createStore` 工厂 + `<StoreProvider>` 注入，避免跨请求状态污染。

```tsx
// ✅ 派生 selector 抽成独立函数，便于复用和测试
export const selectErrorCount = (s: LogState) =>
  s.logs.reduce((n, l) => (l.level === "error" ? n + 1 : n), 0);

// 组件
const errorCount = useLogStore(selectErrorCount);
```

### 1.3 迁移期的兼容层模式

当从 Context 迁移到 Zustand 时，用兼容 hook 让消费方零改动：

```tsx
// ✅ 过渡期：组合 selector 模拟旧 API shape
export function useIOEditContext() {
  const workflowIO = useIOEditStore(selectWorkflowIO);
  const ioEditMode = useIOEditStore(selectIoEditMode);
  const toggleIO = useIOEditStore((state) => state.toggleIO);
  return { ioEditMode, workflowIO, toggleIO };
}
// 迁移完成后删除此函数，消费方直接 import selector
```

**迁移顺序建议**：① 新建 Zustand store + selector；② 新增兼容 hook，旧 Provider 继续存在；③ 逐个消费方从 `useContext` 切到 `useStore`；④ 全部切换完成后删除 Context 与 Provider。

### 1.4 不要在 Zustand 之上模拟 Context 的 props-drilling

// ❌ 错误：已经用 Zustand 了，还把整个对象当 prop 传
const io = useIOEditContext();

### 1.5 状态归属原则

| 状态类型 | 归属 | 说明 |
|---------|------|------|
| 节点位置/连线/选择 | React Flow 内部 | 不要复制一份到 Zustand |
| 节点业务参数（prompt/seed） | Zustand 或 tRPC 缓存 | React Flow 的 `node.data` 只放展示用的最小字段 |
| UI 面板开关（右栏/open） | Zustand | 多组件需要读/写 |
| 表单输入临时值 | 组件内 `useState` | 不要过早提升 |
| 服务端数据（任务列表/项目） | tRPC `useQuery` 缓存 | 不要存进 Zustand 再手动同步 |
| 跨页面临时草稿 | Zustand + `persist` 中间件 | `sessionStorage` 级，刷新保留、关闭清除 |

### 1.6 React Flow 状态边界（本项目特化）

- **权威源**：节点/边的真实状态以 React Flow 的 `useReactFlow()` + `getNodes()`/`getEdges()` 为权威源。
- **禁止双写**：不要在 Zustand 里再维护一份 `nodes` 数组，否则两边容易不一致（Flow 内部交互改了节点，Zustand 那份不会自动更新）。
- **业务字段**：节点的 `data.prompt`、`data.seed` 等业务字段通过 `updateNodeData(id, patch)` 写入 Flow，Zustand 只存"哪些节点被选中/面板开关"等 UI 状态。
- **大对象不进 `node.data`**：`workflowInputs` 等大结构放 Zustand，按 `nodeId` 索引，`node.data` 只存 `workflowId` 引用。

### 1.7 tRPC / React Query 与 Zustand 的分工

| 职责 | 工具 | 说明 |
|------|------|------|
| 服务端数据获取、缓存、失效 | tRPC `useQuery` / `useMutation` | 自带 SWR、后台 refetch、`placeholderData` |
| 跨组件共享的 UI 状态 | Zustand | 面板开关、选择态、临时草稿 |
| 乐观更新 | tRPC `onMutate` + `queryClient.setQueryData` | 见 §8.3 |

**反模式**：把 tRPC 查询的结果再 `setStore({ tasks })` 进 Zustand。这等于放弃了 React Query 的缓存/去重/失效机制，徒增同步逻辑。

### 1.8 状态持久化

```tsx
// ✅ 仅对真正需要持久化的状态使用 persist
import { create } from "zustand";
import { persist, createJSONStorage } from "zustand/middleware";

const useDraftStore = create(persist(
  (set) => ({
    drafts: {} as Record<string, string>,
    setDraft: (id: string, text: string) => set((s) => ({ drafts: { ...s.drafts, [id]: text } })),
  }),
  {
    name: "comfyapp-drafts",
    storage: createJSONStorage(() => sessionStorage), // 关闭标签页即清除
  }
));
```

**规则**：`persist` 只用于用户草稿、偏好（主题/面板布局）；**不要持久化派生数据、列表、日志**——这些数据应来自服务端，持久化会拿到过期快照。

### 1.9 认证与会话（better-auth，对齐主规范 §2.4）

- 会话校验集中在 **tRPC context**：所有涉及用户数据的查询/变更必须走接入 better-auth session 的**受保护 procedure**，禁止裸 public procedure 暴露私有数据。
- 组件侧使用 better-auth hook（`useSession`）获取用户，**禁止组件直接访问服务端 session 对象**。
- 登录/注册/退出走 better-auth 标准流程，禁止自建凭据存储。
- 环境变量校验用 `@t3-oss/env-nextjs`（`src/env.ts`），禁止在组件里直接读 `process.env`。

```ts
// trpc/context.ts 示意
export async function createTRPCContext(opts: { headers: Headers }) {
  const session = await auth.api.getSession({ headers: opts.headers });
  return { session, db };
}
// 受保护 procedure：session 为 null 时抛 UNAUTHORIZED
```

### 1.10 数据层规范（Drizzle ORM + better-sqlite3，对齐主规范 §2.3）

- schema 是 TS 源码：`src/server/db/schema.ts`；变更后 `pnpm db:push` 增量同步进项目根 `db.sqlite`（保留数据；启动器每次启动也会自动执行一次 push）。
- 查询热点（外键、过滤列）必须建索引：`index(...)` / `uniqueIndex(...)`。
- **禁止 N+1**：repository 层循环内逐条查询必须改为批量查询 + 内存映射。
- 敏感字段（密码哈希、token）禁止 select 到客户端；密码哈希由 better-auth 内置在服务端处理。
- **数据访问只走 repository**（`src/lib/core/repository*.ts`）；业务/路由禁止直接 import `drizzle-orm`（eslint boundaries 强制）。
